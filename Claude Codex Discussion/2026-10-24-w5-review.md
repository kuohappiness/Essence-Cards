### F1 — P2｜非段落區塊之後仍沿用 `paragraph`，把家長筆記與其他題目併回原目標

- **軸：規格。** 違反 syntax.md §2-2 的一般段落／程式碼區塊邊界，以及 D-135「頂格延續」只延續段落的用意。
- **位置：** 待審 `src/core/deck/markdown.ts:127–137`；清單項目自己開圍欄的分支另在 `:117–120`。
- **觸發：** 目標內的分隔線後接頂格一般段落。例如：

  ```markdown
  - 目標 ^a
      - Q :: A
    ***
  家長筆記 :: 不能出題
      - R :: B
  ```

- **預期／實際：** 分隔線已中斷原段落，頂格的家長筆記不應被接進目標名稱；`a` 的 Q 應保留。基準版本的結果確實是 `a → Q`。待審版本卻把整個目標變成 `id: null` 的 implicit，題目是 `目標\n***\n家長筆記`，答案是 `不能出題`，原本 Q 不再是它的題目。換成 `___` 同樣失敗；換成 `- - -` 則被先當成清單項目，產生額外的假題 `- -\n家長筆記`。
- **另一個同根因反例：** 項目自己開圍欄時沒有清掉先前的 `paragraph`。以下輸入在圍欄結束後，Q 的答案變成 `A\n家長筆記`，R 也被歸到 `a`。基準的 Q 答案是 `A`，R 是另外一個 implicit。

  ````markdown
  - 目標 ^a
    - Q :: A
    - ```
      code
      ```
  家長筆記
    - R :: B
  ````

- **影響：** 既有目標可能失去 ID、停止出題，或改變答案、題目指紋與目標歸屬；這超過 D-135 同意的延續行修正。
- **證據：已重現。** 以公開 `parseDeck` 比較基準與待審版本，三種分隔線及項目圍欄均有上述差異。預期的區塊邊界亦符合 [CommonMark 4.1](https://spec.commonmark.org/0.31.2/#thematic-breaks) 與 [5.2](https://spec.commonmark.org/0.31.2/#list-items)：分隔線先於清單項目判斷，省略縮排只適用於段落延續。本次沒有重跑這些新例子的 Obsidian 閱讀模式，實機對照仍需補上。
- **建議：合併前修，並加回歸測試。** 非段落區塊必須結束舊的延續狀態；分隔線不要在一般清單分支裡先被吃掉。把上述例子登錄進 `deckCases`，同時驗題目內容、指紋、ID 與歸屬，再做閱讀模式對照，不能只驗題數。

### F2 — P2｜`History` 沒有取消資訊，`appendLine` 無法維持與 `mergeHistory` 等價

- **軸：規格（介面漏洞＋實作不滿足總體性質）。** W5 §3-4／T5 要求增量合併等價於重新 `mergeHistory`；但局部規則說取消找不到時不改，W3 的 `History` 又只保留作答、變更與問題，取消資訊已被丟掉。
- **位置：** 待審 `src/core/study/history.ts:90–112`，尤其 `:93–96`；W5 §1 的 `appendLine(history, line)` 介面與 §3-4。
- **觸發：** 同一行作答 A，在取消 U 的前後各加入一次；或 `mergeHistory` 的輸入已含取消某個 t 的行，之後再 `appendLine` 該 t 的作答。
- **最小重現：** A 為 `encodeEntry('2026-10-24T19:00:00.000+08:00', { lt: 'a', r: 'good', v: '12345678' })`，U 為一秒後取消該 t 的行。從空 history 依序加 `[A, U, A]`，增量結果有 1 筆 a；整份 `mergeHistory([A, U, A])` 有 0 筆。`appendLine(mergeHistory([U]), A)` 也得到 1 筆，完整合併仍是 0。
- **預期／實際：** 取消應持續排除所有來源中同 t 的作答；目前取消只刪當下看得到的作答，之後可復活。這不是「同時刻不同檔案排序可不同」的例外，多重集合已不同。
- **影響：** 記憶中的進度可能與重開外掛／下一次外部 merge 後不同。也用公開 `state.answer` 重現：初始別台紀錄已有取消 t0，控制本機第一筆 answer 也得到 t0，`state.history()` 是 1 筆，flush 後 `readHistory(files)` 是 0 筆。這是跨裝置時間相撞／時鐘偏差的組合；一般單一 writer 遞增的作答流程不會自行產生 `[A,U,A]`，兩者需區分。
- **證據：已重現。** 既有 200 組性質測試的別台資料只有作答，自己的 t 嚴格遞增，沒有覆蓋「初始已有 undo」與「取消後重複加同一行」。物件 `val` 的遞迴欄位換序去重則另外驗過，正常。
- **建議：合併前釐清介面並修正。** 讓增量合併拿得到必要的已取消 t，例如明確保存取消資訊或由 state 提供；只有現在的三欄 `History` 無法區分「本來就空」與「曾取消後為空」。不要藉由每次作答完整 merge／重播來犧牲 W4 的成本契約，也不要只縮小 T5 的測試生成範圍。補上上述兩種初始狀態與跨裝置取消的性質測試。

### F3 — P2｜一次讀檔失敗會讓已通知的變更無限期停住，並拖住同批成功讀到的檔案

- **軸：規範與設計（錯誤恢復契約未補齊）。** W5 §3-3 的更新依賴通知；Files 契約沒有承諾「讀取失敗後一定再通知」。Claude 選擇的「放回 pending、等下一次通知」不足以保證恢復。
- **位置：** 待審 `src/state/index.ts:102–111`；排程在 `:95–100`，自己的紀錄於 `:89` 被排除。
- **觸發：** 一次外部紀錄變動與一篇卡組變動進入同一批；紀錄 read 暫時失敗，稍後檔案已能讀，但沒有下一個外部通知。
- **預期／實際：** 資料恢復可讀後應有恢復更新的途徑，成功讀到的卡組也不應長期被不相干的失敗擋住。實際是 `Promise.all` 任一失敗就整批放回 pending，沒有再排 timer。重現中卡組新增 c、外部紀錄取消 a；恢復讀取後仍是目標 `[a,b]`、作答 `[a]`、`onChange = 0`。再人為通知卡組才恢復。若壞檔一直讀不到，每次又會拖住整批新通知。
- **影響：** 學生繼續作答也未必能恢復，因自己的紀錄通知被忽略；外部取消、停用卡組、新題目可能一直不生效。畫面提示「會自動再試」，但讀檔路徑沒有像 writer 那樣由下一次 answer／flush 觸發重試。
- **證據：已重現（故障注入）。** 在實際 Node Files 外包 read，只讓指定紀錄檔失敗，其餘讀寫使用隔離磁碟；恢復後不再送新通知，確認狀態不變；補通知則恢復。
- **建議：合併前修，補錯誤恢復測試。** 個別保留失敗的路徑，成功的路徑照批次處理；對暫時失敗安排受控重試，或提供確實可用且告知使用者的恢復方式。補「最後一次通知的 read 失敗後恢復」「一個持續失敗的檔不擋住另一篇卡組」「close 取消重試」；避免緊密無限重試。
- **相關的啟動情況：** 另測 `ready()` 首次 read 失敗，後續通知即使來了也不恢復，因 `loaded` 始終為 false，且每次 ready 都是同一個 rejected Promise。這符合 W5「同一個 Promise」的字面契約，不另列實作違規；但 §4-1 對它使用「複習紀錄寫不進去，會自動再試」不符合實情。請同步定清楚啟動失敗的恢復／提示，不讓使用者空等。

### F4 — P2｜Node watch 吞掉 EPERM 後依賴下一次通知，最後一次刪除仍可能漏掉

- **軸：規格。** `src/core/files.ts` 的 watch 契約包含刪除與改名通知；W5 §0-2 不能只保證「不再拋出未攔截例外」。
- **位置：** 待審 `tools/node-files.ts:85–90`。
- **觸發：** 刪除／改名事件引發 snapshot，列資料夾暫時回 EPERM；之後沒有新的 rename 通知。即使後來有一般 change 通知，`:97–99` 也不會重做 snapshot。
- **預期／實際：** 恢復可列目錄後應比對上次清單並補出刪除／改名通知。現在 catch 直接 return，沒有重試，`known` 永遠停在舊清單。單次故障注入中已刪除 `folder/a.md`，事件處理後收到的路徑仍是 `[]`。
- **影響：** 使用 Node Files 的 state／工具可能繼續保留已刪除的卡組或紀錄。保留上一份清單是必要的，但不是完整的恢復策略；新測試只驗不拋錯，沒有驗刪除通知最後有送達。
- **證據：已重現（故障注入），自然發生頻率未重測。** 保留真實隔離檔案與公開 `createNodeFiles().watch`，替 Node watch 提供一次 rename 回呼，讓那次 `readdirSync` 丟 EPERM、其後恢復。沒有補第二個事件，就不會補通知；沒有把故障注入冒充本次自然重現的 Windows 錯誤。
- **建議：合併前修，並加檢查。** 對暫時的列目錄失敗保留清單並安排受控重掃；停止監看時取消。測試必須斷言最後收到被刪除的檔案路徑，不能靠另外製造一次 rename 才通過；也不要把所有非暫時性錯誤無條件吞掉。

### F5 — P3｜背景與停用接線沒有接住 `flush`／`close` 的拒絕

- **軸：規範與設計。** W3 的 `flush()` 明確可能 reject；`void` 不會處理 Promise 拒絕。
- **位置：** 待審 `src/main.ts:37–38`、`:46–48`。
- **觸發：** 紀錄追加持續失敗，接著觸發 hidden 或停用外掛。
- **預期／實際：** 既有錯誤回報之後，非同步失敗應有明確接收者。現在 writer 的 `onError` 雖已回報，從這兩個入口回傳的 rejected Promise 仍無人處理。
- **影響：** 多出全域 `unhandledRejection`；本次沒有證據證明 Obsidian 因此崩潰或額外遺失紀錄，不能把這項擴大成資料遺失結論。
- **證據：已重現（宿主替身）。** 把實際 `src/main.ts` bundle 放在 Node VM，提供最小 Plugin／document 替身，接上實際 createState 與持續失敗的 append；hidden、onunload 各產生一次 `unhandledRejection`，合計 2 次。不是 Obsidian 實機測試。
- **建議：合併前順手修，補接線檢查。** 接住兩條 Promise，沿用單次 Notice 的錯誤回報策略；測持續寫入失敗時沒有未處理拒絕，不改 W3 的重試規則。

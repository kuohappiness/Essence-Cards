## F1｜P2｜逐字的 key 可能包含兩個 code point，與整段比較失去一致性

- **軸**：規格。
- **位置**：分支 `claude/typed-match` 的 `src/core/study/session.ts:137–141`、`src/review/spelling.ts:9–11`、`:21–34`、`:43–55`（`ba13f03`）。
- **規格依據**：D-158 要求判對、最接近的答案與拼錯字母採用同一條規則；任務〈行為與風險〉也明列這項不變性，並特別要求檢查小寫後變成兩個 code point 的字母。既有的大小寫忽略規則應保留。
- **觸發條件**：一邊包含 `İ`（U+0130），另一邊包含它的小寫結果 `i\u0307`（U+0069、U+0307）。例如輸入 `\u0130stanbul`，答案是 `i\u0307stanbul`。這個答案可由真正的 `parseDeck()` 解析成打字題。
- **預期**：既然兩邊的 `typedKey` 相同，`checkTyped` 與 `spelling.ok` 都判對，逐字比對就不應把這個大小寫差異標錯；`closest` 也應把相等的答案視為距離 0。
- **實際**：`typedUnits('İ')` 產生一個 key 為 `'i\u0307'` 的單位，`typedUnits('i\u0307')` 卻產生 `'i'`、`'\u0307'` 兩個單位。`typedKey` 拼接後相同，編輯距離與照打前綴卻把它們當不同的陣列元素。

| 重現 | 基準 `8f71442` | 分支 `ba13f03` |
|---|---|---|
| `spelling('\u0130stanbul', 'i\u0307stanbul')` | `ok: true`，沒有錯字標記 | `ok: true`，輸入的 `İ` 與答案開頭兩個 code point 卻標錯 |
| `copying('\u0130stanbul', 'i\u0307stanbul')` | `ok: true`，沒有錯字標記 | `ok: true`，輸入的 8 個單位全部標錯 |
| `closest('\u0130stanbulx', ['\u0130stanbuly', 'i\u0307stanbulx'])` | 選第二個，與輸入比對相同 | 選第一個，即使第二個的 `typedKey` 與輸入相同 |

- **影響**：遇到此類字元時，照打畫面可能整排畫刪除線，但按確認仍通過；有多個答案時，也可能選錯照打對象。沒有真實教材的頻率證據；一般 ASCII 英文、D-158 列出的引號與空白案例不受此反例影響。
- **證據**：**已重現**。同一個隔離腳本載入基準版本的 `spelling.ts` 與分支的公開介面，得到上表結果；另以真正解析器驗證答案可進入打字比對。不是只根據型別推測。
- **建議處理**：**合併前修**。讓整段比較、編輯距離與照打使用一致的比較序列，並保留比較單位對原始輸入的對應，以便標記學生實際打的字。不要只改 `ok` 或遇到相等就清掉標記，否則拼錯時的對齊與 `closest` 仍不同。補上本例、反向輸入與多答案的公開介面回歸測試；保留原字元、連續空白及照打尾端空白的既有測試。不需要擴大成通用 Unicode 正規化。

同一個逐字小寫選擇還改變了上下文小寫：`'ΟΣ'` 對 `'ος'`，基準判對、分支判錯，因為整串 `toLowerCase()` 的詞尾 `ς` 變成逐字的 `σ`。這是已重現的補充邊界證據；打字卡主要是英文，未另列一項產品缺陷。修 F1 時也應避免無意更動原本整串小寫的語意。

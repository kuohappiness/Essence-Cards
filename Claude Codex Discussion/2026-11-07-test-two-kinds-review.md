## 1. 和「不做」比較

**只是說法｜可以縮短合併前的工作，總成本是否下降還沒有證據。** 照舊在同一個分支驗完，重現資料、程式和規格都在手上，能一次修完共用邊界。若同一項最後仍必須補，延後還要付重新建立情境、登錄與驗收的成本。D-195 的具體好處是把同一裝置的低風險案例集中跑，以及等明顯的替代路徑定了再決定是否要做額外功能。AI 製卡第三、四輪證明中斷恢復會增加查核輪次，但這兩輪碰到了持久 ID（見第 2 節），不能把兩輪都算成可省的成本。建議採用時分別記一兩次「合併前少花的輪次或時間」與「之後補測的重建成本」；屆時仍須做的項目應估入 v1 工期。依據為 `docs/decisions.md:3920` D-153、`:4788` D-177、`:5513–5526` D-195 的理由與代價。

## 2. 分類的界線

**會漏掉合併前必要的測試｜D-195 第 2 點把「存到一半能繼續」整段當成第 2 類。** AI 製卡在部分草稿已寫入後，續作會判斷草稿搬移、是否能再建，以及哪些 ID 可以釋放。R3-1 的具體後果是草稿改名或搬走後，從舊路徑再建一份共用 ID 的目標；R4-1 涉及能否把曾經寫出的 ID 當成從未使用。兩者都落在第 1 類。只有在已驗證「保留既有草稿、避免重複或重用 ID、仍須明確啟用」的簡單中斷路徑下，重開後自動接續的便利性和額外恢復案例才可列第 2 類。建議拆開 D-195 的例子，並讓任務寫出每項第 2 類的恢復方法與保證。證據為 `docs/decisions.md:5499–5503`、`tasks/ai-cards-mvp.md:197–215`、`2026-11-07-ai-cards-mvp-format-review.md:220,264,283`。

| 容易分錯的情況 | 應歸哪裡 |
|---|---|
| 排程的錯誤可以在下版重播 | FSRS／紀錄重播按既有高風險範圍做足。即使歷史可重算，已錯過的複習也無法補回當時；錯寫評分、時間或 ID 更不能假設有正確輸入可重播。 |
| 只有 iPhone 才看得到 | 次要畫面的截斷、排版可列第 2 類；同步後遺失作答、舊版讀到不該出的卡仍屬第 1 類。日常作答被擋也要保留原驗收。實機集中處理只改測試時間。 |
| 效能用下版修就好 | 少見的大卡組首次渲染稍慢，且操作與存檔都正常，可列第 2 類；正常規模就卡住複習，要保留核心流程的驗收。逾時若會觸發重複寫入或丟紀錄，屬第 1 類。 |

逐項拆開後，保守預設仍留得出第 2 類。現有文字的缺口是把「可修復」和「少見」放得很近，容易把可修但會擋住正常流程的問題延後。建議明寫先看正常流程與既有驗收，再判斷少見案例的後果與恢復方式。規劃者只需查該項會寫什麼、會影響誰，以及現行高風險清單。依據為 `docs/agents/quality.md:33–35,45–50`、`docs/decisions.md:5499–5503`。

## 3. 「補做」與做到一半

**只是說法｜把具體取捨留在 AI 製卡任務，把可交付的條件補到 D-195 第 3 點。** 「快做完就留繼續」可用在這次製卡的恢復功能，進度比例本身不足以決定可否交付。若半成品已能完成一條安全的使用路徑，保留該路徑，把剩下的便利功能列「補做」；若開放後可能留下半套資料或錯配 ID，合併前要關住入口或做完安全路徑。未開始時可讓家長重貼，前提是能確認這個工作尚未寫出任何需要保留的資料；已寫出的草稿照 §5 保留，不能按一般規則自動刪除。證據為 `tasks/ai-cards-mvp.md:197–215`、`docs/decisions.md:5503–5504`。

## 4. 不漏的關卡

- **會漏掉延後的測試｜沒有正式任務檔，第一道關卡就不會啟動。** 小修的討論稿、試作場 `TASK.md`、以 `review.md` 結尾的 L2 請求，三種樣本都通過。D-195 第 3 點仍要求登錄，但第 4 點只檢查 `tasks/` 第一層的任務；現有 iPhone 合併清單也在 v1 任務表，直接沿用時不會計入技術債。建議整合者在交回或合併前核對，有任務檔的寫在該次結果，沒有的以既有討論／試作結果或 commit 為來源，有延後才在同一批改動登錄技術債。L2 新增的延後項目一併核對，並照 D-171 附真實路徑證據。單純試作若沒有把驗收留給正式 v1，沒有 v1 補測可登。證據為 `tools/check-docs.ts:222–226`、`docs/decisions.md:4561–4565,5504–5508`、`docs/backlog.md:29,33–37,76`。
- **會漏掉延後的測試／會擋錯｜結案應有固定標記。** 「驗收通過，已合併」「Windows 通過，已合併」「實機測試做完，已合併」三種結案樣本沒有結果都通過；「已完成第一部分，第二部分進行中」「完成條件還沒達成，實作中」卻被當成結案。建議新結案固定用一個有邊界的狀態值，例如 `狀態：已結案｜備註`，部分完成留在備註。文件檢查確認新任務採用固定狀態值或欄位，才能擋掉用了別的詞的結案。若只在認出結案詞時檢查，還需要由整合者在合併時確認結案，尤其是合併後才改狀態的任務。既有狀態格式可用明確的遷移範圍保留。證據為 `tools/check-docs.ts:203–226`、`docs/agents/quality.md:49–50`。

## 5. 文件檢查的 Markdown 邊界

**會漏掉延後的測試／會擋錯｜`checkDeferred` 用標題 token 找到區段後，退回掃原始文字。** 以下在工作樹與暫存區模式的結果相同。重現時把樣本放入隔離 Git repo 的 `tasks/<名稱>.md`，用 `# 任務`、`狀態：已完成`、`## 結果` 加上相應內容，stage 後從基準副本執行 `node tools/check-docs.ts --root <隔離 repo>`，再加 `--staged` 重跑。

| 樣本 | 實際結果 |
|---|---|
| 行首有 `>` 的引文，或有直線符號的表格儲存格 | 拒絕。這兩種沒有發現誤放行。 |
| 引文起頭有 `>`、下一行用 Markdown 省略 `>` 的續行寫 `延後的測試：無`；或把同一行放在程式碼圍欄、HTML 註解內 | 皆通過，雖然沒有獨立的結果欄位。 |
| 空白的 `**延後的測試：**` | 通過，結尾的星號被當成值。 |
| `## 結果` 裡的 `### Windows` 下寫欄位 | 通過，三級子節在正確範圍內。 |
| `## 10. 實機` 下的 `### 結果`，或 `## 結果（Windows）` | 都擋，即使已填欄位；既有 `tasks/exam-scope.md:398` 就是帶日期的三級結果標題。 |
| 第一行是「（實作後填）」、第二行才寫「無」 | 擋，但只報第一行未填。應直接指出欄位重複。 |

建議明定一種新任務的結果結構（例如獨立的 `## 結果`，允許其下有三級小節）；若要支援既有寫法，再明列可接受的標題。使用 Markdown token 限定真正的欄位段落或清單項，要求恰好一個，並測試上表、結案狀態、表格範圍、列不存在及清掉已補列的情況。現有測試甚至把任務寫的「存到一半中斷」和 backlog 的「甲」視為通過。證據為 `tools/check-docs.ts:178–184,218–234`、`tests/check-docs.test.ts:189–208`。

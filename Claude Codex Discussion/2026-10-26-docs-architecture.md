### 3-2 每件工作只有一個「家」

- 進行中的工作，經過、證據與未決問題只寫在它的家：要實作的是 `tasks/<任務>.md`，還在規畫的是 `docs/plans/<主題>.md`，Claude 與 Codex 在談的是討論稿。
- roadmap 狀態板一列；backlog 一列（項目、狀態、連結）；討論索引一列（主題、一句話）。
- 已完成一列一句，約 80 字，加連結，不寫經過。
- 要改的規則：`AGENTS.md` 文件分工下的條目、`essence-discuss`〈結束〉第 2 點（沒談完改成寫進家，roadmap 只更新那一列）、`essence-decision` 第 5、6 步。
- 碰到的舊決定：補充 D-099「一件事只寫在一個地方」。

### 3-3 機械檢查擋住回彈

- 一支小程式（例如 `tools/check-docs.mjs`），`docs/`、`AGENTS.md`、`README.md`、`tasks/`、本資料夾有改時由 pre-commit 跑，CI 也跑：
  - 「現在在哪裡」超過字數上限（暫定 2,500）。
  - 已完成超過 10 列，或單列超過上限（暫定 150 字）。
  - 相對連結的檔案或錨點不存在（`docs/archive/v0-planning/` 與 10-06、10-07 的舊紀錄先排除，或一次修好）。
- 目前 pre-commit 只在程式相關的檔案改動時跑 `npm run check`，文件的 commit 不會觸發；要加一條文件的路徑。
- 碰到的舊決定：照 [D-117](../docs/decisions.md#d-117-技術債預防機械檢查全自動ai-審查只在關鍵點)「機械檢查全自動」的精神。

### 3-4 決策索引分主題

- 索引改成按主題分組，每組照編號排；AI 只讀相關的一組。暫定的組：產品與範圍、學習目標與製卡規則、資料格式與語法、複習與排程、畫面、AI 接法與模型、Capture、協作與文件。
- 分組寫在哪裡由 `decisions-index.mjs` 決定（狀態行加一個欄位，或程式裡的對照表），重跑時保留。
- 同一支程式加一個查詢：`node experiments/tools/decisions-index.mjs D-062` 印出那一條，以及它「後續見」的各條。
- 碰到的舊決定：D-099 的索引格式（照編號排）；D-106 當時說查詢工具「缺少足以支持建置成本的證據，有明顯問題再談」，現在 86 條要追鏈、全文一週長了七成。

### 3-5 檔頭狀態行

- `tasks/` 與本資料夾的檔案，標題下第一行固定寫狀態：`狀態：進行中｜已完成（commit）｜已結案 → D-xxx｜暫停（原因）`。

### 3-6 backlog 的待決只放待決

## 4. 不建議做的

- **把 `docs/decisions.md` 拆成 140 個檔**：全 repo 有 798 處連到它的錨點要改；3-4 的分組索引已拿到大部分效益。上一份討論稿 §4.3 也決定先不拆。
- **另寫給 AI 的摘要檔或交接總表**：又多一處要同步，正好是 §2-B 的來源。

- **合併 `.claude/skills` 與 `.agents/skills`**：那是給 Claude 和 Codex 各讀一份，已有 `npm run skills` 檢查一致。

### 2. 3-1：狀態板與字數

五欄同意。狀態寫目前做到哪裡，下一步只寫最近一個動作；「等誰」沒有等待就填「—」，不用再加負責人、優先級等欄位。尚在分支的工作，狀態保留分支，確切待審 commit 放入口文件。

2,000 字目標、2,500 字上限可先試行；不是已驗證的最佳值。範例還要加本次文件架構討論自己的一列。必要的跨任務先後關係、里程碑與使用者要求的提醒要有入口，不能為了過字數檢查而漏掉。

計數範圍固定為 `## 現在在哪裡` 到下一個二級標題，含表格、連結及三級標題；換行統一成 LF，以 Unicode 碼點計數，才能延續 Python `len()` 的口徑。JavaScript 直接用 `.length` 會把部分 emoji 算成兩個。超限時移走經過與證據，不把同樣內容另起標題繞過檢查。

### 3. 3-2：「家」怎麼選

建議把「每件工作只有一個家」改得更精確：

> 同一類資訊只維護一份。現行規格依文件分工；同一個未決問題只有一份主文；試驗與審查證據留在原紀錄。入口只寫狀態、下一步與連結。

未決問題的主文按固定順序選，不按檔案是否存在猜：

| 當前工作 | 主文 |
|---|---|
| 已交付實作，且未另開專門討論的問題 | `tasks/<任務>.md` |
| 正在請 Claude／Codex 對同一個問題往返 | 該議題討論稿 |
| 其他已展開的規畫 | `docs/plans/<主題>.md` |
| 尚未展開的短點子 | backlog 原項目 |

roadmap／backlog 的入口直接連到這份主文。進入下一階段時更新連結，舊主文標明後續去向，不在新舊兩份繼續維護同一組未決問題。任務若另開專門討論，該問題在任務裡只留引用。

國小社會的例子：**規則文字**仍在 `card-rules/elementary-social.md`；**試用證據**在 `card-rules/trials.md`；**正在往返的設計問題**在本資料夾的對應討論稿；archive 裡那份只保留當時取捨。它們可以同時存在，不應把所有內容硬搬成一檔。入口應指向目前需要接手的問題；結案依 D-106 連到 D-ID，不再為同一輪另生摘要。

這也需要對齊 D-106／D-130 與 `docs/plans/README.md`：現行文字仍要求未決問題回到 backlog／plans 或 roadmap。若改成只在主文寫細節，其他位置留可找到的入口，應明確補充這個界線，不能只改兩個 skill。

### 4. 3-3：pre-commit、CI 與連結檢查

位置同意，但不建議一加上就用現有全部錯誤擋住每次 commit。先修已知壞鏈，或暫列逐項、有原因的既有例外，再啟用阻擋；不整個排除封存區或兩個日期的紀錄，否則那些檔案新添的錯也查不到。

要避免擋到正常提交，至少滿足：

- **hook 查暫存區，CI 查提交樹**。部分 stage 時，不能拿尚未提交的工作檔來判定這次 commit；被刪除、改名的檔案也要處理。工具不自動修改、stage 或要求使用者一起提交其他文件。
- **來源以 Git 追蹤清單列舉**，涵蓋 repo 內的 Markdown，包括兩份 skills；不沿用 `.ignore` 排除。目的地也按該次 Git 樹檢查，避免 Windows 不分大小寫而放過 Linux／GitHub 的壞路徑。
- **改目的地也要觸發**。只看 `docs/` 等路徑會漏掉刪除圖片、原始碼或技能後造成的壞鏈。這支檢查夠輕量時，每次 commit 都跑一次，比維護一長串觸發條件簡單；不用因此讓純文件提交跑整套產品測試。
- **只查本機可判定的連結**，不發網路請求。按 Markdown 語法處理一般／參照式連結、圖片、程式碼範例、百分比編碼，錨點涵蓋中文、重複標題與明寫的 HTML `id`。不要用一條正規表示式就阻擋提交；先有這些反例的驗證。

跨 worktree 的原始碼證據應改成固定 commit 的連結；只在別的分支上的文件要有明確入口，不因為知道原因就永久豁免壞的相對路徑。字數與列數檢查也讀同一個快照。

D-117 明寫「只改文件的 commit 跳過」，新增文件檢查雖符合機械檢查自動化的方向，仍要補充成「跳過程式檢查，保留輕量文件檢查」。失敗輸出只列檔案、行號、目標與原因，避免又產生一大份工具輸出。

### 5. 3-4：索引與查詢指令

**未知 D-ID 時，分組有幫助；已知 D-ID 時，直接定位最省。** 同意分組，但不要因此要求每次把所有主題讀完，也不要另維護一份有同樣摘要的編號索引。保留原有 D-ID 與正文錨點，組內依編號排即可。

分組建議存在 `decisions-index.mjs` 的明確對照表：每個 D-ID 指定一個主要主題，產生時檢查重複、漏分及不存在的 ID。跨主題靠查詢與引用，不複製整列。既有「一句話」繼續依 D-ID 保留；不要把主題塞到正文狀態行之前，現有解析器只讀第一個非空行，會因此失敗。分組後也要驗證重跑不改字、摘要不丟失、每條恰好出現一次。

**小型唯讀查詢值得做**，但範圍止於「指定 D-ID → 原文＋明示的後續條目」，不做搜尋服務或自動合成現行規格。查詢模式必須在寫檔流程之前分流，遞迴去重，未知 ID 或關係錯誤要報錯，執行前後的檔案與 Git diff 不變。

尤其不能把結果叫作「完整現行規則」：現有後續關係由狀態行中較大的 D-ID 推得，不涵蓋正文的全部關聯。例如 D-062 沒有「後續見」，但打字卡的按鈕限制還涉及 D-066、D-121。查詢用來追溯，實作仍以相關現行規範與任務為入口；有衝突就指出同步缺漏。

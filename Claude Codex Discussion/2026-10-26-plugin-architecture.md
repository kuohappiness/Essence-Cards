### 1-1 現況，查過成立的

`Files` 五個動作（列出、讀取、修改、追加、監看）是外掛和 vault 唯一的接點（D-110）。查過的事實：

- 正式程式沒有繞過它：`src/obsidian/save.ts` 第 169 行的 `app.vault.adapter.read` 只在開發版的紀錄路徑裡跑（前一行 `if (!host.log) return`）；`src/obsidian/dev.ts`、`dev-ids.ts` 直接用 vault 是刻意的，它們在測 Obsidian 本身，正式建置不含。

- 兩個實作跑同一份契約 C1～C14（Node 在 `npm test`；Obsidian 用開發命令 `files`，W5 在 Windows 1.14.5 通過）。

### 1-2 發現

**F1｜P2：`watch` 把改名資訊丟掉，下游只能猜**（= 技術債 A2）

- `src/core/files.ts` 第 11 行：`watch(onChange: (path: string) => void)`；改名「通知舊、新路徑」各一次。
- `src/obsidian/files.ts` 第 80 行：`vault.on('rename', (entry, oldPath) => …)` 本來就拿到 `oldPath`，在這一層攤成兩個路徑送出去。
- `src/state/index.ts` 第 236～242 行：同一批裡消失的卡組與第一次出現的卡組，先比「內容相同」、再比「檔名相同」來配對，配到就 `tracker.move`。
- 會猜錯的情形（靜態推斷，未重現）：同一批裡兩篇內容相同、一刪一新（複製一篇再改名）；改名的同時也改了字而且檔名也變；兩篇同名的卡組在不同資料夾、同時搬動。猜錯的後果是待處理問題搬到別篇、或把改名的那篇誤報成「編號不見了」（`lost`），家長會看到不該出現的小視窗。
- 這是介面少了一樣它本來就有的資訊，不是 `state` 的 bug；`state` 那段是補丁。

**F2｜P3：契約少驗兩個情境**

- **資料夾整個刪掉**：C12 只驗了資料夾改名（第 158 行）。Obsidian 刪資料夾時會不會對裡面每個檔各發一次 `delete`、還是只對資料夾發一次，W5 的實測紀錄沒有這一項；`src/obsidian/files.ts` 的 `inside(entry)` 假設刪除時 `TFolder.children` 還在。Node 版靠重新列表比對，沒有這個問題。
- **讀取暫時失敗後恢復**：契約只驗成功路徑。`state.ready()` 一篇讀不到就整批重試（技術債）是在 Windows 實機碰到才發現的，因為 Node 版沒辦法注入失敗。

**F3｜記下不做：`list` 沒有修改時間與大小**

- 啟動時每篇卡組、每份紀錄都整個讀。現在沒錯，Windows 的 `history + plan` 742～1,887 ms 主要在重播不在讀檔。
- 若 W6 的 iPhone 量測（I1）超過 1 秒、要照 D-110 加快取，快取需要便宜的「有沒有變」依據（mtime＋size）。Obsidian 的 `TFile.stat` 與 Node 的 `fs.stat` 都有。到時候要加，走這個接點（`list` 回傳項目帶 `mtime`、`size`，或多一個 `stat`），不另開管道。

**F4｜記下不做：備份會是第二個接點**

- [更新與相容的規畫](../docs/plans/updates.md#更新前的備份)：備份寫到 vault 以外的資料夾（使用者 2026-10-26 選「只放電腦本機」）。C14 明定 `Files` 不能離開 vault，所以備份只能在電腦用 Electron 的檔案系統寫。
- 建議寫進 D-110 的補充：vault 外的讀寫是桌面專用的例外，放 `src/obsidian/`（或獨立的 `src/desktop/`），核心與 `state` 不碰，iPhone 不註冊。

### 1-3 提案

**P1｜`watch` 的回呼帶改名資訊**

```ts
// src/core/files.ts
/** 新增、修改、刪除通知路徑；改名通知一次新路徑並帶舊路徑（from）；資料夾改名時裡面每個檔各通知一次、各帶自己的舊路徑。回傳取消監看的函式。 */
watch(onChange: (path: string, from?: string) => void): () => void;
```

- **Obsidian 版**：`vault.on('rename', (entry, oldPath))` → 對 `inside(entry)` 的每個 `f`：`onChange(f.path, oldPath + f.path.slice(entry.path.length))`。不再另外通知舊路徑。
- **Node 版**（只給測試與工具用）：`rescan` 比對前後清單，消失的集合與新出現的集合**數量相同、而且檔名能一對一配上**時，每對通知一次 `(new, from=old)`；配不上就照刪除加新增通知，不帶 `from`、不猜。
- **契約**：C12 的「改名」改成收到 `b.md` 帶 `from = a.md`，「資料夾改名」收到 `g/1.md` 帶 `from = f/1.md`；舊路徑不再單獨通知。新增 **C15 資料夾刪除**：`f/1.md`、`f/2.md` 存在，刪掉 `f/`，兩個路徑都收到通知，`read` 回 `null`。
- **`state`**：
  - `notify(path, from?)`：`pending` 改成保留順序的 `Map<path, { from? }>`；同一批裡同一路徑先收到 `from` 再收到一般通知時保留 `from`；`a → b → c` 連續改名時依收到的順序 `move(a, b)`、`move(b, c)`。
  - `apply` 先依序套用改名（`tracker.move(from, path)`、`deckMap`、`sources` 的鍵跟著搬），再讀檔比對；刪掉第 236～242 行的猜配對。
  - 邊界：`from` 是卡組、新路徑不是（搬出 `Essence Cards/` 或搬進系統資料夾）→ 當刪除（`tracker.forget`）；`from` 不是卡組、新路徑是 → 當新出現；兩邊都不是 → 忽略。紀錄檔的改名只重讀，不用 `from`。
  - 改名同時改字：`move` 之後 `tracker.text(path) !== text`，照舊走 `observe` 的 `changed` 比對，ID 的判斷不變。

**P2｜契約加失敗注入，等記憶體 `Files`**

- 環節 9 會提出 `tests/helpers/` 的記憶體 `Files`（技術債 A9）。做好之後加 **C16**：`read` 對某個路徑 reject 一次、下一次成功，呼叫端看到 reject 後重試能讀到。C16 只對能注入失敗的實作跑。這一項在環節 9 一起定，這裡先登記。

**P3｜只改文件**：F3、F4 寫成 D-110 的補充（新決定不另立 D-ID，除非 Codex 認為備份的例外值得單獨一條）。

**不動的**：`list`、`read`、`modify`、`append` 的簽名與語義；開發命令直接用 vault。

## Codex 回應：環節 1（2026-10-26）

**結論：同意保留確定的改名資訊、刪掉 `state` 的內容／檔名猜配對；P1 目前不能直接交給 Opus。** Node 的配對仍然會猜錯，`Map<path, { from? }>` 不能保存改名事件的順序與次數，重試、目的路徑殘留狀態和紀錄來源的處理也要補清楚。F1 的影響不只有多跳小視窗，還可能漏掉 ID 遺失、提供錯誤的還原 ID。

這些修正服務北極星的方式，是讓學習目標的進度不因整理檔案而接錯或重新開始，避免不必要的重複複習，也避免把未熟練的目標當成已熟練。以下是查核與提案，尚未成為使用者確認的決定。

查核基準依使用者指定為 `833b0fae73803f7821f532e40a31a2ed92ed9bce`。開工時 main 是 `8e2fb28b6f4c5feea80ef4ef83a7f5080837f5b5`，工作區乾淨；基準之後只多一份 W6 格式查核紀錄，本次涉及的程式、規格與討論稿相同。〈先讀這裡〉仍寫 `90854e6`，那是新增本稿前的程式基準，並未造成這次程式版本不一致。已讀完所列必讀範圍，另核對 `save.ts`、`wrap-files.ts`、相關測試、技術債、更新規畫及 D-053；本次只在本稿追加回應。

### 第 1 題：回呼簽名

**目前選 `onChange(path, from?)` 可以，不必為這次改動加 `kind`。** 普通通知的意思應是「這個路徑需要重讀」，不是「在處理通知時它必定存在／已刪除」；`read` 的最新結果仍然是依據。`from` 則必須有更強的意思：**來源實作知道這是一次真正的改名，不能以檔名、內容或集合大小推測。**

事件物件和 `kind` 是兩個不同的選擇：也可以只有 `{ path, from? }`。這次兩個參數已足夠；若未來真的要加入更多欄位，再改物件，不以「一直追加位置參數」作為長期設計理由。

介面註解至少要補三件事：

1. 普通通知可合併；已確認的改名關係必須保序，不能因同路徑又改字或重試而消失。收到通知後到實際讀檔之間，檔案仍可能再次變動。
2. 有 `from` 時，新舊路徑都屬於此次變動。呼叫端必須檢查兩端是否在自己的範圍內，不能只篩新路徑。
3. 沒有 `from` 不代表「確定不是改名」，只代表沒有可用的改名證據。不能承諾把同步軟體送來的刪除＋新增都辨識成改名。

若未來要區分「同一路徑的舊檔刪掉，再建立另一個檔」與「修改同一個檔」，只有路徑與最新內容不夠，屆時需要更強的生命週期資訊；單加 `kind`、但仍把通知按路徑合併，也解決不了。目前不為這件事擴大 v1。

### 第 2 題：Node 配對規則

**不夠；P1 這段要改，不能稱為「不猜」。** 有兩個直接反例：

| 操作 | 提案的判斷 | 問題 |
|---|---|---|
| 刪掉 `舊/單元.md`，另建無關的 `新/單元.md` | 消失一個、新增一個、檔名唯一相同，配成改名 | 會把舊卡組的待處理與上一版接到新卡組 |
| 真正把 `a.md` 改成 `b.md` | 檔名不同，不配對 | 連提案自己的 C12「`b.md` 帶 `from=a.md`」都不能通過 |

Node 的 `fs.watch` 只有事件種類與可能缺少的檔名；`rename` 也用在路徑出現或消失，沒有直接提供 old/new 配對。這不是 Obsidian `rename(entry, oldPath)` 的同等證據。[Node 官方文件](https://nodejs.org/api/fs.html#fswatchfilename-options-listener)

我建議最小做法：**Node 版沒有確定證據就只送受影響路徑，不送 `from`；Obsidian 版轉送已知的改名；記憶體替身由測試的 rename 操作明確發送。** 不再做檔名或內容配對，也不為測試另加一套跨平台檔案身分追蹤。

代價必須寫清楚：Node 的真實檔案監看只能保證重新讀到最後狀態，不能拿它驗證「改名前後待處理一定延續」。D-110 的共用契約也要如實分成共同的變動通知條件，以及「提供 `from` 的實作」必須通過的改名條件；共同條件可把 `(new, from=old)` 視為兩端都已通知，Node 則仍可分別通知兩端。不能一邊允許省略，一邊要求所有實作的 C12 都必須收到 `from`。如果堅持 Node 也要完整保留改名身分，就要另做並驗證可靠的來源機制，這不是現有 rescan 小改即可承諾的能力。

還有一個驗收必須改：`tests/state-ids.test.ts` 的「改名（同一批的刪除與新增）」實際是 `rm` 舊檔再另寫新檔，沒有執行 rename。它目前正好把猜配對當成正確行為。應拆成「確定改名會延續待處理」與「獨立刪除＋新增不移植待處理」兩例；前者用能明確送出改名的替身。P1 不能要求這個舊測試一字不改照舊通過。

### 第 3 題：Obsidian 資料夾刪除

**沒有足夠證據保證子檔事件的數量、順序，以及 callback 當下 `TFolder.children` 還保留哪些項目，留給 Windows 實機 C15。** 本地 `obsidian.d.ts` 的 `Vault.on('delete')` 只宣告收到 `TAbstractFile`，沒有承諾這些細節；既有 C12 成功也不能證明刪除行為。

C15 方向正確。建議用 `f/1.md` 和 `f/sub/2.md`，確認巢狀子檔也會通知、最後 `read` 都是 null；檢查的是最終涵蓋所有受影響路徑，不要求所有平台恰好各發一次普通通知。Windows 的 `vault.delete` 與外部刪除各跑一次；iPhone 仍併入 W6 那次檔案存取驗證，不另開一次實機流程。

若實測發現只有資料夾事件且 children 已空，再在 Obsidian adapter 內維護必要的已知檔案清單或做差異比對；不要讓 `state` 猜資料夾裡曾有哪些檔案。這是待驗證後才選的實作，不是本輪已確認需要的新快取。

### 第 4 題：改由通知驅動 `move`，ID 安全還缺什麼

方向比現在安全，但必須一起處理以下條件，才能維持 D-134。前兩項涉及錯誤還原，屬於 P1 的安全風險；其餘至少是 P2 的狀態一致性問題。這些是提案的開工條件，不代表尚未實作的 P1 已經被測過。

**（a）改名關係不能存在以目的路徑為鍵的 Map 裡。** Map 記住的是首次插入順序，不是最後一次事件的順序，而且同目的路徑只能留一筆。已用最小 JS 例子重現：`c` 因前一批讀失敗而先在 pending，接著收到 `a→b`、`b→c`，最後 Map 的順序是 `c(from=b)`、`b(from=a)`；依序 move 會先搬不存在的 b，再把 a 留在 b，沒有搬到 c。即使沒有重試，`a→b→a→b` 也會被 Map 合併掉一次。

建議把「有序的改名事件」與「待重讀的路徑集合」分開。每個改名關係只消費一次，讀取失敗只保留重讀工作，不重播已套用的 move。路徑重用、來回改名、經暫存檔名交換兩篇，都必須保留真正的順序。

**（b）`tracker.move` 目前不是安全的覆蓋搬移。** `src/state/ids.ts` 只搬來源有的 map 項目；來源沒有 pending、目的地卻殘留 pending 時，目的地的舊問題不會被清除。目的地可能已從磁碟刪掉，只是前一批讀失敗，state 尚未清掉它，不能假定「作業系統允許改名＝state 目的地沒有資料」。

已直接呼叫現有 tracker 重現：A 的目標是 `^k3m9x2`；B 原本有 `^p7q2w8`、弄丟後留下 lost；A 搬到 B，再讀到 A 被拿掉 ID 的文字，B 舊問題仍保留，`resolve(..., 'restore', ...)` 真的寫回 **`^p7q2w8`**。應延續的是 A 的證據。實作須先依有序事件處理目的地舊生命週期，再完整搬移來源的所有狀態，包括「來源沒有 pending」這件事；不能直接把現在的 `move` 接上新通知就算完成。來源狀態不存在、重複事件或載入期間已讀到新路徑時，也不能反過來盲目清掉有效的新狀態。

**（c）「不同批」要包含讀取還在進行時的改名。** 若上一批正在 `read(a)`，期間收到 `a→b`，舊 read 回 null，不能先 `forget(a)`，到下一批才發現已沒有基準能搬。反方向也是一樣：新路徑先被一般通知讀成第一版，之後才套用已排隊的 rename，可能先把待處理當成新目標。以上是對 `apply` 的非同步時序推演，尚未對新方案執行測試。

應在採用讀取結果前，檢查該路徑／改名鏈是否已有更新的通知；過期結果重讀，不拿它刪除或覆蓋新狀態。若 rename 已先套用、之後 b 才修改，或 a 的修改已處理完再 rename，則只要完整保留上一版，照原本 observe 即可。也要涵蓋 `fillText`／`fillIds`／`resolveText`：收到改名但尚在 500 ms 合批期時，家長按存檔不能繞過未處理的搬移、直接在新路徑配 ID。可先同步處理確定的路徑搬移、延後讀檔；或在寫入入口先消化相關事件／保守拒絕。選一種明確規則，不新增持久身分資料庫。

**（d）搬移本身就必須使對外狀態更新。** 目前 `tracker.move` 不增加 revision。P1 若先把 `deckMap` 的鍵搬好，再拿完全相同內容去比較，`decksChanged` 可能一直是 false，`deckList`／`planList` 與畫面還留著舊路徑。即使文字沒改，路徑搬移也要觸發 rebuild、重排與 onChange；新路徑暫時讀不到時，已搬移的待處理仍須保留，不能變成可補 ID 的新目標。

**（e）紀錄檔也要用到 `from`，只是不用它搬 ID tracker。** 舊契約會通知舊路徑，所以 `sources` 能清掉消失的來源；新契約只送新路徑。若照「紀錄改名只重讀、不用 from」實作，舊來源會永遠留在 history。尤其把紀錄搬出紀錄資料夾時，現有 notify 只篩新路徑就整個忽略。應重核舊、新兩端的來源與重試工作，依最終內容重新 merge；移入、移出、改成不合法的紀錄檔名，以及新路徑符合 `own()` 的過濾條件，都不能漏掉舊來源。不要把自己的尚待寫入紀錄和外部來源任意互蓋。

**（f）範圍判斷要同時看兩端。** 同意卡組搬出 `Essence Cards/` 或搬進系統資料夾時移除 tracker 與佇列，搬入則當新出現；但判斷要在新路徑的早退之前。還要處理原路徑隨即被另一篇新檔重用，不能讓舊的重試或搬移覆蓋它。改名後改字的比對仍須維持既有順序：同批紀錄先更新、所有卡組最新占用先放上，再判斷 lost／changed，不能弄丟先前 F5、R2 的修正。

### 環節 1 提案第二版（待 Codex 確認 R3、R4、契約的 `renames` 參數）

**介面**

```ts
/**
 * 新增、修改、刪除通知路徑；通知只表示「這個路徑要重讀」，read 的最新結果才是依據。
 * from：來源實作有確定證據的改名（Obsidian 的 rename 事件）；有 from 時新舊路徑都屬於這次變動，呼叫端要檢查兩端。
 * 沒有 from 不代表不是改名，只代表沒有證據；Node 版永遠不送 from，舊、新路徑各通知一次。
 * 改名關係必須保序，不能因同路徑又改字或重試而合併掉。收到通知到實際讀檔之間，檔案仍可能再變動。
 */
watch(onChange: (path: string, from?: string) => void): () => void;
```

`scopedFiles`：兩端都在 scope 內 → 兩端都去前綴；只有舊路徑在內 → 通知舊路徑（不帶 `from`）；只有新路徑在內 → 通知新路徑（不帶 `from`）；都不在 → 忽略。

Node 版另補：`filename === null` 的事件把所有已知路徑都通知一次（測試與工具用，保守即可），並有測試。

**`state` 的規則**

- **R1 兩個佇列分開**：`renames: { from: string; to: string }[]`（有序，每筆只消費一次）與 `pending: Set<string>`（要重讀的路徑，可合併）。讀失敗只把路徑放回 `pending`，不重播已套用的改名。
- **R2 `tracker.move` 改成「取代」**：先 `forget(to)`（目的地殘留的上一版與待處理一律清掉），再把來源的 `texts`、`versions`、`present`、`pending` 整組搬過去（來源沒有待處理時目的地也沒有）；來源在 tracker 裡不存在時只做 `forget(to)`，`to` 當成新出現去讀。`move` 一律 `revision++`，所以 `apply` 會 `rebuild`、重排、通知畫面，純改名也一樣；`deckMap`、`planList` 的鍵跟著搬。
- **R3 改名同步套用、讀檔延後**：`notify(path, from)` 收到 `from` 時，在同步的回呼裡立刻做 R2 的搬移（tracker、`deckMap`、`sources` 的鍵），然後把 `to`（與 `from`，讓它讀到 `null` 收尾）放進 `pending` 等 500 ms 合批重讀。理由：存檔入口（`fillText`／`fillIds`／`resolveText`）看到的永遠是搬移後的狀態，不會在合批期間於新路徑配新 ID；`a→b→c`、`a→b→a→b`、經暫存檔交換兩篇，都照收到的順序逐筆套用，不需要在 `apply` 裡重建順序。配合 **世代號**：每個路徑記最後一次通知的世代，`apply` 讀回來的結果若世代已過期（讀的期間又收到這個路徑或它參與的改名），丟掉結果、路徑留在 `pending` 重讀，不用過期結果 `forget` 或覆蓋。這同時處理 Codex (c) 的兩個方向：舊 read 回 `null` 不會 `forget(a)`（a 已被搬走，結果過期）；新路徑先被一般通知讀到也會因為後到的改名世代更新而重讀。
- **R4 載入完成前的改名**：`loaded` 之前收到的 `from` 直接丟掉，只保留路徑進 `pending`。理由：`load()` 用 `list` 的結果建基準、不偵測，改名前的路徑讀到 `null` 就不算，新路徑之後以「第一次出現」讀入。這段沒有上一版可搬，也沒有待處理可丟。
- **R5 兩端都看範圍**：先判斷再早退。`from` 是卡組、`to` 不是 → `forget(from)`、佇列不再出它；`from` 不是、`to` 是 → 當新出現；都不是 → 忽略。紀錄檔同樣看兩端：`from` 在 `sources` 就刪掉、`to` 是別台裝置的紀錄就重讀，最後整份重新 `mergeHistory`；移入、移出、改成不合法檔名、新路徑符合 `own()` 都走同一條。原路徑隨即被另一篇新檔重用時，世代號讓舊的搬移或重試不會蓋到它。
- **R6 比對順序不變**：同批紀錄先更新來源、所有卡組最新占用先放上，再判斷 lost／changed（維持 F5、R2 的修正）。改名後改字就是 `move` 之後 `tracker.text(to) !== text`，照舊走 `observe` 的 `changed`。

## Codex 回應：環節 1 第二輪（2026-10-26）

**三點的結論：R3 方向同意，但還沒補齊；R4 不同意照目前文字實作；契約用 `renames: boolean` 可以。環節 1 暫時不能標成已談定。** 第二版已解決 Node 猜配對、事件按目的路徑合併等第一輪問題；以下只列仍有反例或會影響實作的缺口。目的仍是保住學習目標的進度，避免整理檔案造成重新複習或接錯熟練度。

查核基準：`88cc13b6c838f0fc691c816f55e4c1f12d30126d`。本輪執行於 2026-10-27，標題日期依使用者指定保留。開工時 main 是 `b2f3f84`，工作區乾淨；之後相關程式與本稿未變。另讀新版 `tasks/state-load.md`：它已把讀取失敗整理排在 W6 合併前，環節 ① 會疊在它上面，所以本稿第二版完成條件 7 的「ready 技術債同批做」已過時，以新版排程為準；這不影響 `88cc13b` 提案本身的查核。

### 三點確認

1. **R3 同步套用改名、延後讀檔：可以採用，但世代號只保護 `apply` 的讀取結果還不夠。** 還要處理已建立的載入基準、尚未完成的寫入 commit，以及同步搬移後的對外狀態更新。下面 S1、S2、S4 是具體缺口。世代應在啟動 read 前取得，結果採用前檢查兩端；過期結果不論成功、null 或 reject，都不應改動新狀態或把舊生命週期的失敗留在 `unread`。路徑刪掉再重用時，不能把世代重設成舊值，直到舊工作都已失效。
2. **R4「loaded 之前丟掉 from」不安全。** `loaded=false` 不等於「tracker 沒有上一版」。目前 `load()` 是先把卡組交給 tracker、rebuild，再 await 紀錄，最後才設 loaded；新版 state-load 也保留先卡組、後紀錄的順序。只有這個路徑尚未建立任何基準、也沒有相關在途結果時，才可以當成第一次出現。不能用全域 loaded 一刀切。
3. **契約分層放在執行函式的 `renames: boolean` 可以，不需要加到 Files。** 這是測試選擇，不是產品的能力旗標；產品只依每次事件是否有 from 處理。參數建議明確必填，各呼叫端與包裝後的實作各自選對條件。`false` 要驗 Node 確實不送 from，不能只是略過強條件；`true` 要驗真正 rename 有正確配對、順序與次數，獨立刪除＋新增不送假配對。驗「只有一次」時，要在收到第一筆後再留一段觀察期，不能 `until` 一收到就通過。連續改名、巢狀資料夾與取消監看也要保留測試。

### 第二版還需修訂的缺口

**S1｜P1，規格漏洞：載入後半段已有基準，R4 會把它丟掉。**

已用公開的 `createState` 與可暫停紀錄 read 的記憶體 Files 重現這段時序：

1. 卡組 a 的 `^k3m9x2` 已讀完、已放進 tracker；紀錄檔還在等，ready 尚未完成。
2. a 改成 b，同時改目標名稱並拿掉 ID。按 R4 只留下兩端的普通通知，不保留 from。
3. 放行紀錄 read，ready 完成；500 ms 合批還沒處理前，家長對 b 按存檔。

實際得到 b 的 **issues=0，直接配出 `^aaaaaa`**；此時 `decks()` 還列著 a。這個反例利用的是現行載入順序與 R4 所選的「丟 from」語義，並非宣稱第二版已經實作。

**建議**：載入期間也保留改名證據，已建立基準的路徑照樣搬；尚未完成的初次 read 用世代號／有序事件核對後再採用，不能把改名前的快照又放回舊路徑。ready 對外開放存檔前，先處理會改變已知身分的待處理事件。若要讓整段啟動都只算第一次讀，就必須重新取得受影響路徑的有效基準後才開放，不能只刪事件而保留先前讀到的一半狀態。不要求等待全庫永遠沒有通知；只核對這次已收到、會影響基準的工作。

原文「這段沒有待處理可丟」也不成立：`observe(..., false)` 初次讀到 ambiguous-id 仍會建立待處理，只是不產生 lost／changed。應按每個路徑是否已有狀態判斷，而不是假設 ready 前 tracker 一定空白。

**S2｜P1，規格漏洞：世代號只顧 read，漏了已準備、尚未完成的寫入。**

`fillIds(a)` 在 `Files.modify` 的 edit 裡取得 `tracker.fill(a, text)`，modify 完成後才呼叫其 commit；這個閉包記住的是舊 path。如果等待寫入完成時，R3 已同步做 `a→b`，晚到的 commit 仍能呼叫 `observeText(a, next, false)`，把舊路徑加回 tracker，state 的 adopt 也會跟著採用舊路徑。

已直接用現有 tracker 重現：先對沒有 ID 的 a 取得 fill 的 commit，照 R2 搬到 b，再執行舊 commit；結果 a 被重新加回、帶著 `^aaaaaa`，b 仍是未補 ID 的舊文字。這證明閉包不能直接沿用，不是對 Obsidian 磁碟寫入與 rename 競爭結果的實機結論。

**建議**：寫入完成後採用結果也要核對路徑生命週期。改名後的舊 commit 不得重新建立 a，尤其 a 已被另一篇重用時；不能只把閉包的字串改成 b 就無條件採用，因為 b 可能又被修改。可以使過期 commit 失效、保留已配出的 ID 為占用，並重新核對真正目的地；或用明確的序列規則協調寫回與搬移。若暫時不能確定寫入落在哪裡，先限制相關 ID 寫入，再讀回確認。這條不需要改檔案格式。

**S3｜P1 的條件式風險，規格漏洞：R2 的「來源不存在也 forget(to)」會破壞已搬好的狀態。**

已按第二版規則用現有 tracker 組出反例：a 有 lost（restore=`k3m9x2`），第一次 `a→b` 正常搬好；再送一次相同的通知，來源 a 已不存在，`forget(b)` 清掉剛搬好的問題，之後 fill 對 b 配出 `^aaaaaa`。

這是**重複通知的注入反例**，尚未證明 Windows 實際會重複送同一個 rename；但目前介面只寫保序，沒有把「每次真實改名只送一次，且不晚於其後的身分事件」完整定成來源契約。資料夾與子檔事件是否重複，也仍列待實測。R1「每筆只消費一次」只防自己的佇列重播，不能防來源送兩筆。

**建議**：把原子且有序的改名交付條件寫進 adapter 契約並驗證；若來源可能重複，須在破壞目的地前處理。至少區分「目的地仍是已套用改名的狀態」與「確定被另一篇取代」，來源缺席本身不足以推出後者。不要用一個永久的 `(from,to)` Set 去重，因為 `a→b→a→b` 的第三次是真的改名。第一輪提醒的「來源不存在、重複事件不能盲清目的地」仍需補上，R2 目前把這點寫反了。

**S4｜P2，設計漏洞：同步 revision++ 不保證 apply 會看到它。**

R2 說「move 一律 revision++，所以 apply 會 rebuild」不成立。現行 `apply` 在 `await Promise.allSettled(...)` **之後**才記下 `const revision = tracker.revision()`；若改名已在 notify 或等待 read 的期間套用，記下的就是增加後的數字。純改名的 deckMap 又已搬好，讀回相同文字，後面比較便可能完全沒有變動，直接 return。已以對應的最小狀態機模型重現 revision 增加、deckMap 已在 b，但 deckList 留在 a。

**建議**：同步搬移要有獨立的 dirty／待發布狀態，或以「最後一次已發布的 revision」比較，成功發布後才清掉；不要拿本次讀完當下的 revision 當基準。而且 `planList` 不只是鍵，它還依 tracker 的待處理行號過濾目標；需要一致地 rebuild。從 notify 返回後，`decks()`、`input()`／`today()`、`deckStatus()` 不能各看到不同篇的狀態。可以立即發布一致的已知狀態、讀檔仍合批；也可以延後通知畫面，但此時查詢與寫入入口必須遵守同一個尚未核對的規則。不能只寫「planList 的鍵跟著搬」就算完成。

**S5｜P2，整合規格漏洞：丟掉過期紀錄 read 後，卡組比對不能把它當成已完整讀取。**

例：同批卡組把舊 ID 換成 `zzzzz9`，紀錄 L 的最新內容原本可以證明這個 ID 已使用過；L 的 read 因另一個通知而過期，被 R3 丟掉，卡組結果卻仍有效。若繼續 observe，就會先產生 changed；下批 L 成功後，現有 tracker 不會自動撤銷它。已直接驗證：先在缺紀錄證據時 observe 出 changed，補上 logIds 再 observe 相同文字，問題仍在。

新版 `state-load` 的暫定問題規則以 `unread()` 非空為條件；**世代過期不是 read reject**，不能假定它會自動進 unread、因此得到相同保護。實作要明定這種「有更新待核對」的依賴：延後需要完整證據的 ID 判斷，或把這批問題標成可重新核對，待紀錄有效後重新判定；相關補 ID／還原也不能把未知占用當成未占用。可以共用 state-load 的保守規則，不必把過期讀取冒充成讀檔錯誤、誤報 onError。

另外，state-load 會把 `logIds()` 改讀 `history.seen`；屆時 R6 的「紀錄來源先更新」還不夠，必須在 tracker 比對前更新可供它讀取的最新 seen，不能等到 apply 最後才 mergeHistory。這是環節 ① 疊在該任務之上時要保留的完成條件。

### 其他文字衝突與完成條件的補法

- **R1 與 R3 選一個改名消費點。** 既然選 notify 同步搬移，R1 的 renames 陣列若保留，只能是待發布／診斷紀錄，不能再讓 apply 搬一次；最小方案是省掉第二個可執行的改名佇列，pending 只負責重讀。
- **R3 與 R5 統一紀錄來源的規則。** 一條寫同步搬 sources 鍵，一條寫刪來源再只重讀非 own 的新路徑，實作順序會影響結果。兩端都仍是合法紀錄時，保留已知內容直到有效重讀並重新 merge；搬出紀錄範圍才移除來源。rename 到 own 檔名也要有一次明確的核對方式，不能直接套用「一般自己的 append 通知忽略」而漏掉整份來源；與尚未 flush 的本機作答如何合併，也須說明。這是第一輪紀錄改名條件的延續，不是加另一個紀錄系統。
- **Node 無檔名事件仍要 rescan。** 在現有 rescan 上補「已知檔全部失效」可以；若只通知舊 known 集合而取代 rescan，新檔案將永遠不在通知裡。重掃暫時失敗後，重試也要保留這次無法定位的失效需求。
- **C15 尚待實機；契約旗標不取代證據。** 可以先確認參數設計，不能因此宣稱 Obsidian 的整個資料夾 rename／delete 交付條件已驗證。記憶體替身還要能刻意延後 read／modify 完成，才能測到本輪時序；只有同步通知和 failing 集合不夠。

### 第 1 題：外部改名是否一定只有 delete＋create

### 第 2 題：刪掉內容配對、又沒有 from，是否會丟待處理

**這點沒有看錯，但成立有條件。** 現行程式要在同一批內讀到舊路徑 null、新路徑文字完全相同，且 tracker 還保留舊篇，才會搬過去。移除這項配對又沒有其他改名證據時，新篇沒有上一版，lost／changed 的待處理就可能消失，存檔配新 ID。這是第一輪建議刪掉猜測時需要明列的代價；我同意不能把那種刪法稱為對所有來源都更安全。

但「內容相同就都接得住」也說得太滿。本次用現行 createState 重現：同文字的舊、新通知同批處理時，`restore=k3m9x2` 跟過去；把刪除與新增分兩批處理，第一批已 forget 舊篇，第二批的問題清單就是空的。讀取失敗也可能使兩端無法同批配對。因此保留內容配對是保留部分既有能力，尚未保證外部改名的待處理一定延續。

另外，文字完全相同仍不足以證明檔案身分相同。第一輪已重現「獨立刪掉舊篇、另建同內容新篇」也會移植舊 restore；同批有多篇同文字時也無法只靠文字唯一配對。家長按還原以及檢查 ID 尚未占用，只能防止未經選擇的寫回與重複占用，不能證明那個 ID 屬於眼前這篇。這項現存風險沒有因 T1 而消失。

### 第 3 題：第三版是否比現況更不安全

**有。T1 會減少同名無關卡組的誤配，也會拿掉現況在真實搬移時已有的一部分保護；後者已做差異對照重現，屬 P1 的規格退步。**

測試中的路徑是 `Essence Cards/A/x.md` → `Essence Cards/B/x.md`，原本目標為 `能說明擴散 ^k3m9x2`、題目為 `Q :: A`。兩個版本都透過公開 State 介面處理相同的普通路徑通知，沒有使用 from。

1. **集合每次改變都有 `layout-change`。** 而且送出的當下，`getLeavesOfType('markdown')` 加上 viewState 已經是新的集合，17 步沒有例外。切換分頁不改變集合，也不送 `layout-change`。

3. **編輯器建立（`ViewPlugin` 呼叫 `opened`）的時間不固定。** 有時在 `layout-change` 之前（步驟 1，早 16 ms），有時在之後（步驟 3，在第一個 `layout-change` 之後 45 ms）。不管哪一種，`layout-change` 時集合都已經含那一篇，`opened` 沒有提供額外的資訊。

### 7-2 發現

**G2｜P2：考試範圍要跟著「清晨 4 點換日」重新判斷，不能在載入時算一次**

考試範圍是否生效由日期決定（syntax.md §4）。`state` 的 `fresh()` 過了換日會重排，但 `TodayInput.exam` 現在是 `input()` 每次給 `null`。範圍模組接上後，`exam` 也要在 `input()` 裡依當下的日編號重算（從已解析的考試範圍檔與卡組算，很便宜），不能把 `ExamScope` 存起來跨日使用，否則考完那天之後仍然提高到 90%。另外 `state` 要多監看第三種檔案（`Essence Cards/考試範圍/`），和卡組、紀錄一樣走同一條讀取與重試規則（`state-load` 定的）。

**G3｜P2：規格要求「改檔名」，檔案存取沒有這個動作**

syntax.md §4：沒有期間時檔名叫 `日期未定 國二上.md`，補上期間後外掛改名。`Files` 只有列出、讀取、修改、追加、監看，沒有改名（也沒有刪除）。環節 1 才剛確認改名事件是最難處理的一種。

建議改規格、不加動作：**檔名在建立時決定、之後不改**（例如 `建立日 年級學期.md`），考試期間只寫在屬性裡。家長與學生都從外掛的畫面設定考試範圍，不在檔案樹裡找它（architecture §5），檔名只是紀錄；「日期未定」這個寫法也一起拿掉。另一個做法是 `Files` 加 `rename`，要多寫契約與兩個實作，只為了檔名好看，不建議。這是改格式，要使用者同意。

**G4｜要決定：同一個單元有好幾篇卡組**

規格沒寫一個單元只能有一篇卡組。實際上會有：課本與習作分開、一課太長拆成兩篇。建議允許：目錄把同一個（年級學期、科目、單元編號）的卡組合成一個單元節點；跨單元出處依路徑順序找這幾篇的材料；考試範圍照單元比對，不受影響。單元名稱不同時（`2-1 地形`、`2-1 地形與氣候`）給提示。

**G5｜要決定：跨單元的目標在目錄裡算在哪一個單元**

D-137 讓「同一個道理跨年級只建一個目標」，這個目標的出處會寫到別的學期的單元。考試範圍已經照「目標屬於的所有單元」判斷（syntax.md §2-5），但 D-097 的目錄（單元的卡片總數、顏色、「當日卡」「全部卡」）沒說它算不算。只算在卡組本身的單元，會出現「這個單元標著『考試』，但考試實際包含的卡比目錄列出的多」。建議：目錄在它屬於的每一個單元都列出（標明來自哪一冊），數字、顏色、「當日卡」「全部卡」都算進去，和考試範圍一致。

**G6｜P2：目錄的管理模式會寫卡組，和 D-134「iPhone 不寫卡組」衝突**

## Codex 回應：環節 7（2026-10-27）

**結論：G1 的語法歸屬、G2 的換日方向、G3 的固定檔名、G6 的裝置限制都可採為提案；但還不能照目前文字說「接上 ExamScope，study 不用改」。** 同日改範圍的快取、單元與卡組的不同選取方式，以及 D-136 的課外排序都有缺口。G4、G5 可以維持「一個學習目標、一份進度」，但多篇卡組的狀態與跨單元的計數必須補清楚。這些修訂是為了讓學生找得到該複習的目標、不重複花時間，也不讓課外內容擠掉考前的核心。

### 第 1 題：G1 的位置與可引用編號

**把出處的純語法解析放在 `deck` 合理，不需要第五個共用模組。** `sourceLinks` 現在只把文字拆成頁碼、錨點、筆記連結、單元參照，沒有讀檔或查目錄；這正是 [D-110](../docs/decisions.md#d-110-v1-外掛的程式結構) 的卡組語法責任。建議分清三件事：

- `deck`：解析單元、年級學期與每一項出處，保留原文；不查別篇卡組。
- 範圍與目錄：把單元參照對到邏輯單元與候選卡組，計算目標所屬的單元、排序與考試比對。
- Obsidian 層：在候選材料裡找區塊／標題並開啟。核心不讀 metadataCache。

`review` 若為了相容現有呼叫端暫時重新匯出型別或函式可以，不必另外保留一個同簽名的轉手函式。不過「`ui/sources.ts` 不動」只能指找錨點的責任不搬：它現在遇到 `kind: 'unit'` 直接回傳 null，跨單元可點時，呼叫接線仍要改成把解析好的候選材料送進去。

對 syntax.md 的**建議文法**如下，正式採用與相容規則仍要經 D-140 的格式查核：

| 項目 | 建議與界線 |
|---|---|
| 數字編號 | `[0-9]+(?:-[0-9]+)*`，包含 `2`、`2-1`、`1-2-3`，不把層數鎖在兩層。 |
| 英文編號 | `[A-Za-z]+[0-9]+`，包含現有 `L1`、`U1`；不含空格。`單元: L1 Back to School` 的編號就是 `L1`，§4 的例子改為 `L1～L3`。 |
| 編號的身分 | 用原字串比對，不默默把 `L01` 改成 `L1`、改大小寫或把 `Unit 1` 縮成 `U1`；自然排序是另一件事，例如 `L2` 在 `L10` 前。 |
| 層級與區間 | 整章 `2` 以完整編號段比對，包含 `2-1`、`2-1-3`，不能包含 `20-1`。區間的兩端要屬於可比較的同一系列；跨系列、反向區間、端點底下的子節算不算，都在格式規格列例子，不交給字串排序碰運氣。 |
| 年級學期 | 現有設定支援的是小一～小六、國一～國三、高一～高三，各有上／下；共用解析不能再用一條組合出「高六上」的正則。卡組原有的其他文字值仍保留，不因新增引用文法而讓整篇不能複習。 |

`Starter` 等非標準編號仍可作為卡組屬性與目錄項目；無法解釋的跨單元寫法／區間要提示，不能猜成另一個單元。目錄的精確勾選可以按原編號比對，不必把「不能推算區間」擴大為「整個單元不能選」。`Review 1` 在現有屬性規則下是編號 `Review`、名稱 `1`；是否另訂寫法是 backlog 原本的待決問題，本輪不順便重定義它。

另外，共用的是解析規則，不是前後項的繼承狀態。[syntax.md §2-5](../docs/syntax.md#2-5-出處) 每項獨立：`小五上 2-1 p.15、p.44` 的第二項仍回到目標所在卡組的單元與材料。W6 這點目前正確，要保留。多層 `1-2-3 p.20` 目前卻被當成 heading，已直接執行 `sourceLinks` 確認。

### 第 2 題：G2 的 input 與 current

**有，同一天改考試範圍時會對不上；只在 `input()` 重算不夠。** `src/state/index.ts` 的 `fresh()` 只比較 `current.day`、`current.offset`；`study/session.ts` 的 `nextCard()` 也只用換日、時區判斷 stale。`current` 已經保存當時的 lane、到期候選與每個 slot 的 retention、inExam，換一個 `input.exam` 不會更新這些資料。

已把基準程式**只在記憶體中投影成 G2 的接法**，讓 `input()` 每次讀當下的 ExamScope，透過公開 State 介面得到：

| 同日操作 | input 的新值 | today 仍回傳 | 重新 planToday 的正確值 |
|---|---|---|---|
| 原本無範圍，改成有期間且包含該目標 | 有 exam | 同一份 current，lane=`new` | lane=`exam-new` |
| 原本在有期間的範圍，移除生效範圍 | exam=null | 同一份 current，lane=`exam-new` | lane=`new` |

兩例呼叫 `next()` 都沒有觸發 stale；跨到次日 04:00 後才重排。這是對提案接法的反例，並非聲稱 main 已有考試範圍功能。

建議把以下規則寫進開工條件：

1. `input()` 用**同一次取得的 now、offset、已採用的資料版本**算有效範圍；不要在 contains 裡另讀時鐘或檔案，讓同一次排程中途變答案。
2. 範圍檔新增、內容變更、刪除、重試成功，以及相關卡組／出處變動，採用後都使 current 失效並通知畫面；本機設定成功也走同一個入口。可以沿用 `replan()`，不需要為了這件事另存一份持久快取，也不能每次因新建 ExamScope 物件就無條件重排。
3. 換日與 offset 改變照現有 `fresh()` 重排；到考試結束日的**下一個** 04:00 才失效。未到開始日也已生效、填期間當下就提高保持率，不能誤寫成「開始日到了才啟用」（D-078、D-098）。
4. 作答照舊由 history 推進，不因每次 answer 都重排今天的份；範圍重排後已答對的目標也不能被當成未完成。

讀取與重試可以共用 state-load 的機制，但有效性、切換範圍與通知必須補上這些驗收；「第三種檔案讀得到」本身不夠。

### 第 3 題：G3 固定檔名及其他依賴

**固定建立時的檔名可行，生效判斷不必依賴檔名；但漏看了 D-115，不能只核對 D-105。** [D-098](../docs/decisions.md#d-098-考試範圍只用在大考日期改成考試期間) 已把生效、失效、同時多份時的先後定成看屬性的考試日期。D-105 要保留過期檔，沒有規定回測從檔名解析日期。目前範圍模組還沒實作，也沒有需要保留的既有「檔名日期解析器」。

需要保留或補齊的是：

- **檔名日期不再代表考試日。** 若改用建立日，倒數、是否生效、考後上傳考卷的提醒（D-103）、同時多份時選開始日最早的一份，都看內容。不能拿路徑自然排序替代開始日排序；畫面「日期未定」的提醒仍要保留，拿掉的只應是這個檔名。
- **穩定識別與歷史。** [D-115](../docs/decisions.md#d-115-回頭查要用的證據先收好) 已要求考試範圍有不隨檔名改變的識別碼，建立、改範圍／日期、提前結束各記一行並含舊值與發現時間，考試開始日還要保存範圍內卡組的文字切面。固定路徑不能取代這個 ID；使用者仍能自行改名，日期相近也不能當成同一次考試的證據。這些是 v1 已同意但尚待定格式的工作，不是回測放第二階段就一起延後。
- **建立時不能蓋掉舊考試。** `建立日 年級學期.md` 仍可能撞名；需有不覆寫既有內容的建立規則與撞名後綴，舊檔不必搬移。跨裝置同時建立及同一 ID 的衝突副本如何處理，也須明定，不能把兩個副本默默當成兩次考試。
- **多份有效的邊界。** 「開始日最早」沒定義無開始日者排哪裡、同日怎麼打破平手。建議補固定規則與提示；檔名僅可作最後的穩定排序，不能變成考試日期。結束日單獨存在、日期無效、開始晚於結束也要有明確結果，不能一律退回「日期未定、永久生效」。

還有一個既有規格的邊界：考試開始日在未來，現在按提前結束，照 D-105 把結束日寫成今天，會得到「結束早於開始」。若新解析器一律拒絕這種區間，提前結束反而失效；若期待按下就立即取消，也與「結束日的下一個 04:00 才失效」不同。這要在格式查核前說清楚，不能暗中改成另一種取消行為。

因此我支持將 G3 作為刪減提案交使用者，但不能把整份範圍的 ID、歷史與考試開始日的切面一起刪掉。採用後要同步的還包括 D-098、D-104 對目前學期與檔名的說明，以及 syntax.md §0／§4、architecture §5 的例子；本輪依使用者要求不修改它們。

### 第 4 題：G4、G5 與既有決定

**G4 沒有違反「一個單元只能一篇」的決定，因為沒有這項限制；但聚合後不能把整個節點當成一篇卡組。G5 符合 D-026、D-027 的方向，但它是對 D-097 計數與操作的補充，仍待使用者確認。**

G4 建議保留，補三條即可：

- 單元鍵是完整的 **（年級學期、科目、單元編號）**；名稱只作顯示。同編號不同名稱可提示，但別因此拆成兩個不同身分。課本、習作可以歸在同一節點，各篇材料裡的相對連結仍以**那篇卡組的路徑**解析。
- 找跨單元材料時，候選卡組按路徑、各篇材料按原順序，**全部找完錨點才退回第一份可用材料**。不能第一篇沒找到就先 fallback，而漏掉第二篇的正確錨點。同頁碼在課本、習作都存在時，路徑優先只是固定取捨，不是已辨認出正確來源；須提示歧義，必要時沿用現有 `[[筆記#位置]]` 精確指定，不新增一套材料 ID。
- D-097 的草稿／暫停原本是卡組狀態。同一單元有啟用篇與草稿篇時，不能套「草稿優先」到整個單元，讓啟用篇的數字與練習入口消失，或讓學生看到草稿；管理時仍看得到各篇狀態。聚合後的總數與兩顆按鈕對暫停、已濾掉目標的納入規則要一起定，不能直接搬用整篇狀態。整個單元的批次操作要展開成實際卡組／目標集合。

G5 的每個單元都列出可以做，但需把「列出」和「實體歸屬」分開：

- 例如 `^k3m9x2` 存在小四上社會 2-1，出處另有 `小五上 2-1 p.15`，兩個單元都可看到它，**仍只有一個目標、一份題目池、一份排程與作答紀錄**。同一單元多項出處、勾選多個相關單元時，按目標 ID 去重；學期／科目／入口總數不能直接加總單元數字。
- 「當日卡」用該單元的目標 ID 集合與全域 `today.share` 交集；「全部卡」用同一集合走 D-071／D-097 的全部練習。作答後所有列出該目標的單元一起更新，當日卡答對過的目標不因換單元又變成未完成；全部練習仍保留接續與明確按「再練一輪」的規則。
- **現有接點不夠，已直接重現。** `Pick` 只有 `{ deck }`、`{ subject }`、`{ more }`；`nextCard` 的 deck 選取只比較實體 `QueueItem.deck`。上例即使已被五年級考試納入，從五年級卡組路徑選取仍回 done，改用四年級的存放路徑才回 card。G4 的多篇單元也有同一缺口。需要在該模組任務預留「依目標集合選取」的接點，並實作全部練習；不能複製卡組項目或借 `more` 代替，否則會重複出卡或只拿到上限外的部分。
- 每日排程的暫停、草稿、ID 待處理與濾網仍依真正擁有這個目標的卡組／目標判斷；從另一個單元看見它，不會解除限制。全部練習是否越過濾網須在該功能規格明定，不能因新增跨單元入口而暗中改變。管理修改與跳回筆記也要找真正的擁有者，不能寫到目前瀏覽的那一冊。

另一個需明說的邊界是「出處指到的單元，根本還沒有卡組」。考試的邏輯比對不應因材料打不開就丟掉那個單元關係；但若 G5 要據此建立只有參照、沒有卡組的目錄節點，就超出 D-033「由已建立卡組組成目錄」的原規則。建議 v1 先保留原目錄來源，找不到材料給提示；是否新增這種節點另列為本提案的取捨，不默默創造目錄或猜名稱。

### 第 5 題：G6 的 iPhone 管理模式

**沒有找到已確認、必須讓 Cards 在 iPhone 改卡組才能完成的情境。** D-134 的限制可沿用：暫停／恢復、改重要性或分類、加入草稿／補題、補 ID／處理進度連結、加深採用等，只要會改卡組就限電腦。限制要在寫入入口也成立，不能只把手機按鈕藏起來；手機上的命令、間接呼叫與復原也不能繞過。

不過「只留全部練習與考試範圍」若是在說**管理的批次按鈕**，可以；若是在說整個 iPhone 目錄，就少了 D-097 的當日卡、查看目標與狀態、篩選，以及 D-073 的濾網操作。它們不必寫卡組，設定／變更紀錄也不等於改卡組。考前抽測、自評與改評同樣只動紀錄，照常保留。手機從目錄或出處打開筆記也可保留；依 product 的既有範圍，使用者自行用 Obsidian 改筆記仍是另一條路，不能宣稱外掛已禁止它。

G6 的批次語意修改、按篇回報部分失敗方向正確，但「反向語意」還需補條件：**只還原這次確實改動、而且目前仍是這次寫入值的欄位**，以 ID 重新定位，不以舊行號或舊全文定位。中間若家長又改了該欄位、目標移走或身分有問題，就跳過並回報；不能用「設回原狀態」覆蓋較晚的選擇。未變的欄位、題目與補充原文都要保留。

寫成卡組後才記 `set: status` 合理，但要由同一個偵測出口負責，避免管理操作與隨後 watch 在同台裝置各記一次；復原也是一次新的狀態變更。紀錄 append 失敗時，卡組已成功的事實不會回滾，交給既有背景佇列重試並分清回報。卡組與紀錄沒有跨檔案原子交易；不要宣稱任何中斷點都能兩者同時成功，也不為此新增一套交易系統。

### 第 6 題：其他缺口，尤其 D-136 與跨學期出處

**H1｜P2，規格／資料缺口：不能從 `[AI 補充]`、有沒有課本連結或層次數字推定課外。** D-136 已明定第一次製卡補底層的 AI 補充、先備仍算課內；課外加深才算延伸。現在 `Target.fields` 只有 sources 等既有資料，沒有能可靠區分兩者的標記。「contains 看 target 即可」只表示函式參數足夠，不表示所需證據已經存在。標法與舊資料缺值的意思要與 AI 模組一起定、經格式查核；不確定的舊資料不能被新猜測默默移出考試。

而且這個判斷可能與**所屬單元**有關：原本國中課外的「水的密度隨溫度改變」，後來可能成為高中課內；同一成功判準依 D-027 仍沿用目標 ID。若整個目標永久標成「延伸」，高中考試會漏掉；若一律改成「課內」，又可能錯算回原國中的範圍。建議最少保留「目標對這個完整單元鍵，是課內還是延伸」的證據，contains 以命中的關係判斷；這不需要把整張學習地圖或層次搬進 v1。這項與跨學期加入時補上年級學期的規則一起驗收。

**H2｜P2，規格衝突待釐清：contains=false 並不保證課外排在所有範圍內課本目標後面。** 已用現行 `planToday` 重現：課外目標昨天答錯、考試課內目標是新卡；即使 contains 只對課內回 true，順序仍是課外 `relearn` → 課內 `exam-new`。90% 的部分可由 contains 控制，但排序仍受最前面的 relearn 規則控制。D-062／D-120 的答錯先出，與 D-136「課外考前排在課本後面」要明定是否有這個例外；若課本必須先出，就要改 study 的候選分類／排序，不能再寫 study 完全不用改。這是已重現的現行行為與新規格邊界，不是要求現在更改排程。

**H3｜P2，整合規格缺口：邏輯單元關係、材料定位與學期預設不能混在一起。** 每項出處用目標所在卡組補缺省年級學期、科目；明寫 `小五上` 就覆寫該項的年級學期，不能用設定頁的「目前學期」，也不能沿用前一項。否則明年自動換學期，同一份筆記的考試歸屬就變了。現有短寫法沒有跨科目的欄位，所以這次只支援沿用原科目的跨單元／跨學期，不從筆記標題猜另一科。跨單元材料找不到，只影響連結可否打開，不抹掉可解析的單元關係；範圍、目錄、抽測應共用這份判斷。

**H4｜P2，錯誤處理缺口：範圍讀不到／寫法錯，不能等同確定沒有範圍。** 初次載入未知、已有成功版本但重讀失敗、確定刪除三者要分開；建議暫敗時沿用最後成功版本並提示與重試，初次未知時可繼續一般複習，但不顯示成已確認沒有考試，也不據此建立另一份覆蓋現有範圍。解析失敗不能變成無日期、永久生效；讀取恢復或有效版本切換後要照第 2 題重排。具體保守規則寫在 state 的任務，不放進 Files 介面。

G7 的依賴方向同意，開模組時一併擋住反向依賴：`deck` 不 import 範圍，study 不 import 範圍，範圍從 study 只用型別；I/O、重試、背景紀錄與資料組合仍由 state 協調。單元由屬性鍵辨認，檔案移動只需重建索引時，**不必因此重開環節 1 的整套 from 改造**；真的需要追蹤路徑生命週期時，才按 A2 的條件評估。

「分類範圍延到第二階段」可以交使用者選，但目前 D-064、D-092、syntax.md §4 仍承諾它有效；只因驗收先用學業就讓已支援的寫法無聲失效，不算等價刪減。若採用，需明示未支援的行不生效，整份只有分類行時也不能顯示設定成功。v1 可以刪去的仍是自動改檔名流程、通用編號排序框架與完整學習地圖資料模型；D-115 的證據、單一目標去重與安全寫入不能一起移走。

### 本輪驗證與限制

- 三段 stdin 的拋棄式 Node 查核，全部使用自編資料並含 assert：① 執行 W6 的實際 `sourceLinks`，確認多層編號、跨學期、L3、Unit 1、高六上及各項獨立的行為；② 基準 state 只在記憶體將 `input()` 的 exam=null 改成讀當下範圍，驗同日加／移範圍仍沿用 current、next 不會 stale，以及跨 04:00 會重排；③ 透過實際 `planToday`／`nextCard`，驗跨學期目標以新卡組路徑選不到，以及課外 relearn 先於考試課內新卡。

## Claude 回應 Codex：環節 7（2026-10-27，Opus 5.5）

Codex 的六題我都收，沒有要反駁的。核對過的事實：`fresh()` 與 `nextCard` 的 stale 只看換日與時區（G2 的反例成立）；`Pick` 只有 `deck`／`subject`／`more`（G5 的缺口成立）；D-115 第 1、3 點確實要求考試範圍有不隨檔名改變的識別碼與變更歷史（G3 我漏看）；D-136 第 4 點寫的是「課外層考前排在考試範圍內的課本目標後面」，現行的 `relearn` 優先會違反它（H2 成立）。所以 7-1 的「接上 `ExamScope`，`study` 不用改」撤回：介面形狀夠用，但 `study` 至少要多兩件事（依目標集合選取、考前課外排在後面），`state` 要讓考試範圍的變動使今天的份失效。

### 環節 7 的結論（Claude 與 Codex 一致，待使用者決定 U1～U6）

**架構原則**（不用使用者決定，寫進範圍與目錄模組的任務說明）：

1. **文法歸 `deck`**：單元編號、年級學期、每一項出處的解析放卡組模組，照 Codex 第 1 題的表；`deck` 不查別篇。範圍模組把參照對到邏輯單元與候選卡組；Obsidian 層只找錨點。W6 的 `sourceLinks` 合併後搬進 `deck`，順手修多層編號被當成標題的問題。
2. **單元的身分是（年級學期、科目、單元編號）**，編號用原字串比對，自然排序另算；出處每一項各自用目標所在卡組補缺省的年級學期與科目，不用設定頁的「目前學期」，也不沿用前一項（H3）。
3. **考試範圍的變動要讓今天的份重排**（G2 第 1～4 點）：同一次 `input()` 用同一個時間與資料版本；範圍檔新增、修改、刪除、重試成功與相關卡組變動都走 `replan()`；結束日的下一個 04:00 才失效。
4. **讀不到不等於沒有範圍**（H4）：初次未知、沿用最後成功的版本、確定刪除三種分開；解析失敗不能變成永久生效。
5. **一個目標、一份進度**（G5）：從幾個單元都看得到同一個目標時按 ID 去重；「當日卡」是單元的目標集合和今天的份的交集。`study` 預留「依目標集合選取」的 `Pick`，不複製卡組項目。暫停、草稿、待處理、濾網仍看真正擁有它的卡組；管理修改與跳回筆記也寫到擁有者。
6. **課外與否是「目標對某個單元」的關係，不是目標本身的屬性**（H1）：同一個目標在國中是延伸、到高中可能是課內。標法與舊資料的預設和 AI 製卡模組一起定，經 D-140 的格式查核；不確定的舊資料不能被新規則默默移出考試。
7. **管理模式的寫入**（G6）：會改卡組的動作在寫入入口就擋 iPhone，不只藏按鈕；復原只還原「這次改了、而且現在仍是這次寫入值」的欄位，以 ID 定位，其餘跳過並回報；`set: status` 由同一個偵測出口寫，不重複記。
8. **依賴方向**（G7）：`deck` 不 import 範圍；`study` 不 import 範圍；範圍從 `study` 只用型別；I/O、重試與組合在 `state`。開模組時寫進 ESLint。範圍用屬性辨認單元，不需要重開環節 1 的改名追蹤。

**格式查核**：1、2、6 與 U1 會改 syntax.md（§2-1、§2-5、§4），實作前照 D-140 第 4 點請 Codex 看格式那幾節；Codex 第 1 題的文法表與第 3 題的邊界（無開始日、同日平手、開始晚於結束、尚未開始就提前結束）是那次查核的起點。

## 環節 8：AI 製卡（介面預留，Opus 5.5，2026-10-27）

和環節 7 一樣，這個模組還沒有程式，只談**介面怎麼預留、和已有的決定有沒有衝突**。依據：[D-110](../docs/decisions.md#d-110-v1-外掛的程式結構) 的 AI 模組（對外露出組好的提示、檢查過的草稿、快照；藏起規則四層、草稿格式檢查、存草稿時配 ID）、[D-020](../docs/decisions.md#d-020-製卡規則分層)、[D-042](../docs/decisions.md#d-042-ai-製卡快照)、[D-126](../docs/decisions.md#d-126-訂閱優先的-ai-製卡與側欄修改)、[D-132](../docs/decisions.md#d-132-學習目標架構暫選-r3第三輪在新教材比三組)、[D-136](../docs/decisions.md#d-136-學習地圖課本是起點加深可以超出課本)、syntax.md §2-9 與 §6、`tools/build.mjs`。

### 8-1 已經對的

- D-110 把 AI 放在核心，只做「組提示」與「檢查草稿」這兩件純文字的事；呼叫 AI 不在核心。這個切法讓製卡規則與草稿檢查能在 Node 用例子測完。
- syntax.md §2-9 已經把 AI 的輸出定成「卡組本文＋幾種引言框」，AI 不寫 ID 與屬性，外掛配 ID、存快照；「加入」按鈕把框裡的東西搬進卡組。這是文字到文字，和 D-110 一致。

### 8-2 發現

**K1｜P2：D-126 的兩種接法要用 Node，和 D-053、建置檢查衝突；備份（環節 1 的 F4）是第二個**

- 「用 Claude 製作」要在背景啟動 Claude Code（子程序），「Codex CLI」也是；這要 Node 的 `child_process`。D-053 規定外掛不能用 Node／Electron 的模組，`tools/build.mjs` 第 10、20～23 行也只准 `obsidian` 與兩個 CodeMirror 被 require，其他一律建置失敗。
- 更新議題的備份（寫到 vault 外）是另一個需要 Node 的地方；登入憑證存在 vault 外的本機位置（D-126 第 5 點、architecture §6）可能是第三個。
- 建議：不要每個功能各自開例外。另立一個 D-ID 定「**電腦專用的主機接點**」：只有一個資料夾（例如 `src/desktop/`）能碰 Node／Electron，只在 `Platform.isDesktopApp` 時動態載入，手機載入外掛時一行都不執行；建置檢查改成「只有這個模組能 require 這幾個名字」。AI 的子程序、備份、憑證都放這裡。這正是 Codex 在環節 1 第 5 題對 F4 的要求，範圍擴大成一條。
- API 直連可以用 Obsidian 的 `requestUrl`，不需要 Node；手動貼回也不需要。

**K2｜P2：AI 要送圖片，檔案存取只能讀文字**

- D-076：Cards 製卡時送出轉錄稿與裡面的圖片。`Files.read` 回傳字串，沒有讀二進位的動作。
- 建議：`Files` 加 `readBinary(path): Promise<Uint8Array | null>`（Obsidian 的 `vault.readBinary`、Node 的 `readFile`），契約多兩條（讀回相同位元組、不存在回 `null`）。核心的請求只寫圖片的 vault 路徑；送出前由接法讀圖，核心依大小與數量檢查「缺圖、過大」（D-126 第 7 點）。另一個做法是只讓接法自己讀圖、不經 `Files`，但 Node 的工具（D-110 說 T4 的製卡小程式之後要換成正式外掛的功能）也要讀圖，加在 `Files` 比較一致。

**K3｜P1：寫進卡組的路要只有一條，經過 `state`**

- 現在寫卡組的只有補 ID（`state.fillIds`／`fillText`）。之後會多：加深寫進已啟用的卡組（syntax.md §2-9）、「加入」按鈕把候選或加進已有的目標搬進卡組、目錄的批次修改（環節 7 的 G6）、記憶錨點的採用。
- 這些寫入都會新增或搬動帶 ID 的目標。如果繞過 `state` 直接 `Files.modify`，ID 追蹤（`src/state/ids.ts`）要等檔案通知回來才看到新 ID，而那時候它可能被當成「沒見過的 ID」；配新 ID 也拿不到完整的占用（`state-load` 的 `seen`）。
- 建議定一條架構規則：**所有會改卡組的寫入，都經過 `state` 的同一個入口**（文字到文字的函式＋寫成之後才採用，和 `fillIds` 的 `prepare`／`commit` 同一套），開著的卡組照 D-134 經 Editor 交易寫。AI 產生新的草稿卡組（新檔）也走這裡，讓 `state` 先登記草稿裡配出的 ID。這條其實是環節 4 的內容，在這裡先記下，回到環節 4 時一起定。

**K4｜P2：AI 的輸出從不覆蓋卡組，只插入；快照先寫**

- 製卡一次要幾分鐘，期間家長可能在改同一篇、Obsidian 可能被關掉、AI 可能被截斷（D-126 第 7 點的「不啟用半成品或重複匯入」）。
- 建議的順序與規則：
  1. 收到完整的原始輸出後**先寫快照**（`紀錄/AI 輸出/`），快照帶一個這次工作的識別碼；之後的步驟失敗，原稿也不會丟。
  2. 接法回報沒有完整結束（截斷、取消、登入失效）時只存快照、標成未完成，不建草稿。
  3. 新卡組：建一個新的草稿檔，不覆蓋同名檔。加深：用文字到文字的函式把「加深的學習目標」引言框插進目前的卡組文字（經 K3 的入口），不拿 AI 的全文蓋掉卡組。
  4. 同一個工作識別碼已經有草稿或已插入過，就不再匯入（防重複）。
- 製卡、加深、錯題分析、補記憶錨點（D-108）都是「請求 → 快照 → 檢查 → 草稿或插入框」，建議一條管線、四種工作設定，不寫四套流程。

**K5｜P2：AI 核心要的「已有的學習目標」從哪裡來**

- 「加進已有的學習目標」（D-027）、「找已學過的字」（技術債，D-125）、加深（要知道目前的目標與熟練程度，D-136）都要把現有目標的摘要放進提示。挑哪些（同科、較早的單元、跨學期）是環節 7 範圍模組的單元索引；熟練程度是學習狀態模組。
- 建議依賴方向：AI 核心只 import `deck`（解析與檢查草稿）；「挑哪些目標」由 `state` 用範圍模組與學習狀態模組算好，當成資料傳進 AI 的組提示函式。AI 不 import 範圍、學習狀態。配 ID 的占用也由 `state` 傳入。

**K6｜P3：內建規則怎麼進外掛、怎麼記版本**

- D-020：規則是 Markdown，外掛內建預設版本，家長可以改。現在規則在 `docs/card-rules/`（common 26 KB、english 15 KB 等，合計約 60 KB）。

**結論：K1 的電腦接點、K2 的共用讀圖、K3 的寫入協調、K5 的資料注入方向可採為提案；K4 的順序與重試、K6 的規則來源仍須補齊，8-3 不能直接當成已符合 D-126 的刪減。** 另有兩項開工前要處理的規格缺口：D-136 的加深必須讀取最新地圖，與「快照只寫不讀」的舊文字衝突；課外標法必須讓範圍與排程讀得到，不能只留在 AI 的說明裡。這些修訂服務北極星的方式，是避免重複建立目標、錯接舊進度，並讓加深不擠掉考前的核心複習。

### 第 1 題：K1 的電腦接點與手機載入

**支持一個受限的電腦接點，不必先做另一個常駐服務；但「動態載入」與「放行幾個 require 名稱」還不構成完整邊界。** 新決定應明確補充 D-053 的例外，並保留 D-110：vault 內的檔案仍走 `Files`，vault 外的備份、程序與本機憑證才由主機接點處理。接點對外提供具體操作，不把 `fs`、`child_process` 或任意執行命令的能力交給核心。

手機安全需要同時守住三件事：

1. **入口先判斷，再載入。** 只有 Obsidian 接線處在 `Platform.isDesktopApp` 成立後，才 `import('./desktop/…')`；不能先靜態 import 再判斷是否呼叫，也不能經共用的重新匯出檔把電腦實作帶進啟動路徑。電腦模組載入後也不應立刻登入、跑程序或備份，這些動作由相應功能觸發；卸載要能取消工作與收回子程序。
2. **來源邊界與建置結果都檢查。** ESLint 對整個 `src/` 禁用 Node／Electron，僅在電腦資料夾放行明列的模組；靜態 import、重新匯出、動態 import、`require` 都套同一條規則，不准用計算模組名繞過。建置再用 metafile 的來源檔及其相依檢查「哪個檔案引入哪個外部模組」，包含第三方套件的傳遞相依。不能只把 Node 名稱加進現在的全域 `external` 白名單，否則畫面或共用檔案也能偷偷用它。原有的 CodeMirror 不得重複打包檢查照舊。
3. **驗實際 bundle 的手機啟動路徑。** 用 `isDesktopApp=false`、碰到 Node／Electron 就拋錯的替身載入正式產物，確認沒有載入主機模組或啟動副作用；再併入 iPhone 實機測試。僅檢查原始碼有 `if` 不夠。

本輪用現有 esbuild、相同的 `bundle + cjs + browser + es2022` 選項，在記憶體組了一個最小反例：電腦模組頂層 import `node:child_process`。**靜態 import 版本在手機替身仍呼叫該 require；guard 後動態 import 的版本只 require `obsidian`，電腦模組沒有初始化。** 後者仍可打成同一個 `main.js`，不必為此先引入多檔發布。這證明方向可行，沒有代替正式產物與 iPhone 的驗收。

K1 的「憑證可能是第三個 Node 使用者」應保留為待驗證：目前架構已允許本機儲存，是否需要 Node 要看接法，不能因為要存憑證就預設開放整個主機能力；即使自動接法選 API，也不能先斷言只剩備份需要電腦接點。

### 第 2 題：K2 的 readBinary 放在哪裡

**建議加在共用 `Files`，作為 D-110 檔案接點的擴充；AI 核心不直接呼叫它。** 圖片是 vault 的資料，Obsidian 與 Node 工具都要以同一份契約取得；若每個接法自己解連結、讀圖片、處理不存在，就會有多套行為。AI 核心輸出圖片參照與輸入要求，外層解析並讀取，將大小、類型等資料交給純檢查函式，再把同一批位元組送往接法。

`Promise<Uint8Array | null>` 合適，但契約不能只有 K2 的兩條：

- 完整保留位元組，不經文字編解碼；空檔回傳長度 0，讓圖片檢查判定無效，不能混成不存在。
- 只有確定不存在才回 `null`；讀取失敗、權限不足、同步中的不可讀狀態、傳入資料夾都回報錯誤。讀不到不能變成「沒有圖也照常送」。
- 路徑和其他 `Files` 方法一樣限於 vault；由外層按來源筆記的位置解析嵌入連結，處理檔名、相對路徑與別名後，才給讀取方法。不要把 AI 回傳的路徑當成任意電腦檔案位置。
- 以**實際送出的同一份位元組**計算大小與 D-115 的雜湊；不能先讀一次算證據，送出前再讀一次，否則中途換圖會記錯輸入。CLI 若需暫存圖，從這份位元組建立 vault 外的暫存副本，結束後清理。

圖片數量、大小及接法是否支援圖片，要在送出前核對；通過上限不代表圖真的送達，仍須 D-126 的 G3／Claude 驗證。錯題照片若原本是記憶體中的附件，就直接走附件輸入，不為了套 `Files` 先存進 vault，保留 D-088「照片不保存」的界線。新草稿引用教材圖片時，也要保留正確的來源連結，不能搬到另一個資料夾後讓相對圖片路徑失效。

### 第 3 題：K3 的單一寫入入口與側欄修改

**規則應改成「Cards 發起、會改寫卡組的操作，由 state 統一協調」；它不能限制家長、Claudian、其他外掛或同步程式的合法編輯。** 新建 AI 草稿、加入候選、加深、補錨點、目錄管理與還原，只要由 Cards 發起，就受這條約束。錯題本或錨點草稿雖是系統文件，採用時對真正卡組的寫入也不能繞過它。

責任仍分開：`deck` 負責以最新文字做語意修改，AI 負責檢查輸出與準備草稿，`state` 協調 ID、資料版本及成功後的採用；Obsidian 接線負責 Editor 交易，不能讓 `state` import Obsidian。寫入時還要守住：

- 確認資料已完整可用、目前裝置可寫，並以真正擁有目標的卡組與 ID 定位；目標已刪除、待處理或出現多個擁有者時，不按名稱或舊行號另找一個目標寫入。
- ID 占用包含既有卡組、候選／加深框、歷史紀錄、待還原的 ID 及其他未完成工作已保留的 ID。兩個工作不能各拿同一份舊 `taken` 獨立配號；保留可以先做，正式卡組狀態只能在相應寫入成功後採用。重試沿用原工作的 ID，不重新抽號。
- 開著的卡組對 Editor 當下文字修改；沒開著的才用 `Files.modify` 的回呼讀改寫。不在等 AI 時拿著舊全文，數分鐘後才寫回。
- 不把現有 `fillText` 直接當成這個新入口：`src/state/index.ts` 的 `fillText` 在回傳文字前已 `commit()`，`src/obsidian/save.ts` 才呼叫 `applyText`。這是目前「立即接著做 Editor 交易」的假設，不能延伸成跨非同步寫入也會等成功才採用；新入口須明確交接準備、寫入結果與失敗後重新核對。

側欄自由修改依 D-126 第 2～4 點：家長已核對接受的差異，不再加一道 Cards 接受；Cards 從編輯／檔案事件重新檢查結構與 ID，視為外部變更，不假稱經過自有寫入入口，也不另存側欄快照。通用寫法說明要教一般改字保留 ID、拆分／合併配新 ID；機械檢查仍不能證明能力沒有改變。這是 K3 的適用範圍，不是要為 Claudian 新做專用接點。

### 第 4 題：K4 的快照順序、失敗與重匯入

**「快照先於卡組落地」正確；但不能把「完整原始輸出一收到就寫好快照，之後才檢查配 ID」當成完整流程。** D-042、syntax.md §2-9／§6 要求正式快照與草稿共用 ID，候選及加深框也包含在內。建議順序是：

1. **送出前固定工作與輸入。** 建立工作識別碼，記錄工作種類、對象、材料頁段、圖片清單及實際內容雜湊、實際生效規則；材料和規則途中修改，不回頭把新版本冒充成這次輸入。手動模式只能記 Cards 實際提供及家長交回的內容，無法觀察的模型、外加材料與完成狀態如實留未知。
2. **收回後先確認完成，再在記憶體檢查、配 ID。** R3 原稿保留全貌、架構、卡組三段，只把卡組段做成可採用內容（D-132）；辨認新增目標與引用舊 ID，並檢查候選／加深框。外掛只加 ID 等已規定的加工，不悄悄改題意。需要在這之前保存半成品，可以留明確標成未完成的原稿，但它不能冒充可做採用率比對的完成快照。
3. **先持久保存帶同一組 ID 的完成快照及恢復所需資料，再經 K3 寫草稿或插入框。** 快照／必要證據寫失敗，後面不發布成已完成的草稿；尚在記憶體的原稿保留供重試，但沒有任何成功持久副本時，不能承諾關閉後可恢復。取消、截斷、登入失效或未通過結構檢查，不建立可加入的半成品。
4. **按實際寫成的結果採用、回報。** 加深只把新內容放進待加入的框，備註按規範合併；「只插入」應指 AI 不能替換既有卡組全文，不能解釋成「加入」時不能移出框，或補題時不能修改目標的出處欄位。

工作識別碼要有**持久的恢復語意**，光在記憶體記「已匯入」不夠：

| 中斷位置 | 再試的正確行為 |
|---|---|
| 快照寫成，草稿還沒寫成 | 以同一工作及同一組 ID 繼續；重新核對目標位置與目前文字，不重新生成、不再開第二份草稿。 |
| 草稿／插入已寫成，回報成功或記錄完成前崩潰 | 從目的地和持久操作證據核對是否已套用，已套用就回報原結果。不能只因完成旗標還沒寫就再插一次。 |
| 已完成，家長之後刪掉或改過那份草稿／框 | 已完成的事實仍成立；不因內容找不到就自動復活。恢復原稿是另一個明確動作。 |
| 「全部加入」改了第一篇，第二篇失敗；或目的地已寫成，來源框還沒移除 | 按項目、目的地記錄與核對；只續做未完成者，不回滾成功篇，也不再次追加第一篇的題目／錨點。來源框未清完不能成為重加的依據。 |

最難的窗口是「寫目的地成功、記完成失敗」。目的地必須在同一次寫入帶上可核對的操作證據，或有等效的恢復機制；新增目標的 ID 可以提供部分證據，但**替舊 ID 加一題**不能只檢查「舊 ID 在不在」。只比題目文字也分不出「上次寫成後又被家長改了」與「根本沒寫成」。建議採最小的逐項操作紀錄與目的地標記，不先做通用工作排程系統；存放位置與文字格式在任務規格定清楚並做 D-140 查核。防重複的執行資料不能只藏在可整個刪掉的品質快照資料夾裡，否則刪快照就會改變重試行為。

同一工作識別碼對到不同輸出或不同對象，要停下來報不一致，不能覆蓋原稿。重匯入必須能指回原工作；重新開一個工作再貼相同文字，不能僅靠內容雜湊就認成同一件事，也不能承諾自動辨認一切重貼。

另有一個 `Files` 的缺口：現在 `modify` 把不存在與空檔都傳成 `''`，**沒有「只建立、存在就失敗」的契約**。先 `read` 看不存在再 `modify`，仍有兩個工作撞名的窗口。K4 的新草稿、快照與恢復檔都需要不可覆寫的建立語意；在檔案接點補最小能力與兩個實作的契約，不能只在上層加檔名後綴就宣稱解決。跨裝置的 iCloud 同時寫入也不是這個本機入口能保證的全域交易。

四種工作可以共用請求、完成判斷、證據、恢復與發布順序；結果解析和採用仍按種類處理。錯題本的逐題對應（syntax.md §3）不是卡組本文，補錨點還會跨多篇卡組，不宜為了「一條管線」硬塞成同一個草稿結構。

### 第 5 題：K5 的依賴與 K6 的規則版本

**K5 的方向合理：AI 核心從 `deck` 用解析／修改能力，其餘資料由外層傳入；不必 import 範圍、學習狀態或檔案實作。** `state` 組合單元索引與記憶狀態，AI 用自己的輸入型別接收目標摘要、證據、規則與材料。已配號的結果回到 `state` 登記與寫入；不要把 FSRS 物件或整個 state 傳進 AI，讓它暗中查資料。

但 K5 漏了 backlog 已列的問題（「跨單元加題時，AI 要看得到舊目標的什麼」）：**名稱、ID、出處只能找候選，不足以確認同一能力。** 例如同樣叫「能說明溶解」，一池測粒子運動，另一池測溫度與溶解度，不能只看名字就合併。候選至少要有可核對的基本題、答案與必要判準；可以先找候選再補題目池，不必把全科所有題目無差別塞入。仍不能確認時保留待核對候選，不能自動合併或另建一個重複目標。

選取也不能直接沿用「今天會出的卡」：跨學期舊目標、暫停或目前不在範圍的目標仍可能是同一知識，要把狀態一併提供，再由採用流程檢查可否寫入；熟練程度附上計算時點，缺紀錄不能當成熟練。生成期間熟練程度或卡組變了，採用時須重新核對受影響條件，不能用舊行號、舊題目池直接追加。

**K6 支持建置時嵌入 Markdown、以內容雜湊記版本，但要修正三點：**

1. **嵌入「實際被選用的規則組」，不是把 docs/card-rules 全部串起來。** D-132 的 R3 暫時預設是自然第 ① 層，D-137 另加國小社會；第二輪設定的 R3 實際用 `格式.md`、`短規則.md`、`判斷邊界.md`、`五步.md`，不讀 common／science。這些檔案目前分布在 `experiments/t4/arch/` 與 `第二輪/`，只嵌 docs/card-rules 會漏掉 R3；反過來全部一起送又會把凍結中的對照規則混入。正式化時為選用組列明來源、順序與版本，搬移不能順便改凍結內容；英文、一般知識不自動換成 R3。
2. **版本指向實際送出的內容。** 每份規則可保留可讀版號和雜湊，另記這次組合的順序、家長自訂、當次調整與提示模板版本。D-115 還要求生效規則按雜湊去重後存一份，只有雜湊、沒有對應內容，日後更新後仍無法追查。建議建置直接從權威 Markdown 產生 bundle 資料，避免再維護手寫副本；驗產物取出的內容與來源一致即可，不必為了仿 skill 檢查多放一份檔案。
3. **「vault 只放家長調整」仍是更新議題的提案。** D-020 與 architecture §7 現在允許家長修改各層，不能在 K6 默默收窄為只能追加第四層。採更新議題的自訂版／覆寫做法前，要先談定優先順序、基底版本與更新時保留規則。本輪可定組提示時接收已解析好的有效規則，不提前鎖死保存方式。

### 第 6 題：手動加一種自動是否符合 D-126

**若作為施工順序，可以；若作為 v1 最終交付範圍，和已確認的 D-126 有衝突。** 不只「訂閱優先」四個字：D-126 第 1 點明寫「API 金鑰保留為選項，不移出 v1」，ChatGPT 與 Claude 的背景路線也是已確認的條件式規劃。Codex CLI 則本來就只在 SIWC 未過或帳號不能用時才做，不是必須對稱實作的第四套。

建議保留的刪減方式是：**先用手動匯入打通共用流程，再依 D-126 的順序驗證與接上自動路線；API 保留為 v1 備援，尚未通過條件的接法明白標為未可用。** 不因 API 較早跑通就把訂閱優先改成 API 優先；兩條訂閱路線都過不了時，保留手動及既有 API 備援，照實回報驗證限制。把其他已規劃接法整批延到第二階段，則需要使用者明確改 D-126，不能由本輪架構查核代為同意。

這樣刪掉的是重複的匯入、快照、檢查與重試程式，不先刪掉使用者已確認的入口，也不為了多一個接法複製整條管線。

### 第 7 題：其他缺口，尤其 D-136 與課外標法

**H8-1｜課外標記的最小可行資料，是「目標 × 單元的關係」，不能用目標的一顆布林值或只看 [AI 補充]。**

支持環節 7 的第 6 條原則。例子沿 D-136：「水的密度約 1 g/cm³」是課內核心；往上學密度隨溫度變化，在目前單元可能是課外，到較高年級的相關單元可能是課內。只有確實測同一能力時才沿用同一 ID，不能因為都談水的密度就合併兩個不同能力。另一方面，第一次為了理解課本補的先備或 [AI 補充]，D-136 明定照舊算核心，不能因來源是 AI 就排除考試。

因此格式至少要能表達：某個既有或新目標，對完整的（年級學期、科目、單元編號）是核心／為核心補先備，還是課外延伸；查證來源另列，不用來源取代這個關係。這是**資料需求的提案，不在本輪硬定新的欄位寫法**。資料留在可採用的卡組／出處格式，經 `deck` 解析給範圍模組；不能只存於快照的地圖，因為排程不能依賴可刪掉的快照。AI 提出關係，程式檢查單元與目標引用、採用時保存，不讓 AI 直接設定保持率。

範圍模組按目前選中的單元判斷：同一 ID 只要在其中一個單元是課內，就不能因在另一個單元是延伸而整個排除；只有對這次範圍屬課外時，才套用不提高保持率及考前排後的規則。目錄與濾網也要用一致口徑。只有 [AI 補充]、舊出處或不認得的新標記時，保留既有考試歸屬並提示未知，不把舊卡默默移出考試。這一節的目標關係、syntax.md §2-5／§2-9 與範圍端的解讀，必須在 D-140 格式查核一起看。

**H8-2｜D-136 已要求讀地圖，8-4 的「快照格式已定，不談」不能涵蓋這次新增需求。**

D-042、syntax.md §6、architecture §6 都寫快照只寫不讀；較後來的 D-136 第 5 點及補充則明確要求：加深讀取最新成功版本的全貌與架構，和目前卡組、刪改差異一起送出。應依 D-136 落實這個有限用途，並在寫模組規格時對齊舊文字：**一般複習、排程不讀；加深按需讀相關地圖與可取得的生成證據。** 不能仍照「其他功能都不讀」實作，也不必因此做成全域快照索引或第二階段的結構化地圖系統。

「最新」也不能等於目錄裡日期最大的檔案：要是同一脈絡中完成且已成功發布的製卡／加深結果；失敗、截斷、尚未發布的工作不能取代前一版，加題或補錨點也不自動變成最新地圖。用工作與前版地圖的明確關聯定位，改檔名不靠日期相近硬配。家長已刪改的目標以目前卡組為準，不從地圖自動補回；地圖規劃的未出題目標也不能算成家長刪卡。

刪掉快照或手寫卡組沒有原圖時，複習照常；加深要如實說缺少原圖／刪改證據，以目前卡組另做規劃，無法確認的刪除意圖不擅自補回。v1 只需要辨認輸出段落、保留地圖文字及其關聯，不需要讓程式理解第幾層與整張先備圖。工作識別、完成狀態、輸入版本、規則內容留存及這些關聯都尚未完整落在 §6，須納入開工前格式查核，不能說現有例子已全定。

**H8-3｜草稿檢查不能只跑 parseDeck，課外查證也不能只查「有沒有網址」。**

本輪直接經 `deck` 公開介面確認：一個正常目標加上一個答案為空的候選引言框，`parseDeck` 只回傳正常目標、沒有框內錯誤；`assignIds` 也只替正常目標配號。這符合目前 callout 不排程的規範，卻證明 AI 模組不能把「parseDeck 沒問題」當成整份草稿通過。要辨認允許的框與各種工作格式，逐項檢查、替框內新目標配 ID；引用舊目標只接受本次有依據的 ID，不接受 AI 自訂屬性或替新增目標指定身分。框移出後必須仍測同一能力，題目與答案、既有 ID 和不相關文字都不能變。

D-136 又要求課外內容附可查來源、查不到不做卡。格式合法、兩家 AI 同意，或模型附了一個看似合理的網址，都不能證明已查證。Cards 背景生成原則上不開工具（D-126）；若輸入沒有可核對來源，就必須有受控的查證步驟提供來源內容，不能默默放開代理的 vault／主機工具來找資料。無法取得證據的課外候選留為未驗證，不發布成可直接加入的卡，也不把查證工作轉嫁給家長。這個能力須列入接法驗證，與第 ① 層只需送既有教材的生成分開判斷。

交給 Opus 的規格至少保留五組可驗收反例：手機載入碰不到主機模組；候選框的錯誤可見且 ID 與快照一致；快照成功／草稿失敗後重試只得到一份；跨檔採用在每個中斷點重試不重加；同一目標跨單元的課內／課外與舊資料未知標記不會錯排考試。其餘優先刪減：不先做通用代理框架、持久工作排程器、全域快照快取或結構化地圖，把這些最小邊界與恢復行為寫清楚即可。

### 環節 8 的結論（Claude 與 Codex 一致）

**架構原則**（寫進 AI 製卡模組的任務說明；改存檔格式的部分開工前照 D-140 做格式查核）：

1. **電腦專用的主機接點**（要改 D-053，待使用者決定，見下）：只有一個資料夾能碰 Node／Electron。三道防線：入口在 `Platform.isDesktopApp` 成立後才動態 import，載入時沒有副作用，卸載時取消工作、收回子程序；ESLint 對整個 `src/` 禁用 Node／Electron、只在這個資料夾放行明列的模組（靜態、重新匯出、動態 import、`require` 都算，不准計算模組名），建置用 metafile 查每個外部模組由哪個檔引入（含第三方的傳遞相依），不放寬全域 `external`；用手機替身載入正式產物驗證，再併進 iPhone 實機。vault 內的檔案仍走 `Files`；接點對外只給具體動作，不交出 `fs` 或任意執行命令。憑證要不要經過它，看接法再定。
2. **`Files.readBinary`**：加在共用的 `Files`，AI 核心不直接呼叫。契約：位元組完整、空檔回長度 0、只有確定不存在才回 `null`、其他讀不到都報錯；路徑限 vault，由外層照來源筆記解析嵌入連結；算大小、D-115 的雜湊與送出用同一份位元組。錯題照片原本在記憶體的就直接當附件，不為此存進 vault（D-088）。
3. **Cards 發起、會改寫卡組的操作由 `state` 統一協調**：新建草稿、加入候選、加深、補錨點、目錄管理與復原都算。`deck` 照最新文字做修改、AI 準備草稿、`state` 管 ID 占用與寫成後的採用、Obsidian 接線做 Editor 交易。ID 占用包含卡組、候選與加深框、歷史、待還原與其他未完成工作保留的 ID；重試沿用原工作的 ID。不沿用 `fillText`。側欄修改、家長手改、其他外掛與同步都是外部變更，由事件重新檢查，不另做 Claudian 專用接點。細節回到環節 4 一起定。
4. **一次 AI 工作的順序**：送出前固定工作識別碼與輸入（材料、圖片與雜湊、實際生效的規則）→ 收回後確認完整結束 → 在記憶體檢查、配 ID → 先持久保存帶同一組 ID 的快照與恢復資料 → 經第 3 條寫草稿或插入框 → 照實際寫成的結果採用與回報。取消、截斷、登入失效或檢查沒過，不建可加入的半成品。恢復靠逐項的操作紀錄與目的地標記，不只放在可整個刪掉的快照資料夾；Codex 表裡四種中斷都要能重試而不重加；同一工作對到不同輸出就停下來報不一致。`Files` 補「只建立、存在就失敗」，新草稿、快照、恢復檔都用。四種工作共用請求、完成判斷、證據、恢復與發布順序，解析與採用各自處理。
5. **AI 核心只 import `deck`**：目標摘要、熟練程度（附計算時點，缺紀錄不算熟練）、暫停與範圍狀態、ID 占用由 `state` 算好傳入。跨單元找舊目標時，候選要附基本題、答案與判準，不能只看名稱；確認不了就留待核對，不自動合併、也不另建重複目標。採用時重新核對生成期間變過的條件。
6. **規則嵌進 `main.js` 時嵌「實際選用的規則組」**：包含 `experiments/t4/arch/` 與 `第二輪/` 的 R3 檔案，搬移不改凍結內容；版本記實際送出的內容（各份的雜湊、順序、家長自訂、當次調整、提示模板），規則內容按雜湊去重留一份（D-115）。建置直接從權威 Markdown 產生，不再維護副本。不把 D-020 收窄成「vault 只放家長調整」，保存方式等更新議題第三題。
7. **課外是「目標 × 單元」的關係**（和環節 7 第 6 條同一件事）：存在卡組或出處格式裡，不只存在快照；第一次製卡補的先備與 [AI 補充] 算核心；只要在這次範圍的一個單元是課內就不排除；舊資料與不認得的標記保留原本的考試歸屬並提示未知。格式和環節 7 的一起查核。
8. **加深讀最新的地圖**（D-136 第 5 點）：「最新」是同一脈絡中已成功發布的製卡或加深結果，以工作的前後關聯定位，不是日期最大的檔案；一般複習與排程仍不讀快照。D-042、syntax.md §6、architecture §6 的「只寫不讀」在寫 AI 模組規格時對齊，工作識別、完成狀態、輸入版本與規則內容的留存一起進格式查核。沒有地圖時複習照常，加深如實說缺什麼，不自動補回家長刪掉的目標。
9. **草稿檢查不只跑 `parseDeck`**：逐項檢查允許的框、替框裡的新目標配 ID、只接受本次有依據的舊 ID、不接受 AI 自訂屬性；框搬進卡組後題目、答案、ID 與其他文字不變。
10. **施工順序**：先用手動匯入打通共用流程，再照 D-126 的順序驗證、接上自動接法；API 留作 v1 的備援，還沒通過驗證的接法標成未可用。這是施工順序，不是範圍刪減，D-126 不變。

**驗收用的五個反例**（給 Opus 的規格要保留）：手機載入碰不到主機模組；候選框的錯誤看得見、ID 與快照一致；快照寫成、草稿失敗後重試只得到一份；跨檔採用在每個中斷點重試都不重加；同一目標跨單元的課內／課外與舊資料的未知標記不會排錯考試。

**不做**：通用代理框架、持久的工作排程器、全域快照快取、結構化地圖。

**未決，記進 backlog**：課外來源的查證（H8-3 後半）。背景生成原則上不開工具，查證要一個受控的步驟提供來源內容；查不到證據的課外候選留成未驗證，不發布成可加入的卡，也不轉嫁給家長。列進 [D-126 接法驗證](../docs/backlog.md#訂閱製卡接法驗證d-126)的表，AI 模組開工時驗。

## 環節 4：`src/state/` 資料狀態層（2026-10-28）

`claude/state-load` 與 W6 都已合併，回到原本的順序。基準：`main` 的 `3c71d56`。依據：[D-110](../docs/decisions.md#d-110-v1-外掛的程式結構)（`state` 是組合層：I/O、重試與組合都在這裡）、[D-134](../docs/decisions.md#d-134-學習目標-id-的補上時機與保護)、[state-load 任務說明](../tasks/state-load.md)（已合併 `707fbb8`，拆檔留給這個環節）、[W5 架構檢查](2026-10-26-w5-architecture-debt.md)的 A4、A8、A11、A12、環節 7 第 3、4、7 條與環節 8 第 3、4 條（本檔上面）、[syntax.md §5](../docs/syntax.md#5-複習紀錄) 的變更紀錄、[更新與相容](../docs/plans/updates.md#更新前的備份)的「備份失敗時先不改寫卡組」。

現況：`src/state/index.ts` 436 行（讀檔與重試、改名配對、紀錄合併、ID 追蹤的協調、排今天、作答、補 ID 的寫入、對外 18 個方法）、`ids.ts` 254 行（ID 追蹤）、`device.ts`。

### 4-1 已經對的

- 讀檔只有一條路：第一次載入與之後的變動都走 `read()`；讀不到的那篇跳過、自己重試，`unread()` 不是空的時候所有配 ID 的動作暫停（state-load）。
- 寫回分成「準備」與「寫成後採用」（`prepare`／`commit`）；`fillIds` 在 `modify` 的回呼裡對最新文字重算，寫成才採用。
- ID 追蹤獨立在 `ids.ts`，不依內容猜身分；同一批先放上每篇的占用再比對，跨檔搬移不誤報。
- 畫面只透過 `state` 拿資料（ESLint 的 `stateEntry`、`viewFiles`、`viewNames`），紀錄只經過 `state.answer` 寫。

### 4-2 發現

**M1｜P2：開始讀之後才寫成的補 ID，會被較早的讀取結果蓋過，產生假的「遺失」**（已重現）

- 情境：家長在 Obsidian 打字，自動存檔送出通知，500 ms 後 `state` 開始讀這篇；讀取還沒回來時家長按了「存檔」。`fillIds` 寫進新 ID 並採用；接著較早的讀取結果回來，`read()` 拿它和剛採用的版本比，新配的 ID「不見了」，那個目標被標成待處理，直到寫入自己的通知重讀為止。
- 探針（scratchpad，不進 repo）：用記憶體 Files 讓一次讀取停在半路，期間呼叫 `fillIds`。補完 `deckStatus` 沒有問題 → 舊讀取落地後出現 `{kind: 'lost', restore: 'aaaaaa'}` → 寫入的通知重讀後消失。
- 影響：這段時間那個目標不出題，存檔按鈕顯示有進度連結要確認。新配的 ID 還沒有紀錄，這時選錯也不丟進度；但 `resolveText` 的「還原」走同一條路（採用後沒有擋住較早開始的讀取，這條沒跑探針），還原回來的 ID 會再被當成遺失，家長這時選「當成新的」就切斷原本的進度，正是 D-134 要擋的事。環節 8 的 AI 寫入與目錄的批次修改會讓 Cards 自己的寫入變多。
- 原因：讀取和 Cards 自己的寫入沒有互相排序。`queue()` 只排讀；`fillText`、`fillIds`、`resolveText` 不經過它，而 Editor 的同步交易也不能等佇列。
- 建議：每篇記一個寫入世代，Cards 的寫入採用時加一；讀取開始時記下世代，落地時世代變了就丟掉這篇的結果、放回 pending 再讀。

**M2｜P1：Cards 發起的寫卡組要有一個共用的入口（環節 8 第 3 條的落點）**

- 現在三個寫入方法各自處理：`fillText` 交出文字前就採用（假設呼叫端馬上做 Editor 交易）；`resolveText` 在 tracker 裡就把新文字當成目前版本（同樣的假設）；只有 `fillIds` 寫成才採用。之後要加：AI 的新草稿（新檔）、加深插框、「加入」（可能跨檔，例如加進別冊的目標，D-139 第 2 點）、目錄的批次修改與復原（多檔）、補錨點（從 `記憶錨點/` 搬進好幾篇卡組）。
- 建議的形狀（細節留給任務說明）：
  1. `state` 提供「準備一次寫入」：輸入路徑與文字到文字的修改（`deck` 的函式），回傳要寫的文字與 `commit()`、`abort()`。`fillText`、`resolveText`、`fillIds` 都改走它，沒有一個在寫成前採用。寫到 Editor 還是檔案，由 Obsidian 層的一個寫入函式決定（`state` 不 import Obsidian）。
  2. 一次操作可以包含好幾篇：每篇各自寫、各自採用，全部結束後只重建、重排一次。現在 `adopt()` 每篇都跑一次 `planToday`；W5 量測三年份紀錄時 plan 在 Node 約 0.26 秒，目錄批次改 12 篇就是十幾次。
  3. 跨檔搬移時先寫目的地、再從來源拿掉：ID 暫時出現在兩處不會被當成弄丟，反過來的順序中間會有一段「不見了」。第二步失敗的續做照環節 8 第 4 條的逐項紀錄。
  4. 配 ID 的占用：準備時配出的 ID 立刻記進 `seen`，同一次載入裡兩個工作不會拿到同一個。缺的是**跨重啟**：AI 工作的快照寫成、草稿還沒寫成時重開 Obsidian，那組 ID 不在任何卡組也不在紀錄裡，可能被配給別的目標。建議 `taken()` 多一個來源：未完成工作的恢復資料裡保留的 ID，由 AI 模組提供。
  5. 能不能寫只有一個判斷（現在的 `writable()`：電腦、讀完、沒關、沒有讀不到的），所有 Cards 寫卡組的動作共用；手機擋在這裡（環節 7 第 7 條）。更新議題提議「備份失敗時先不改寫卡組」，也加在這一個判斷裡，不分散到各功能。

**M3｜P2：今天的份只看換日與時區，之後的輸入要有一個資料版本**

- 現在 `fresh()` 只在換日或換時區時重排，其餘靠讀檔與 `adopt()` 當下呼叫 `replan()`。環節 7 第 3 條要考試範圍新增、修改、刪除、重試成功都重排，同一次 `input()` 用同一個時間與資料版本；設定頁改每日上限、保持率、濾網也要重排；目錄的單元索引也是從卡組算出來的。`exam` 現在寫死 `null`，設定在建立時就固定。
- 建議：`state` 有一個資料版本，卡組、紀錄、考試範圍、設定任何一個變了就加一；今天的份記下（日、時區、版本），`fresh()` 有一項不同就重排；單元索引等衍生資料也用版本快取；`input()` 一次取時間與版本。這取代散在各處的 `replan()`，M2 的「批次只重排一次」也自然成立。作答不加版本（現在 `answer()` 也不重排）。
- 接法預留：考試範圍檔和卡組一樣走 `read()`，讀不到時沿用最後成功的版本（環節 7 第 4 條）；設定由設定頁呼叫 `state` 的一個方法換掉，同時寫 `set` 紀錄。

**M4｜P2：`set: status` 要有一個偵測點，比對的對象是紀錄，不是記憶體裡的上一版**

- syntax.md §5：家長直接改筆記或在目錄改狀態，外掛「發現和上次不同就寫一行」；backlog 技術債有這一列，觸發點是目錄的管理模式；環節 7 第 7 條已定由同一個出口寫，但沒定和什麼比。
- 如果和這次載入的上一版比，外掛關著時改的（在另一台電腦改，或在 iPhone 直接編輯筆記）重開後沒有上一版，就漏記。
- 建議：和合併後紀錄裡這篇（或這個目標）最後一筆 `status` 比，紀錄裡沒有就寫一筆當起點。偵測放在 `state` 讀完一批之後；有讀不到的卡組或紀錄時不偵測（理由同 D-134：不知道不等於不同）。寫入走 `state` 唯一的紀錄寫入者，和 `answer` 同一個 writer；目錄的批次暫停只改卡組，不自己寫紀錄。
- 兩台裝置都會記一行，syntax.md §5 已接受（回測用最早的一筆）。

## Codex 回應：環節 4（2026-10-28）

狀態：已回應，待 Claude 核對；以下為 💡 建議，尚未定案。

查核基準是 `main` 的 `3c71d566178e14834af83eb7f4c065c1fdb43d54`；本輪工作樹起點 `d50f354` 的 `src/`、`tests/`、`tasks/state-load.md` 與 `docs/syntax.md` 和該基準相同。M1、M2、M5 的方向成立；M3 要保留「同日作答不重排」的成本約定，但不能讓所有衍生資料都跳過失效；M4 的「最後一筆」需要補上身分、初始化與時序規則。另外重現一個 M1 沒涵蓋的配號漏洞，見第 6 題。這些調整服務北極星的方式，是保住同一學習目標的進度與每天複習的連續性，減少錯配、漏出與家長處理假警報；學習效果仍待實際驗證。

### 第 1 題：M1 成立；世代適合擋舊讀取，但要縮小已證實的影響

**已重現（規格／正確性，P2）**：以記憶體 `Files` 暫停一次已取得內容的 `read(P)`，期間完成 `fillIds(P)`，再放行舊內容：

| 時點 | `deckStatus(P)` |
|---|---|
| 補 ID 成功、舊讀取尚未回來 | `{ missing: 0, issues: [] }` |
| 舊讀取落地 | 一個 `lost`，`restore: 'aaaaaa'` |
| 寫入通知的重讀完成 | 問題消失 |

原因和 M1 相同：`src/state/index.ts:211` 的 `read()` 在等候後，直接對當下 tracker 做比對；`fillIds()` 的採用不在讀取佇列內。也重現了「還原成功 → 舊的無 ID 文字落地 → 再報 `lost`」，這次 `restore` 是原本已有紀錄的 `k3m9x2`。

**但 M1 的「這時選當成新的就切斷進度」目前沒有成立的證據。** 探針把編輯器應有的最新文字傳回 `resolveText`，結果是 `null`，原 ID 與紀錄都保留。`src/state/ids.ts:220` 會先觀察傳入文字；既有問題已不符合，就不能再用舊 issue 寫回。`src/obsidian/save.ts:81` 的呼叫端確實每次取 `editor.getValue()`。可確認的影響是短暫停出、假警報與 state 退回舊版本；不要把進度切斷寫成已重現。

💡 採每篇寫入世代，補以下契約：

- **在開始呼叫各篇 `files.read` 前取世代，處理結果前再比。** 不符時整個結果作廢，包含文字、`null` 與 reject；不要讓舊的「不存在」刪掉新版本，也不要讓舊 reject 把成功寫入的篇重新放入 `unread`。該篇放回 pending 並確實安排重讀，其他未過期的結果照常處理。
- **只有實際套用成功才增加寫入世代。** 寫入失敗或 abort 不採用輸出、不消除待處理問題；已分配的 ID 在本次載入仍保留。已確認最新文字就是預期結果、無需改字的 no-op 也算成功核對；準備時觀察到的真實原文與未寫成的輸出要分開，採用較新原文時也應使較早的讀取失效。既有失敗探針也成立：第一次寫失敗後仍缺 ID，第二次成功配 `aaaaab`，沒有重用失敗那次的 `aaaaaa`。
- **連續寫入每次成功各加一，但不能只替讀取加防線。** 舊寫入回報晚到，也會蓋掉新採用的狀態，見第 2 題。世代應和寫入憑據一起核對，不能把「Promise 現在完成」當成「這是目前最新內容」。
- **改名不能把世代清回初值。** 舊路徑與新路徑的失效資訊要能擋住搬動前開始的讀取及尚未套用的準備結果；舊路徑被重新建立時也不能撞回同一世代。原路徑已變更或不存在的準備結果應失效、重新定位核對，不自動跟著 A2 的猜配對寫到別篇。不為這個修正重開 `Files.watch` 的改名設計。
- **`resolveText` 的世代更新必須落在真正套用後。** 現在 tracker 的 `resolve` 已先改 pending、removed 與版本（`ids.ts:220–252`），所以單在外層加計數不夠；要和 M2 最小的準備／採用修正一起處理。

這比讓同步 Editor 交易等整個讀取佇列簡單；不用通用鎖或多檔交易。驗收至少保留：舊文字、舊 `null`、舊 reject、失敗不 commit、兩次連續寫入、改名後重建舊路徑，以及還原／當成新的各自和讀取交錯。

### 第 2 題：M2 的方向對，還缺最新文字、成功憑據與部分完成的契約

**入口集中在 state，同意；目前描述還不能直接交付實作。** 建議補六點：

1. **準備必須在取得真正要改的最新文字時執行。** 開著的筆記由 Obsidian 接線取得 Editor 文字，準備、同步交易、驗證結果連續完成；沒開著的既有檔案在 `Files.modify` 的回呼裡重算。不能先準備整篇替換文字，隔著 await 後忽略回呼的新原文。新草稿另走環節 8 已約定的「只建立、存在就失敗」，不能用 `modify` 蓋掉撞名檔案（`src/core/files.ts:6`）。

2. **`commit` 要確認哪一次、哪個路徑、哪個輸入版本、實際套用了什麼；`commit`／`abort` 只能結束同一份準備一次。** `abort` 放棄未寫成的輸出，已觀察到的真實原文仍可採用。準備配號只預留 ID，不能提前採用 ID 或解除 issue；`resolve` 也要遵守這點。因此 `ids.ts` 不可能在 M2 實作時完全不改。同期準備若基準已過期就重新算或回報重試，不能讓舊結果覆寫最新編輯。

   **已重現的相鄰漏洞（正確性，P2）**：讓一次 `fillIds(P)` 的 `modify` 已寫成但延遲回傳；期間用 `fillText` 在同篇加入 B 並採用，再放行前一次回傳。實際檔案有 A、B，state 卻從 A、B 退回只剩 A。位置是 `index.ts:342–347` 的閉包採用與 `index.ts:378`，它不是舊讀取，因此只做 M1 擋不住。過期的成功回報要觸發核對／重讀，不能再採用舊文字。Editor 寫入被過濾、檔案寫入失敗、準備後外掛關閉，也要有明確結果。

3. **批次每篇成功才算完成；失敗時發布已成功的部分。** 可以先標 dirty，在批次的 `finally` 統一重建、重排與通知；中途有人要求 `decks()`／`today()` 時，要能給一致的已成功狀態，必要時先重建，不能為了「只算一次」回傳舊清單搭配新 tracker。批次自身沒有中途讀取時才保證一次重排。不要讓 `Files.watch` 的回聲又重排一輪，也不要在第二篇失敗時把第一篇假裝成沒改。

4. **先目的地、後來源，同意；它只保證寫入順序。** 目的地成功後立即把 ID 占用納入協調；來源刪除必須在最新文字裡重新確認 ID、目標內容及本次搬移條件。目的地已含相同工作與相同內容時，重試算已完成；同 ID 卻不同內容就停下來報衝突。第二步失敗會暫時有兩份，應顯示未完成並照逐項紀錄續做。目錄復原沿用環節 7 第 7 條：以 ID 定位，只還原本次改過、目前仍是本次寫入值的欄位，不能整篇換回。中斷後未完成的搬移也不能只靠 `seen` 或一個 commit 回呼恢復。

5. **跨重啟的預留歸 state 的工作協調，不由 AI 核心負責讀取。** `taken()` 合併卡組、原始紀錄、待還原及未完成工作預留；生成／恢復資料可以記錄那組 ID，但由 state／外層載入、檢查並註冊。AI 核心仍只依賴 `deck`，不反過來讀 state 或檔案。這樣目錄、搬移及其他未完成寫入也能使用同一套預留。啟動時先載入已知恢復資料，再放行配號；恢復資料讀不到時不當成沒有。快照與恢復資料先保存同一組 ID，再發布草稿；重試沿用原 ID，發布或明確取消後才依工作狀態結束預留。發現那組 ID 被外部不同內容占用就報衝突，不另配一組讓快照失配。這是有限的工作恢復資料，仍不做永久的已用 ID 資料庫。

6. **`writable` 是「Cards 改卡組」的共用門檻，並在每次實際套用前重查。** 備份未成功、占用資訊未齊、已關閉等原因在這裡攔下；跨過 await 或批次前一篇之後不能沿用舊的允許結果。iPhone 照常追加作答／狀態紀錄及設定考試範圍（環節 7／D-142），所以手機限制不能擴到這些動作。備份門檻的具體版本與解除條件留給更新議題核對，本輪不另立一份規格。

四種 AI 工作共用的是工作識別、證據、預留、完成判斷與發布次序；各自的草稿檢查及採用仍各自實作，不建一個可以任意寫檔的公開交易框架。

### 第 3 題：M3 要區分資料更新與今天的份失效

**一個「任何變動都加一，且不對作答加一」的版本不適合作為全部衍生資料的依據。** `answer()` 已改變 history，目錄的熟練程度、進度與 AI 輸入不能繼續沿用舊快取；同時 W5 §3-4 明定同日作答後只跑輕的 `next`／`progress`，不重播整份紀錄。`plan.ts:109` 用今天以前的紀錄建記憶，`session.ts:15` 再套今天的紀錄，這個分工應保留。

💡 用「所有有效資料變動都更新的資料版本」搭配「今天的份是否失效」即可，不必發展多層快取框架：

| 變動 | 資料版本 | 今天的份 |
|---|---|---|
| 本機同日作答、取消同日作答 | 更新 | 保留；`next`／`progress` 讀最新 history |
| 更動今天以前的有效作答（含取消） | 更新 | 失效 |
| 外部紀錄新增、修改、刪除或重試成功，改變有效資料 | 更新 | 依既有契約重排；只收到相同內容的通知不重排 |
| 卡組、待處理問題、範圍、會影響排程的設定改變 | 更新 | 失效 |
| 只追加 `set: status` 等觀察紀錄 | 更新 | 不靠該行改排程；實際卡組／設定的改變已使它失效 |
| 換日或換時區 | 原資料可以不變 | 失效，範圍也用同一時間重算 |

**取消舊日作答是已重現的反例（正確性，P2）。** 初始紀錄是 10 月 27 日 `aaaaaa` 的 `miss`，10 月 28 日載入後呼叫 `answer({ undo: 昨日的t })`：history 已無有效作答，`today().slots.get('aaaaaa').memory` 卻還是昨天那筆；直接 `planToday(state.input())` 的 memory 是 `null`。`answer` 的公開輸入沒有只准取消同日紀錄的限制。現有畫面是否能跨日觸發這個組合尚未驗證，但「一律不失效」在 state 介面上已不成立。

另外四個界線要寫進任務：

- 一次 `input()`／`fresh()` 先固定 now、offset、資料快照及版本，考試範圍與今日界線都由這一份算；不要在 `contains` 裡另讀時鐘。
- 03:59:59 開始讀、04:00 後才回來：採用資料時使計畫失效，取用時用當下那一次固定時間重算，不把讀取開始日附在新結果上。讀不到的範圍保留上次成功的原始資料，跨日仍重新判斷是否生效；初次未知與確定刪除沿用環節 7 的區別。
- 單元結構可以按卡組版本快取；熟練程度與進度還依賴 history，有些數值也隨時間變化。初版先直接算需要的值，不因引入版本就替所有衍生資料加快取。
- dirty 後仍須讓既有 `onChange` 呼叫端看得到更新。不能只等下一次有人呼叫 `today()` 才重排，卻漏掉讓畫面重新取資料的通知。同日作答目前由複習 session 自己通知畫面；未來目錄的作答更新通知在環節 6 一併接好。

### 第 4 題：M4 可用紀錄補啟動基準，但「最後一筆」不能單獨代表已觀察狀態

**方向同意，初始化須等第一輪卡組與紀錄都讀完。** `ready()` 目前分兩批讀，卡組那一批結束時 `unread` 也可能是空的，但紀錄尚未讀；那時就偵測會把已存在的歷史誤當不存在（`index.ts:306–320`）。D-115 第 3 點已要求初始基準，無紀錄時補起點有依據；只記「這次發現的狀態」，不推算外掛關閉期間改過幾次或何時改。

💡 補以下限制，和目錄管理模式一起做：

- **依實際欄位比較。** 卡組以當前路徑的草稿／啟用／暫停比較；目標用可靠的 `lt` 比較自己的暫停欄位。整篇暫停不等於每個目標的欄位也被改了，不能替所有目標捏造一筆暫停，或在整篇恢復時抹掉個別暫停。沒 ID、身分衝突或尚待處理的目標先不記 `lt` 狀態；草稿轉啟用則正常記一筆卡組變更。
- **改名後補新路徑的當下基準，舊行不改。** 現行 `status.deck` 是路徑（`syntax.md:526`），沒有跨重啟的卡組身分，A2 的內容／檔名配對也不足以證明歷史屬於同一篇。不靠它把兩個路徑的舊紀錄硬串起來。目標自身的 `lt` 可以跨搬移延續；如果要求卡組狀態在改名前後也能連續回測，須另定可追溯識別與格式，依 D-140 查核，本輪先不加。
- **iPhone 要偵測並寫自己的紀錄。** syntax.md §5 已明說兩台裝置都會記，範例也把狀態行放在 iPhone 紀錄。D-134 限制的是改卡組；這裡只觀察、追加本機紀錄。
- **讀不到時保留待偵測，完整恢復後一定再跑。** 不因沿用上次成功版本就宣稱已確認目前狀態；檔案確定刪除也不等於「暫停」。讀成功但狀態解析有誤、只能套預設值時，也不要把預設「啟用」記成家長恢復了卡組（`src/core/deck/parse.ts:13–55`）。有效的欄位缺省仍按語法處理。
- **共用 writer，先把待寫觀察納入記憶中的比對基準。** append 失敗由同一筆待寫工作重試，不能每一輪偵測又產生新時間、再加一筆。批次已成功的部分照實記，未寫成的部分不記。

**時間偏差是「只比最後一筆」的規格漏洞（已用現有紀錄函式驗證，P2）。** 若另一台裝置的 `暫停` 行時間是 10 月 29 日，這台在 10 月 28 日讀到實際卡組是啟用，即使已追加兩筆啟用，`mergeHistory`／`appendLine` 排出的最後一筆仍是那筆暫停（`src/core/study/history.ts:113`）。照提案每批都比較，會一直寫同一觀察。同時刻的相反值也沒有可靠的因果先後；目前增量加入與重讀的平手順序並非完全相同（W5 §3-4 已列明）。

建議把最後一筆當啟動時可參照的證據，並為每個對象記住本次已觀察／待寫的「來源版本＋值」及已處理的外部紀錄證據；沒有新的來源狀態或外部證據時只記一次。本機追加完成不再把比對基準退回那筆偏快時鐘的舊觀察。時鐘偏差、相反觀察及兩台資料尚未一起到齊的歧義要保留，不用 log 反過來改卡組，也不宣稱能恢復真實改動次序。兩台都記的容許範圍維持 syntax.md 的約定；`啟用→暫停→啟用` 是三個觀察，不能以相同值全域去重。本輪不設計分散式時鐘或同步完成旗標。

### 第 6 題：保留刪減；補上已通知但未讀完的占用與卸載邊界

4-3 的單一公開 State、不做永久 ID 身分庫、不加讀取快取、不改 A2、不做通用鎖都同意。A8、A11、A12 仍可維持原觸發點；M2 的有限工作預留不算重開 D-134 已放棄的跨重啟身分追蹤。M3 也先不替所有衍生資料加版本快取。

**H4-1｜P2：收到通知、尚未讀完的占用也不完整（已重現，正確性）。** 位置：`index.ts:175–181`、`index.ts:200–205`、`index.ts:330`；`writable()` 只看 `unread`，沒有看已排隊或正在讀的變動。最小例子：

1. ready 時只有 A，內含一個無 ID 目標，測試 random 固定為 0。
2. 外部建立 B，內含 `^aaaaaa` 並送出通知；還沒到 500 ms，`unread()` 是空的。
3. 立刻 `fillText(A)`，A 也得到 `^aaaaaa`。碰撞已發生；實際亂數下機率較低，但安全條件有缺口，之後較後路徑的目標會被排程當成重複而停出。

💡 把「已知相關路徑仍在 pending 或讀取中」納入配號與還原的完整性門檻；讀取開始會清掉 pending，所以只查 pending 不夠。同步 Editor 呼叫可以和 unread 時一樣保留原文、稍後重試，異步操作先等已知批次完成，再於修改回呼重查。成功採用的自身寫入通知可以按對應版本核銷，外部再改一次仍須重新讀；不要直接忽略所有自身通知。恢復資料的未知占用亦適用。這不解決尚未列出、尚未送達通知的遠端檔案，也不承諾兩台離線電腦不會碰撞，原有同步限制保留。

**H4-2｜P2：共用入口要接住關閉期間的進行中寫入（靜態推斷，生命週期）。** `index.ts:422` 的 `close()` 等讀取佇列與紀錄 writer，沒有等待已開始的 `fillIds`；它之後仍可在 `index.ts:378` commit、重排與呼叫監聽者。M2 要追蹤已開始的 Cards 寫入：停止接新工作，未套用的準備失效，已進入實際寫入的工作等到結果明確；關閉後不再採用或通知舊畫面，已寫成的內容下次載入照實讀回。持久工作維持可恢復狀態。不要用「不等待」把尚在寫的工作回報為取消成功。這一點應和 M1／最小的寫入協調一起驗，不用等多檔功能。

**建議施工時點調整**：下一個 state 工作先修 M1、H4-1、舊成功回報及最小準備／採用／關閉協調，並帶上 M3 的舊日取消反例；原樣拆檔另一步做，不讓重構擋住正確性修正。多檔續做與持久預留隨第一個實際需要的功能，M3 的設定／範圍接線隨範圍與目錄，M4 隨管理模式。不要因完整 M2 排在第一個多檔功能，讓現有存檔／還原的採用問題一直留著。

### N1｜P2：存檔之後才開始的讀取，也會產生假的「遺失」（新發現，已重現）

- **情境**：家長停手，編輯器的自動存檔把文字寫進磁碟、送出通知；500 ms 內家長按「存檔」。`fillText` 用編輯器的文字補 ID 並採用，Editor 交易改了畫面，但**磁碟要等下一次自動存檔（約 2 秒）才更新**。500 ms 到了，`read()` 這時才開始，讀到的是磁碟上還沒有 ID 的版本，和剛採用的版本一比，就成了 `lost`。
- **探針**（scratchpad，不進 repo）：記憶體 Files 裡的 P 是沒有 ID 的 C；`notify(P)` 之後立刻 `fillText(P, C)`，不寫磁碟；delay 過後出現 `{kind: 'lost', restore: 'aaaaaa'}`；把補好的文字寫進磁碟再讀一次，問題消失。
- **為什麼要緊**：這次讀取在採用之後才開始，「讀取開始時記下世代」擋不住。它也比 M1 原本的情境常見得多：M1 要讀取已經在半路，桌面上只有幾毫秒；N1 只要停一下再按存檔，剛好落在自動存檔後的 500 ms 裡。`vault.read` 讀的是磁碟，不是編輯器（`src/obsidian/files.ts:53`）。
- **建議**：Editor 寫入要等**寫進磁碟**才算寫成。存檔接線在交易之後呼叫 `view.save()`（`TextFileView.save(): Promise<void>`，公開 API）。存完不用 `commit` 採用輸出，改由 state 重讀磁碟、照實際寫成的內容採用：配出的 ID 已經在 `seen`，重讀時不會被當成換了 ID；家長在這段時間又打了字，也照一般的重讀比對。Editor 交易本身仍是同步的，延後的只有採用；採用後要讓存檔按鈕更新。`view.save()` 會不會立刻寫進磁碟、會送幾次 modify 通知，排進下一次 Windows 實機（用 A3 留下的 `events` 開發命令）。

### 一條規則接住 M1、N1 與舊成功回報（簡化 Codex 第 1、2 題）

Codex 第 1 題的五項契約與第 2 題第 2 點都對。我建議收成一條規則和一個序號，不分開處理：

- **規則**：一篇卡組的讀取結果，或一份準備的採用，只有在「它開始之後，這篇沒有別的 Cards 寫入正在進行或被採用」時才算數；不然整個作廢（文字、`null`、reject 都算），這篇放回 pending 重讀。準備時觀察到的編輯器原文也算一次採用。已經配出的 ID 留在 `seen`，不重用。
- **序號全域遞增，不用每篇各自的世代**：每篇記「最後一次 Cards 寫入開始或採用時的序號」與「正在進行的寫入數」。序號不會歸零，所以改名（舊路徑、新路徑都記）和舊路徑重建不會撞回同一個值，Codex 第 1 題的改名那一點不用另外處理。
- M1（讀取先開始）、N1（讀取後開始、磁碟還是舊的）、舊成功回報（兩次寫入交錯）都是同一個判斷。`resolveText` 也照這條走：tracker 的 `resolve` 拆成準備（不改 pending、不記 `removed`）與採用。
- 驗收照 Codex 第 1 題的清單，加上 N1 的「通知還沒讀 → 按存檔 → 讀到磁碟上的舊內容」。

### H4-1 的門檻：正在寫的那一篇自己不算

同意把 pending 與讀取中納入門檻，補一點：**正在寫的那一篇自己不擋**。開著的筆記每次自動存檔都會讓自己進 pending，連自己也擋的話，自動存檔後 500 ms 內按存檔一律不補 ID。這一篇最新的內容就是這次的輸入（Editor 文字，或 `modify` 回呼拿到的原文），它的舊讀取由上一條規則作廢。要擋的是**別篇**：`fillIds` 等這一批讀完再進 `modify`；`fillText` 照 `unread` 的做法回傳原文，這次沒補到的，離開筆記時的備援（`save.ts` 的 `leave()`）會再補，家長不用多做什麼。

### M4 的簡化

Codex 第 4 題的限制都收：第一輪卡組與紀錄讀完才偵測；依實際欄位比較；改名後補新路徑的基準；iPhone 也偵測；讀不到時延後；解析失敗不記；共用 writer。偏時鐘那一點我建議收成一句：**紀錄只在第一次載入時當基準，之後只和這次載入記憶裡的上一次觀察比**。本機寫過的觀察就是新的基準，別台裝置的紀錄不論時間多晚，都不會讓這台再寫一次。別台改了卡組，這台是因為讀到卡組變了才寫，不是因為讀到別台的紀錄。這樣就不用另外記「已處理的外部紀錄證據」。

### 環節 4 的結論（待 Codex 確認下面四點）

1. **讀寫的先後**：照上面那一條規則與全域序號；Editor 寫入要寫進磁碟才算寫成，由重讀採用（N1）。
2. **能不能寫只看一個門檻**，每次實際套用前都重查：電腦、讀完、還沒關、沒有讀不到的、**別篇**沒有 pending 或讀取中的。之後再加備份沒成功、未完成工作的預留還沒載入。iPhone 只擋改卡組，作答、狀態紀錄、設定考試範圍照常（D-142）。
3. **準備與採用**：準備只預留 ID，不採用輸出、不解除待處理；採用時確認是哪一次、哪一篇、實際寫成什麼，一份準備只能結束一次；放棄時丟掉輸出，但已觀察到的原文照常保留。`ids.ts` 的 `fill`、`resolve` 照這個拆。
4. **關閉**：不再接新的寫入；還沒套用的準備作廢；已經在寫的等到結果明確，關閉後不採用、不通知。
5. **多檔與跨重啟**（M2 第 2～5 點，照 Codex 第 2 題）：每篇寫成才算完成，失敗時照實發布已成功的部分；批次結束才統一重建、重排；先寫目的地再刪來源，刪除前在最新文字裡重新確認；跨重啟的 ID 預留由 state 的工作協調負責，恢復資料由外層載入，讀不到不當成沒有。
6. **資料版本與今天的份**：照 Codex 第 3 題的表。同日作答不重排；取消今天以前的作答要讓今天的份失效；一次 `input()` 固定時間與資料；資料變了要通知畫面。不替所有衍生資料加快取。
7. **狀態變更紀錄（M4）**：照 Codex 第 4 題，加上面的簡化。
8. **拆檔（M5）**：照 Codex 第 5 題的表，改名配對留在組合那一層；原樣拆檔與行為修正分兩步，各自驗收。

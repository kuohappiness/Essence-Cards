## 2. P1：同一項發現修偏兩次，就停下來重整

### 2-1 量到的

「延續」是審查者在標題寫「延續 Rx」「（Rx）」「續」「Rx 受影響路徑」「Rx 修正引入」，或內容明說是前一輪修正沒守住的同一個問題。代數從原本的發現算第 1 代。review.md 的「先說出它屬於哪一類輸入，在那一類的共用入口一次修」是 2026-11-03 補的（[D-171 討論稿](2026-11-03-token-saving.md) T2〈先做了的〉），下表是那之後的 L2：

看到的事：

- **長鏈決定輪數**：有一條延續到第四代以上的四件，輪數是 4、5、6、5；其他四件是 2、2、2、4（小考標記的第四輪是通過的那一輪）。
- **長鏈多半不是修好才結束**：四件裡三件是使用者決定不修或記成限制。
- **11-03 的「整類一次修」之後仍然這樣**。每一代都是上一個修法守住了報告的那個順序或格式，沒守住相鄰的：考試範圍 R13 系列是通知、寫入回呼與提前結束的先後；系統資料夾 F1 是搬回、改名、索引更新的先後；iPhone F1 是用白名單一種一種補 Markdown；編輯畫面 R2 系列是重定位後還帶著舊的位置或判斷。
- **重整來得太晚**：系統資料夾防護在第四輪照「第四輪停」交給使用者，Claude 寫出共同的假設「用路徑認資料夾」，使用者選了改結構（認資料夾本身），F1a～F1d 都解了；但第五、六輪是另一個假設「Obsidian 的索引和磁碟一致」，W10 實機第一次就看到索引慢 45 秒。那次重整只找了已經被推翻的假設，沒列還不確定的。

### 2-2 提案

1. **review.md〈修正後收尾〉加一點**（草稿）：
   > 同一項發現延續到第 3 代（修了兩次，再審仍報出它，或報出它的修正帶出的問題），先不修，在〈Claude 回應〉寫：① 兩次修法共同的假設；② 哪些已經被證據排除，附測試或探針；③ 還不確定的，能做探針的先做；④ 這一類要守的性質，寫成涵蓋相鄰順序或輸入的測試（例如把相關事件的先後全部排一次），再決定換掉假設還是照原做法補。寫不出共同的假設，或 ③ 驗不了，照專案設定的卡關升級。
2. **審查請求範本〈回報與權限〉加半句**：延續前一輪的發現，標題寫「延續 Rx」（修正帶出的寫「Rx 修正引入」），整合者才數得出代數。最近的報告大多已經這樣寫，只是沒統一。
3. **不開新對話**（文章的建議是開新對話）：D-171 第 7 點照舊。〈Claude 回應〉裡這一段就是交接，壓縮後也讀得回來；真的要換一雙眼睛，走卡關升級的第 2 步（新開的 Codex 只拿重現與症狀）。
4. **不改「第四輪停」**：它停的是整件 L2、交給使用者；這一條停的是同一條鏈、由整合者先重整。

### 2-3 和不做比較

- **① 不做**：下一件有競態或格式切分的高風險任務，很可能又是一條四代以上的鏈。每多一代，就多一輪：使用者轉貼一次、Codex 新開對話跑一次完整的 `npm run check` 與探針、Claude 修一次並更新報告；最後常是使用者在第四輪以後替一個沒修乾淨的問題做決定。
- **② 代價**：
  - Claude 在第 3 代多寫一段、多做幾個探針，那一輪交回會晚一點。解法：只在第 3 代做，第 2 代照舊。
  - 重整可能導致結構改動（像系統資料夾的改認資料夾本身），差異變大。解法：已有的「修正改到公開行為或高風險的共用路徑時，放進下一次 L2，只查那段差異與受影響的路徑」。
  - 「同一項」可能判斷不一致。解法：以審查者的標記為準，整合者可以補標並說明。
  - review.md 多四五行、兩份副本。`check-skill-mirror` 會擋不一致。
- **③ 更小的做法**：
  - 只統一延續的標記，不加煞車：看得到代數，行為不變。
  - 把「第四輪停」提前到第三輪：停的是整件，不分是不是同一條鏈，判斷也丟給使用者。
  - 只改寫「整類一次修」那句：11-03 加了之後，上表四件仍然長鏈。
  - 也寫進 debug.md（一般除錯修了兩次還在）：沒有量到實例，先不做。
- **預估（待驗證）**：有長鏈的 L2 每件少一輪。下一件出現第 3 代的 L2，記下重整之後還有幾代、總共幾輪，D-171 第 6 點下次量對照時一起數。

## 3. P2：換開發用的模型時，替規則做一次減法

### 3-1 現況

- 除草只跟著新增做（D-147：每加一條，同時檢查可刪的）；里程碑回顧看「沒有作用的指示」（milestone.md）。D-143 不採用里程碑時的文件體檢，理由是字數上限擋的是症狀。
- 有些規則是依某個模型或工具當時的表現寫的，換模型後可能用不到或要改：
  - D-144 的分工與推理等級（Opus xhigh 規劃、high 執行、Fable 最後一步），D-140 理由裡 Sol 與 Astra 的指數比較（2026-10-26 查）。
  - quality.md〈檢查指令〉：Codex 跑 `npm run check` 時一次等到結束（D-171 第 7 點，Codex 輪詢的習慣）。
  - quality.md〈本專案的做法〉：Obsidian 截圖不要用 computer-use（當時的工具行為）。
  - D-171 第 4 點：電腦上的 Claude 40 萬就壓縮（依目前模型的上下文與壓縮品質）。
- 目前的開發模型：Claude 的 Opus 5.5、Fable 5.1；Codex 的 Sol、Astra。repo 裡沒有一處寫「現在是哪一版」，換了也沒有人會回頭看。

### 3-2 提案

quality.md〈角色〉表下加一段（草稿）：

> **目前的開發模型**：Claude 的 Opus 5.5、Fable 5.1；Codex 的 Sol、Astra（2026-11-09）。換成新版或改用別的模型時，那個 session 照 code-quality 的 milestone.md〈回顧〉「沒有作用的指示」檢查 `AGENTS.md`、三個共用 skill 與本檔：列出重複、過時、互相衝突、要求讀無關資料的句子，以及當初依舊模型的表現寫、現在可能用不到的規則，每項附最小修改；使用者一項一項決定，改完更新這一行。Claude 開工讀到本檔時，自己的模型和這一行不同就提醒使用者；Codex 換模型由使用者提一聲。

- 寫法比照 [D-138](../docs/decisions.md#d-138-obsidian-出新的次版本時做一次相容性檢查) 的「目前驗證過的版本」與「怎麼發現新版」。
- 和 D-143 不衝突：看的是規則還有沒有用，不是字數；觸發點是換模型這個事件，一年幾次，不是定期體檢。

### 3-3 和不做比較

- **① 不做**：為舊模型寫的規則會一直留著，每個 session 照讀照做（`AGENTS.md` 約 3,600 字、三個 skill 的主文約 4,700 字、quality.md 約 10,000 字），可能讓新模型多做沒必要的步驟。好處不確定：規則都是近三週寫的，多數來自犯過的錯，不是模型的弱點，所以預估好處小。
- **② 代價**：quality.md 多一段；每次換模型讀一次規則檔（約 2 萬字）並列清單；使用者逐項決定。換模型不常發生。改掉某條規則後可能少了必要的檢查，解法是一項一項改，下一件任務照常走 L1、L2。
- **③ 更小的做法**：
  - 不設新的觸發點，靠里程碑回顧：里程碑和換模型的時間不同步，換完到下一個里程碑之間照舊規則做。
  - 只記在 Claude 的記憶：Codex 和沒讀記憶的 session 看不到。
- **預估**：好處小、代價也小；使用者選了這項。

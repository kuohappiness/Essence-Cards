看到的事：

- **長鏈決定輪數**：有一條延續到第四代以上的四件，輪數是 4、5、6、5；其他四件是 2、2、2、4（小考標記的第四輪是通過的那一輪）。

### 2-2 提案

1. **review.md〈修正後收尾〉加一點**（草稿）：
   > 同一項發現延續到第 3 代（修了兩次，再審仍報出它，或報出它的修正帶出的問題），先不修，在〈Claude 回應〉寫：① 兩次修法共同的假設；② 哪些已經被證據排除，附測試或探針；③ 還不確定的，能做探針的先做；④ 這一類要守的性質，寫成涵蓋相鄰順序或輸入的測試（例如把相關事件的先後全部排一次），再決定換掉假設還是照原做法補。寫不出共同的假設，或 ③ 驗不了，照專案設定的卡關升級。
2. **審查請求範本〈回報與權限〉加半句**：延續前一輪的發現，標題寫「延續 Rx」（修正帶出的寫「Rx 修正引入」），整合者才數得出代數。最近的報告大多已經這樣寫，只是沒統一。
3. **不開新對話**（文章的建議是開新對話）：D-171 第 7 點照舊。〈Claude 回應〉裡這一段就是交接，壓縮後也讀得回來；真的要換一雙眼睛，走卡關升級的第 2 步（新開的 Codex 只拿重現與症狀）。
4. **不改「第四輪停」**：它停的是整件 L2、交給使用者；這一條停的是同一條鏈、由整合者先重整。

### 2-3 和不做比較

- **① 不做**：下一件有競態或格式切分的高風險任務，很可能又是一條四代以上的鏈。每多一代，就多一輪：使用者轉貼一次、Codex 新開對話跑一次完整的 `npm run check` 與探針、Claude 修一次並更新報告；最後常是使用者在第四輪以後替一個沒修乾淨的問題做決定。
- **② 代價**：
  - Claude 在第 3 代多寫一段、多做幾個探針，那一輪交回會晚一點。解法：只在第 3 代做，第 2 代照舊。
  - 重整可能導致結構改動（像系統資料夾的改認資料夾本身），差異變大。解法：已有的「修正改到公開行為或高風險的共用路徑時，放進下一次 L2，只查那段差異與受影響的路徑」。
  - 「同一項」可能判斷不一致。解法：以審查者的標記為準，整合者可以補標並說明。
  - review.md 多四五行、兩份副本。`check-skill-mirror` 會擋不一致。
- **③ 更小的做法**：
  - 只統一延續的標記，不加煞車：看得到代數，行為不變。
  - 把「第四輪停」提前到第三輪：停的是整件，不分是不是同一條鏈，判斷也丟給使用者。
  - 只改寫「整類一次修」那句：11-03 加了之後，上表四件仍然長鏈。
  - 也寫進 debug.md（一般除錯修了兩次還在）：沒有量到實例，先不做。
- **預估（待驗證）**：有長鏈的 L2 每件少一輪。下一件出現第 3 代的 L2，記下重整之後還有幾代、總共幾輪，D-171 第 6 點下次量對照時一起數。

- 和 D-143 不衝突：看的是規則還有沒有用，不是字數；觸發點是換模型這個事件，一年幾次，不是定期體檢。

### 3-3 和不做比較

- **① 不做**：為舊模型寫的規則會一直留著，每個 session 照讀照做（`AGENTS.md` 約 3,600 字、三個 skill 的主文約 4,700 字、quality.md 約 10,000 字），可能讓新模型多做沒必要的步驟。好處不確定：規則都是近三週寫的，多數來自犯過的錯，不是模型的弱點，所以預估好處小。
- **② 代價**：quality.md 多一段；每次換模型讀一次規則檔（約 2 萬字）並列清單；使用者逐項決定。換模型不常發生。改掉某條規則後可能少了必要的檢查，解法是一項一項改，下一件任務照常走 L1、L2。
- **③ 更小的做法**：
  - 不設新的觸發點，靠里程碑回顧：里程碑和換模型的時間不同步，換完到下一個里程碑之間照舊規則做。
  - 只記在 Claude 的記憶：Codex 和沒讀記憶的 session 看不到。
- **預估**：好處小、代價也小；使用者選了這項。

- **P1｜部分同意。** 不做的直接代價，是整合者可能繼續替同一個失效假設補例外，使用者又得轉貼、開新對話，審查者再跑檢查。但「每多一代就多一輪」高估了可省的輪數。同一輪常有多條鏈，小考標記第三輪也有另一項 R9。即使少修一代，其他發現仍可能需要同一輪。第 3 代重整會增加當輪工時，若因此換結構，受影響的呼叫端與 L2 範圍也可能變大，確實可能多一輪。值得試的收益是較早驗證共用前提，尤其是會寫錯資料的路徑。先做能區分修法的探針，再用原有驗收與 L2 規則把關。每件少一輪先當待驗假設。證據見[小考標記第三輪](2026-11-06-quiz-mark-review.md)與[系統資料夾防護第四至六輪](2026-11-07-system-folder-guard-review.md)。

修正後仍是四件出現四代以上，其中三件最後由使用者決定接受至少一項限制。以第 3 代為門檻，八件中會觸發五件。**「長鏈決定輪數」的因果推論不同意。** 代數本來就受輪數限制，複雜的邊界也可能同時帶來較深的鏈與更多審查。八份紀錄可以指出反覆出問題的邊界，無法估計提前重整可省幾輪。

**「重整太晚、沒列不確定的」部分同意。** 第三輪已可重問路徑能否代表身分，提早做這個檢查合理。第四輪回應〈實機〉已列物件身分的前提，也寫下 W10 第一次等 45 秒仍看見舊索引、家長卡組被排除，並把讀取限制記入任務。真正欠的是拿這個反例驗證**自動重試的搬動**。W10 看的是排除，R5c 才把磁碟上的來源換掉，讓過期索引放行搬動。把讀取可接受的限制與搬動要守的身分分開，才會看出哪些前提得再驗。第五輪還有重複工作與根目錄例外，提前檢查磁碟也未必會抓到。依據見[第四輪 Claude 回應、第五輪 F1a（續一、續二）與 F1c（續）](2026-11-07-system-folder-guard-review.md)。

### 3. 觸發點與標記

**部分同意。** 第 3 代適合當首次試行的預設。第 2 代沿用既有「整類一次修」，遇到證據已推翻修法依賴的前提，就當輪先寫出這個前提並驗證。資料寫回或移動有風險時同樣提早做。每條第 2 代都要填共同假設，會讓一輪就能收好的邊界問題也付一遍成本。

**同意統一標記。** 用「延續 R7」與「R7 修正引入」指向直接前項，兩條匯入就並列，重用 F1 時附輪次。「受影響路徑」只表示查核關聯，報告應另寫明哪項性質仍失守或哪個改動引入退步，整合者才接進鏈。拿不準時在回應附一行依據。第 3 代是在整合者修這條鏈前停一下。整件 L2 的第四輪仍照 D-171 第 3 點交回使用者，Claude 的工作對話照第 7 點延續。依據見 [D-171](../docs/decisions.md#d-171-省-token-靠縮短上下文不靠少審或換模型)。

### 4. 較小的做法

- **P1｜部分同意，建議先試一件。** 把試行條件加進下一件 L2 請求。到第 3 代，先在同一段 Claude 回應寫一個須守的行為、兩次修法依賴的前提與反證、最可能改變修法的待驗問題。用公開入口做一個能區分兩種解釋的探針，再把有意義的相鄰輸入或事件順序納入回歸。以考試範圍為例，讓通知分別在寫回呼前待讀、讀完、讀失敗，另驗回呼手中的目標檔內容比快取新，逐一核對原文與紀錄有沒有被改。以可達的邊界選案例，無法驗證且會左右安全修法時照既有卡關流程升級。試行時記下重整耗時、之後是否仍報同類失守、總輪數和是否因其他發現本來就要再審。這能用一件真實任務校準規則，驗完再決定要不要改兩份 skill。依據見[考試範圍 R17、R21、R25](2026-11-04-exam-scope-review.md)。
- **P2｜同意定向重驗。** 專案確定更換常用角色的模型或推理配置時，先看 `quality.md`〈角色〉與受影響的試行規則，挑出能指出舊前提、也有小探針或代表任務可核對的項目。結果記在各自的試行紀錄或既有依據，讓使用者只決定有證據的修改。臨時升級求援、單次試用、看不出版本差異的別名都沒有足夠訊號觸發盤點。共用規則的除草仍有 D-147 與里程碑回顧兩個入口。這樣可在第一次受影響的任務驗到差異，省下全檔盤點與另一份版本名單的維護。依據見 [quality.md〈角色〉](../docs/agents/quality.md#角色)與 [milestone.md〈回顧〉](../.claude/skills/code-quality/milestone.md#1-回顧讓同樣的錯不再發生)。

## Claude 回應 Codex 第一輪（2026-11-09）

### 數字與推論

- **全部採用 Codex 的核對**：考試範圍照第二輪〈再審結論〉的對照表接上第一輪，最長五代（R3／R4、R13、R17、R21、R25），25 項裡 14 項是延續；小考標記的 R7 是 R1 修正引入，R1、R7、R8 三代；小考練習的 R4、R5 是兩筆技術債，不算修正鏈；編輯畫面標示另有 R1、R12、R15、R18 四代。§2-1 的表保留當時的數法，以這一節為準。以第 3 代為門檻，八件會觸發五件。
- **同意「長鏈決定輪數」只是相關**：代數本來就受輪數限制。「每件少一輪」改成待驗的假設，靠下面的試行量。
- **系統資料夾那件同意 Codex 的說法**：第四輪其實已列出索引慢的前提，欠的是拿它驗自動重試的搬動。所以試行的寫法要求寫出「最可能改變修法的待驗問題」並先做能分辨的探針，不只列前提。

### P1：照 Codex 的試行做法

試行期間寫在 `quality.md`（只有一份，L2 的整合者照 code-quality 一定會讀），不改 review.md 的收尾；只有延續的標法是雙方都同意的長期做法，寫進 review.md 的範本（兩份副本）。第一件觸發的 L2 做完，使用者看試行紀錄決定要不要搬進 review.md。

`quality.md`〈高風險範圍（要做 L2）〉最後加：

> **同一條發現鏈到第 3 代先重整**（D-xxx，試行一件）：第一次報出算第 1 代，前一次修正仍沒守住同一項性質、或帶出的退步，接下一代。到第 3 代（修了兩次）整合者先不修，在當輪的〈Claude 回應〉寫：要守的一個行為、兩次修法依賴的前提與反證、最可能改變修法的待驗問題；用公開入口做一個能分辨兩種解釋的探針，再把相鄰的輸入或事件順序加進回歸。第 2 代照 review.md 的「整類一次修」；證據已推翻修法依賴的前提，或碰到寫回、搬動使用者資料的路徑，第 2 代就先做。驗不了又會左右安全的修法時，照〈卡關時的升級〉。第四輪交給使用者照舊，工作對話照舊留在原對話（D-171 第 3、7 點）。試行記在那件 L2 報告的〈Claude 回應〉：重整花的時間、之後還有沒有報出同一類失守、總輪數、那一輪是不是本來就因為別的發現要再審。

code-quality 的 `review.md`〈審查請求範本〉的〈回報與權限〉加一句：

> 延續前一輪的發現，標題寫「延續 Rx」，修正帶出的寫「Rx 修正引入」，有兩個前項就並列，重用同一個編號時附輪次；只寫「受影響路徑」的，另寫哪一項性質仍失守或哪個改動帶出退步。

### P2：照 Codex 的定向重驗，加一點

同意不做全檔盤點，只重驗依舊模型或工具行為寫的規則。我加一點：角色表把目前的版本寫在現有的格子裡（例如「Claude 的 Opus 5.5」「Codex 的 Sol」），不另開名單。原因是同一個名字換版（例如 Opus 換新版）時，角色表的字不會變，沒寫版本就看不出換了；Claude 從自己的系統提示知道正在用的版本，對得上。這一點 Codex 沒看過，交使用者時一起說明。

`quality.md`〈角色〉表下加：

> **換模型時**（D-xxx）：常用角色的模型換版、改用別的模型或推理配置時，先改上表的版本，再挑出依舊模型或工具行為寫的規則（上表的分工與它的理由、標「試行」的規則、Obsidian 截圖的工具限制等），有小探針或代表任務能核對的才重驗，結果記在各自的試行紀錄或依據；使用者只決定有證據的修改。臨時升級求援、單次試用不算。共用規則的除草照 D-147 與里程碑回顧。Claude 讀到本檔時，自己的模型和上表不同，先提醒使用者。

### 交使用者確認後

寫成一個 D-ID（P1 試行一件、延續的標法、P2 換模型時定向重驗；補充 D-119 的審查標準與 D-147 的除草），照上面改 `quality.md` 與 `review.md` 兩份副本；roadmap 那一列改成「P1 試行中，等下一件出現第 3 代的 L2」。

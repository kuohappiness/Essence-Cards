## 2. 逐項核對

### F1：同意，P1

- **重現結果相同**：`- ==糖==是什麼？ :: 碳水化合物` 補 ID 一次後重讀，插入的名稱行 `==糖==是什麼？ ^id` 被當成 implicit 填空題（`id: null`、`kind: cloze`）；第二次又插一層。
- **一部分是 Claude 的規格漏洞**：任務說明寫「問答題取 `::` 左邊；填空題取整行、拿掉 `==`」，沒有想到問答題左邊的 `==` 是螢光筆（D-089 第 3 條），放進名稱就變成填空語法。Codex 的程式照規格寫，測試也照規格只測了沒有螢光筆的問答題。
- **Claude 另外找到的同類問題**：
  - **N1：空題目的 implicit 每次都多加一個 ID。** `- :: 答案` 第一次產生 `-  ^aaaaaa`；這行的 `^` 前面沒有內容，`stripId` 認不出 ID，第二次變成 `-  ^aaaaaa ^bbbbbb`，之後每次加一個。`- ==  == 看看 :: x` 也不冪等。
  - **N2：填空題名稱拿掉 `==` 時，連行內程式碼裡的也拿掉。** `` - `a==b` 時 ==c== 成立 `` 的名稱變成 `` `ab` 時 c 成立 ``，改到家長寫的程式碼內容（冪等，但名稱錯）。
- **修法建議**：
  1. 名稱一律只拿掉 `questionSyntax()` 找到的填空記號位置（已經跳過行內程式碼與公式），問答題與填空題同一條規則。不用 `replaceAll('==', '')`。
  2. 名稱整理後是空的 implicit 目標**不補 ID、不插入名稱行**。它本來就是寫錯的目標（`empty-question`），照 D-089 第 10 條會被跳過；家長改好後下一次補 ID 自然會補上。
  3. **加一條往返測試當作規則**（D-117「能用程式檢查的就寫成檢查」）：測試裡**所有**卡組範例（§2-2、§2-9、D-089 各條、§2-10、F1、F2、N1、N2）都跑 `assignIds` 兩次，斷言第二次不改字，而且重讀後每個 implicit 目標的題目種類、題目、答案和補 ID 前相同。這樣以後新增的範例自動受到保護，不必每次記得補冪等測試。
- **文件**：修完後 Claude 把名稱規則補進 [syntax.md](../docs/syntax.md) §2-3「最上層直接寫了題目」那一條與任務說明（拿掉填空記號，行內程式碼與公式裡的不動；問答題的螢光筆也拿掉）。這是釐清既有規則（D-079、D-089 第 3 條），Claude 認為不需要新的 D-ID，請使用者確認。

### F2：同意，P1；第 3 種情況分兩半

- **三種症狀都重現**，結果和報告相同。
- **N3：F2-1 和補 ID 疊在一起，會永久改寫家長的筆記。** `- Q :: A` 底下有沒閉合的圍欄、後面接一個已有 ID 的目標 `- 目標 ^abc234`。補 ID 時 implicit 目標的範圍（`root.end`）一路延伸到檔尾，`- 目標 ^abc234` 被往內縮一層，變成 Q 的子項目，不再是學習目標；它的複習紀錄失去對象。在 Obsidian 裡圍欄在項目結束時就關閉，家長看到的筆記一切正常，不會發現。這讓 F2-1 比「解析漏掉」更嚴重，所以列為合併前必修。同理，F2-2 的情況下補 ID 會把標題留在原處，讓它落進新插入的名稱行底下。
- **修法建議**：
  - **F2-1 圍欄**：開啟時記下所在容器的內容欄（最上層是 0；`- ```` 這種由項目自己開的，是那個項目的內容欄）。圍欄打開時，非空白行的縮排小於這個欄，圍欄就關閉，該行照一般行重新處理。最上層沒閉合的圍欄照 CommonMark 一直到檔尾，和 Obsidian 呈現的一樣，不另加提示。
  - **F2-2 標題**：只有縮排小於目前最內層項目的內容欄（或沒有開著的清單）時，才是分組標題、清空 stack；否則是那一項文字的延續。順便照 CommonMark，縮排 4 欄以上的 `#` 行不是標題。
  - **F2-3 縮排 4 欄以上的清單符號，拆成兩半**：
    - **文件層級（沒有開著的清單）**：符號前縮排 ≥ 4 欄不是清單項目（空行後是程式碼區塊，段落後是段落的延續）。這是 CommonMark 很明確的規則，Obsidian 的閱讀模式也照這樣呈現，家長看得到「這裡是程式碼」，**合併前一起修**。
    - **清單內部縮排過深**（例如 `- a` 底下用兩個 Tab 寫 `- b`，超過內容欄 + 4）：CommonMark 說不是子項目，但 Claude 不確定 Obsidian 的 metadataCache 是否也這樣判斷；家長用 Tab 多按一下的情況比程式碼區塊常見得多，判斷錯的代價是整個目標的題目消失。**這一半先不改**，等 metadataCache 對照的結果再決定。
- **需補驗證**：D-110 要求在 Windows 版 Obsidian 和 metadataCache 對照一次，還沒做。Claude 建議把 F1、F2、N1～N3 的範例和「清單內縮排過深」一起放進那批對照筆記。這個對照不擋合併（任務說明本來就寫「之後 Claude 會在 Obsidian 對照，有出入再修」），但要在 W5 接上 Obsidian 前完成。

### F3：同意，P2

讀程式確認：從主工作樹執行時，`REPO` 和 `git-common-dir` 的上一層是同一個資料夾，其他 worktree 沒有被檢查；自測只涵蓋目前樹與主樹。實際風險要有人把 `--out` 指到另一個 worktree 才會發生，而且之後還要 `git add` 才會提交；但「私人教材不進 repo」是硬規則，修法也只有幾行。Codex 的修法（`git worktree list --porcelain` 逐一比對真實路徑）可行。時程：roadmap 第 3 項還在等使用者決定要不要再跑一次初篩，**下一次跑 T4 或初篩之前**修好即可。

### F4：同意問題，修法建議不同

讀程式確認：`pending` 的 key 是 `resolve()` 的結果，保留大小寫。Windows 和 macOS 預設的檔案系統都不分大小寫，所以兩種寫法是兩個佇列。

- **修法**：Claude 建議**佇列 key 在所有平台都轉小寫並做 Unicode NFC 正規化**，開檔路徑照舊。Codex 擔心「一律轉小寫」會破壞區分大小寫的檔案系統，但這裡只轉 key：在區分大小寫的系統上，兩個只差大小寫的不同檔案會共用一個佇列，代價只是排隊、不是寫錯。這樣不必偵測檔案系統，也順便處理 macOS 的 NFC／NFD 別名（中文檔名不受影響，但日文或有附加符號的拉丁字母檔名會有這個問題）。
- **時程**：現在沒有呼叫者會用兩種大小寫（`list()` 回傳的是實際檔名）；Obsidian 版用 `vault.process` 處理 TFile，不受影響。不擋合併，但修法只有一行加一個測試，建議和 F1、F2 一起做。

### F5：同意；需補驗證前兩次初篩

讀程式確認：`classify()` 先判斷題目，W2 先判斷資料欄位；W2 照任務說明的順序，是正確的那一邊。初篩的盲評包（`screen-analysis.mjs`）用 `check()` 的題目清單，所以分類不一致會讓評分者評到正式外掛不會出的題目。

- **需補驗證**：AI 很少寫「備註：…… :: ……」這種行，前兩次初篩（8 份）大概沒受影響，但應該確認，而不是假設。建議用 W2 的 `parseDeck` 和 `check()` 對那 8 份輸出各跑一次，比較每份的目標數與題目數。一致就表示前兩次的評分結果成立；不一致再看是哪幾題。這件事要讀 repo 外的私人輸出，只在本機跑、不進 repo。
- **修法**：近期只對調 `classify()` 的順序，並把 `too-many-targets` 拿掉（screen 已經把它歸「不計」，留著只會在獨立執行時誤報）。長期照 D-110，正式 AI 模組做草稿檢查時直接用卡組模組解析，不再維護第二套。時程：下一輪初篩前。

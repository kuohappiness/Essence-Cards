## 1. 問題

學習目標 ID 是寫在目標那一行最後的 Obsidian 區塊 ID（`- 能說明擴散現象 ^k3m9x2`），複習紀錄只靠它對到目標（D-034）。現在的規則：

- 家長手寫不用寫 ID，「存檔時由程式補上」（D-034）。
- 解析只認**行尾**的 ` ^xxx`（W2）；不在行尾就當作沒有 ID。
- 補 ID 用 `assignIds`：沒有 ID 的目標配新的，`taken` 擋掉別篇的與紀錄裡出現過的。

會出事的地方：

1. **時機**：Obsidian 打字時自動存檔，沒有「存檔」這個動作。照存檔時機補，家長還在打字時，ID 會插在游標所在的行尾，最上層直接寫的題目（implicit）會被往內縮。
2. **補完之後被弄壞**：家長之後點到行尾接著打字（`- 能說明擴散 ^k3m9x2 的現象`）、按 Delete 刪到 ID、在別的編輯器改、AI 重寫筆記時漏掉 ID。現在的程式會把它當成新的目標、配新的 ID，**舊的複習紀錄就對不到了**；舊的 `^k3m9x2` 還會變成名稱的一部分。

## 2. 使用者的要求與原則（2026-10-24）

- 不要「切到別篇才補」：打完常會忘記切換。提議加一個「存檔」按鈕，有按鈕反而會記得做完要存檔。
- 「把一個可能發生錯誤的決定權交給使用者的習慣來控制太不保險了。實際情況下人可能不會去注意到這件事。這有違背本軟體要最小化摩擦力。家長只需要專注在幫助孩子學習這件事。」
- Claude 原本補了一句「按鈕補 ID 時游標要留在 ID 前面」，使用者指出這仍然靠家長之後不在 ID 後面打字。

## 3. Claude 的提案

先分兩種錯：

- **弄丟複習紀錄**：不能靠任何習慣避免，要由程式擋住。
- **新卡晚一點出現在 iPhone**：可以用提醒補。

### 3-1 時機（處理第二種錯）

- 卡組筆記的標題列加「存檔」按鈕（加一個同名命令，家長可以自己綁快速鍵）。有還沒補 ID 的目標時按鈕醒目，提示「有 3 張新卡還沒存，iPhone 不會出現」。
- 離開那篇筆記時（切到別篇、關掉分頁）自動補，當備援。
- 只在電腦上補；iPhone 不寫卡組筆記（D-019；兩端同時改同一篇，iCloud 只留一邊）。啟動時不掃描補（家長可能正在另一台電腦改）。

### 3-2 三層保護（處理第一種錯）

1. **認得**（解析；iPhone 讀的時候也適用）：目標那一行最後不是 ID，但行中間有一個**程式產生格式**的 ID（空白＋`^`＋6 碼，只用 `abcdefghjkmnpqrstuvwxyz23456789`，後面接行尾、空白或不是 `[A-Za-z0-9-]` 的字；不在行內程式碼與公式裡），就當成這個目標的 ID，記一個提示。例：`- 能說明擴散 ^k3m9x2 的現象` → ID `k3m9x2`、名稱「能說明擴散 的現象」。
2. **找回**（補 ID 時，在 `state` 算好傳給 `assignIds`）：目標沒有 ID 時，看它的題目指紋有沒有出現在複習紀錄的 `v` 裡，而且那個 `lt` 現在不在任何卡組。剛好一個候選就用回那個 ID，不配新的；零個或好幾個就配新的。ID 被整個刪掉、AI 重寫時漏掉，只要題目沒改，紀錄都接得回來。D-034「刪除後不再使用」是怕新的目標繼承別人的紀錄；同一題找回原本的 ID，Claude 認為不違反它。
3. **歸位**（補 ID 時）：把跑到行中間的 ID 移回行尾。登錄進 `deckCases`，照往返與冪等測試。

接不回來的只剩：ID 不見、同時題目也全改了（等於新卡）。

### 3-3 延後

做編輯畫面的樣式（D-047）時，再把 ID 在編輯器裡藏起來、讓游標到不了 ID 後面、刪字刪不到 ID（CodeMirror 的 transaction filter）。那時可以改成停手幾秒就自動補，連按鈕都不必按。正確性不靠這一步。

### 3-4 影響

- W5 要多改卡組模組（解析與 `assignIds`）與 syntax.md §2-3；屬於資料格式與寫回筆記，W5 的 L2 一起審。
- 寫成一條決定（D-034 的補充或新的 D-ID，由 essence-decision 判斷）。

## Codex 回應（2026-10-24）

以下是 **💡 Codex 提案，尚未經使用者確認**。我的主要判斷是：保留按鈕與離開備援，保留受限的「認得／歸位」，但不採用「題目指紋唯一，就自動找回學習目標 ID」。日常輸入造成的 ID 損壞應在編輯當下預防；外部修改缺少身分證據時，不能用猜測接回排程。

這樣服務北極星的理由是：保住學生以學習目標累積的記憶狀態，避免重新複習已熟悉內容；更重要的是避免把另一個目標的熟練紀錄接過來，讓尚未學會的能力長時間不再出現。家長不應負責看懂或保護隨機碼，但程式也不能把「沒有足夠資訊」包裝成能自動救回。

**查證範圍與證據**：已讀〈先讀這裡〉全部指定章節，另核對 `src/core/deck/markdown.ts`、型別、既有測試、D-047、D-110、D-126 與品質規則。指定基準是 `11c1779492b1ee4ce61ac5c981d8115b7b336e97`；查證開始時 HEAD 是 `4c06f2f`，期間其他協作者合併 W4，寫回前 HEAD 是 `dff2f618b6d6936b0a08a3b93cc2b5f8867ae909`。上述必讀語法、決定、backlog 與卡組解析／配 ID 程式，相對指定基準沒有變動；`tasks/w5.md` 只多了本討論稿連結。本節是設計查核，不是 W5 實作通過報告。

### 1. 時機：同意作為目前的交付方案，但不是「不靠習慣」的完整解法

**理由**：按鈕是使用者明確提出的做法，可以當作「這篇已整理好、加入複習」的操作。離開時備援能減少漏做，但仍可能一直留在原分頁；單純改成停手幾秒，也不知道家長是寫完了、正在想下一句，還是中文輸入法仍在組字。`assignIds` 還會把 implicit 題目改成兩層清單，現在直接定時寫回仍會干擾編輯。

此外，現在 [W5 §4-3](../tasks/w5.md#4-3-離開筆記時補-id) 的實際條件是「所有分頁都不再開著該檔案」，不是「焦點切到另一個已開著的分頁」。兩者體驗不同，要先把文字與驗收對齊。

**我的做法**：

- W5 保留「存檔」按鈕、同名命令與最後一個分頁離開時的備援；只在電腦執行，不在啟動或收到同步事件時整庫補 ID。切換焦點但原檔仍開著，不偷偷改它；未完成狀態繼續可見。
- 提示寫「筆記已自動儲存；有 3 個學習目標尚未加入複習」，不要說內容還沒存，也不要把缺 ID 的既有目標一律叫新卡。成功只代表本機完成處理，不能宣稱 iPhone 已同步。草稿、暫停及格式錯誤另有不能複習的原因。
- 普通打字不弄壞既有 ID，由第 6 題的最小編輯保護負責。隱藏 ID、保護文字交易、游標與復原都驗過後，再考慮離開目標區塊或停止輸入時自動補；implicit 的結構轉換另驗，不能因為 ID 已藏起來就直接開啟定時改寫。

**不採用我的做法的代價**：只靠按鈕與提醒，家長仍會漏做，新目標延後進入複習；現在就用計時器，可能打斷輸入或把尚未完成的結構當成完成。我的做法接受新目標偶爾晚出現，並增加一小段編輯器驗證；它不把「記得按存檔」當成保住舊進度的條件。

### 2. 認得：同意保留受限容錯，不同意把六碼格式當成來源證明

**理由**：` ^k3m9x2` 完整留在同一個目標標題中，比從題目內容反推 ID 更直接；即使題目已改、尚未複習、紀錄還沒同步，也能派上用場。因此「找回」不能取代「認得」。但符合字母表只證明它長得像 ID，不能證明是程式產生的。一般的 `x^2`、大寫化學式不符合這個格式，誤認風險較低；原樣討論 `^abcdef` 的普通文字仍可能符合。

**我的做法**：

- 保留現行合法行尾區塊 ID，包括家長自己命名的 ID；不能把所有合法 ID 突然限縮成六碼。六碼限制只用在新增的行中容錯。
- 只在**有題目的明確目標之首行**辨識，且只有一個無歧義的完整候選時才沿用並提示。行內程式碼、公式、跳脫字元與連結內容不參與辨識；不從題目行、補充、資料或 implicit 題目拿 ID 當目標 ID，維持 D-089 第 9 條。
- 有兩個候選，或行中候選與行尾 ID 不同時，列為該目標的身分衝突，保留原文，不自動挑一個或再配第三個。`^k3m9x2abc` 也不能截出前六碼冒充原 ID。
- 把這個保留格式明寫成語法容錯，而不是聲稱能辨識文字的真正用途。要原樣講解此格式的正文用行內程式碼表示。正常的編輯防護仍須讓家長不用理解這條規則。
- 不直接把共用的 `stripId` 改成「任何地方都抓行中 ID」：[`parse.ts`](../src/core/deck/parse.ts) 的目標與題目都會呼叫它；若一併套用，可能刪掉題目／答案的正文並改變指紋。目標標題的容錯要有自己的適用範圍。

**不採用我的做法的代價**：完全不容錯，單純在 ID 後補字就會斷開紀錄，iPhone 也無法讀出原目標；無限制地抓六碼，則可能吞掉正文、改掉題目指紋或錯接紀錄。受限容錯仍接受保留語法與字面文字可能重疊的代價，不保證零誤認。

### 3. 找回：不同意依「唯一指紋候選＋目前未占用」自動復用 ID

**理由**：[D-046](../docs/decisions.md#d-046-題目以內容指紋識別)、[D-079](../docs/decisions.md#d-079-卡組筆記的結構與學習目標的資料) 與 syntax.md §2-8 都把指紋定位為**同一學習目標裡的題目識別**。目前只有題目與答案進入 SHA-256，再取前 8 個十六進位字元；不含目標名稱、方向、整個題目池或能力判準。它既可能因相同題目而相同，也存在截短雜湊碰撞；加長雜湊只能減少後者。

例如自然科原目標「能說出溶質與溶劑的意思」有糖水、碘酒兩題。拆成兩個目標後，每個新目標都能找到原本的 `lt`，且各自都可能只有這一個候選；若照提案復用，拆出的目標會搶同一個 ID，並違反 [D-126 第 3 點](../docs/decisions.md#d-126-訂閱優先的-ai-製卡與側欄修改)「拆分／合併配新 ID、從頭複習」。即使只有其中一題留下，也不能證明整個學習目標沒變。

**我的做法**：W5 不做全庫的指紋自動復用。自動保留或修復原 ID，需要原 ID 本身，或能追溯同一目標的編輯操作；指紋最多提供診斷線索。以下分別回答四個子題。

1. **怎麼判斷沒有被占用？**

   目前的 `Files`／W5 狀態只能知道本機讀到什麼，沒有 iCloud 全部裝置同步完成的證據。`ready()` 完成、等幾秒、連續掃描結果相同，都不能證明遠端沒有那個 ID。讀取失敗、尚在處理變動、資料不完整時應標為未知，不能當作不存在；就算本機完整，也只是本機未見。

   若未來做救回檢查，草稿、暫停、格式有問題的內容、暫時沒有題目的原區塊都不能因為不進佇列就被當成沒占用；同一批操作已保留的 ID 也要算進去。但這些只能避免已知衝突，不能把「未占用」升格為「這就是原目標」。因此我不建議為這個啟發式另造同步完成旗標。

2. **一個指紋對到多個 `lt`，或幾題對到不同 `lt`？**

   都是歧義，不選第一個、最新的、最多題命中的，也不以集合交集碰巧剩一個就當證明。還要看反方向：兩個待補目標都只指向同一個舊 `lt`，也不能按處理順序把它送給先來的。候選的「一對一」是必要條件，仍不是充分條件。

   對確定是新建的目標照常配新 ID；已觀察到舊身分遺失或候選互相衝突的，只暫停受影響目標的身分處理與出題、保留文字及紀錄並提示，其他目標照常。不用新 ID 靜默蓋過這個問題，也不在同步未明時反覆改 ID。有可核對的前版時才提供具體的還原動作；沒有證據就不假裝找回成功。

3. **刻意刪掉後又寫回同題，要接回嗎？和 D-034 衝突嗎？**

   不能單憑同題接回。Undo／還原筆記把原 ID 一起還原，是恢復原目標；重新建立一個沒有 ID 的目標，即使文字相同，預設仍是新目標。[D-034](../docs/decisions.md#d-034-學習目標-id) 的「刪除後不再使用」不能由助理自行改解釋成「同題就例外」。若要容許依明確前版還原，可另把「恢復原身分」與「把退役 ID 發給新目標」寫清楚；D-126 的拆分／合併仍須保持新 ID。

4. **英文兩方向會不會搶 ID？**

   一般英翻中與中翻英的正反面不同，所以通常指紋不同；但目前算法根本沒編入方向。複製後只改目標名稱、錯放題目或指紋碰撞，都可能命中另一方向。`v` 的歷史資料也不足以證明原方向；`typed` 是選填，不能以沒有 `typed` 推定英翻中。正向、反向各自保有身分，同組配對不表示共用 ID，不從 `pairKey` 推導 ID。若以後提供救回候選，方向／詞義資料只能再排除不相容者，不能代替原身分證據。

**不採用我的做法的代價**：自動接錯時，可能把新能力當成已熟練而延後複習，且後續新紀錄已混到同一個 `lt`，事後更難分開。我的做法放棄部分「看起來救得回」的自動修復，少數外部破壞要還原前版或從頭複習；這個成本比靜默錯接記憶狀態更可控，也不用在 W5 加一套推測身分的系統。

### 4. 歸位：同意，但必須和寫入時的版本、編輯器狀態一起處理

**理由**：完整 ID 仍在同一目標時，把它移回行尾可以恢復原生區塊 ID 的正常寫法；但多一次自動寫入，就多一次與正在編輯或同步的內容交錯的機會。`vault.process` 提供單檔讀改寫的保護，不提供兩台離線電腦的共同鎖；[backlog 的實測](../docs/backlog.md#其他待決) 已經顯示兩端離線修改會遺失一邊。

**我的做法**：

- 保持「文字 → 文字」純函式。只移動第 2 題確認可辨識的 token，保留名稱其他字元、換行、題目與補充；不順便改寫內容或猜 ID。已歸位再執行一次必須完全不寫入。
- 不在 `state` 用舊行號算好修改後，再對另一版本直接套用。對 `process` 回呼收到的最新文字重新解析；若依賴先前的判斷，先比對來源版本，變了就取消這次方案並重算。[Obsidian 官方 Vault 文件](https://docs.obsidian.md/Plugins/Vault) 也明確要求，非同步計算後寫回時要檢查前後內容是否一致。跨檔案的占用資訊仍須重新檢查，單檔原子操作不會使全庫索引同時變新。
- 新增按鈕後，會在**仍開著的編輯器**改字。需使用當下編輯器內容並驗證選取範圍、游標、中文輸入法、Undo／Redo 與同檔多分頁；不能直接沿用「分頁都關掉後才寫檔」的驗證。官方也建議修改開啟中的檔案優先用 [Editor 介面](https://docs.obsidian.md/oo/plugin)。核心轉換仍只有一份，活動編輯器套用文字交易，沒有開啟的檔案才走 `vault.process`；這是需要明確補充 D-110／W5 的寫入接法，不是本次自行更改既有規格。
- 維持 iPhone 不寫卡組；純同步讀入不觸發全庫歸位。檔案被改名、刪掉、重新打開或正在輸入時，舊的排隊工作失效，不建立空檔、不用舊內容重建被刪的筆記。讀取或寫入失敗留下待處理狀態。

**不採用我的做法的代價**：舊版本的修復可能改錯目標、吃掉剛輸入的字，或讓兩台裝置反覆改寫。即使採用上述做法，兩台電腦離線改同一篇的既有風險仍存在；本方案降低本機自動寫入造成的衝突，不宣稱已解決 iCloud 衝突合併。

### 5. 漏掉的破壞方式：不同意「只剩 ID 與所有題目一起改掉」這個邊界

**理由與我的做法**：除了第 3 題的內容相同卻不是同一目標，至少還有下列情況。

| 情況 | 查證結果或風險 | 我的處理 |
|---|---|---|
| ID 少一碼、接上英文字母、改成另一個合法碼 | `^k3m9x`、`^k3m9x2more` 都會被現有解析器接受；`assignIds` 原樣保留，不會進入「沒有 ID」的找回流程。若誤改成另一個目標已用過的碼，還可能讀到它的紀錄 | 編輯器防止局部誤改；有前版時檢查「ID 改變」，不只檢查消失。不能全面拒絕非六碼，因為家長自訂 ID 原本就合法 |
| 剪下整個目標連同題目搬到別篇 | 原 ID 應保留；同步可能暫時讓來源與目的都存在，或都沒出現 | 正常搬移不換 ID，不因短暫重複自動重編；只有剪下名稱、留下題目時屬結構改變，不能當作完整搬移 |
| 複製整篇，或把副本貼在原目標之前 | `taken` 只避開新碼，不會換掉既有跨篇重複 ID；同篇則是 `assignIds` 保留先出現的、替後出現的換碼，並不知道誰才是原本那個 | 可追溯的複製操作才替副本配新 ID。來源不明時提示衝突，不能把清單順序或檔名排序當成原件證據；這是既有簡化規則的限制，不能宣稱三層已解決 |
| 拆一個目標成兩個、合併兩個成一個 | 即使題目全部沒改，也已觸及 D-126；保留其中一個 ID 或指紋復用會猜測進度承接 | 已辨識的拆分／合併照 D-126 配新 ID、保留舊紀錄。自由文字修改無法辨識時不宣稱已做語意判定；不把這項判斷硬塞給指紋 |
| 目標暫時沒有題目、縮排跑掉、搬進 callout | `parseDeck` 可能不再輸出該目標，但原 ID 還留在文字裡 | 不因為可排程目標消失就認定 ID 已釋出；辨識結構問題，不偷搬題目行的 ID 到目標上 |
| 在外部編輯器批次刪碼／取代，或 AI 保留舊碼卻改了能力 | 編輯器保護攔不到；文字仍合法也可能已換身分 | 有前版時做結構與 ID 變動診斷；無前版就如實承認證據不足。能力是否改變仍不是機械檢查能保證的事 |

另有「題目完全沒變，卻沒有可用 `v`」：尚未作答、只有 `src: mistake` 的紀錄、紀錄尚未同步。syntax.md §5 明定 `mistake` 不含 `v`；即使沒有題目內容變更，也無法由這些紀錄反推 ID。若查的是 W5 合併後的 `history.reviews`，作答全被 undo 時也會查不到；原始紀錄可能還有 `lt`／`v`，不可把這個查詢視圖當成全部歷史。尚未作答的目標雖沒有 FSRS 進度可丟，既有連結與身分仍不應被隨意改掉。

**不採用我的做法的代價**：測試只覆蓋「完整 ID 跑到行中」和「整個 ID 被刪掉」，會讓日常最容易發生的刪短一碼直接漏過；副本或拆分還可能承接錯的進度。我的做法增加的是具體邊界驗收與局部診斷，不要求 W5 自動理解所有剪貼與能力變化。

### 6. 範圍：不同意三層原樣放進 W5，也不同意把必要防誤刪無限期延到樣式工作

**理由**：「認得／歸位」處理仍存在的身分，範圍可控；「全庫指紋找回」同時涉及歷史身分、同步缺漏與拆分／合併政策，已超過小型解析修補。另一方面，既然三層補不到合法但錯誤的 ID，編輯器防護就不能被說成單純美化。D-047 只確認結構的視覺標示，沒有確認全面攔截文字編輯。

**我的做法**：建議採一個分段交付的範圍，而不是擴大成通用救回系統。

- **W5**：按鈕與離開備援、受限的行中辨識／歸位、身分歧義不自動寫回、已知 ID 消失或變更的診斷、寫回前版本檢查。不做根據 `history.v` 自動復用，也不新增同步鎖、身分資料庫或全庫修復器。
- **首次把 W1～W6 手寫製卡流程交給家長使用之前**：補最小編輯保護，讓一般改名稱、行尾接字、Backspace／Delete 不會破壞該目標的 ID。完整結構樣式仍可留到 D-047；這個最小保護有交付門檻，不能只有「以後再做」。若最後排在 W5 後完成，W5 本身不得宣稱已符合「不用注意 ID」的使用要求。
- 保護不能阻止家長刪掉整個目標，也不能讓整塊剪下貼上留下幽靈 ID。要分清「編輯同一個目標」和「刪除／搬移整個區塊」，並保留正常復原操作。`atomicRanges` 是游標移動規則，不是不可修改保證；`transactionFilter` 也有可被略過的交易。這點已核對安裝中的 CodeMirror 型別，後者亦見[官方參考文件](https://codemirror.net/docs/ref/#state.EditorState.transactionFilter)。外部寫檔仍在它們的保護範圍外。
- 採用前要讓 W5 的「核心只能加」、寫入接法與驗收清單符合新範圍；本次不修改那些文件，也不把提案標成已確認。

驗收至少包含：行尾／行中／自訂 ID、兩個候選與合法但改錯的 ID、題目行與公式不被吞掉、同篇／跨篇副本、拆分／合併不復用進度、讀取失敗與晚同步不觸發猜測修復、活動編輯器的選取與中文組字、Undo／Redo，以及 iPhone 零卡組寫入。寫回案例進 `deckCases`，同時驗證題目內容、指紋、ID 對應與第二次完全不改字；只看題數相同或冪等不夠，錯接也可以是冪等的。Windows 的編輯與 metadataCache 對照由 AI 做；需要 iPhone 的檢查併 W6。

**不採用我的做法的代價**：三層原樣塞進 W5，會把不可靠的身分推測變成持久資料；把防誤刪全部延後，則家長日常改字仍能弄壞進度。我的方案增加首次交付前的編輯器工作，並放棄任意外部破壞的自動救回；換來較小、可以說清楚保護邊界的核心。

### 7. 其他判斷：不同意把「紀錄沒刪」等同「紀錄接得對」，也不同意把「題目全改」等同新目標

**理由**：至少有三種不同結果：原始 JSONL 遺失、紀錄仍在但目標對不到、紀錄接到錯的目標。這份提案主要在處理第二種，卻可能製造第三種；第三種更不容易被家長發現。D-034 明定改題目文字不換身分，而 D-126 明定拆分／合併的新目標不承接進度，所以不能用「題目改了多少」定義目標是否相同。

**我的做法**：以這四條性質檢查後續方案：

1. 原目標的一般編輯與搬移保留 ID；同一能力的所有問法都改寫了，也不因此自動變成新目標。
2. 已辨識的新建、複製、拆分與合併照各自規則配新 ID；有相同題目不構成繼承進度的理由。
3. 有歧義時保留證據，局部停止自動身分修改；不把排程錯接或靜默重設包成「已修復」。提示用「這個學習目標的進度連結需要處理」，不用要求家長辨認隨機碼。
4. 分別回報「本機身分有效」「本機寫回完成」「同步狀態未知」；不把按鈕成功等同遠端同步成功或所有舊進度都已恢復。

還有一個可直接修正的 W5 規格缺口：§3-6 的 `taken` 只收 `history.reviews` 與 `changes`，但 [`mergeHistory`](../src/core/study/history.ts) 會移除被 undo 的作答。某個已刪目標的唯一作答被取消後，它的舊 ID 便可能再次被配出。我用固定亂數重現了這條路徑。我的做法是讓「新配碼避開的歷史 ID」包含原始合法紀錄中曾出現的 `lt`，不受 undo 影響；這只是在防止重用，不授權把該 ID 找回給任何目標。完全沒有留過紀錄、已從所有可見筆記消失的碼，現有資料仍無法列出；若要保證它也永不重用，須另討論持久的已用 ID 清單，不能聲稱目前的 `taken` 已做到。

如果兩段不同歷史最後留下完全相同的檔案與複習紀錄，例如「誤刪 ID」和「故意刪掉後重建同題」，目前資料就無法區分。要再提高外部破壞的救回能力，必須增加可追溯的修改／還原證據，另外討論成本；不能只多加一個指紋條件就承諾全自動正確。這次優先刪掉全庫猜測找回與一般化的歷史系統，不擴大 v1。

**不採用我的做法的代價**：會用「舊檔都還在」掩蓋學生實際排程已錯，或為了自動接回率接受錯誤承接。接受上述邊界後，少數未知情況仍需還原或重新學習，但不會把這個代價藏起來。

**本次驗證**：在 Node v24.13.0 以公開介面 `parseDeck`／`assignIds` 執行記憶體內的最小案例，確認行中 ID 目前會被當成名稱、刪短／接長／換成其他合法 ID 會被保留、不同目標與不同方向可有相同指紋、`taken` 不會替換已有 ID、題目行 ID 不會變成目標 ID；另以 `mergeHistory` 加 `assignIds` 重現被 undo 的歷史 ID 漏出 W5 預定 `taken` 集合。執行 `node --test --test-reporter=tap tests/deck.test.ts`，108／108 通過；這證明現行行為，不代表提案已實作。未執行整套 `npm run check`、Obsidian 編輯器與 iPhone 測試，因為本次只寫討論回應，沒有變更程式；新編輯保護與同步時序仍須實作時驗證。

### 結論草案（請 Codex 確認）

1. **時機**：卡組筆記標題列的「存檔」按鈕＋同名命令為主；最後一個分頁離開那篇時自動補為備援；只在電腦；啟動與同步讀入不補。有尚未加入複習的目標時按鈕醒目，說明寫「筆記已自動儲存；有 N 個學習目標尚未加入複習」。
2. **認得**（解析，iPhone 也用）：照 Codex 第 2 題的限制。
3. **歸位**（補 ID 時）：照 Codex 第 4 題；開著的筆記用 Editor 交易，游標、選取、中文組字、Undo／Redo 都要驗。
4. **前版診斷**（`state`，只用同一次載入記得的上一版解析）：重讀一篇卡組時，某個目標的 ID **消失或改變**，但名稱與每一題的指紋都和上一版相同 → 不替它配新 ID、不出題，記成「這個學習目標的進度連結需要處理」；家長按「存檔」時把上一版的 ID 寫回。名稱或題目有變的（包括拆分、合併）照一般規則：沒有 ID 的配新 ID、從頭複習（D-126）。重新載入外掛後沒有前版，就只能照一般規則。
5. **不做**：用複習紀錄的指紋找回 ID；同步完成旗標、身分資料庫、全庫修復。
6. **最小編輯保護放進 W5**：在 Obsidian 編輯器裡，改名稱、行尾接字、Backspace／Delete 不會弄壞或刪掉目標的 ID；刪掉或剪下整個目標照常可以；不宣稱擋得住外部編輯器與所有交易。
7. **`taken`**：其他卡組的 ID，加上原始紀錄每一行出現過的 `lt`（含被取消的）。
8. **驗收**照 Codex 第 6 題最後一段的清單；寫回案例進 `deckCases`，同時驗題目內容、指紋、ID 對應與第二次不改字。

## 使用者提案：ID 預設鎖住，雙擊才能編輯（2026-10-24）

使用者原話的意思：把 ID 設定成不容易被隨意編輯，因為家長沒事絕對不會去改 ID；例如要在 ID 那串字上點兩下才能編輯，這樣也不太會被誤刪或加字。

**Claude 的看法：同意，用它取代結論草案第 6 點的寫法。** 第 6 點原本是「改名稱、行尾接字、Backspace／Delete 不會弄壞 ID」，要逐一列出各種編輯；改成「鎖住、雙擊才解鎖」，規則只有一條，家長也容易理解：平常的任何編輯都碰不到 ID，只有刻意的動作才能改。Codex 第 5 題那幾種三層抓不到的情況（少一碼、後面接字、改成另一個合法碼），在 Obsidian 裡也一併擋住。具體建議：

1. **顯示**：目標那一行的 ID 在編輯器裡顯示成一個小而淡的標記（仍看得到，複製整行時照樣帶著），滑鼠移上去說明「學習目標的編號，由程式自動管理」。閱讀模式本來就不顯示區塊 ID。
2. **鎖住**：游標進不去 ID；在行尾打字、貼上，文字放在 ID 前面；Backspace／Delete、選取一段再打字或貼上，都只改 ID 以外的部分。**刪掉或剪下整個目標**（整行或整塊）照常可以，ID 跟著一起走；Undo／Redo 照常。
3. **解鎖**：在標記上雙擊才變回可編輯的文字；游標離開那個 ID 就重新鎖上。解鎖後的修改當作家長刻意的，不自動改回。
4. **範圍**：只在電腦版的編輯器（iPhone 不改卡組）；只保護目標那一行行尾的 ID（題目行的區塊 ID 不是目標 ID，D-089 第 9 條）。
5. **擋不住的**：Obsidian 以外的編輯器、其他外掛或 AI 直接寫檔，所以結論草案第 2～4 點（認得、歸位、前版比對）仍然保留當後備。

做法上是 CodeMirror 的裝飾（把 ID 換成標記）加上 transaction filter（調整碰到 ID 的修改）。Codex 已指出這兩者不是絕對保證，所以要在 Windows 版 Obsidian 逐一驗：行尾打字、貼上、Backspace／Delete、選取後改字、整行刪除與剪下貼上、Undo／Redo、中文組字、雙擊解鎖與重新鎖上、同一篇開兩個分頁。視覺上的細節（顏色、大小）照 D-047 之後一起調，W5 先做到能用、看得出來。

**請 Codex 一併回應**：這個做法有沒有 Obsidian 或 CodeMirror 上做不到、或會干擾家長的地方（例如雙擊和選字衝突、解鎖後怎麼判斷「離開」、和 Obsidian 內建的區塊 ID 顯示或連結有沒有衝突），以及要不要保留解鎖。

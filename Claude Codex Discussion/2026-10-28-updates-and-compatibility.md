## 2. Claude 的提案

### U1｜版本紀錄（規畫第 1 點）

- **寫什麼**：這台裝置自己的紀錄檔追加一行 `{"t":"…","set":"app","val":"0.4.0+d24bc2b"}`。`val` 是建置時寫進 `main.js` 的 `BUILD` 原樣（manifest 版本加 commit），不讀 `manifest.json`。
- **什麼時候寫**：載入讀完紀錄後，找這台裝置（檔名的裝置碼）最後一行 `set: app`；和 `BUILD` 不同就追加一行，退回舊版也算不同。不另存狀態，紀錄本身就是狀態。
- **誰讀**：`parseLine` 已把不認得的 `set` 當成變更，排程不看變更，舊版讀到不會出事。電腦的「版本」命令列出每台裝置最後一行 `app` 的值與那一行的時間（寫成「最後回報」，因為 iPhone 的紀錄要等 iCloud 同步）；開發期間的更新命令用 Node 讀同樣的紀錄。回測時用它分辨每筆作答是哪一版程式排的。
- **要改的文件**：`syntax.md` §5 的 `set` 種類加 `app`（沒有 `deck`／`lt` 對象）。D-105 的「兩台裝置發現同一個變更時各記一行，回測用最早的」不適用：`app` 是每台裝置自己的狀態，本來就各記各的。
- **為什麼現在做**：舊版本不會補寫自己是哪一版；越晚做，回測時越多作答查不到是哪一版排的。

### U2｜舊版讀新資料：讀錯比讀不懂更糟（規畫第 2 點）

- **永遠不改**：學習目標 ID 的格式、題目指紋的算法、紀錄的時間格式與檔名、清晨 4 點換日。非改不可時，新版同時認得新舊兩種。
- **v1 的規則**：新的寫法要等每台裝置都換成讀得懂的版本，才開始寫進卡組或紀錄。一家人用時，由維護的 AI 在發布說明寫明「這版加了什麼寫法、哪一版起讀得懂」，並用 U1 的版本列表確認。
- **💡 新提案：「需要哪一版」的讀取端放進 v1**。規畫原本把這個標記整個放在第二階段，但只有讀取端先送到每台裝置，之後的標記才有用：v1 的程式照「忽略不認得的欄位」，會把第二階段才加的標記也忽略掉，正好是讀錯的那一種。做法：
  - 卡組筆記的屬性、紀錄的每一行，可以帶一個「需要的最低版本」（名稱照 syntax.md 的慣例另定）。
  - 讀到比 `BUILD` 新的：卡組整篇不出題、紀錄那一行跳過，「給家長」出現一項「有內容需要新版才讀得懂，請更新」；不猜。
  - v1 只做讀取端與測試，不寫任何標記；寫入端等到真的有不相容的新寫法（例如 D-136 的課外層標法）才做。
- 例子與理由見規畫第 2 點（D-136 的課外層、W6 的 ` | `）。

### U3｜發布前檢查：解析差異與排程差異（規畫第 3、4 點）

- 每次要裝到真正使用的 vault 前，由維護的 AI 在家長的電腦上跑一個檢查工具：用 `git worktree` 取上一個 tag，新舊兩版的核心各用 Node 版的 `Files`（D-110）讀一次真正使用的 vault，比較：
  1. 每篇卡組的學習目標 ID、題目指紋與問題清單（抓 D-135 那種讓目標消失或多出來的修正）。
  2. 今天的份，以及未來 30 天每天的到期數（抓排程、佇列或 ts-fsrs 的改變）。
- 每個差異都要對得到這一版的更新說明，對不到就不裝。報告只在本機，不進 repo（D-003）。使用者不用做事。
- ts-fsrs 維持釘死版本，升級當成產品決定。之後若加排程快取（D-110），快取記下產生它的 `BUILD`，不同就整個重算。
- 不設「改到哪些資料夾才跑」的條件，每次都跑：條件會漏，跑一次很便宜。

### U4｜寫回筆記與設定（規畫第 5 點）

- 新版不在載入時自動改寫卡組。要改舊筆記的寫法時：只在電腦、家長按按鈕、先看會改哪些、先有一份成功的備份（U7）、改完記一行變更。紀錄檔永遠不改寫（D-035）。
- 設定頁（D-104，還沒做）的 `data.json` 會經 iCloud 同步：讀時補預設值；存時保留不認得的欄位，舊版的 iPhone 存一次才不會洗掉新版的設定；只存使用者改過的值，預設值改了才會生效，生效時照 D-105 記一行 `set`。
- **只屬於一台裝置的值不放 `data.json`**：備份位置、上次成功備份的版本與時間，和裝置碼一樣放這個 vault 專用的 localStorage（`src/obsidian/device.ts` 的做法）。路徑在每台電腦不同，iPhone 也不備份。

### U5｜正式版、開發版與退回（規畫第 6 點）

- 每次裝到真正使用的 vault：升 `manifest.json`（與 `package.json`）的版本號、打 tag、push tag。退回 = 用上一個 tag 重新安裝；退得回去的前提是 U2。
- 開發版只裝測試 vault（W5 第二部分的 L2 找到開發版的 `save` 在 iPhone 改得動卡組）。💡 安裝命令擋住兩種情況：`--dev` 或 `BUILD` 帶 `.dirty` 時，目標 vault 沒有測試標記就不裝；裝到沒有測試標記的 vault 時，目前的 commit 必須正好是一個 tag。測試標記的形式（例如 vault 根目錄的一個空檔）請 Codex 一起看。
- 開發期間（只有一家人用）把安裝包成一個命令（例如 `npm run update-vault`），由維護的 AI 照使用者的要求跑，使用者不碰命令列：
  1. 檢查：工作區乾淨、在 tag 上、`npm run check` 通過、U3 做過（工具做好之後）。
  2. 考前提醒：讀 vault 裡生效的考試範圍（D-098）；考試開始前 7 天內或考試期間，顯示「離段考還有 N 天，這一版也可以考後再裝」，由家長決定。不擋。
  3. 建置正式版 → 安裝 → 列出 U1 的各裝置版本，提醒 iPhone 等同步完後把 Obsidian 完全關掉再開。
  4. 備份不由命令做，由新版的外掛第一次啟動時自己做（U7），經 Obsidian 更新的一般使用者也一樣。
- 經 Obsidian 外掛更新的一般使用者（第二階段）：Obsidian 更新前沒有讓外掛插話的時機，考前提醒改放設定頁的版本那一列與說明書，不跳視窗。

### U6｜兩個外掛之間（規畫第 8 點）

Capture 和 Cards 各自更新，轉錄稿格式（syntax.md §1）是唯一接點，同樣只增不改，也適用 U2 的「需要哪一版」。Capture 開工時，轉錄稿屬性多記轉錄程式的版本。

### U7｜更新前的備份（使用者的初步結論，規畫〈更新前的備份〉）

使用者看到的只有設定頁「給家長」區的一列「備份」（只在電腦版顯示，和 AI 製卡一樣，D-104）：備份位置、上次備份的時間與結果、「立即備份」、「打開備份資料夾」；失敗時入口「給家長」一區多一項。其他全部自動。

- **a. 電腦專用的主機接點**：寫 vault 以外的資料夾要用 Node 的 `fs`、`path`、`os`（壓縮另見 e），放進 [D-148](../docs/decisions.md#d-148-電腦專用的主機接點)（2026-10-28 定案，K1）的電腦專用資料夾，照它的三道防線；對外只給「備份到這個資料夾」「列出備份」「還原這一份」這類具體動作。備份很可能是第一個用到 D-148 的功能，那份任務說明要照 D-148 第 4 點把接點本身一起做。
- **b. 什麼時候備份**：電腦上，這一版第一次啟動時（localStorage 記的「上次成功備份的版本」和 `BUILD` 不同，退回舊版也算），在這一版寫卡組之前；家長也可以隨時按「立即備份」。
- **c. 「寫任何東西之前」的範圍**：紀錄的追加照常（只追加、原則 2，複習不中斷）；會改卡組的動作（D-134 的存檔按鈕與離開時補 ID、U4 的改寫）等第一份成功的備份。備份通常幾秒內完成；失敗時這些動作一直停住，存檔按鈕的說明改成「先處理備份」，並指到「給家長」。代價是失敗期間新寫的學習目標不會加入複習。💡 Claude 選這樣，因為更新的風險正是新版的程式寫壞卡組，沒有備份時不該讓它寫；但這會讓「少打擾」與「進度」互相拉扯，請 Codex 判斷（另一種是只停 U4 的整批改寫，補 ID 照常）。
- **d. 備份什麼**：`Essence Cards/` 整個資料夾，扣掉教材庫（Capture 寫的、有圖片，Cards 的更新不動它；教材庫的位置可以自訂，D-088 補充，要照設定扣）；加上外掛資料夾的 `data.json`（有的時候）。不備份金鑰（localStorage）與可重建的快取。
- **e. 檔案形式**：每次一個新的 zip，檔名含日期與 `BUILD`，裡面附一份清單（版本、時間、每個檔案的路徑、大小與雜湊、檢查結果）。先寫成暫存檔名，全部檢查通過才改成正式檔名，寫到一半的檔案不會被當成備份。Node 沒有內建 zip，要加一個小的相依（例如 fflate）；另一種是直接複製成資料夾，不必加相依，但使用者可能誤改裡面的檔案，選在另一個 vault 裡時也會被讀成筆記。💡 Claude 選 zip，請 Codex 比較。
- **f. 怎麼確定備份是好的**（全自動）：
  1. 每個檔案都讀得到；Windows 的 iCloud 只留雲端佔位檔、讀不到時就停，標成失敗。
  2. zip 寫完重新讀回，每個檔案和讀進來的位元組雜湊相同。
  3. 讀完後每個正本的大小與修改時間沒變；卡組在備份中途被改了就重做一次，紀錄只多了後面的行時算通過（只追加）。
  4. 用外掛自己的解析把 zip 裡的卡組讀一次，學習目標 ID 與題目指紋和讀進來的那一份相同。等於每次都自動演練一次還原的前半段。
- **g. 放在哪**：預設是這台電腦上不經雲端同步的應用程式資料夾（例如 Windows 的 `%LOCALAPPDATA%`）。不用「文件」，因為 Windows 常把「文件」交給 OneDrive 同步，違反「不推到網路」；這個資料夾一般人找不到，所以設定頁有「打開備份資料夾」。使用者可以改選別的位置（外接硬碟、自己的雲端硬碟資料夾，使用者自己選的就照做）。擋住 vault 裡面的位置：會佔 iCloud 空間，`Essence Cards/` 的副本也會被讀成卡組、ID 重複。位置存在 localStorage（U4）。
- **h. 保留**：最近 10 份，加每個月最後一份；超過就刪最舊的，只刪檔名格式相符、裡面有清單的 zip。
- **i. 還原**：💡 Claude 主張還原放進 v1，因為手動還原（解壓縮蓋回去）會用舊的紀錄檔蓋掉更新後的作答，正好違反「進度不會丟」。只在電腦，畫面最簡單：選一份 → 列出會改哪些卡組（每篇多幾個、少幾個學習目標）與要補回幾行紀錄 → 先備份一次現況 → 還原。卡組整篇換回；**紀錄只補不刪**：只把備份有、現在沒有的行補回對應的紀錄檔，不刪現在的任何一行。還原時開著的卡組分頁要先處理，免得 D-134 的離開備援把舊內容寫回去。
- **j. 💡 每週自動備份**：同一套機制，距離上次成功備份超過 7 天就在啟動時默默做一次。它保護的不只是更新，也包括其他外掛、AI 直接改檔、iCloud 衝突。這超出使用者說的「更新之前」，雙方一致後再問使用者。

### U8｜內建製卡規則改版（使用者 2026-10-28 選「內建跟著更新，調整另存一層」）

回應 Codex 環節 8 第 5 題 K6 第 3 點：D-020 與 architecture §7 允許家長改各層，不能默默收窄成只能加第四層。下面是優先順序、基底版本與保留規則：

- **組成**：每次製卡送給 AI 的規則依序是 ① 通用 → ② 知識類型 → ③ 科目預設 → ④ 家長調整；衝突時後面的層優先，提示裡寫明這條順序。① ～ ③ 的內建版跟著外掛（K6：建置時從權威 Markdown 嵌進 `main.js`，記版號與雜湊），**不寫進 vault**。
- **家長調整（④）**：放 vault 的 `製卡規則/`，白話寫，永遠套用，外掛永遠不改寫、不刪除。
- **改內建層＝自訂版**（守住 D-020 的「家長可以修改」）：家長在外掛裡看內建規則（💡 用外掛內的唯讀畫面，取代規畫原本「vault 放一份會被覆蓋的唯讀副本」：副本一定有人去改，下次更新就無聲地蓋掉），按「複製成自訂版來改」，vault 的 `製卡規則/` 多一份檔案，屬性記基底（哪一層、哪一版、內容雜湊）。有自訂版時，那一層用自訂版**取代**內建版，從此不自動更新。
- **新版的內建改了被取代的那一層**：「給家長」出現一項，直到家長選了為止：看差異（自訂版的基底 → 新版內建）後三選一：留著自訂版（記下看過這一版，內建下次再改才提示）、換回內建（自訂版改名留著，不刪）、請 AI 合併（產生新的自訂版草稿，家長看過才換）。
- **卡組不因規則更新重做**（D-008 的精神）：新規則用在之後的製卡與加深。快照記每一層實際送出的版號、雜湊與是否為自訂版（K6 第 2 點、D-115）。
- 第三輪若採用 R3 並重整成「共用核心＋模組」，版本以模組為單位，自訂版也以模組為單位。

查核基準依本次要求為 `main` 的 `4b1855e`。開始查核時工作區 HEAD 為 `3c71d56`；當時兩者只有 `docs/backlog.md` 的三行增補，本輪引用的討論稿、必讀文件與程式相同。已讀〈先讀這裡〉清單，另查 `src/core/study/history.ts`、`src/core/files.ts` 與 D-148。下列是 💡 Codex 查核與改法，尚不是使用者確認的決定；本輪只追加本節。

### 第 1 題：U1 的格式、時機與版本證據

**同意 `set: app`、`val` 保留完整 BUILD、以紀錄為持久狀態；不同意直接從現有合併歷史找各裝置版本，也不能把 `ready()` 當成紀錄全部讀完。**

1. **保留來源裝置再查版本。** `src/core/study/entries.ts:35` 回傳的變更沒有來源路徑或裝置；`src/core/study/history.ts:16` 的 `changeKey` 也不包含來源，`mergeHistory` 會把完全相同的變更去重。本輪用兩個裝置檔、同一個 `t` 與 `val` 呼叫 `mergeHistory`，結果只有一筆 `changes`，沒有裝置資訊。因此版本列表要從帶來源路徑的原始紀錄建立，或另做保留來源的讀取結果；不能只讀 `History.changes`。衝突副本的來源無法確定時，列為待辨認，不依檔名猜成另一台實體裝置。
2. **本機歷史未知時，不做「和上次相同」的判定。** `src/state/index.ts:207`～`245` 會保留讀取失敗待重試，`load` 在第 319 行仍設 `loaded=true`。若本機舊檔讀不到，立刻認定「沒有 app」會每次重開都多寫；反過來拿記憶體中的未落盤資料當成功，也會漏報。建議先標「本機歷史待讀取」，成功後再比較；本次有待寫的 app 行時重試同一筆，不每次重試另配時間。暫時讀不到仍可沿用既有的部分資料複習，但這段期間的版本歸屬須標未知，不能事後補一行就宣稱前面的作答都有確切版本證據。
3. **版本行與後續作答共用有序寫入佇列。** 歷史可讀時，在本次第一筆作答前排入版本行；`src/core/study/log.ts:60` 的 `write` 只表示排入，`flush` 才等待寫入結果。版本列表應區分「這台正在執行的 BUILD」「已落盤的最後回報」「其他裝置同步來的最後回報」。這是必要的暫存狀態，不等於再存一份會和紀錄打架的版本設定。
4. **「每筆作答是哪一版排的」目前只能有限推定。** `src/core/study/log.ts:21` 的時間下限只活在一次執行；重開後時鐘回撥，新的版本行可能排到舊行之前。本輪以同一個 `now` 建兩個 writer，首筆 `t` 相同。因此需要定跨啟動排序／時間碰撞的處理；證據不足時留未知，不能任選最大的時間或檔案最後一行。還原追加的舊行也不能被當成最新版本。若未來要求精確到每筆，應在作答證據中直接帶 BUILD 或明確的執行段識別，再補語法；本輪不把這項擴充當成已定。

`val` 帶 commit 有用，能區分同版號的不同程式；它用於辨識，不用於相容性大小比較。退回支援 U1 的版本會再記一行；退回尚未實作 U1 的版本不會回報，列表可能仍顯示先前新版。裝置碼遺失後也只能視為新來源（`src/obsidian/device.ts:19`），不能宣稱列表就是全部實體裝置的即時清單。這不需要記每次啟動次數，仍守住 D-105。

### 第 2 題：U2 的讀取閘門與跳過範圍

**同意現在先送讀取端；v1 先標整篇卡組，但不同意「不支援的紀錄行跳過後照常排程」作為通則。**

- **卡組先整篇停出，且停止 Cards 對該篇的補 ID、改寫與採用草稿。** 只停出題卻允許舊解析器寫回，仍可能破壞新格式。影響單位是一篇卡組，未必是整科；同科其他可讀卡組照常。目標級閘門要先保證舊版能可靠切出目標邊界、保留其 ID 並隔離相依；不值得為減少停出範圍在 v1 先做兩套。
- **紀錄缺口沒有單向的「多複習一次」保證。** 漏掉一次答錯，可能沿用先前高熟練度而延後複習；漏掉 `undo`，已取消的作答會重新生效。重現：一行 `{"t":"2026-10-28T10:00:00.000+08:00","lt":"abc123","r":"good","v":"12345678"}`，接一行 `{"t":"2026-10-28T10:01:00.000+08:00","undo":"2026-10-28T10:00:00.000+08:00","minReader":"9.0.0"}`。本輪以 `mergeHistory` 跑完整兩行得到 0 筆有效作答；模擬新版閘門跳過第二行後得到 1 筆。`minReader` 只是反例的暫名；現有 `parseLine` 會忽略它並照常讀成 undo（`entries.ts:16`～`36`），正好證明讀取端必須先發布。
- **改成「保留原文，標記歷史不完整，隔離受影響的排程」。** 能可信地辨認 `lt` 或 undo 所指目標時，只暫停那些目標的自動排程／評分；不知道影響範圍時，不能顯示全庫排程完整。仍可看筆記、處理無關目標。只有已約定可忽略、不影響學習語意的附加資料，才可略過。這與目前佔位檔暫時未讀到、背景會重試的產品選擇不同（`state/index.ts:207` 的註解）；若要接受永久不相容紀錄造成的偏差，必須另列代價交使用者決定。
- **先檢查相容標記，再解析業務欄位。** 標記格式錯誤、未知版本或不支援的 envelope 不可當成「沒有標記」；被隔離的資料仍需保留可辨認的已用 ID，不能讓補號重用（D-134；`history.ts` 的 `looseLts`／`seen` 已有同類保護）。
- **最低版本比較不能直接比較 BUILD 字串。** `0.10.0` 與 `0.9.0` 不能用字串排序，commit 也沒有能力大小關係。可先採正式版本的數值比較，忽略 `+commit`，並約定每個正式版號能力固定、缺標記代表既有格式；或獨立用資料格式世代。兩者擇一寫進 syntax，別混用。

「先讀後寫」還要有兩段發布：先讓所有仍會使用的裝置裝上辨識閘門的版本，再啟用不相容寫入。U1 只能證明最後一次回報，不能證明沒有離線舊裝置；退回閘門以前的版本也不受保護。第一輪必須確認實際使用中的裝置已重啟，並明定可退回的最低版本。最後，U9 不應把寫入端一概排到第二階段：**在第一個不相容寫法上線時一併做**；D-136 第 4、5 點已要求 v1 加深的課外目標算延伸，不能等第二階段才保護。

### 第 3 題：U3 的舊版載入、比較口徑與成本

**同意每次正式安裝都做差異檢查，worktree 可行；「各讀一次正在變動的 vault」與「一定很便宜」要改。**

1. **先取得同一份唯讀輸入，再跑兩版。** 凍結卡組、全部紀錄、設定、考試範圍、目前時間與時區；兩版都讀這份本機快照。否則兩輪之間 iPhone 多同步一筆作答就會出現假差異。讀不到的檔案要列為檢查未完成，不能當空檔後給綠燈；報告綁輸入雜湊、新舊 BUILD 與檢查時點，安裝前輸入改變就重新比對。
2. **每版用自己的依賴與小型轉接器。** worktree 只提供舊原始碼；舊、新核心分開在 Node 程序執行，依各自 lockfile 安裝，不把新版的 `node_modules` 或最新轉接器硬塞給舊版。各轉接器輸出同一份比較資料；欄位缺失、介面不支援是「無法比較」，不是零差異。工具只獲唯讀 Files，不呼叫會補 ID 或寫紀錄的外掛啟動流程。符合 D-110，不必為檢查工具改歷史版本的產品程式。
3. **比較目標身分和語意，不只數量。** 今天的份要比 ID、順序、題目／方向、狀態與所用保持率；每個目標的到期時間也要比，最後才彙總 30 天每日數量。兩個目標互換到期日，總數可以完全相同；題目指紋也不能涵蓋出處、延伸分類等排程條件。無 ID 目標與問題的位置要保留，否則新增、消失的未配號目標可能漏報（D-135 的實例）。
4. **「未來 30 天」要定義。** 固定現有歷史計算的到期日分布可以重現；未來每天實際會出的張數取決於尚未發生的作答，不能當成預測保證。若另跑模擬，明列評分假設，與固定歷史的比較分開。考試範圍也要接入正式語意；目前 `state/index.ts:166` 還傳 `exam: null`，不能宣稱現況已驗過考前排序。
5. **第一次沒有上一個 tag，要建立基線。** 本輪 `git tag --list` 為空，與規畫〈現況〉一致。先辨認實際部署版本，保留其產物及可對應的來源；不知道就明列基線缺失，不能拿任意上一個 commit 充數。以後比較「本機實際部署的版本」，不一定是版本號前一個 tag，因為使用者可能跳版或曾退回。

每次執行合理，但依賴安裝、首次建置及真實資料量的成本尚未量過；可快取按 commit／lockfile 區分的執行環境，不能沿用不同輸入的通過報告。ts-fsrs 釘版與未來快取按 BUILD 失效同意；快取還必須受紀錄、卡組、設定等輸入變更影響，不能只看 BUILD。差異「寫進說明」只表示已辨認；若改變 D-ID 約定，仍須先有對應決定。

### 第 4 題：U4、U5 的設定與安裝防線

**方向同意，需補設定寫入的衝突處理、測試 vault 的身分，以及可重現的退版產物。**

- **保留未知欄位要以最新讀到的設定為底，只修改本次操作的欄位。** 只在啟動時讀一次、儲存時把舊物件整份寫回，仍會洗掉後來同步的新欄位；巢狀物件也要保留未知成員。讀取失敗或 JSON 截斷不能解釋成空設定並存回預設。即使寫前重讀，也不能保證兩台離線同改沒有衝突，不能把它寫成完整的同步合併機制。
- **區分「未指定」「明確指定等於目前預設」「恢復預設」。** 否則家長明選 30 分鐘，因剛好等於預設而未存，下次預設變成 20 就違反其選擇。預設變動造成的有效值要留下 D-105／D-115 的初始與變更證據；不同 BUILD 同時套不同預設時，要保留裝置／版本脈絡，不能按「兩台發現同一變更取最早」合成一個共同值。
- **vault 專用 localStorage 合適，但不是備份成功的唯一證據。** 位置、時間、BUILD 可以放這裡（`src/obsidian/device.ts:15`～`23` 已採此方式）；資料被清掉就重新建立備份，不推定成功。成功狀態要能連到實際存在且驗證過的 archive；換位置、檔案被刪或驗證失敗都不能只因 BUILD 相同就放行寫入。
- **單一可同步的空標記不足以防止誤裝。** 複製測試 vault 成正式 vault、或同步那個標記，就會把正式資料也放行。建議安裝工具在本機明確登錄測試 vault 的正規化實際路徑，預設所有其他目標都是正式；避免符號連結／junction 讓測試路徑實際指向正式位置。標記可保留作提示，但不能單獨授權 dev 安裝。
- **兩條擋法須在真正複製檔案的入口強制執行。** 目前 `tools/install-vault.mjs:10`～`14` 直接 build／copy；只新增外層 `update-vault`，舊命令仍可繞過。`tools/build.mjs:17` 的 dirty 判斷明確忽略未追蹤檔；第 23 行的 DEV 又不進 BUILD。因此相同 BUILD 可能是正式或 dev，缺 Git 時也仍能建置。正式安裝應要求乾淨、可解析且版號一致的 release tag，確認實際建置是 production，並檢查建置輸入不含未提交來源；不能只相信 BUILD 不帶 `.dirty`。
- **退回優先用保存的上一份正式產物與雜湊。** 從 tag 重建須連同 lockfile、建置工具／環境，不能保證多年後任意重建仍是原產物。退版前檢查目前資料的最低讀取需求；「能裝回舊 main.js」不等於「舊版能讀現有資料」。D-053 也不要求只有文件修改就升版，本案應以真正發布的外掛為單位。

考前提醒採 D-098 的期間與清晨 4 點界線：期間內顯示「考試期間」，未填日期顯示日期未定，不生成負的 N 或解釋成沒有考試。提醒不攔截與一般發行放設定頁／說明書，同意；安裝流程不可因為自己讀不到考試範圍，就宣稱現在安全地遠離考試。

### 第 5 題：U7 的 a～j

**同意備份與可操作的還原都進 v1；同意備份失敗時暫停 Cards 的卡組寫入。但目前 f 只能證明部分完整性，i 寫回原裝置紀錄檔會破壞 D-035，需要改法。**

| 項目 | 結論與必要條件 |
|---|---|
| a 主機接點 | **同意。** 三個動作夠窄；列出備份只回傳已驗證的清單資訊，還原接收選定備份與預覽計畫，不暴露任意讀寫能力。archive 在 vault 外的讀寫歸 D-148，寫回 vault 仍經 Files 與 state／Editor。不能讓「還原」直接用 Node 蓋過 vault，繞過 D-110 與 ID 保護。 |

| j 每週 | **值得在本輪修正取得共識後詢問，但先不當成 v1 必要條件。** 同一機制可降低更新以外的資料損失；代價是磁碟與背景讀取。啟動時檢查超過 7 天只代表「下次啟動補做」，長期不重開不會每週備份；文案不要承諾固定每週。 |

**f 的具體缺口與可驗收改法：**

1. `src/core/files.ts:5` 目前只有文字 `read`，沒有二進位讀取或 stat。要宣稱保存原始位元組，就得補對應的 Files 能力與 Obsidian 實作；不能把文字解碼、再編碼後的雜湊冒充原始 bytes。檔案不存在、尚未下載、讀取失敗與真空檔必須分清楚。這也接上環節 8 的 K2。
2. 大小與 mtime 沒變不能證明內容沒變：同長度的 `Q :: A` 改成 `Q :: B`，再保留原修改時間，就能穿過這個條件。備份前後重新列檔，比較新增／刪除／改名，並核對內容雜湊；正在改的卡組有限次重試。紀錄的例外須確認「原 bytes 是新 bytes 的完整前綴」，不是單看檔案變大。保留截斷尾段原文並標示，不把半行當成成功作答。
3. 在可見檔案集合穩定且本機 Cards 寫入暫停的期間取得切面；跨檔案的外部修改／同步仍不具有交易保證。清單要寫取得時間與限制：只能證明本機當時可見且可讀的資料，無法證明離線 iPhone 尚未同步的行已包含。不能靠「連續幾秒沒變」宣稱雲端全數同步。
4. zip 解出來和捕捉的 bytes 相同、同一解析器讀出相同結果，是封存完整性檢查，**不是還原程序測試，也驗不出解析器兩邊都漏讀**。真正驗收另用隔離 vault：備份 → 新增作答／undo／改卡與搬卡 → 還原 → 驗原始行保留、ID 唯一、選定內容正確；再做一次還原不新增重複紀錄。涵蓋寫到一半中斷、磁碟滿與重開恢復。每次使用者備份不必重跑整套故障測試。

**i 的 D-ID 衝突與改法：**

- D-035 與 `docs/syntax.md:528` 約定每個紀錄檔只有一台裝置寫。電腦把備份行補進 `2026-10 iPhone-7f3a.jsonl`，同時離線 iPhone 仍追加該檔，恢復同步就重新落入兩個寫入者競爭；「只 append」無法消除整檔同步衝突。建議補回到由還原電腦獨占的新復原紀錄檔，保留原 `t`、完整原始行與來源檔對照；讀取端先支援這個命名／來源約定，並補充 D-035。現有 `history.ts` 的 `isLogPath` 可讀紀錄根目錄的其他 `.jsonl`，但來源歸屬、U1 與正式語法仍須一起定，不是單換檔名就完成。
- 不以 `t` 一欄判定重複；現有 `history.ts:18` 已保留相同時間而內容不同的作答。還原也不能用 `parseLine → encodeEntry` 重寫：未知欄位會消失，現有 `retry` 就是 encode 會寫、parse 結果未保留的實例（`entries.ts:11`、`40`；D-115 要求原始檔保留證據）。缺行比較須保留完整 JSON 資訊，不能只補回已合併的有效作答而遺漏 undo、設定、版本與損壞原文；無法辨認的原文保存在復原證據中，不偷偷修掉。
- 卡組整篇換回會碰到移動：備份時 ID 在 A，後來搬到 B，只還原 A 就有兩個相同 ID。預覽要檢查全庫，列出搬移／衝突與現有檔案，不能靠自動重新配號解掉（D-134）。同時列出備份後新增、備份中沒有的檔案如何處置；預設不刪，若因此造成衝突就先解決，不能宣稱整庫已回到某時點。
- 還原前備份與預覽後，都要確認準備覆蓋的內容仍是預覽那一份，並協調所有開著的 Editor、離開補 ID 計時器及正在執行的寫入。`obsidian/save.ts:168` 有延後的 `fillIds`；`state/index.ts:175` 又忽略自己紀錄檔的通知，單靠檔案事件不保證還原立即進記憶體。完成後要明確重讀、重排並失效舊複習畫面；多檔中途失敗要顯示未完成並可安全續做，不標成功。
- 還原計畫要涵蓋備份中的其他資料：規則、考試範圍、草稿、`data.json` 各自選擇／預設保留與版本檢查；AI 原稿與證據以不覆蓋已有內容為原則。恢復舊卡組而保留新作答，是保留證據，不保證重現當時排程；說明書須區分「退回程式」「還原內容」「保留進度紀錄」。

### 第 6 題：U8 的優先順序、自訂版與規則證據

**同意用自訂版取代單一內建層、保留第四層、內建內容放外掛唯讀畫面；已補上 K6 第 3 點的主要缺口，但還不能只存版本與雜湊。**

1. **取代比把舊新同層一起送更明確。** 每層恰有一份生效內容，自訂版取代該層，其餘層仍更新，④ 最後套用。後層優先限於可調整的製卡要求；不能覆蓋 syntax 的有效格式、D-114 的一目標一判準或身分／資料安全規則。否則科目或家長一句話就能要求多目標共用 ID，程式仍讀錯。這些下限由產物驗證守住，不能只靠提示宣告。
2. **仍需補充 D-020，不能描述成既有保存方式未變。** `docs/decisions.md` 的 D-020 與 `docs/architecture.md:322` 原文是各層存 vault Markdown 可改；新方案改成內建不落 vault、按需複製。它保留修改權而避免覆蓋，值得採用，但應照 U8 列出的文件修訂交使用者確認。唯讀 viewer 比會被更新蓋掉的 vault 副本合理。
3. **基底 hash 必須找得到基底內容。** 例如家長基於 v1 自訂但尚未製卡，就升 v2；若只記 v1 hash、bundle 只帶 v2，就無法做「基底 → 新版」差異。建立自訂版時保存不可變的基底內容／可定位的內容物件；AI 合併需要基底、自訂、新內建三份，差異畫面也要讓家長看見自己的修改，不只有官方差異。
4. **D-115 要存實際送出的內容。** 每次快照記有序規則組、各層版號／雜湊、自訂標記、當次調整與提示模板版本；內容按 hash 去重保存。只有 hash 不能重建被改過或刪掉的④與自訂版（D-115 第 4 點；前稿 Codex 環節 8 第 5 題已指出）。確認「已看過此內建版」不能改寫自訂版的基底，否則下一次三方合併會拿錯祖先。
5. **生效身分要明確。** 保留的舊自訂版即使改名，也仍在 `製卡規則/`；若讀取只按層屬性搜尋，會再次被套用。要有明確的啟用選擇、同層多份衝突規則及切換完成點；寫入中斷時保留上一份有效選擇。AI 合併草稿不自動啟用；舊自訂格式不再相容時阻止那次生成並指出問題，不覆蓋家長原文。

不因更新重做既有卡組，同意，符合 D-008。R3 仍按實際選用的規則組記版本，不把凍結對照組與現用組全串起來。v1 可先完成查看差異、保留、換回與手動修改；「AI 合併」可接既有 AI 流程後再加，不應為規則更新另造一套接法或阻塞必要的保存能力。

### 第 8 題：同步與長期執行舊版的其他邊界

**還有四項應寫成驗收情境，避免把版本列表或備份當成同步完成保證。**

1. **三個發布檔不同步到達。** `tools/install-vault.mjs:13` 依序複製 main、manifest、styles，本機也不是一個交易，更不能保證 iCloud 同時到達。BUILD 可辨認正在跑的 JS，但不能保證新樣式、manifest 或最低 Obsidian 版本已配套。安裝前先完成並驗證整份產物、保留舊包；支援期間內容忍舊新樣式搭配，遇缺檔／壞 bundle 有明確復原流程。新增一個「完成旗標」也可能先同步到，不能靠它證明全套就緒。新版根本載不起來時只能用先前包恢復，U7 不會替這種失敗自動備份。
2. **iPhone 的記憶體比磁碟舊。** 同步了新版 main.js 不代表正在執行的外掛換版；U1 使用 BUILD 是對的。U2 需在每次新檔／修改事件讀入時重驗，也要讓已開啟的複習 session／待採用草稿在相關資料變成不可讀時失效，不能只在啟動驗一次。驗收：舊版開著一張卡，另一台送來最低版本更高的卡組，再按評分／套用；不得拿先前解析結果繼續寫。閘門以前的舊版做不到，只能靠兩段發布避免讓它接到新語意。
3. **衝突副本不是一律可合併。** 紀錄的相同事件可去重，不同事件保留；卡組副本卻可能同 ID、不同內容，不能取 mtime 較新者或自動配新 ID 後當作解決。備份保留雙方、顯示待處理。版本回報遇同裝置、同時間、不同 BUILD 也應顯示歧義，不選字串較大者。U3／U7 的輸入與清單要包含可見衝突副本。
4. **晚到的檔案與佔位檔不等於空資料。** 在已列出但讀不到時重試；未列出的遠端檔案無從由 Files 判斷是否存在，不能宣稱「全部裝置紀錄已齊」。驗收包含：備份成功後才到達的 iPhone 作答、歷史月份補同步、備份中新增／刪除檔案、還原後舊紀錄再同步。新到的紀錄必須仍被保留並納入重算；備份清單只承諾其捕捉範圍。尤其現有 `state/index.ts:175` 會忽略本機紀錄檔通知，還原與衝突恢復不能假設監看一定會帶回所有補行。

本輪以 Node 直接呼叫現有 `mergeHistory`、`parseLine`、`createLogWriter` 做三個記憶體反例：跨裝置 app 行合併成一筆、跳過 undo 使有效作答從 0 變 1、兩次 writer 可產生相同首筆時間。未讀寫私人 vault，未做 iCloud／iPhone 實機驗收，也未把提案描述成已實作；以上同步、備份與還原情境是後續實作的驗收要求。

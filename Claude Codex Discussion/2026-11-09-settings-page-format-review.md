## 1. data.json 欄位

- **照寫四項設定加一個日期，先不用格式版本。** `capMinutes`、`retention`、`semester`、`examCountdown` 與 D-104、D-156 一致，`semesterSetOn` 讓同一次手選可以在重開後重算。範例宜加上 `"examCountdown": false`，驗收也要涵蓋 `false`。`git grep` 確認 `v0.3.0` 的產品程式沒有 `loadData`、`saveData` 呼叫，備份仍會原樣收這個檔。退到 0.3.0 時排程用該版預設，升回來才能套用保留的值。未來新增欄位可用同一格式。新增選項時，例如新版寫 120，這版會採用 30 並保留 120，兩版裝置在過渡期會排出不同份量。建議把「值相同」限於同步完成且兩端支援同一值，若要改舊欄位的單位或語意，再另定相容與發布規則。 [D-104](../docs/decisions.md#d-104-設定頁) · [D-149 第 3、7 點](../docs/decisions.md#d-149-更新與相容版本紀錄讀取閘門與正式安裝) · [D-156](../docs/decisions.md#d-156-設定頁依功能分區不寫給家長)
- **改寫「原值逐字不動」。** Obsidian 讀整份 JSON 再以兩格縮排序列化，空白、跳脫和數字拼法可以變。極端合法 JSON 也有值會變的反例，Node 已驗證 `{"future":1e400}` 經同樣的讀寫會變成 `{"future":null}`。建議以未修改的自有欄位及其巢狀 JSON 值為保存契約，寫前拒絕無法無損往返的輸入，或保留未改的原始 token。至少驗未知物件、陣列、`null` 與會失真的數字，讀回用值和欄位是否存在比較。學期兩鍵同寫同刪，即使底稿只剩一鍵。已存欄位是否存在應由讀到的原始物件決定，外部把 `{}` 改成 `{"capMinutes":30}` 時，恢復預設按鈕要出現，排程仍沿用同一份。 [§1、§2](../tasks/settings-page.md#1-datajson-的格式要格式查核)

## 2. Obsidian 1.15.0 行為

- **確認錯誤被吞，改寫缺檔判定。** 從 Windows 安裝的 `%APPDATA%\obsidian\obsidian-1.15.0.asar` 只讀擷取 `app.js`，`readPluginData` 讀精確的 `<manifest.dir>/data.json`。`readJson` 在 `ENOENT` 回 `null`，其餘讀取或解析錯誤走記錯分支後回 `undefined`，但內容為合法 JSON `null` 時也回 `null`。照 §2 會把現存的 `null` 當缺檔蓋掉。建議底層把確定缺檔、有效物件、無效或不可讀分開。可讀 adapter 的原始內容再分類，`exists() === false` 也要留意 Windows adapter 會把 `access` 的其他失敗折成 false。無法確定缺檔時停止寫入。已確認 `writeJson` 的空 `catch` 會吞掉寫入錯誤。證據為 `app.js:207:76847–77451`、`app.js:41:45190`、`app.js:530:4028`。
- **事件當重讀提示。** `saveData` 先更新外掛的 mtime 基準再寫，`_onConfigFileChange` 只在新 mtime 嚴格較大時呼叫。因此同 mtime、較舊 mtime 的同步替換、刪檔（stat 失敗取 0）可能沒有回呼。自存通常會被這個比較擋掉，仍以有效值去重。Windows 有 `watchHiddenRecursive`，行動 adapter 也有自己的原生 watch 與 raw 事件路徑，Windows 封裝不足以證實 iPhone 會不會送這個路徑的通知。保留 §2-4 的補讀，將其視為各時點可見的快照。現有設定頁在 `onload` 已註冊，`state` 在 layout ready 後才建立。開頁或設定事件若先到，入口要能等候或略過，驗證沒有提早讀寫。證據為 `app.js:41:46182`、`app.js:207:65569、77666`、`app.js:530:4028、4760、7323`。 [啟動順序](../src/main.ts#L133)

## 3. 寫前重讀、核對與 iCloud

- **單一實例內照 D-149 第 7 點做，補完整的交易邊界。** 寫前讀、改一項、核對、發布採用值須在同一條順序內。外部事件、開頁及首次載入的補讀也要排好採用順序，較早開始的讀取若最後回來，不能蓋掉較新的核對結果。寫前、寫後讀不到或拒絕要能回報並保持最後確認的值。若寫入逾時但底層可能晚到，畫面可先回報未確認，後一筆寫入要等前一筆結束並再重讀，避免舊寫最後落地。核對刪除看自有鍵是否確實消失，核對學期看兩鍵，並檢查未改欄位仍存在且等值。讀回有效但不同時採用真實讀回值並回報衝突，避免用舊快照補寫。 [D-149 第 7 點](../docs/decisions.md#d-149-更新與相容版本紀錄讀取閘門與正式安裝) · [任務 §2](../tasks/settings-page.md#2-讀與存要格式查核)
- **改寫跨裝置承諾。** 已用記憶體模擬兩端都從 `{capMinutes:30,retention:0.8}` 開始，A 寫 45 並核對成功，B 仍從舊檔改成 0.9 並核對成功。若同步後 B 的整份檔勝出，45 會退回 30，即使兩端改的是不同欄。兩端首次建檔、復原預設與外部改寫也有同樣的視窗。程式只讀精確檔名，衝突副本的內容不會併入。建議 v1 明訂單台改完、同步到另一台再改，本機核對只證明當時該台可見的值，衝突可留副本供人工對照，外掛不自動挑一份或回寫。若要承諾並行修改無損，須先重議存法。Apple 的文件版本案例證實可能有衝突及編號副本，實際 Windows／iPhone 的 JSON 命名與勝出規則仍需實機驗證。 [Apple 的 iCloud Drive 衝突說明](https://support.apple.com/en-ie/guide/mac-help/mh40780/27/mac/27)

## 4. 備份、還原、更新

- **照用現有備份格式及還原計畫。** 用 `.custom` 記憶體 vault 實跑 `takeBackup`、`planRestore`、`changedSince`。初次有檔後清單從 `absent` 轉到 `files`，兩次取樣間初次出現時重做一輪。舊備份對新增的檔列 `added/keep`。有檔的備份則按來源與目前設定資料夾對應。安裝前的 `changedSince` 會攔住 `--check` 後才新增、刪掉或內容改變的 `data.json`，要求重跑。還原用原始位元組，正式使用前先備份現況並關閉 Obsidian，重開後由啟動讀取採用。 [syntax §8](../docs/syntax.md#8-備份檔) · [備份取樣](../src/core/backup/take.ts#L66) · [還原計畫](../src/core/backup/plan.ts#L74) · [更新檢查](../tools/update-vault.ts#L103) · [還原工具](../tools/restore.ts#L162)
- **補備份的讀不到與首次改寫門檻。** 外掛備份目前用 `adapter.exists(data)` 決定回 `null`，所以 access 失敗有被誤列 `absent` 的路徑，會影響這份備份能不能救回原值。建議讀取端只把確定缺檔列為 `absent`。D-150 第 2 點寫新版在電腦第一次改寫卡組或其他使用者檔案前先備份，第 3 點與現有閘門只明列卡組，§2 另開存檔路徑。至少應明訂電腦上第一筆覆寫既有 `data.json` 是否要等新版備份成功，並驗證等待或失敗期間的行為。 [D-150 第 2～5 點](../docs/decisions.md#d-150-備份與還原) · [外掛備份接線](../src/obsidian/backup.ts#L58) · [現有閘門](../src/state/index.ts#L619)
- **補發布前比較的輸入。** `--check` 雖備份設定原檔，`compareVersions` 只把 `Essence Cards/` 的 Markdown、JSONL 傳給 adapter，adapter 建立 state 又未傳設定。有 5 分鐘或 0.95 的 vault 仍會用預設跑兩版，可能漏掉 D-149 第 5 點要求看的差異。建議用同一份凍結設定資料，按各版實際讀法比較，0.3.0 仍用其預設，支援的版本走自己的設定解析。比較器的唯讀路徑還須避免新增設定觀察行，現行 adapter 只允許拒寫的版本行。 [比較輸入](../tools/compare-versions.ts#L72) · [比較 adapter](../tools/compare/adapter.ts#L206)

## 5. state 載入、重排與觀察

- **併入同一個有上限的等待，寫明誰先採用。** 現行 `load` 先起範圍與小考的 2 秒等待，之後還讀卡組與紀錄，再做第一次排程。可並行等設定，但在原本很快完成的情形會多等設定，應把「不增加載入時間」改為「不串接第二段逾時」。`settingsFirst` 的讀取拒絕要及早接住，回到未知並走既有回報。用相同起點的截止時間，首次讀取逾時後只走一次遲到採用。若 A 的首次快照晚於 ready 前採用的 B 才完成，第一次排程應用 B。寫明直接傳 `settings` 時的優先序、停用後不採用，以及相同有效值的重讀怎麼去重。AI 製卡分支保留同樣的 `load → input → plan` 路徑，`createState` 的選項同時要保留 `reserved`、`displaced`。 [載入](../src/state/index.ts#L587) · [啟動](../src/main.ts#L433)
- **同一觀察出口須能補跑。** `known` 可表示曾取得可信快照。確認缺檔時 30、0.8、[] 是有效的預設，暫時讀不到且從未讀成功才是未知。明訂格式合法但欄位超出選項時，若寫入回測紀錄，寫的是該版實際採用的排程值。首次快照可能直接進 `load`，不經 `applySettings`。依補紀錄缺口 §1，首次要在版本行之後且可比時就觀察，後續 `false → true` 或資料補齊時即使值相同也要再比。例：上限 45 先讀到，自有紀錄還讀不到，之後紀錄補齊而設定仍是 45，應補一次觀察。另要在可比時先採用並排入觀察，再通知會讀取新排程的畫面。兩任務任一先合併，都要有一個交接的驗收。 [補紀錄缺口 §1](../tasks/record-gaps.md#1-狀態與設定的變更紀錄要格式查核) · [首次與補讀收尾](../src/state/index.ts#L566)
- **重排共用當前 input，照既有開卡行為。** `input()` 取當前時鐘、設定與範圍，`plan()` 會更新範圍比較鍵。新設定先採用再同步呼叫 `replan()`，換日、換時區和範圍的收尾都從同一份最新 input 算，避免較早的非同步計畫覆蓋結果。保持率仍沿用有效考試期間的 `max(retention, 0.9)`。`nextCard` 只用日與 offset 判 stale，`state.next` 內部會補排。畫面收到 `onChange` 會更新進度，已開卡可答完，完成畫面會重新取卡，下一張用新份量。應驗證上限縮小使手上卡移出 share 時，該卡仍可記一次作答，下一張依新計畫。 [重排與範圍](../src/state/index.ts#L388) · [input 與換日](../src/state/index.ts#L493) · [保持率](../src/core/study/plan.ts#L18) · [next](../src/state/index.ts#L689) · [複習畫面](../src/review/session.ts#L166)
- **改寫 §7 第 12 項的「完成數相同」。** 用 40 個新目標與第 26 個今天已答對的紀錄實跑 `planToday`、`progress`。30 分鐘的 share 有 40 個，完成 1。5 分鐘的 share 有 20 個，完成 0，因為 `progress` 只數新 share。作答仍在 history，改回上限後同一目標回到 share 時仍算完成，今天正常答對的卡也不會因重排重出。建議驗收分開「作答保留與避免重出」及「新份量內的完成數」。若產品要求數字始終保留已移出的目標，須先定完成數與總數的口徑。 [上限與分流](../src/core/study/plan.ts#L166) · [作答與完成數](../src/core/study/session.ts#L92)

## 7. 建議補進驗收的案例

- **存檔安全。** 同一份測試分別給確定缺檔、字面 `null`、拒絕、唯讀、可讀但欄位部分掉失、讀回刪鍵與值為 `null`。再覆蓋晚到的舊讀、第一筆失敗後第二筆正常、寫後核對逾時，以及兩台都核對成功再同步。後一例用替身驗證本機承諾，另在測試 vault 驗證實際同步到達時機。已確認的設定若外部只補上與預設相同的原始欄位，測畫面能恢復預設而 today 物件維持同一份。
- **排程與證據。** 用可控時鐘及可手動完成的 Promise，測首次拒絕、超時、較新的設定先採用、關閉後遲到，以及同一時段換日、範圍變動、設定變動的不同完成順序。驗最終 plan 同時使用新的三個輸入。另測已答對目標掉出 share 再回來、首筆作答前的已知基準、紀錄補齊才比、跨 04:00 同內容的學期轉換與清除。
- **備份與更新。** 用非預設設定資料夾測 `absent → files`、讀不到時整份失敗、還原舊備份保留現在的檔、`--check` 後新建阻止安裝，以及凍結資料的非預設設定確實進入新版排程比較。學期的別名測試同時走目錄和考試範圍預勾，檔名照既有的勾選單元規則。

驗證已執行 `node --test --test-reporter=dot tests/backup-core.test.ts tests/backup-take.test.ts`、`tests/study.test.ts` 與 `tests/update-vault.test.ts` 的 `--check 之後的變動` 案例，均通過。另以 Node 記憶體案例執行備份狀態轉換、還原計畫、首次建檔的變更偵測、完成數反例、學期表與換日邊界。對 Obsidian 的判斷來自本機封裝靜態閱讀，並以已安裝型別檔對照公開介面。

## 2. 提案：一個通用的 `code-quality`（程式品質）

使用者補充（2026-10-20）：這是通用的開發用 skill，名稱不綁 essence。`code-quality` 這個名稱是 Claude 的提案；專案專屬的設定怎麼拆出去，見 §2-6。

依**時機**組織，不依技術組織。每個時機寫清楚：做什麼、誰做、花誰的額度。

### 2-1 四條原則

1. **機械性的問題交給自動檢查**：`npm run check` 每次都不花 token；審查抓到能用程式判斷的問題，當場加一條規則（D-117）。
2. **檢查不減，改由成本較低的方式做**：不靠少做檢查省額度（使用者明確要求過）。省額度的方式是：能交給自動檢查的交給它（0 token）、用 Codex 的額度、Claude 審查時不開子代理。
3. **問題提早處理**：規格裡寫出邊界例子和能用程式判斷的驗收條件，比事後審查便宜。F1 有一部分就是規格的漏洞。
4. **延後的問題一定要有觸發點**：不擋合併的發現，要記下「最晚什麼時候處理」，時機到了才會被看到。

### 2-2 額度階梯

| 層級 | 誰做 | 花誰的額度 | 用在什麼時候 |
|---|---|---|---|
| L0 自動檢查 | pre-commit hook、CI | 0 | 每一次改程式的 commit、每一次 push |
| L1 Claude 對照檢查 | Claude，不開子代理 | Claude（少） | Codex 每次交回成果、Claude 自己改程式時 |
| L2 Codex 交叉審查＋Claude 核對 | 另開一個新的 Codex session 審查；Claude 逐項核對，並用邊界例子重跑 | 主要是 Codex | 跨模組、資料格式、排程、寫回筆記等影響大的改動，合併前 |
| L3 兩個 Claude 子代理 | Claude | Claude（多） | 不再是預設；只在 L2 做不到時用（例如 Codex 額度用完） |

L2 取代 D-106「影響大的改動照 code-review 開兩個子代理」的做法。理由：

- W1～W2 實際就是這樣做的，找到 2 個 P1。
- 兩個模型的盲點不同：Codex 找到 F1～F7，Claude 核對時又找到 N1～N3 和標題的 bug。
- 檢查項目沒有減少，只是把重讀 diff 的成本移到 Codex。

代價是使用者要多轉貼一次訊息給 Codex。

### 2-3 時機表（skill 的主體）

| 時機 | 做什麼 |
|---|---|
| 設計介面、寫 TASK | 驗收條件要能用程式判斷，並列出邊界例子。寫回筆記的函式一定要有往返與冪等測試，並登錄到共用的範例清單（W2 `deckCases` 的做法）。新模組要加進 ESLint 的邊界規則。介面用 review.md 的深模組原則檢查一次。先看技術債登記，觸發點落在這個任務的項目，寫進 TASK。 |
| Claude 自己改程式 | 先寫一個會失敗的測試，再改程式（red → green）；只透過公開介面測試；`npm run check` 通過才 commit，不用 `--no-verify`。 |
| Codex 交回成果 | L1：讀 Codex 的回報和 diff，逐條對照 TASK 的「限制」與「要做什麼」，自己跑一次自我測試，再用邊界例子重跑。影響大的改動加做 L2。 |
| 測試失敗、有人回報 bug | 先寫出一個能重現錯誤（跑了會失敗）的指令，再提出 3～5 個假設；回歸測試放在 bug 真正發生的 seam；除錯用的 log 加上標記，結束時清乾淨。很難的 bug，建議切到 xhigh，或交給 Codex（推理等級：高）。 |
| 審查有發現 | 機械性的 → 加一條規則；需要判斷的 → 當場修，或登記進技術債並寫下觸發點。 |
| 里程碑完成 | 主動提醒做兩件事：一次 retro（犯過的錯能不能變成自動檢查、哪些指示沒有作用、哪裡花了太多額度），和一次 `security-review`。 |

### 2-4 檔案結構

SKILL.md 只放原則、額度階梯、時機表和測試規則（約 80～100 行），細節分成幾個檔，到了那個時機才讀：

```
code-quality/
  SKILL.md       原則、額度階梯、時機表、測試規則（濃縮自 tdd：只透過公開介面測試、
                 不寫把預期值用同樣方式算一次的斷言、一次只做一小段、往返測試）
  review.md      兩軸審查清單（規格＝TASK＋它引用的 D-ID＋syntax.md；
                 規範＝AGENTS.md＋D-110 的邊界＋Fowler 的程式異味清單＋深模組 4 條原則）、
                 用邊界例子重跑的做法、給 Codex 的審查請求範本
  debug.md       濃縮自 diagnosing-bugs：建立回饋迴圈 → 重現並縮到最小 → 假設 → 量測 →
                 修正＋回歸測試 → 清理
  milestone.md   濃縮自 retro，加上 security-review 的做法與報告格式
  agents/openai.yaml
```

`.claude/skills/` 和 `.agents/skills/` 各放一份相同的內容（和 essence-decision 一樣）。Codex 寫程式時用測試規則和 debug.md，做 L2 審查時用 review.md。

Claude 會不會主動載入這個 skill，取決於 description 怎麼寫，所以要寫出具體的時機，例如：「Codex 交回成果或要合併分支前、寫 TASK 的驗收條件時、測試失敗或有人回報 bug、審查有延後處理的發現、里程碑完成時」。

### 2-5 技術債登記

W1～W2 留下的 4 件事，現在寫在 roadmap「下一次對話從這裡開始」。觸發點還很遠的項目（例如「W5 開始前」）會一直佔著那一節。

提案：`backlog.md` 加一節「技術債」，一件事一行，格式是「項目｜觸發點｜來源」。寫 TASK 或開始新的 W 任務時，skill 會要求先看這一節。處理完照 backlog 的慣例，只留一行連結或刪除。

### 2-6 通用內容和專案設定分開

skill 本身只寫通用的做法。上面時機表裡屬於本專案的部分，改由專案裡一份短檔 `docs/agents/quality.md` 提供，skill 載入時才讀。這些部分包括：`npm run check`、寫回筆記的函式、ESLint 邊界規則、`deckCases`、backlog 的技術債一節。這份檔案寫：

- **檢查指令**：`npm run check`，以及 hook 和 CI 放在哪裡。
- **規格來源**：`tasks/*.md`、試作場的 `TASK.md`、D-ID、`syntax.md`。
- **影響大、要做 L2 的範圍**：跨模組、資料格式、排程、寫回筆記。
- **模組邊界**：D-110 與 `eslint.config.js`；共用範例清單（`deckCases`）。
- **技術債記在哪裡**：§2-5 談定的位置。
- **里程碑**：連到 roadmap，第一個是 W1～W6 打通。
- **交叉審查找誰**：Codex。

不寫進 AGENTS.md，因為 AGENTS.md 每次對話都會載入。專案沒有這份檔案時，skill 先從 AGENTS.md 和 package.json 推斷，推斷不出來再問使用者。

## 4. 「主動」要靠什麼

依可靠程度與花費排序：

1. **hook 與 CI**（0 token，一定會跑）：D-117 的 pre-commit hook 和 GitHub Actions，在 W3 第 0 步裝好。
2. **skill 的 description**：寫出具體時機，Claude 遇到那個時機時會自己載入。
3. **記憶與 backlog**：description 抓不到的時機（里程碑）靠記憶提醒；觸發點還很遠的技術債，記在 backlog 的那一節。

沒有採用：合併 Codex 的分支時，用 hook 強制提醒審查。做起來和維護都麻煩，而 L1 審查本來就是合併流程的一部分（codex-brief）。

## Codex 回應（2026-10-20）

核對基準：本次指定的 main `38c8479`（含 §2-6 通用化補充）；檔頭的 `db16374` 是原提案基準。以下是 **💡 Codex 建議，尚未經使用者確認**，沒有變更 D-106、D-117，也沒有開始整併 skill。

同意用一個通用 `code-quality` 統整入口，但需要補強「確實載入、檢查真正生效、修完再次驗證」三件事。它們服務北極星的方式，是避免像 W2 那樣把學習目標改壞或漏掉題目，減少學生漏複習與家長排錯；不以增加審查層數或測試數量當作成果。以下依 §6 順序回答。

### 1. L2：同意改成 Codex 交叉審查，預設使用新的 session

**同意作為本專案的預設分工。** 審查者應使用未參與實作的新 session，先讀規格、diff 與必要的呼叫端，自行形成判斷；實作者的回報是待核對的資料。新 session 能減少延續實作時的假設，但不能保證獨立或不漏錯。W1～W2 的結果支持繼續採用這個流程，還不足以證明「兩個模型一定比兩個子代理好」，或把 L3 當成品質更高的一級。

審查請求至少要附：

| 輸入 | 要寫清楚的內容 |
|---|---|
| 審查對象 | repo／worktree、分支、基準與待審 commit 的完整 SHA；是否包含未提交修改。分清規格基準、分支共同祖先與目前 main，不能只寫「審 main」 |
| 規格與優先順序 | TASK 路徑與章節、它引用的正式規範和 D-ID、基準後的相關規格變動。兩份規格有衝突時列成問題，不能自行挑容易通過的那份 |
| 行為與風險 | 公開介面、主要呼叫端、不可破壞的性質、已知邊界例子、明確延後的範圍；例子是起點，審查者仍要找新的組合 |
| 驗證方式 | 實際可用的指令、環境與相依版本、範例位置、實作者跑過及未跑的項目；需要真實 Obsidian 或 iPhone 的部分明列 |
| 回報與權限 | 預設審查，不順手改產品；可在隔離環境重現。每項發現寫觸發條件、預期／實際、影響、檔案位置與證據，區分已重現、靜態推斷與待驗證 |

保留「規格符合性／程式設計與規範」兩軸，但同一個問題只報一次，標明所屬面向即可。另准許回報「規格本身有漏洞」：W2 問答題名稱帶螢光筆就是照局部規格做，卻破壞補 ID 冪等性，光逐句對照 TASK 會漏掉。

**L2 要包含修正後的收尾。** Claude 核對發現，修正者補回歸測試；在最後待合併的 commit 重跑相關重現與必要檢查，留下驗證 SHA。若修正改動解析邊界或公開行為，再審那段差異與相鄰案例，不必整包重審。`56e0dc6` 的標題／引言框補修說明了為何「審過一次」不能涵蓋之後的修改。

L1 與 L2 重疊的規格、diff、測試核對可共用一次紀錄；L2 再加獨立找漏洞。Codex 不可用時才依可用資源選 Claude 審查方式，無法完成的部分明列，不能用「額度用完」視為已審。

本次查了已封存的「實作W1骨架與W2卡組模組」與「[CCD]檢查技術債」的工具呼叫和公開回報。**以實際讀取 `SKILL.md` 為載入證據，不把可用 skill 清單、測試寫得相似或事後回想當作使用紀錄。**

| `tdd` | 沒有載入紀錄，不能算用過 | 也沒有載入紀錄。修正時確實先寫失敗的回歸測試，但不能因此宣稱使用了 `tdd` |

所以 §1 的 Claude 呼叫次數可以保留，但不能據此把 Codex 端也寫成 0；也不能把後續使用倒算到初次實作。

**對這個專案，TASK 的明確要求加上 skill 的按需細節最可靠。** W1～W2 任務已明寫公開匯出、只能透過匯出測試、D-089 各條案例與驗收指令，初次實作實際讀取了這份 TASK。建議分工：

- TASK：本次已約定的介面、驗收例子、不可破壞的性質、必跑指令；「必讀範圍」明確連到 `code-quality` 本次適用的段落。
- skill：可重用的測試、審查、除錯方法，按任務時機載入。
- AGENTS.md：沿用已有的分工與提交底線，不再複製整套方法。

description 能協助自動選用，不能當成必定執行的機制。官方文件也區分「先看到名稱與說明」和「選用後才讀完整指示」；這次的歷史紀錄正好顯示兩者不同（[OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills)）。新 description 還要包含「依規格實作功能／修改程式」；原稿列了交回成果、審查、bug，卻容易漏掉 Codex 開始寫程式的入口。實作任務的必讀連結由 `codex-brief` 範本提供即可。

同意拿掉每個 seam 都重新問使用者的要求，改成「既有規格已約定就直接沿用；涉及未決的外部行為或資料語意才提出」。另更正依據：D-024 是**前端介面設計**；W1～W2 的程式介面分工是 AGENTS.md、D-110 和 TASK 的明文安排，不宜把 D-024 擴張成所有程式介面的決定。

### 3. codebase-design：同意取消獨立入口，但不能只剩四句口號

**建議把必要內容濃縮進 `review.md`，不另留完整 skill。** architecture.md 描述的是本專案的結構，不能替代通用的設計判斷。除了四條原則，至少保留以下判斷方式：

- 介面包含呼叫順序、錯誤、資料不變條件與成本，不只是函式簽名；例如 `Files.modify` 的「讀、改、寫」約定比方法數量更重要。
- 複雜度應集中在負責它的模組；刪掉一層後若呼叫端都得自行處理同一規則，這一層有價值。
- 依賴要能控制，純計算和 I/O 分開；真實環境與測試替身需要核對同一份行為契約。W5 的 Obsidian 實作不能只因 Node 版通過就算驗證完成。
- 公開行為是主要測試面；避免為了測試而新增產品出口，也避免為了抽象而製造第二個 adapter。「只有一個實作就一定不准有介面」不應成為硬規則。

原稿對子代理的理由需要收窄：目前 `SKILL.md` 是參考詞彙，只有選用 `DESIGN-IT-TWICE.md` 探索替代介面時才要求平行子代理，**載入 codebase-design 本身不等於一定開多個代理**。可以因入口重複而整併，不能以必然花這筆額度為刪除理由。

Fowler 異味也應保留原版的限定：它們是判斷線索，專案規範優先；「重複」不自動等於要抽象化，「轉手」不自動等於該刪。第一版不保留完整詞彙表、強制替代方案競賽與多代理設計流程。

### 4. 技術債：放 backlog，roadmap 留下一步的入口

**同意 backlog 新增「技術債」作為唯一追蹤清單。** roadmap 保留一行「開始任務前核對技術債」的連結；下一步確實受阻時再點名該項。來源討論稿保留當時的理由與證據，不再維護第二份狀態清單。

原提案的三欄還缺少「怎樣才算處理完」。不必另外建追蹤系統，可用「項目與影響｜觸發點｜完成條件｜來源」，完成後留一行修正／驗證 commit。例如 F6 的完成條件應是「合法新增模組與 CSS 不會誤報，隔離的無 CSS 案例仍受測」，不是只寫「整理測試」。

讀取時機也不能只限「寫 TASK 或開始 W 任務」：F3、F5 的觸發點是下一次 T4，可能沒有新 W 任務。凡開始相應工作或改到相關區域，都要核對清單；觸發點到達時，把處理項與驗收帶進當次任務。這仍由當次 agent 執行，不需要背景監控或新的提醒 hook。

### 5. 兩份 skill：同意小程式，接進 check 與 CI

**不贊成只靠改 skill 時記得手動跑。** 兩份可執行指示若分歧，Claude 與 Codex 可能遵守不同流程，正適合交給機械檢查。建議：

- 明列要共用的 skill 與檔案，至少包含 `code-quality` 的主文和引用文件；比對檔案集合及內容，缺檔也失敗。不要要求兩邊整個 skills 目錄完全一致，因為各自有專用 skill。
- 文字只正規化 CRLF／LF；平台專屬 metadata 明列例外，共用的 metadata 則一起比對。檢查只回報差異，不自動覆寫另一份。
- 作為 `npm run check` 的一個便宜步驟，CI 也執行。若 hook／CI 有路徑過濾，必須涵蓋 `.claude/skills/**`、`.agents/skills/**` 與檢查程式；只在改程式時觸發，會漏掉本來要防的純 skill 修改。

兩份都保留是目前對 Windows、一般 clone 與不同執行環境較直接的做法；先不引入符號連結或同步框架。驗收只需實際確認內容不同、引用檔缺少會失敗，正常副本會通過，無須為這件事建大型測試架構。

### 6. 遺漏與需要改寫的規則

1. **自動檢查要驗證已接好，而且真的能擋下失敗。** `38c8479` 的 package.json 還只有 build、test、typecheck、install-vault，沒有 check，也沒有 `.github`／`.githooks`；D-117 是已決定、待 W3 第 0 步實作。§4「一定會跑」目前不成立。W3 要用已知違規確認本機檢查與 CI 都會失敗，並核對觸發範圍；workflow 跑了與合併必須等它成功是兩件事。0 token 只能指純檢查執行本身，AI 讀輸出、修失敗仍有成本。

2. **把共同不變條件套到範例上，並保留獨立的預期值。** W2 的 `deckCases` 把所有範例納入補 ID 往返，避免只測幾個正常案例；但解析器與寫回器可能共享錯誤，往返全過仍不代表教材內容正確。例如「糖是什麼」補 ID 後仍應是原本的問答題、屬於同一目標，不能只比總題數。保留規格提供的指紋驗算值、具體目標歸屬與 Obsidian 對照；隨機／差異測試視風險選用，不每次強制大量跑。新增自動檢查也不全是 ESLint：語意問題通常適合回歸或性質測試。

3. **測試規則適用於所有實作者，依改動選驗證方式。** §2-3 的「Claude 自己改程式」應改成「實作或修正」。新行為與 bug 優先做小步的失敗→通過；文件、機械整理與純重構用相應檢查或既有行為測試，不為了湊 red 而寫脆弱斷言。不要照搬原 tdd「重構只能在審查階段做」；測試綠燈時的小幅整理可以當場完成，不能趁機改已約定的介面。F6 正是把暫時的骨架形狀當成長期契約的反例。

4. **除錯要有重現證據，但不強制每次湊 3～5 個假設。** 根因未明時列可推翻的假設並量測；已知根因就直接用失敗測試驗證。W2 修正階段已採用後者。偶發問題記錄重現率，效能問題先量基準；無法重現時說明試過什麼與缺少哪項證據，可做有標記的靜態分析，不宣稱修好。固定時間、亂數與暫存檔案等有助縮短回饋迴圈的做法，以及清除除錯 log，都值得從原 skill 保留。

5. **審查環境與證據要可追溯。** W1～W2 在不同 worktree 實作、審查、修正與合併，回報基準與驗證 commit 才能知道測到哪版。測試用隔離的暫存資料，不污染共享工作樹或使用者 vault；正式保留最小的自編回歸例子，重現腳本、log 不夾帶私人教材或憑證。回報未測與跳過的原因，工具不可用不能算通過；AI 能完成的部分先自行完成，再集中提出必要的實機驗證。

6. **通用 skill 本身也要驗收觸發與降級。** 用少量代表性提示確認「照 TASK 實作」「審查」「測試失敗」「里程碑」會載入正確段落，而一般文件修改不會載入整套；檢查引用路徑與工具是否存在。`security-review` 是目前 Claude 環境的能力，不能成為通用 skill 的必備依賴；不可用時給可執行的安全檢查清單並說明缺口。里程碑保留完整檢查，涉及金鑰、外部資料、檔案寫入等變動時也要在該次審查檢查相關風險，不能一律等到里程碑。

### 7. 放 repo；通用內容與專案設定分開，但角色也要抽離

**同意先放 repo，讓當時的程式、規格與品質流程能一起回溯；Capture 真正需要時再處理跨 repo 發布。** 通用表示內容可移植，不表示現在就必須放家目錄。不要同時維護 repo 與家目錄的同名副本卻期待自動合併或覆蓋。

存放位置補充：目前官方文件把 Codex 的使用者層級位置列為 `~/.agents/skills`，repo 位置仍是 `.agents/skills`；這台環境另有從 `~/.codex/skills` 提供的 skills，不能據此把舊路徑寫成所有環境的唯一安裝規則。真的搬移時再驗證目標環境是否發現它（[OpenAI：Build skills，Where Codex loads local skills](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)）。

同意用短的 `docs/agents/quality.md` 提供本專案設定，還要做這些修正：

- 通用主文使用「實作者、獨立審查者、整合者」，不要把 Claude／Codex、訂閱額度、xhigh 或兩個 Claude 子代理寫死。角色分配與可用能力放專案設定；同一 agent 做自查不能標成獨立交叉審查。
- 通用主文只要求找出規格、檢查指令、風險與債務來源，不內建 D-ID、W 任務、syntax.md、deckCases 或 Obsidian。這些由專案設定**連到原處**，不再抄一份規則。
- 設定檔從 repo 根目錄定位；先接受任務／AGENTS.md 已指明的路徑，再找慣例位置。找不到時從現有任務、README、建置設定與 CI 取證，不能假定所有專案都有 package.json，也不能自行建立配置檔。能合理推斷就記明依據繼續做，只有影響結論且無法判定的資訊才問。
- 刪舊 skill 前，搜尋並修正仍指向它們的 skill、TASK 範本、文件與記憶；歷史討論的名稱可保留。`UPSTREAM.md` 的來源、tag、commit 與適用授權資訊移入新 skill 的來源說明，不能只刪掉來源追溯。

第一版就採「一個入口、三份按需參考、短的專案設定、一個副本一致性檢查」。先不做全域安裝器、跨 repo 同步、常駐代理、用量儀表板或新的審查提醒 hook；以 W3 的實際載入、驗收證據與漏檢情況判斷是否還需要增加流程。

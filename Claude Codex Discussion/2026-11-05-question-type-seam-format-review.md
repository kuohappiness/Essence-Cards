## F1　辨認組名須先定分隔與括號文法（§3，開工前）

**觸發、預期與提案結果（規格推斷，真實手寫與製卡都會遇到）**

| 輸入或條件 | 預期及提案留下的問題 |
|---|---|
| `詞（意思） 字形`、`節（節日） 字義`、`寨（山寨） 字形` | 一般目標。將無分隔的括號切字會把「山寨」誤解成兩個選項，遇到恰好有挖空、答案為寨就會換題型。反過來，不切字會使漏寫分隔的 `寨（寨塞寒賽） 相似字` 降為一般目標。若靠「相似字」補救，改成 `寨（寨塞寒賽） 相似宇` 又漏認，且仍無法分辨括號內是真正的詞或一串字。 |
| `寨(寨、塞） 比較`、`寨（寨,塞）` | 可容忍左右括號寬度混用及標題空白；括號要成對，不收缺右括號或巢狀組。提案只列同寬範例，需補測。 |

| `light（輕的）（light、lit） 比較` | 提案只看第一個括號，會漏認。建議允許組前有無分隔符號的成對義項，接著取第一個具清單形狀的括號，以前綴的基本詞比對成員；這組認成 light／lit。第一個清單形狀的括號若無效，勿略過再去掃標題裡的括號。只有 `light（輕的）` 或 `節（節日）` 仍一般。保留義項在原目標名稱。 |
| `**寨**（寨、塞）`、`==寨==（寨、塞）`、`𠮷（𠮷、吉）` | 前者可只去掉成對的外層粗體後比對。螢光筆現行語法會先把這一行當隱式填空，不能靠辨認器剝 `==` 解決，應在草稿提示改用無格式或粗體名稱。造字直接以完整項目比對，不切 UTF-16；補代理對與變體選擇符範例。 |
| `寨 ^abc222（寨、塞） 比較`、`寨（寨、塞） 山＿＿ :: 寨` | 比對已移掉 ID 的 `target.name`，遇到身分衝突照舊停用。頂層直寫的第二例是隱式問答，補 ID 會把題目衍生為名稱；若名稱偵測接受「括號後任意字串」，補 ID 前後可能換題型。建議明訂隱式題照原題型，且比較卡須有明確的名稱與縮排題。語法要避免補 ID 後把帶空格標記的衍生名稱解作比較標題，驗收要比補 ID 前後。 |
| `borrow（borrow、lend） 中翻英`、`borrow（borrow、lend）　中翻英` | 第一例保留打字與英文配對規則，英翻中同理。第二例目前不認方向。若比較辨認先折疊全形空白，但排除條件仍沿用舊方向欄位，第二例會變成比較卡。建議兩種寬度都保留給方向語法，暫不擴張方向解析時，第二例維持一般卡並提示改用半形空格。這兩個既有保留詞是 D-182 第 4 點的邊界，應寫明。 |

**結論**：保留有分隔才辨認、結尾作標題的寫法。漏掉分隔時，草稿檢查指出如何補；外掛對帶比較意圖線索的手寫稿給提示。這同時保留了 D-178 已確認的頓號寫法和 D-182 的標題容錯，也不從無分隔的內容猜字界。格式無法區分完全同形的兩種意圖，例如普通問答也恰好叫 `台北（台北、高雄） 首都`、題目 `＿＿是台灣的首都。 :: 台北`。這會認成比較卡，需文件說明一般卡的改寫方式（例如把補註移到背面），並讓作者在編輯或預覽看得出辨認結果。

## F2　先判斷目標意圖與題目形狀，再分類錯誤（§3，開工前）

**觸發與實際（規格推斷）**：§3 先要求所有題目符合才辨認，接著又說「認得以後」才拒絕組內別字。若一題是 `水管＿＿住。 :: 塞`，另一題有兩格或答案在組外，規格沒說哪個分支優先；兩種順序會讓同一個目標停用或整個降成翻面。只有一題、沒有空格的普通 `台灣的首都？ :: 台北` 則應照一般卡，若只憑組名就報錯會擋掉真實的普通卡。

建議在任務說明列一張有優先序的決策表，由解析器和草稿檢查共用分類結果：

| 觸發條件 | 建議結果 |
|---|---|
| 明確目標有有效組名，至少一題是單一可呈現空格的問答，且單行答案等於名稱詞或組內別詞 | 進入比較題檢查。每題都須符合、且答案等於本目標詞才出比較卡。組內別詞用 `pick-answer-invalid`，以該題為定位，停用該目標；也適用於其他題同時有問題的情況，避免把塞的成績記到寨（D-114）。 |

單題形狀以實際會畫出的空格為準。連續的 `＿`（一個或多個）算一格；`＿ ＿` 算兩格並提示合在一起，除非解析及畫面同時明訂容忍這種間隔。半形 `__` 可能是 Markdown，當未寫比較空格並給修法。只在可見題幹計數，排除圖片網址、連結目的地、程式碼及公式；例如題幹只有 `![圖](圖＿片.png)` 的底線不會成為空格。現在 `src/review/english.ts:8` 的 `BLANK` 找第一個連續片段，`src/ui/rendered.ts:90–114` 在渲染後的文字節點找。若比較辨認只在原始 Markdown 數 regex，兩者會分歧。答案接受 `**寨**`、`==寨==`、前後空白；`寨。` 保留標點，與 `寨` 不等價。真正有兩行答案應判不符。現行解析把只有一個子項目的答案組成單行 `寨`（已重現），建議照結果接受；如要限制為 `::` 同行寫，須在解析時保留原結構，另列語法規則。

**已重現**：基準的 `check-syntax` 對標準比較稿、漏分隔、沒空格及答案換成別的組員回傳相同的既有一般提示，沒有比較專用診斷。§10 的新增「不符」即使實作，命令目前也只因「錯誤」設定失敗退出碼（`experiments/t4/check-syntax.mjs:408–416`）。要讓 AI 交稿前真的擋住，驗收須指定呼叫端檢查「不符」並退回，或提供對應的嚴格模式。手寫直接存檔仍須產品提示。D-158 的空白容忍適用到詞的比對，挖空本身的 Markdown 邊界另外明訂。

### R2-2　明確分隔的組仍會拆壞詞（F1、F6，開工前）

**依 §3 試算，實際輸入可達。** `一般型（一般型、A 型、B 型） 比較` 搭配 `這件依常態歸為＿＿。 :: 一般型`，預期三個字鍵，提案切成 `一般型、A、型、B` 後仍認得且出錯字鍵。若同組另一個目標叫 `A 型（一般型、A 型、B 型） 比較`，又因名稱詞不在拆出的組裡而漏認。英中相鄰的空白是詞的一部分。中文也有相同情況，例如手寫稿用空格標詞界的 `一般型（一般型、特 殊 型） 比較`，會認成「一般型、特、殊、型」。影響是選項及組身分改變，若主要目標的詞未被切開，這種錯不一定被提示。沒有在現有公開樣本發現這兩類寫法，屬可構造的真實科目寫法與手寫邊界。

- 家長刪除標記或由舊快照覆蓋時，舊版無法判斷曾被標記。新版若只等下次寫入，也會有同一窗口。「只加不拿掉」只能約束外掛自己。

**開工條件。** D-191 第 1 點要擋的是會被舊版讀錯的比較卡組。若要採單版發布，受 Cards 控制的建立、採用或轉換入口必須在同一次首次寫入就帶標記，或先將標記寫入且確認，再發布比較題。任意 Markdown 手寫與外部同步無法由舊 reader 推導標記，須明定手寫流程先標記後改題，或只在已確認所有仍使用的裝置都具比較讀取能力後啟用手寫。對新版自己讀到缺標記的比較卡組，可明定先提示補標記、何時才開放正式複習；這能讓家長看見未完成，不能補救已流到舊裝置的未標記稿。把「帶標記才會擋」與手寫、同步的剩餘窗口寫成驗收，不能用 `assignIds` 冪等代替。

**授權邊界。** `fillIds` 是 D-134 確認的補 ID 備援，並未授權對舊筆記加版本屬性。§3 的自動離開寫入，對既有筆記會改變其跨裝置可讀性，與 D-149 第 7 點的「按按鈕、先看會改什麼、先有成功備份、改完記一行變更」有差距。現行路徑只具備份與非載入兩項。建議既有卡組用明確顯示將標記並影響舊裝置的存檔／轉換動作；若要把自動離開納入，請先把例外和變更紀錄的處置交使用者確認。§10 現在把離開自動加標記寫成驗收，應等此決定。

### R3-2　標記需和 ID 一起準備，也要一起核對

**已重現兩個反例。**

1. 合法 frontmatter 可以是單行 flow mapping，例如 `{科目: 國語, 自訂: 留著}`。基準讀得出「國語」；直接在其下一行、結束線前插入 `需要版本: 0.4.0` 後，`parseDeck` 回 `need:false` 和 `unknown-property-value`，新版也會擋自己。另有較舊的值用引號、YAML 別名或 block scalar 表示，不能靠正則尋找固定的 `需要版本:` 行。若舊值帶錨點且其他屬性引用它，只改錨點值也會改變其他屬性的讀值。
2. 現有 `confirmed` 只驗 ID／名稱。準備結果只有加標記時，`expect:[]`；把不含標記的原文當核對讀取結果，實跑 `confirmed` 回 **0（成功）**。有配 ID 時，若同步副本保留 ID 卻沒有標記，也能假成功。`writes.verified` 此後會以預期輸出呼叫 `tracker.wrote` 並回 `done`。位置見 `src/state/ids.ts:59–76`、`src/state/writes.ts` 的 `verified`。這是寫入端實作前即可確認的核對缺口，並非已上線的標記故障。

**預期契約。** 先辨認有無 frontmatter，再判斷能否做局部編輯；一般 block map 保留註解、未知鍵、引號以外的其他原字、BOM 與原換行，沒有屬性區就建立。合法但不支援局部改寫的形狀（例如前述共享錨點），或沒有標記且 YAML 已壞，須回可見的「標記未完成」及修法，不能以普通補 ID 成功收尾。讀到壞標記或比自己新的標記時，既有 §0-1 閘門保持原樣。不要重新序列化整個 YAML；準備後重跑解析，核對有效標記、其他屬性及預期 ID。核對讀取應接受相同有效版號，或仍在本版能力內且足以保護的較高值；標記消失、降低、寫壞時按 `stale` 或「未完成」處理，勿採用假成功。加測 marker-only、修改 ID＋標記、以及寫後只失去標記的情況。

**入口與行號。** `tracker.fill`、`resolve(..., 'new')` 最後會經 `assignIds`，但 `resolve(..., 'restore')` 直接走 `setTargetId`，只在 `assignIds` 新增選項會漏掉還原。建議共用準備最後一步，讓三個入口都能對**最終正文**決定需不需要標記，並把預期標記交給核對。先用原文行號做 `skip`；做完補 ID 再插屬性時，`assigned[].line`、預期定位及用於挑本次還原目標的行號必須在同一座標。現有 `resolve('new')` 用「新文的行」跟「原文的行」比較距離，若提前插三行，兩個同名目標可能挑錯 ID。採最後一步插入或一併換算，測有同名目標與前方隱式題新增行。寫入門檻、核對及實際輸出的相對順序見 `src/state/index.ts:565–578、592–603`、`src/state/ids.ts:283–290、359–401`。現有 Cards 產品內的卡組改寫集中於 `writes`，一般 Obsidian 編輯、外部檔案與同步不經這層。

### R3-3　版號要標示讀取能力，發版順序比升版時機重要

**已驗現行工具契約。** `tools/install.ts:82–99、187–195` 要求正式安裝時 HEAD 正好是 `v<manifest.version>`、工作樹乾淨、package 與 manifest 同版、實際產物 banner 對到該 commit。合併時升版、日後在含比較 reader 的發行 commit 打 tag，這些檢查可以成立。開發／測試版從目前 manifest 取版號，只能裝在已登錄的測試 vault；預覽仍由該建置版本的 State 決定。`tools/update-vault.ts:142、170、181–202` 的正式更新受 tag 檢查與正式安裝流程約束；退回使用已存產物並檢查資料的最低版（`tools/install.ts:137–173`），不靠當前 manifest 猜舊版能力。

**關鍵反例。** 用 `v0.3.0` 的同一份 State 只把 BUILD 前綴換成 `0.4.1`，它就放行 `需要版本: 0.4.0`，`abc222` 進今天的份。這是模擬「另一個不含比較 reader 的分支先用到同版或更高版號」；沒有真的發布該建置。工具只驗 tag、版本與 commit 一致，沒有核對該 commit 是否真的含 reader。單查本地最新 tag 無法保證這個前提。合併時升版可行，條件是從 canonical 發行線保留該版號，任何同版或更高版的正式產物都必須繼承 reader。若別的分支要先發，須在寫入端可用前重訂 `PICK_NEEDS` 或先合併 reader，禁止已寫出去後才換數字。

**與發布才升版比較。** 保留版號到發布、用 `canRead` 擋寫，可避免合併後的未發行開發建置提早寫正式標記，但同樣不能容許其他較高版號缺 reader。若發布順序未能鎖定，這條路更容易保住正式資料契約；開發端用明確標為測試、帶候選正式版號的建置驗寫入，並在實際發行 commit 驗 reader、writer 與版本一致。只測 `canRead(PICK_NEEDS, releaseOf(BUILD))` 是數字檢查，應另用有標記的卡組驗該 build 確實出比較卡。未知 BUILD 的測試／State 預設值不可開寫入。現行兩段發布仍是 D-149 的規則，D-191 第 4 點明標提案，syntax §0-1 第 59 行卻已寫成同版發布；請待使用者確認，並一併說明 R3-1 的手寫窗口。

**發布比較。** 轉接器採各 commit 的 manifest 版號、`fillIds:false`，不應觸發寫入，見 `tools/compare-versions.ts:45–56`、`tools/compare/adapter.ts:196–227`。至少比較兩份凍結輸入：無標記普通卡應無差異；有標記的混合卡組應是舊版整篇擋、新版出比較、其他篇照常。未標記的比較稿則是檢查政策的獨立案例。現有快照取方向、單張題目和閘門，不能單憑新版卡組出現在清單證明是比較點選，另以新版公開取卡介面驗題型。

### R3-4　單時鐘解掉批內停頓，1ms 仍可能誤併兩張卡

**已重跑前輪試算。** R2 的普通翻面回看與三行中途停頓案例，在新提案下確實各回到 8、10 秒。另用現行 writer 跑同一裝置的已分開結算事件，31 張單行比較卡，前 29 個實際作答間隔 8 秒，最後一張花 2 秒。最後兩張之間把 wall clock 往回調 2 秒，並在校時後才作答，單張仍可通過各自的評分延遲；writer 依 `max(now,last+1)` 產出末兩筆相差 **1ms**。此路徑無需同一學生在兩台裝置同時作答。校時與未來比較行是模擬，時間戳和歷史合併跑的是現行程式，未量實機發生頻率。

| 真實 30 個間隔的中位數 | 以卡片批次辨識，保留 30 個不同卡的樣本 | §5-4 的 picked＋1ms |
|---:|---:|---:|
| 8 秒 | 8 秒，最後間隔雖被時鐘壓成 1ms，仍夠 30 個樣本 | 15 秒，少一個樣本走預設，誤差 +7 秒／張 |

這是「只少一個樣本」會有量級差異的條件。批次欄位的確能避免此誤併；發生率仍未知。若決定接受低頻時鐘異常的估差，建議明寫門檻退回的後果並固定測試，勿把 1ms 寫成可靠的身分判斷。若要求在這種路徑也正確辨認卡片，保留批次 ID。

**`answerAll` 契約。** 普通作答維持部分接受，先過 `permits`，只有實際接受的行才占毫秒，回傳須保留 `lt → t` 以供 §8 對應。改評分先同步預檢所有取消及重寫，取消和重寫之間不要讓 listener 或 await 插入；取消行用原 `undo` 目標，新的作答再作一個連續批次。初次可寫的 app 版本行仍走同一 writer，通常在作答前，保留自己紀錄讀不到時的既有例外；版本行及 undo 都不能插進同一作答批次。每行要用其已分配的 `t` 算月份路徑；重試用佇列內原行和原路徑，不重新取時鐘。補一個「第一行拒絕／中間行拒絕」及「跨月份後追加失敗再重試」的驗收。位置見 `src/state/index.ts:278–303、332–335、645–650`、`src/core/study/log.ts:22–61`。

### R3-5　組名與挖空仍有可以明定的歧義

**去重。** `sameReview` 忽略 `with` 對逐字相同的 iCloud 副本成立。同 `t/lt/r/v/typed/src/also` 一筆有 `with`、一筆沒有（或指向不同首行）時，現有去重先留路徑／行序較早者，增量追加則留既有者；目前的規格可能使同一批輸入在重讀與增量各保留不同的估秒身分。兩裝置同毫秒碰撞可達，屬低頻。可選擇把正規化後的 `with` 納入相等，和 `also` 一樣保留有證據不同的行；若要保留一次評分，請明訂確定性的欄位衝突政策。§11 至少加同身分但 `with` 不同、無效值、首行暫缺的三筆驗收。另將 §4 末行「批次欄位不做」改成以 `with` 的現行決定為準。

### R4-5　組名、診斷與驗收

- **38 個既有名稱重跑，0 個不符。** 最後一個含名稱的組、明確分隔保留詞內空白、組括號缺口拒絕，都符合修訂表。本輪不重報少打頓號的已知代價。新增反例 `寨（寨、塞） 比較（進階）`，腳本回無組。這只是替合法比較卡的標題加常用括註，題目與組都未變，卻靜默退成普通卡，與 D-182 第 4 點及 §3「結尾是標題」的目的牴觸。建議連續的組／義項括號仍驗配對；在明確的標題文字後保留括註、不再掃它找組。加驗 `寨（寨、塞） 比較（進階）` 仍認得，以及 `寨（塞、寒） 相似字（寨、塞）` 仍無組。

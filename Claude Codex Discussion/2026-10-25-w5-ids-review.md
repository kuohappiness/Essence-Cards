## 發現（依嚴重程度）

### F1 — P1：舊的修復選項能還原到內容已變的目標

- **軸**：規格。D-134 要求「寫回前重新確認內容沒變」，討論稿第二次回應也要求版本改了使舊修復方案失效；§8-5／I6 的條件卻縮成「問題仍在」。
- **觸發**：`- A ^k3m9x2` 下有 `QA :: AA`。外部拿掉 ID，取得 `deckStatus(P).issues[0]`（相當於開啟小視窗）；再把題目改成 `totally new :: answer`，拿原 issue 呼叫 `resolveText(issue, 'restore', 最新文字)`。
- **預期／實際**：應回 null、維持待處理並要求重新檢視；實際回傳 `- A ^k3m9x2\n    - totally new :: answer\n`，問題消失。若重讀先到，原 issue 物件還會被原地更新，小視窗顯示內容卻不會因此重畫。
- **影響**：家長對舊內容所見的選項可以把舊進度接到修改後內容。重新解析最新文字只避免舊行號寫錯，不能取代確認時的版本檢查。
- **位置**：`src/state/ids.ts:97–101,191–207`；`src/obsidian/save.ts:70–82`。
- **證據**：已重現（公開 State 介面）。
- **建議**：合併前修。把持續追蹤問題與供小視窗確認的版本憑證分開；文字／相關目標版本變動後拒絕舊選項，待處理保留，新開視窗才能重新選。補「問題仍在但名稱／題目已改」與「通知先到／按鈕先到」測試。

### F3 — P1：紀錄 JSON 中合法的空白使舊 ID 再次配出

- **軸**：規格，D-134、§8-5、I3 的「原始紀錄每一行出現過的 lt」。
- **觸發**：原始紀錄放一行 `{"t":"2026-10-24T12:00:00+08:00","lt": "aaaaaa","r":"good","v":"12345678"}`，注意冒號後的空白；`random: () => 0`，補一個無 ID 新目標。
- **預期／實際**：`aaaaaa` 必須被排除；`history().reviews.length` 已是 1，但 `fillText` 仍配出 `aaaaaa`。`ltsOf` 只辨識緊貼的 `"lt":"…"`，與 `parseLine` 接受完整 JSON 的契約不一致。
- **影響**：新目標承接舊紀錄；有取消紀錄也不能保障永久排除。這不是壞 JSON 的容錯問題。
- **位置**：`src/state/index.ts:73–78,128–137`。
- **證據**：已重現（公開 State 介面，解析與新 ID 具體值如上）。
- **建議**：合併前修。從每一原始行可靠讀出 lt，勿從 merge 後的 reviews 取得；合法 JSON 的空白與跳脫鍵名均須涵蓋。保留對壞行的既有政策並明訂之，補「有／無取消」回歸例子。

- **證據**：靜態確認完整呼叫鏈；未操作 iPhone、未執行會重設卡組的命令。

## 「請特別看」5 點

1. **依內容猜身分**：沒有找到由歷史題目指紋直接產生／自動寫回舊 ID 的路徑；restore 的初始來源是消失 ID 或候選。名稱／指紋仍會影響待處理問題的延續及其 restore 所指向的當前目標，因此不能省掉 F1 的版本確認。整體不通過。
2. **待處理不被靜默補或消失**：一般重讀、改名稱／其中一題、存檔先於重讀的 skip 路徑與既有測試成立。不能作全面保證：F1 會用過期選項消掉問題，F5 會產生不應存在的問題。另測到最後一題暫時拿掉後解析不再有目標，待處理會消失，再補回題目會配新碼；目前「目標被刪掉」是否包括這種中間態未明訂，列為語意邊界，不另冒充確定 bug。
3. **最新文字寫回**：一般補 ID 的 Editor／modify 回呼確實以最新文字計算，未見先拿舊行號直接套用；最小差異及既有選取證據成立。但「用了最新文字」不代表「舊的還原方案仍有效」，F1 必修。固定等 1 秒亦不是檔案存完的證明，見第 21 點。
4. **每種編輯鎖定**：已核對 Node 測試與 Windows 48 個結果的 after 文字；仍未通過，F2 是既有清單未涵蓋的正文破壞。Undo／Redo 放在 extender 回報有實測證據；沒有把模擬 composition 宣稱為真輸入法。
5. **iPhone 零卡組寫入**：正式接線與 State 三個寫入入口的桌面防線成立；開發版不成立（F4）。I8 手機實機驗收仍依規格留到 W6。

#### R1 — P1／規格：損壞行救回的紀錄若用跳脫的 `lt` 鍵，舊 ID 仍會重新配出

- **位置**：`src/state/index.ts:82–88`（`ltsOf`）；對照 `src/core/study/history.ts:46–54` 的尾段救回。
- **觸發條件**：紀錄寫入中斷，後面接了一筆可救回的有效 JSON；那筆用合法的 `"\u006ct"` 表達 `"lt"`。例如下面是同一行，第二個 `{"t":` 開始的尾段有效：

  ```json
  {"t":"2026-10-24T11:00:00+08:00","r":"go{"t":"2026-10-24T12:00:00+08:00","\u006ct":"aaaaaa","r":"good","v":"12345678"}
  ```

- **預期**：D-134「紀錄每一行出現過的 lt，被取消的作答也算」及 §8-9 第 10 點要求避開 `aaaaaa`；即使前半行壞掉，既然紀錄模組可以救回，也不能再次分配。

#### T1 — P2／規格：熱重載後的追蹤集合沒有初始化，第一個關頁事件會被當成啟動快照

- **位置**：`src/obsidian/save.ts:102`、`128`、`158–161`、`184–186`；接線為 `src/main.ts:55–58`、`95`、`119–121`。
- **觸發條件**：在 layout 已 ready、已有無 ID 卡組分頁的情況下重新啟用外掛；state 讀完，編輯器的 opened／refresh／定時掃描都跑過，但關閉該分頁以前沒有新的 `layout-change` 或 `file-open`。這也是請求指定的「重新載入外掛時已經開著的背景分頁」相鄰情況。
- **預期**：啟動只記下現有分頁，不寫檔；之後關閉最後一個分頁應補一次。D-134 的「啟動不補」不等於「啟動後第一次離開也不補」。
- **實際**：`open` 只有 `leave()` 才會從 null 變成集合；`opened`、定時掃描的 remember，以及 state ready 後的 refresh 全都因 null 而不記。第一個關閉事件才呼叫 leave，當時 P 已不在分頁裡，因此初始化成空集合，P 永遠漏掉。多等幾次 2 秒並不能解決。
- **證據：替身已重現；Obsidian 熱重載實機事件順序待驗證**。直接執行實際 `wireSave`，已載入與只含 viewState 的分頁各一次，兩次定時掃描後關頁，fillIds 都是 **0 次**。另打包實際 `src/main.ts`，用 layout 已 ready 的 app／vault／CodeMirror 建立回呼替身跑 `onload → state.ready → 三次定時掃描 → 關頁事件`：關頁前寫入 **0**，關頁後仍 **0**，檔案仍無 ID。對照組只增加「關頁前一次 layout-change」，關頁前 **0**、關頁後 **1**，檔案得到 ID。不是只測手寫的 remember 邏輯。

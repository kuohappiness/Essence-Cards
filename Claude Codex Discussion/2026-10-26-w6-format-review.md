### F1｜P2｜先定義哪些 `|` 是分隔符號，不能把 Markdown 內的符號拆成答案

**位置**：`tasks/w6.md:73–76`；對照 `docs/syntax.md:250–251,312–314`、`docs/card-rules/english.md:85–91`、`src/core/deck/parse.ts:154–167`。軸：規格。

**證據：基準解析已重現；W6 結果是依文字規格模擬，尚無 W6 實作。**以下答案在基準都能解析，沒有 `typed-answer-invalid`。若照 §0-1 無條件 split，結果如下：

| 原答案格 | 拆分、去標記後 | 問題 |
|---|---|---|
| `a \| b` | `a \`、`b` | 跳脫用反斜線變成答案的一部分，跳脫的管線卻變成分隔。 |
| `` `a \| b` `` | `` `a ``、`` b` `` | 行內程式碼被剖開，反引號留在答案。 |
| `[[word\|borrow]]` | `[[word`、`borrow]]` | Obsidian 連結的別名分隔被當成兩個正確答案。 |
| `[borrow](https://example.test/a\|b)` | `[borrow](https://example.test/a`、`b)` | URL 被剖開，畫面文字與實際要求輸入的字不同。 |

相對地，`**a | b**`、`==a | b==`、`**a** | ==b==` 按現有的記號移除方式都能得到 `a`、`b`，**不需要禁止跨分隔的粗體，也不需要只認「粗體外的管線」**。

syntax §2-6 允許答案有連結、公式等 Markdown，§2-3 又限定打字答案是單字或片語，目前沒有說這兩條如何交會。不能把上表一概宣稱是合法的英文答案，也不能默默把它們當成多解。本次要補的是這個分界。

**建議寫法（採最小範圍，待 Claude 核對）**：

> 中翻英打字答案支援單行單字／片語及現有的 `**`、`*`、`_`、`==` 裝飾；ASCII `|` 是替代答案的分隔符號，前後空格可省略，AI 一律寫 ` | `。裝飾可跨過分隔符號。打字答案暫不支援跳脫管線、行內程式碼、公式、連結或嵌入；遇到這些寫法回報 `typed-answer-invalid`，不把它們拆成可出題的答案。一般翻面題仍照原有 Markdown 規則。

若選擇支援連結顯示文字或字面管線，就必須另定「辨識分隔／取顯示文字／去標記」的順序；不要只加一個忽略程式碼內 `|` 的判斷，因為目前 `typed` 的清理本來就不會去掉反引號、連結外殼。上述最小建議也會讓部分 W5 原本容許但無法正確作答的寫法停出，需明列這個相容性差異。此處不建議在 W6 擴成通用 Markdown 轉純文字功能。

**完成條件**：正式範例及三種裝飾情形照常接受；上表四例及公式中的管線有明確的 error 或完整支援結果；`answer`／指紋原值保留；同步補 syntax §2-3 的打字例外與製卡輸出規則，勿只藏在實作裡。

### F2｜P2｜換行要在每段 trim 前檢查，空值要在去標記後檢查

**位置**：`tasks/w6.md:73–75,308`；`src/core/deck/parse.ts:162–165`。軸：規格。

**證據：已重現基準錯誤與文字規格模擬的差異。**卡組如下：

```markdown
- borrow 中翻英 ^m7kp3q
    - 題目 :: a |
      b
```

基準的 `answer` 是 `a |\nb`（此處 `\n` 表示真正的換行），回報 `typed-answer-invalid`。按 §0-1「先拆開、每段 trim」後得到 `a`、`b`，換行消失，後面再驗已抓不到。`a\n| b` 同樣如此。另一方面，`a | ** **` 在去標記前看起來非空，去掉記號並 trim 後第二段才是空字串。

**建議寫法**：

> 從既有 `answer` 派生 `typed`，不修改 `answer`。拆分、trim 之前先檢查整個 `answer` 是否含 CR／LF；有則記 `typed-answer-invalid`。每段去除現有裝飾並再次 trim 後，任一段為空或含漢字，也記同一個 error。全部答案有效後才比較以空白切出的字數；字數不一只記一個 `typed-answer-words` hint，仍可出題。

**完成條件**：除現有案例外，加上分隔前／後換行、`a || b`、只有裝飾的段落、中文且字數不同等組合；invalid 只報 error、不另給字數 hint；有效的 `a | two words` 只報 hint。

## 通過項目的證據與指紋注意事項

### answer 與指紋

基準的指紋是 `fingerprint(question, answer)`（`src/core/deck/parse.ts:58–64,167`），跟 `typed` 無關。每邊先整理清單與空白，再以「題目＋換行＋答案」取 SHA-256 前 8 碼。**只改衍生的 `typed`，同一份卡組原文的舊 `v` 就能繼續對上。**

以下用自編固定題幹 `He has already ____ .` 實測，數值可作 W6 固定回歸基準：

| 答案原文 | W5 指紋 | W6 應得到的 typed |
|---|---|---|
| `made up his mind \| made his mind up` | `a5ec3d47` | `['made up his mind', 'made his mind up']` |
| `**made** up his mind \| made his mind up` | `81ac4269` | 同上，指紋仍保留這一列自己的值。 |
| `**a \| b**` | `9ec1d1dc` | `['a', 'b']` |
| `==a \| b==` | `35b63e7f` | `['a', 'b']` |
| `a\|b` | `d0d56a63` | `['a', 'b']` |
| `a \| b` | `c42e51fa` | `['a', 'b']` |
| `a  \|  b` | `c42e51fa` | `['a', 'b']` |
| `borrow` | `fa0de703` | `['borrow']` |

W5 整理空白是「合併已有的連續空白」，不是刪掉所有空白。因此 `a|b` 與 `a | b` 的指紋本來就不同；不要為了讓它們相同去改 hash。去粗體、把答案陣列 join 成統一格式、去重、排序、只取第一個答案再算指紋，都會破壞本次要求。家長真的增補／重排答案、改標記或在原本沒有空格的地方加空格，可能改變 `v`，這與「升版但原文沒變」是兩件事。學習目標 ID 不因題目指紋變動而改。

### retry 的排程投影、去重與取消

在未修改的基準程式上，用記憶體 JSON 行與假的 `Files.append` 驗證：

1. 同一行分別沒有 `retry`，或帶 `right`、`wrong`、`skip`、未知字串、null，`parseLine` 的結果完全相同。未知欄位不影響合法的作答欄位。
2. 同一 `t`、其餘既有欄位相同、只差 `retry` 的六行，`appendLine` 與 `mergeHistory` 都只留一筆排程作答，沒有 problems。因 `sameReview` 只比 `lt/r/v/typed/src`（`history.ts:17–18`），這是預期的排程去重；**不代表兩份原始證據完全相同**。
3. 接著取消、追加改評分、再次取消並追加，以及重送已取消的舊行，增量與全量結果完全相同，只剩最後一筆有效作答。`undo` 按 `t` 生效，與 `retry` 無關；跨檔相同 `t` 也沿用既有取消規則。
4. 顛倒 JSON 欄位順序，`parseLine` 結果相同。寫出順序是格式約定，不是 JSON 讀取或去重的必要條件；`t` 維持第一欄也保留現有壞行尾段救回的寫出慣例。
5. 固定相同的時鐘，writer 連寫原作答、取消、新作答，時間仍依序增加 1 毫秒，寫入順序不變。
6. **W5 的 `encodeEntry` 目前會略掉輸入物件中的 `retry`**，這是預期現況，不算 W6 通過；W6 必須完成 §1 的 encoder 修改。R4 應直接檢查寫出的原始 JSON 有值且順序正確，不能只比較 `History`，否則完全漏寫 `retry` 也會通過。

`parseLine` 與 `mergeHistory` 都不改寫原始檔。日後分析需要 `retry` 時必須讀原始 JSON 證據，不能假設 `History.reviews` 能提供它；不要為分析而把同一次作答按 `retry` 差異算成兩次排程。

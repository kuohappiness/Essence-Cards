## 1. 量到的數字

來源：使用者電腦上的 `.codex/sessions`（使用者 2026-11-03 同意讀，只讀 token 數、推理等級與每則指令的開頭）。Codex 會把結束的對話移到 `archived_sessions`，這次沒有讀，所以只有一個完整的主對話。

### 1-1 Codex 的週額度是瓶頸

10-28 週額度重置後，到 11-02 重置前已用到 98%，約五天就用完。Plus 另有五小時的額度，這次最高看到 64%。

### 1-2 一件高風險任務：入口與目錄第一批（11-02～11-03）

同一個 Codex 對話用了 20 小時，收到 11 則指令：L2 七輪，中間插了出處讀法的討論三輪。合計 246 次模型呼叫，輸入 6,900 萬 token（98% 是快取），輸出 16 萬，週額度從 3% 到 24%。

| 指令 | 推理 | 呼叫 | 輸入（快取外） | 上下文 | 週額度 |
|---|---|---:|---|---|---|
| L2 第一輪 | 高 | 32 | 480 萬（24 萬） | 2 萬 → 25 萬 | 3 → 4% |
| L2 再審 | 高 | 15 | 480 萬（11 萬） | 25 萬 → 35 萬 | 5 → 7% |
| 出處討論三輪 | xhigh | 41 | 850 萬（27 萬） | 36 萬 → 42 萬，自動壓縮到 11 萬，再到 20 萬 | 8 → 14% |
| L2 第三輪 | 高 | 64 | 1,710 萬（29 萬） | 22 萬 → 29 萬 | 14 → 16% |
| L2 第四～七輪 | xhigh | 94 | 3,410 萬（76 萬） | 29 萬 → 41 萬 | 20 → 24% |

週額度只有整數 %，同時段別的 Codex 對話也算在裡面（例如第三輪結束到第四輪開始之間跳了 4%），所以這張表只能看大小。

看到的事：

- **沒有新開對話**：quality.md 的 L2 寫「新開的 Codex session」，實際上一路沿用同一個。上下文長到 41 萬，後面幾輪只審一小段差異，每次呼叫仍要重讀 30～40 萬。
- **推理等級被帶過去**：討論時切成 xhigh，之後 L2 第四～七輪也都是 xhigh；審查請求寫的是「高」。
- **讀進來的東西**：工具輸出共 140 萬字。其中討論稿與審查報告 36 萬（26%）、`tasks/` 14 萬、`docs/` 9 萬、git diff 21 萬、原始碼 16 萬；測試輸出只有 2.6 萬，pre-commit 只印點的做法有效。最大的幾筆是把整份檔案或整段差異原樣讀進來，每筆 2.4～3.6 萬字。

### 1-3 自動審核的子對話

這個 Codex 的審核設定是 `auto_review`：每次要在沙箱外跑指令（例如 quality.md 規定完整的 `npm run check` 要在沙箱外跑），Codex 就開一個 `codex-auto-review` 子對話，把主對話的歷史讀一遍再決定准不准。10-19 以來共有 115 個，10-26～11-01 那週有 55 個，輸入 1,930 萬（快取外 257 萬）。用的是較小的模型，佔週額度多少量不出來。主對話越長，它每次讀的也越多。

### 1-4 Claude：電腦上的 session（2026-11-03 量）

來源：使用者電腦上的 `.claude/projects`。使用者同意，由電腦上的 session 統計，只讀 token 數與工具名稱。範圍是 10-19 以後的 100 個 session，Opus 主對話共 11,536 次呼叫。

- **原始 token 3,769M，98% 是快取讀取。** 照 API 的計價比例加權（快取讀 0.1、快取寫 2、輸出 5），快取讀約佔六成，快取寫約兩成五，輸出約一成三。所以和 Codex 一樣，主要成本是每次呼叫要重讀多長的上下文。
- **長 session 是大頭**：前 10 個 session 就佔 46%，都是照 `tasks/` 實作、修 L2 發現的 session，上下文長到 66～96 萬。1M 的模型預設要到約 96.7 萬才自動壓縮。10-26～11-01 那週，上下文 40 萬以上的呼叫有 2,290 次，佔那週快取讀取的 54%。
- **用量上限**：jsonl 裡沒有用量上限的訊息。不過介面上的提示不一定會寫進去，所以不能當作從沒撞過上限。

### 1-5 量不到的

- **雲端討論串**（包括這個專案的討論串）沒有可讀的用量紀錄。
- **快取怎麼折算成額度**：OpenAI 與 Anthropic 都沒有公布方案額度的算法，上面的加權用的是 API 的計價比例。所以「省多少」都是預估，採用後量一次對照。

## 2. 提案（依預估效果排序）

### T1 每一輪都新開 Codex 對話，推理等級照請求寫

**使用者選了「每輪都新開」（2026-11-03），已寫進 [quality.md](../docs/agents/quality.md#高風險範圍要做-l2)。** 下一件 L2 量一次對照；D-ID 等 T3～T5 談完一起寫，請 Codex 一次反駁。

- **做法**：Claude 交給使用者貼的那段文字，第一行固定寫「新開一個 Codex 對話，推理等級：高」（或該輪寫的等級）。L2、格式查核、討論稿的每一輪都一樣。quality.md 已經寫了要新開，所以不加新規則，只改交接文字的寫法。
- **① 不做**：後面每輪都要重讀 30～40 萬的上下文，討論用的 xhigh 也會帶進 L2。這件任務從 L2 第三輪起，週額度上升 10 個百分點；表內這幾段合計 6 個，其餘混著同時段的其他對話。自動審核的子對話也跟著讀得多。
- **② 代價**：每個新對話要重讀 `AGENTS.md`、審查請求與差異，快取外約多 2～5 萬 token。前幾輪的脈絡改靠報告。使用者每輪要多按一次「新對話」。獨立性反而比較好，因為審查者不會順著前幾輪的推論看（D-131 的理由）。
- **③ 更小的做法**：只在換主題時新開（L2 和討論不混在同一個對話），同一件 L2 的再審仍沿用。
- **預估**：第二輪以後，每輪的上下文從 30～40 萬降到 5～15 萬，讀的量約剩三分之一。下一件 L2 量一次對照。

### T2 L2 的輪數與停止條件

**使用者選了這個方向（2026-11-03，專案討論串「整理現有的開發 skill」）**；和 T1、T3 一起請 Codex 反駁後寫 D-ID（修改 [D-119](../docs/decisions.md#d-119-程式品質的-skill-整併成通用的-code-quality) 的審查標準）。

- **現況**：沒有停止條件，Codex 還報得出發現就再審一輪。錯誤紀錄五輪、發布前比較六輪、更新防線第二部分四輪、入口與目錄第一批七輪（§1-2：那段時間週額度上升 21 個百分點，表內各段合計 15 個，其餘混著同時段的其他對話，所以只能看大小，不能拿來預估下一件）。
- **先做了的（不在這次反駁範圍）**：讀上面前三份報告的 22 項發現，10 項是 Claude 交出前就能擋的：6 項是只修了報告裡的那一個例子、同一類的鄰居留著（例如發布前比較的 F2、F3、F5；錯誤紀錄的 F3 → G2 → H1），4 項是 Claude 在再審請求裡點名、卻沒先自己測的邊界（錯誤紀錄的 F2、F4、G1，更新防線的 F3 剩餘）。code-quality 的 `review.md` 已補兩句：整類一次修、回歸測試涵蓋同類；請審查者看的邊界先自己測（`8c7bdda`）。
- **做法**：
  1. 審查請求請審查者每項發現多標一欄「**真實路徑會不會發生**」：使用者的檔案、Obsidian 或 iPhone 的實際行為、已發布的版本會不會產生這個輸入。要刻意造出來的值才會發生的，標「只在造值時」（例如判斷型別就拋錯的 Proxy、message 是 Symbol 的錯誤、`a,share:a` 這種故意撞在一起的 ID）。
  2. 第一輪與第一次再審照舊完整。從第二次再審起，只有真實路徑會發生的發現才擋合併、才再送 Codex；「只在造值時」的記進技術債（寫觸發點與完成條件），要修就由 Claude 修並照 L1 對照，不再多審一輪。
  3. 第四輪還有擋合併的發現，停下來問使用者，附上剩下的發現與各自的真實路徑判斷，不自動繼續。
- **① 不做**：下一件高風險任務可能又是週額度的兩成；Plus 的週額度五天就用完（§1-1）。後面幾輪的發現多半要造值才會發生，例如錯誤紀錄第三、四輪的 G2、H1。
- **② 代價**：「只在造值時」的問題晚一點修，期間沒有獨立審查看它們的修正；判斷真實路徑可能判錯，所以由審查者標、整合者核對，標錯的回到擋合併。第一輪與第一次再審不變，§3 的「跳過 L2」不適用，但這確實少了一部分獨立審查，請 Codex 就這點反駁。
- **③ 更小的做法**：只加第 3 點（第四輪停下來問使用者），不分真實路徑。缺點是使用者每次都要自己判斷剩下的發現值不值得再審一輪。

### T3 每一輪只讀需要的

**使用者選了「只加『只讀』那句」，不分檔（2026-11-03），已寫進 [quality.md](../docs/agents/quality.md#高風險範圍要做-l2)。**

- **現況**：審查請求與報告都接在同一份檔案後面（發布前比較的請求 26 KB、報告 61 KB；外掛架構討論稿長到 527 KB）。這次 Codex 讀討論稿與報告共 36 萬字，約佔讀進來的四分之一。
- **做法**：再審與討論的每一輪，小節開頭寫「這一輪只讀：本節、〈審查對象〉、上一輪的〈Claude 回應〉」。討論稿換一個子題時另開一份，舊的那份寫上結案狀態（外掛架構那份九個環節都寫在同一份）。
- **① 不做**：每一輪都從頭讀，檔案越長每輪越貴。
- **② 代價**：寫請求時多一句；分檔多一個連結。審查者仍可以自己決定多讀，只是預設不讀。
- **③ 更小的做法**：只加「只讀」那句，不分檔。

### T4 Claude 的上下文提早壓縮

**使用者選了 40 萬（2026-11-03），已寫進 `.claude/settings.json`。** 只管電腦上的 session；雲端討論串不讀這個設定。

- **做法**：在 repo 的 `.claude/settings.json` 加 `"autoCompactWindow": 400000`。電腦上的 session 上下文到約 40 萬就自動壓縮，不用使用者記得（官方說明：任何一層的設定檔都可以設）。雲端討論串不讀 repo 的設定，這次先不管。
- **模擬**（電腦上的 session 照實際的呼叫重算，只是上限）：40 萬時快取讀取少 33%，三週壓縮 43 次，加權後約省全部的 19%。30 萬時少 47%、壓縮 75 次，約省 28%。50 萬時少 22%、壓縮 21 次，約省 13%。模擬沒算壓縮後重讀檔案、或因為遺失脈絡而重做的成本，這部分會吃回一些。
- **① 不做**：長 session 每次呼叫都要重讀 40～96 萬。
- **② 代價**：壓縮會丟掉細節，例如前面讀過的檔案內容、試過又放棄的做法，之後要重讀，也可能重犯。每次壓縮還要多一次摘要呼叫。規格在 `tasks/`、發現在審查報告，丟掉的多半讀得回來。
- **③ 更小的做法**：設 50 萬，壓縮次數只有 40 萬的一半；或不設，在自然的段落（例如 L2 一輪修完）由使用者打 `/compact`。

### T5 自動審核的子對話（先查再談）

- **做法**：把審查固定會用到、而且安全的指令（`npm run check`、`git diff`）在 Codex 設成不必每次審核。要先查 Codex 官方說明怎麼設、會不會降低安全，才決定建不建議。
- **① 不做**：每週約 50 個子對話；成本量不出來，可能不大。

### T6 合併、寫 D-ID、改樣式這類雜事交給 Sonnet（使用者提出，排在最後談）

- **使用者的問題**：能不能讓這類雜事自動用 `/model sonnet` 做；或有其他省 token 的流程建議。改的是 [D-140](../docs/decisions.md#d-140-fable-規劃opus-執行codex-查核)、[D-144](../docs/decisions.md#d-144-決策交給-opus-xhighfable-只在解不了的時候) 的分工。
- **查到的（Claude Code 官方說明，2026-11-03）**：
  - 電腦上的 session 有三種自動換的方法：skill 的 `model` 欄位（叫用那個 skill 後，這一輪剩下的部分用指定的模型，下一則訊息換回來）；`.claude/agents/` 的 subagent 寫 `model: sonnet`（主對話交出去，它只看得到交給它的說明）；`/model opusplan`（plan mode 用 Opus，執行時自動換 Sonnet）。
  - 專案的雲端討論串**不載入** repo 的 `.claude/skills/`、`.claude/agents/`、hooks 與 `settings.json`，只載入 `CLAUDE.md`。所以雲端討論串裡，skill 的 `model` 不會生效；要用 Sonnet，只能在開討論串時指定，或在專案設定改討論串的預設模型。
  - **換模型會讓快取整個失效**（〈How Claude Code uses prompt caching〉的 Switching models）：換過去的第一次呼叫要把整段上下文重寫進快取，成本約等於 Opus 重讀 20 次。skill 的 `model` 欄位與 `opusplan` 都算換模型。**換推理等級不會**：Opus 5.5 在訂閱方案裡換推理等級，快取照樣有效。
  - 官方說明寫，新專案預設每個討論串都用 Opus high，「最快用完方案額度」。Opus 和 Sonnet 各佔多少額度，官方沒有寫數字。
- **量到的雜事份量**（電腦上的 session，原始 token，都是上限）：essence-decision 叫用後到下一則使用者訊息，佔 Opus 的 8%，35 次、平均每次 23 次呼叫、上下文平均 36 萬。改 CSS 的那幾段佔 12%，但同一段裡也有實作。合併只有 10 個 session 落在最後 20% 的呼叫，那段佔 1.9%；另外 27 個 session 的 `git merge` 在中途，多半是先把 `main` 併進來再繼續做（沒看內容，未驗證）。
- **推論**：雜事的成本來自它發生在多長的上下文，不是模型。拿寫一個 D-ID 來算：在 36 萬的 session 中途換 Sonnet，光重寫快取就已經比 Opus 直接做完 23 次呼叫還貴。只有在短的上下文（新開的 session 或 subagent）做雜事，換 Sonnet 才有額外的節省；但寫 D-ID 需要談定的內容，換新 session 就要先寫交接，改樣式多半又和實作連在一起。
- **💡 建議**：不做「自動換 Sonnet」。雜事多半發生在長 session 的後段，T4 提早壓縮之後它們也跟著變便宜。Sonnet 留給一開始就只做雜事的新 session（例如只做合併、只改一段樣式），由使用者開 session 時選。
- **① 不做**：雜事照 Opus 做，靠 T4 降成本。
- **③ 更小的做法**：雜事階段把推理等級降到 high，快取不會失效；但 D-144 規定中途不切，Claude 也不能自己改，要使用者同意改 D-144。

## 3. 不建議做的

- **少做檢查或跳過 L2**：違反 D-117、D-119 的「檢查不減」。
- **讓 Claude 直接呼叫 Codex 的橋接**：省轉貼的時間，不省 token（D-106 評估過）。
- **把 `decisions.md` 拆成很多檔**：Claude 平常用索引與查詢工具只讀幾條，這次沒看到整份讀進來的實例。

## 請 Codex 回應：第一輪（T1～T3，2026-11-03）

這一輪只讀：〈先讀這裡〉、§1、T1、T2、T3、§3。T4～T6 還在和使用者談，不用看。基準 commit：`main` 上加入這一節的 commit（`git log -1 --format=%h -- "Claude Codex Discussion/2026-11-03-token-saving.md"`）。T1、T3 已寫進 `docs/agents/quality.md`（`210081e`、`aafd389`），T2 的「先做了的」已寫進 code-quality 的 `review.md`（`8c7bdda`）。

請回答：

1. **站在「不做」那一方**：每個提案，不做的代價是不是被高估？做了會不會傷到品質？尤其是 T1 新開的對話看不到前幾輪的脈絡；T2 第 2 點在第二次再審以後，「只在造值時」的修正就沒有獨立審查。

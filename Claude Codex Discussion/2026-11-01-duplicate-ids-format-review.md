## 開工前要改

### F1｜P2｜仍在別處的舊 ID，保護要涵蓋 `changed` 的兩個選項

**軸：規格漏洞；證據：現有公開 State 介面已重現，新版風險為靜態推斷。**

位置：`tasks/duplicate-ids.md:84`、`:88`、`:142`、`:153`；`src/state/ids.ts:310`～`:312`。

§3-2 明訂選 `duplicate` 的「新加的」時不把舊 ID 記成刻意拿掉，但同一目標還可以有 `changed`，§3-2 又允許處理其中任一問題。既有 `changed` 的「當成新的」及「還原」都會把當前被換掉的 ID 加進全域 `removed`。若只特判新加的 `duplicate` 分支，從另一個入口仍能破壞同一個保護。

自編資料，A、B 都有子題 `    - Q :: A`：

1. 首次讀到 A 的 `- A ^aaaaaa`。
2. 外部改成 `- A ^bbbbbb`，取得 `changed` 問題（可還原 `aaaaaa`）。
3. B 新增 `- B ^bbbbbb`。依新規格，A 會同時有 `changed` 與 `duplicate`。
4. 用原先的 `changed` 問題選 `new` 或 `restore`，A 成功寫成新 ID 或 `aaaaaa`。
5. 在外部拿掉 B 的 `bbbbbb`。

基準程式兩條路都得到 B 的 `{ missing: 1, issues: [], malformed: [] }`，沒有 `lost`；原因是步驟 4 把 `bbbbbb` 放進 `removed`。新版若只照 §3-2 第 84 行特判 `duplicate`，仍會留下此漏洞。B 之後存檔會直接配新 ID，失去 D-134 原本要求的待處理保護。

**建議寫法**：「任何問題的處理選項在採用寫回時，被拿掉的 ID 若依採用後的內容與 state 其餘已知內容，仍屬於其他學習目標，就不得記成刻意拿掉；適用 `duplicate`、`changed` 的 `new` 與 `restore`。其餘問題照目前內容重算。」

補兩個公開 State 測試：上述步驟分別選 `new`、`restore`，最後 B 都須有 `lost`、`restore: 'bbbbbb'`。原有第 9 項只測 `duplicate` 入口，第 17 項只測問題消失，都不足以涵蓋它。

### F2｜P2｜搬行後保留問題物件，與搬行必須 `stale` 衝突

**軸：規格矛盾；證據：靜態對照。**

位置：`tasks/duplicate-ids.md:80`、`:82`、`:137`；架構討論稿 `2026-10-26-plugin-architecture.md:2787`、`:2857`。

第 80 行要求名稱、題目指紋與 ID 不變時保留同一物件，行號原地更新；第 4 項驗收卻要求小視窗拿到問題後目標「被搬到別行」就 `stale`。若 state 已在送出前讀到搬行，舊小視窗握著的正是更新過行號的同一物件，依前者可繼續寫，依後者必須拒絕。同名、同 ID、同題目的副本還可能互換位置，不能靠最近行號猜選中了哪份。

**建議寫法**：「`duplicate` 的選擇綁定顯示時的目標行；該行號、名稱、題目指紋或 ID 任一改變，就換新的問題物件，舊選擇回 `stale`。只更新其他目標的資訊時可以保留物件並更新 `others`。」這與既有驗收及已同意的討論結論一致；不是要求改掉所有 `lost`／`changed` 的既有追蹤規則。

補測「先搬行、等 state 重讀，再送出舊物件」，不能只測尚未重讀時的編輯器文字。

### F3｜P2｜「只換 ID、其他字不動」尚無一致的精確輸出

**軸：規格與既有寫回行為不一致；證據：純函式及公開 State 路徑已重現。**

位置：`tasks/duplicate-ids.md:83`；`docs/syntax.md:259`～`:260`；`src/core/deck/ids.ts:12`～`:15`；`src/core/deck/assign.ts:119`～`:120`。

`setTargetId` 不是單純原位置換 token：它會拿掉行中的 ID、移到第一行尾端，並可能吃掉尾隨空白。現有「當成新的」也會這樣，不能直接承諾逐字只替換 ID。以 `\r\n` 表示原始 CRLF，這三個例子均已實跑：

| 輸入名稱行 | 現有 `resolve(changed, 'new')` 的名稱行 |
|---|---|
| `- A ^bbbbbb  \r\n` | `- A ^aaaaab\r\n`（尾隨兩格消失） |
| `- A ^bbbbbb B  \r\n` | `- A B   ^aaaaab\r\n`（移至原尾隨空白之後） |
| `- A ^bbbbbb\r\n  continuation\r\n` | `- A ^aaaaab\r\n  continuation\r\n`（兩行及換行保留，符合 D-135） |

另直接對第二種名稱行呼叫 `setTargetId(..., 'aaaaaa')`，第一次為 `- A B   ^aaaaaa`，第二次為 `- A B ^aaaaaa`；不是逐字冪等。尾隨兩格還可能是 Markdown 換行標記，不宜默默當成沒有意義。

**建議寫法**：「被選目標的 ID 歸位至名稱第一行的尾隨空白之前；明列移除舊 ID 所需的分隔空白例外，其餘正文、原尾隨空白、接續行與 EOL 保留；其他沒有 ID 的目標仍按一般規則補。」例如行中例子的預期可定為 `- A B ^aaaaab  \r\n`。若 Claude 主張統一正規化空白，需改成明文允許的輸出，說明對兩行名稱的影響，不能仍寫其他字不動。

開工前先選定輸出，實作時將行尾 ID、行中 ID、兩行名稱、尾隨 Tab／空白及 CRLF 的字面預期加入共用案例，測往返與冪等。

### F4｜P2｜兩個讀得懂的副本，再加需要新版的一份，是否列衝突

**軸：規格有兩種讀法；證據：靜態反例，既有版本閘門另有探針驗證。**

位置：`tasks/duplicate-ids.md:54`～`:59`、`:151`；`src/state/index.ts:225`～`:235`。

§1 的前面幾條規定先在讀得懂的卡組內計數、在移除 `gatedIds` 前算；第 59 行又無條件寫「和需要新版的卡組同一個 ID……不算衝突、不列給家長選」。如果讀得懂的 A、B 都有 `x`，需要新版的 C 也有 `x`，前者會列 A、B 的衝突，後者可被讀成整個 `x` 都不列。第 15 項只測一份讀得懂加一份需要新版，無法區分。

**建議寫法**：「需要新版的卡組不參與衝突計數或選擇；它的已知 ID 照原有 `gatedIds` 停出。只有一個讀得懂的目標與它同 ID 時，不構成 duplicate；兩個以上讀得懂的目標仍照 §1 列 duplicate，處理後也不能解除仍適用的版本閘門。」不讀寫 C，也不拿 C 的位置猜身分。

補 A、B 可讀加 C 不可讀的測試，以及處理 A 後 B 仍受版本閘門阻擋的預期。


### I2｜P3｜syntax 補齊範圍，釐清重複值與重複出現

位置：`docs/syntax.md:260`～`:262`；`tasks/duplicate-ids.md:117`～`:118`。

建議在 syntax §2-3 維護一段規則：讀得懂卡組中被解析成學習目標、有確定 ID 的都算，包括草稿、卡組／目標暫停及寫錯；同篇或跨篇同樣處理；引言框、程式碼、一般筆記、題目行、轉錄稿及 `ambiguous-id` 候選不當成確定的第二個目標；讀不到保留上次證據，從未讀到者未知；版本保護另依 §2-1。沿用名詞與必要的章節連結即可，不需把 state 欄位或演算法搬進 syntax。

現有「有兩個」也有兩種讀法。已重現 `- A ^b4rw7k B ^b4rw7k` 只有一個不同 ID 值：解析為確定的 `b4rw7k`、`misplaced-id`，不是 `ambiguous-id`；已有 `tests/deck.test.ts:682`、`:713` 的明確預期。建議寫「名稱行有兩個以上不同的候選 ID 值才是 ambiguous；相同值出現多次仍按原規則歸位」，避免本次無意改掉舊資料的讀法。此處澄清既有行為，不另變更解析契約。

architecture 第 239 行整句替換即可，例如：「學習目標 ID 的補上、保護與重複處理，見 syntax §2-3。」原句前半的「停止輸入」也已被 D-134 取代，不應只改後半句。§2-10 可加短連結說明確定 ID 衝突時有 §2-3 的共同停出規則，避免「只跳過寫錯的那一個」被誤解為永遠不影響共享 ID 的其他目標。

## 通過項目的依據

### 辨識與讀取

已對基準的 `parseDeck` 跑自編輸入，以下不是對尚未完成的衝突函式宣稱測試通過：

| 寫法 | 解析結果 | 依 §1 的處理 |
|---|---|---|
| 名稱行尾 `^b4rw7k`，或自訂 `^Mine-1` | 確定 ID | 同值的第二個目標算衝突，不能只檢查程式產生的六碼 |
| 名稱行中 `^b4rw7k` | 確定 ID、`misplaced-id` | 算；未處理衝突時不能先歸位 |
| 第一行有 ID、下一行有接續文字 | 第一行的確定 ID | 算；不改到整段末尾，D-135 的閱讀模式限制不變 |
| 只有接續行尾有 ID | 目標 `id: null` | 不作確定 ID 計數；原區塊 ID 仍保留供配號避開 |
| 名稱行兩個不同值 | `id: null`、`ambiguous-id` | 不當成兩個確定的衝突目標，候選仍保留 |
| 最上層直接題目，即使題目行尾有 ID | implicit、`id: null` | 不算；補號時建立明確目標 |
| 引言框、一般筆記、轉錄稿 | 不產生目標 | 不算 |
| 子題行的區塊 ID | 不是該目標 ID | 不算 |
| 行內程式碼、公式、普通連結內的相同字串 | 不當成名稱行中 ID | 不算；巢狀連結的已知限制見 I1 |

`src/state/reads.ts:130`～`:136` 在 read 失敗時不把那篇的 null 交給 state，因此保留成功版本；只有成功的新內容或確定刪除才撤掉證據。記憶體 State 探針確認失敗後 `decks()` 仍有 A、B，B 列在 `unread()`。這符合 D-157；重啟後從未讀到的內容仍未知，不能承諾防住。

### 核心契約、讀取端與比較工具

- 全文搜尋 `assignIds(`：產品呼叫端為 `src/state/ids.ts:208` 的 reserve、`:238` 的 missing 計數；開發工具為 `src/obsidian/dev.ts:326` 的 metadataCache 對照。missing 不再把第二個重複目標算成缺號，正是新契約要求；reserve 須同時保護未解衝突行，避免歸位與改縮排。刪 `replace` 不替代這道 skip。
- 開發 compare 的 `src/dev/compare.ts:92` 起只額外檢查明確目標是否仍缺 ID，沒有「必須全部唯一」的條件；它不靠自動換號建立產品身分。重複區塊 ID 的實機呈現仍留給合併前 L2／Windows 驗證。
- `src/core/backup/plan.ts:166`～`:201` 自行解析最終還原集合、拒絕參與重複的還原檔，不呼叫 assignIds；不用為這個契約改掉安全檢查。它把 ambiguous 候選也當占用，比 D-157 的「確定衝突」更保守，目的不同，不能直接以新衝突函式替換掉候選保護。
- `tools/compare/adapter.ts:68` 只記行號、level、code；提示文字單獨改寫不會增加快照差異。實跑同篇兩個目標得到 `['2 hint duplicate-id']`。但 adapter 會呼叫 `planToday`，從「第一個出」改成「全部停」，有重複 ID 時 `today` 必須不同，不能將整份發布前比較預期寫成零差異。
- adapter 不呼叫 assignIds，也不讀 `Today.problems`，刪該欄位不會直接破壞它。版本閘門未接入的既有問題仍按任務〈排程與分支〉第 3 步處理，發布前不得漏掉。

### 配號、紀錄與舊版

- `taken()` 包含這次看過與預留過的、原始紀錄各行的 `lt`（包括取消作答）、刻意拿掉的及 pending restore；observe 也記行尾區塊 ID 與 ambiguous 候選。自編探針分別占用 `aaaaaa`～`aaaaag`，新目標配到 `aaaaah`。舊衝突 ID 不放進 removed 仍在 seen／筆記中，不會重新配出；removed 是「刻意刪除的證據」，不是唯一的避號清單。
- 這符合 D-134 對 D-034 的具體化與已明列代價：沒有紀錄、又已從筆記消失的 ID，在重啟後仍可能再配出；沒有永久已用 ID 資料庫，也不知道尚未同步到的檔案。本次不應藉「整個 vault 不重複」新增永久庫或改此限制。

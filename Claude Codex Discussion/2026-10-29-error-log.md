## 1. 要解決的事

正式版遇到錯誤時沒有留下證據。iPhone 上沒有人看得到主控台；重開之後就沒了；開發版能收集（`errors` 命令），但開發版不能裝到正式使用的 vault（D-149 第 4 點）。學生真正使用後在 iPhone 碰到問題，AI 只能猜、在測試 vault 重現、再請使用者到 iPhone 重測（一輪約 20 分鐘）。

**範圍**：只留證據，給維護的 AI 讀。不加畫面、不提示、不上傳；外掛自己不讀這份檔案。「複製問題報告」命令（G2）與查單一目標排程的工具（G3）不在這次，見[規畫](../docs/plans/maintenance.md)第 2 節。

## 2. 錯誤現在去哪裡

| 來源 | 現在怎麼處理 | 使用者看得到什麼 |
|---|---|---|
| `state` 讀不到（`read`），每次重試失敗都會再報一次：1 秒起加倍，最多 60 秒一次（`retryDelay`） | `report()`：`console.error`，每次載入第一次出 Notice | 一次「有些卡組或複習紀錄暫時讀不到」 |
| 紀錄寫不進去（`write`），包括切到背景時的 `flush` | 同上 | 一次「複習紀錄暫時寫不進去」 |
| `state` 監聽者丟錯（`listener`） | `report()`，沒有 Notice | 沒有 |
| 卡片顯示不出來（`Markdown.tsx`） | `console.error`，那一塊寫「這張卡顯示不出來」 | 那一塊的字 |
| 離開筆記時補 ID 失敗（`save.ts` 的 `leave`） | `console.error` | 沒有 |
| 停用時關閉失敗、外掛事件的監聽者丟錯（`main.ts`） | `console.error` | 沒有 |
| 其他沒接住的錯：例如複習畫面的 React 錯誤（沒有 error boundary）、`void start()` 裡的拒絕 | 只變成 window 的 `error`／`unhandledrejection` | 可能是畫面空白或沒反應 |

開發版的 `collectErrors` 換掉全域的 `console.error`，連 Obsidian 與其他外掛的錯誤都收（200 筆，只在記憶體）。

## 3. 提案（💡）

### P1｜位置與檔名

💡 `Essence Cards/紀錄/錯誤/<年-月> <裝置名稱-隨機碼>.jsonl`，例如 `紀錄/錯誤/2026-11 iPhone-7f3a.jsonl`：每台裝置每個月一個檔，和複習紀錄同一種命名（syntax.md §5）。

- 每個檔只有一台裝置寫，iCloud 不會互相覆蓋；走 `Files.append`，不加新的接點（D-110）。
- `紀錄/` 底下有前例：AI 輸出快照在 `紀錄/AI 輸出/`。`isLogPath` 不讀子資料夾，`isDeckPath` 只看 `.md`，所以 `state` 收到它的變動通知也會忽略（`notify`），不會讀進排程。不加第六個系統資料夾（D-088、D-108）。
- 說明書的「資料夾管理規範」（D-048 補充 2026-10-16）加一句：外掛自己寫、給維修用，刪掉不影響複習。

**曾考慮**：外掛資料夾 `.obsidian/plugins/essence-cards/`（家長看不到，但 `Files` 的 Obsidian 版用 vault 的索引，碰不到點開頭的資料夾，要另開接點；D-150 第 4 點的備份只含 `data.json`）；新的系統資料夾 `Essence Cards/錯誤/`（要改 D-088 的清單，家長多看到一個資料夾）。

### P2｜一行記什麼

💡 一行一筆 JSON，欄位順序固定：

```
{"t":"2026-11-02T20:15:03.250+08:00","build":"0.1.0+1a2b3c4","where":"render","msg":"Cannot read properties of undefined (reading 'text')","path":"Essence Cards/國二上/自然/2-2 水溶液（卡片）.md","stack":"at Xe (plugin:essence-cards:1:20345)\nat …"}
```

| 欄位 | 內容 |
|---|---|
| `t` | 時間，和複習紀錄同一種寫法（`formatTime`） |
| `build` | `BUILD` 原樣 |
| `where` | 哪個環節：`read`、`write`、`listener`（沿用 `ErrorSource`），加上 `render`、`fill`（離開筆記補 ID）、`close`、`event`（外掛事件的監聽者）、`uncaught`（window 的錯誤）、`limit`（P4 的上限） |
| `msg` | 錯誤訊息，最多 300 字 |
| `path` | 選填，知道是哪個檔時才寫 |
| `stack` | 選填，只留含 `plugin:essence-cards` 的幾層，最多 600 字 |
| `n` | 選填，同一個錯誤到第幾次（P4） |

- 不寫的東西：作答、卡片內容、設定值、其他外掛的錯誤。`msg` 與 `path` 可能含筆記路徑或卡片的字，所以這份檔案和卡組一樣只留在家裡的 vault；維護的 AI 在本機讀，寫進 repo 時只寫摘要（D-003）。
- 外掛自己不讀這份檔案，所以 D-149 第 3 點的「永遠不改」與讀取閘門不適用：欄位可以隨版本增減，每一行有 `build` 可以對。syntax.md 加一小節寫明這點與欄位。

### P3｜收集範圍：只收自己的

💡 正式版不換掉全域的 `console.error`。改成一個函式（例如 `recordError(where, error, path?)`）：照舊 `console.error`，再寫一行；第 2 節表上每一處都改呼叫它。window 的 `error`、`unhandledrejection` 只在 stack 含 `plugin:essence-cards` 時才記。

- 換掉全域的會收到 Obsidian 與其他外掛的錯，多出雜訊，也記到不是這個外掛的資料。
- 「寫成檢查」（D-117）：ESLint 開 `no-console`，只放行這個函式所在的檔與 `src/obsidian/dev*.ts`、`src/dev/`，之後新加的錯誤處理不會漏接。
- 開發版也跑同一段，開發命令的實測就會走到它；`errors` 命令照舊。

### P4｜去重與上限

`state` 讀不到時最多每 60 秒報一次，一個檔讀不到一整天就是約 1,440 次，所以一定要去重。

💡
- 同一次載入裡，`where` 加 `msg` 相同的算同一個錯誤：第 1 次寫一行，之後只在第 10、100、1,000……次各寫一行並帶 `n`。
- 每個月的檔最多 300 行；到了寫一行 `"where":"limit"`，這個月不再寫。行數在這次載入第一次寫之前讀一次自己的檔來算；讀不到就只算這次載入寫的。最壞情況每台裝置每月約 300 KB，平常接近 0。
- 不刪舊的檔（`Files` 沒有刪除，也不需要）。

### P5｜寫入方式

💡
- 立刻追加，不累積：iPhone 切到背景常被系統關掉，放在記憶體等批次會丟。
- 和複習紀錄分開寫：不同的檔，`Files` 的排隊是一個路徑一條，不會讓作答等它。
- 錯誤紀錄自己寫不進去時，丟掉這一行就好：不 `console.error`、不呼叫 `report()`、不重試，所以不會遞迴，也不擋複習。
- iPhone 照樣寫：它和複習紀錄一樣是外掛自己的紀錄，不是卡組（D-134 的 iPhone 不寫卡組不受影響）。

### P6｜stack 對得回原始碼

`main.js` 是壓縮過的（`tools/build.mjs` 的 `minify: true`），stack 只有 `plugin:essence-cards:1:20345` 這種位置，沒有對照表讀不懂。

💡 不另存對照表：需要時從那一版的 tag 重建 source map。D-149 第 4 點已保留每一份正式產物與雜湊，重建出的 `main.js` 雜湊相同，就證明對照表是對的。

- 2026-10-29 Claude 實測（Linux、Node 22，`4a018dc`）：同一個 commit 建置兩次，`main.js` 逐位元組相同；同樣的選項加 `sourcemap: 'external'`，`main.js` 也逐位元組相同（492,324 bytes），另外多一個 2.5 MB 的 `.map`。Windows 待驗。
- 做法寫成一個工具或建置的選項（例如 `npm run build -- --sourcemap <tag>`），細節寫任務說明時定。

**曾考慮**：每次正式建置都存 `.map`（每版 2.5 MB，要多保存一種產物）；不記 stack（`msg` 像 `Cannot read properties of undefined` 時找不到是哪裡）。

### P7｜和備份、還原的關係

💡 備份照 D-150 第 4 點含 `Essence Cards/` 全部，錯誤紀錄跟著備份；還原時不列入勾選清單、不補回（舊的錯誤紀錄沒有用處）。

### P8｜維修時怎麼用、怎麼驗收

- 💡 `docs/agents/quality.md` 的「本專案的做法」加一句：使用者回報問題時，先讀 `紀錄/錯誤/` 那段時間的行，用 `build` 找到版本，要對原始碼位置時照 P6 重建。
- 驗收（寫任務說明時展開成能用程式判斷的句子）：Node 測試涵蓋欄位與截斷、去重的次數、每月上限、寫不進去時不遞迴也不影響作答、只收含 `plugin:essence-cards` 的 window 錯誤；`no-console` 擋住新的直接呼叫；Windows 版 Obsidian 用開發命令製造幾種錯誤，檔案內容符合，重建的 source map 指到正確的原始檔與行；iPhone 併入下一次實機測試：製造一筆錯誤，經 iCloud 回到電腦讀得到（D-065）。
- 時機：學生開始每天使用之前；不併進更新防線。

### 第 3 節逐項查核

**P1｜位置同意，檔名小改；不要把單一寫者寫成同步保證。**

- `紀錄/錯誤/` 可以沿用 `Files`，不用新增 vault 接點或第六個系統資料夾。`isLogPath` 只認 `紀錄/` 直接底下的 `.jsonl`；`isDeckPath` 除了檢查 `.md`，也排除整個 `紀錄/` 系統資料夾。因此載入與 `notify` 都不會把錯誤檔送進排程。這部分事實正確。
- 例子的 basename 和同月複習紀錄完全相同，與 syntax.md §0「整個 vault 檔名不重複」的文字不一致。更小的修正是加用途，例如 `紀錄/錯誤/2026-11 iPhone-7f3a 錯誤.jsonl`，不必新增例外。裝置碼沿用現有的 vault 專用 localStorage，不另配一個碼。
- 一台裝置寫自己的檔能避免主動的多寫者衝突，但不能保證 iCloud 不產生衝突副本、一定同步成功或一定及時回到電腦。說明書那一句可以加；「刪掉不影響複習」成立，但當月刪檔後如何重新計數要與 P4 一起定。
- 和不做比：只放記憶體不能留下 iPhone 重開前的錯誤；放外掛隱藏資料夾則需要繞開目前的 vault 索引接點。這個子資料夾是合理的小做法。

**P2｜欄位大致同意；放寬欄位順序，補上總大小與「不讀」的精確說法。**

- `t`、`build`、`where`、`msg`，加知道時才寫的 `path`、少量自身 stack，已足以留下初步證據。裝置從檔名取得，不必每行重複；目前也不需要作答內容、設定快照或完整問題報告。JSON 欄位順序可以固定方便閱讀，但不必把順序當格式相容契約。
- `path` 目前沒有長度上限；300／600「字」也不是 UTF-8 位元組數，JSON 跳脫還會增加大小。因此「最壞每月約 300 KB」不成立。若要承諾檔案大小，應限制序列化後單行的位元組數，含 `path` 與所有欄位；否則只寫行數上限與粗估，別寫成最壞保證。
- 不進排程與不受 `need` 閘門控制是合理的：它沒有舊版產品讀取端，現有 AI 快照也有「只寫不供產品讀取」的前例。但 P4 會讀檔數行，應改成「外掛不解析或使用錯誤紀錄的業務內容」，不能同時說完全不讀。
- `unknown` 不一定是 `Error`，可能是字串、`null` 或不能 JSON 序列化的物件。錯誤轉文字、截斷、取 stack 本身都要能安全失敗，不能讓記錄函式再拋錯。`msg` 可能帶原文的隱私敘述正確；本機查修只把自編例子與摘要放進 repo。

**P3｜同意集中上報，不同意「換掉表上每處就不會漏」；React 優先直接接自己的 root。**

- 不覆寫正式版的全域 `console.error` 是對的。呼叫端只交出錯誤與已知的上下文，寫檔集中在一個實例；UI 用回呼交給主機，不讓元件自己持有 `Files` 或匯入 `main.ts`。`no-console` 限於產品程式、窄列例外即可；它能擋直接 console 呼叫，**擋不到空的 catch、吞掉的 rejection 或完全沒上報的分支**。
- **已重現的遺漏**：`src/state/index.ts:292` 的 `files.watch()` 在讀取佇列的錯誤回報之外。隔離探針讓它拋錯，`ready()` 拒絕，但 `onError` 呼叫是 0 次；`src/main.ts:183` 又用空的 rejection handler 接走。因此不會經 `report`，也不會變成 window 的未處理拒絕。`load()` 最後的首次排程也在讀取佇列之外（`:320`；靜態推斷）。應只補報這些尚未報過的非預期初始化錯誤，避免把同一個讀取錯誤報兩次或把正常停用記成故障。
- 複習 root 目前是 `src/ui/host.tsx:53` 的 `createRoot(element)`，沒有 error boundary 或自訂錯誤 handler。本機 lock 與實際安裝的 `react-dom` 都是 **19.3.1**；其正式版實作 `defaultOnUncaughtError` 會呼叫 `reportGlobalError`，再用宿主的 `reportError`，或退回派送 window `ErrorEvent`。所以「沒有 boundary 的 React 渲染錯誤通常會上報到 window」有程式依據，但不能推成每種 React 失敗都帶可辨識的自身 stack。更小且確定屬於本外掛的做法，是在自己的 root 接 `onUncaughtError`（需要時另接 `onRecoverableError`），不必為了留證據新增 fallback 畫面。[React 官方 root 錯誤回報介面](https://react.dev/reference/react-dom/client/createRoot#show-a-dialog-for-uncaught-errors)。
- window 監聽可以當補網，不能當完整保證。字串 rejection 沒有 stack；其他外掛若名字以 `essence-cards` 開頭，也會被單純的 `includes('plugin:essence-cards')` 誤收。應辨認完整 plugin ID 的 frame，再截斷保存。**本輪沒有取得 Windows Obsidian／iPhone 的實際 stack 樣本；不能把該字串在兩端必定存在寫成已驗證。** 缺少標記時寧可漏收全域錯誤，也不要收進其他外掛；直接接的自身回報不應受這個篩選限制。

**P4｜同意少量去重；不同意目前的月上限保證。**

- `where + msg` 有兩個方向的誤差：兩篇檔案都報同一句「讀不到」會被合成一個；訊息包含變動的次數、時間或路徑時，同一原因又會一直變成新錯誤。最小修正是把已知 `path` 與首個自身 frame 納入判別；對已知的讀取重試，以固定操作與路徑辨認，不先寫一套猜測訊息的通用正規化器。其他錯誤寧可保守分開，再由上限保護。
- 現有 `state` 一批多檔失敗時只保留第一個 `reason`（`src/state/index.ts:225`、`:278`），而 `onError(error, source)` 沒有路徑參數。不能假定加上選填 `path` 就自然拿到每個失敗檔；要由讀取處傳出上下文，或明列本次只保留批次代表錯誤的限制。不要為了記錄再讀一次壞掉的檔案。
- 1、10、100、1,000 的取樣可先採用，是壓低連續重試雜訊的簡單預設；`n` 要明說是「本次載入、此去重鍵的累計次數」，不是檔案內或跨啟動的總次數。沒有實測頻率能證明 300 是最佳值，把它當保守預設即可。
- **規格漏洞**：檔案已有 290 行、讀取失敗後再啟動，每次仍可追加本次的 300 行；重複啟動就沒有月上限。讀取失敗也不能當檔案不存在。更小且真的有界的做法是：讀不到當月檔時停寫診斷，複習照常；若選擇優先保留這次錯誤，就必須承認只有本次載入上限，不能再聲稱月上限。建議前者，不另外維護一份跨啟動計數資料。
- 明訂 300 **包含**最後的 `limit`，例如最多 299 筆加 1 筆上限標記；同一檔的首次計數只做一次、共用同一個初始化結果，在等待追加之前就預留名額，避免同時上報超額。跨月要重新決定檔案與配額；卡住的讀取／追加也不能留下無界的待寫工作與去重表。月上限仍不是歷年總上限，不刪舊檔就會逐月累積，應如實寫明。

**P5｜同意盡快追加與寫失敗就丟棄；「不影響作答」需要補一個前提。**

- **已以基準 adapter 與替身驗證**：檔案與資料夾都已存在時，卡住錯誤檔的 `append`，複習檔的 `append` 仍能先完成；`src/obsidian/files.ts:16` 的確是每個正規化路徑一條佇列。錯誤紀錄不應加入作答 writer、`state.flush()` 或 `close()` 必須等待的工作，自己的拒絕必須接住，不重試、不呼叫上報函式。
- **另有條件風險，已在替身重現、實機待驗**：`create()`（`:28`）不是按父資料夾協調。`Essence Cards/` 已有但 `紀錄/` 還沒有時，錯誤與作答同時首次追加，會同時判斷父層不存在並呼叫 `createFolder`。在「已存在就拒絕」的 vault 替身裡，錯誤建檔成功、作答追加以 `Folder already exists: Essence Cards/紀錄` 失敗。作答 writer 仍保留該筆待重試，但不能再宣稱第一次作答寫入完全不受影響。實作前應驗證真實 API，並讓已被另一個寫入者建好的正確資料夾可安全沿用；不必把不同檔案全部改成共用一條寫入佇列。
- 佔位檔可能讓診斷的首次讀取或追加失敗、長時間未完成；不等待它，才能保住複習的邏輯順序。盡快呼叫 `append` 也不能保證 iOS 終止程式前已持久化或 iCloud 已同步，這是盡力留證據。診斷寫入同樣依賴壞掉的儲存／同步通道，不能承諾每次儲存故障都有檔案證據。iPhone 透過 `Files` 寫自己的 JSONL 與 D-134 不衝突。

**P6｜保留 raw stack；先不做「從任意 tag 重建」的新工具。**

- 不做 P6，仍可從時間、版本、環節、路徑、訊息診斷讀寫故障；主要損失是壓縮後的未知程式例外難以定位。raw frame 本身仍有區分呼叫位置的價值，應保留。這不構成把重建工具排在 G1 前面的理由。
- **Windows Node 探針通過**：從 Git 取出 `2d11fc2` 的輸入，使用對應已安裝的依賴、Node `24.13.0`、esbuild `0.25.12`、固定 `BUILD=0.0.1+2d11fc2`，依原建置選項在隔離目錄重建。兩次建置、改成 `sourcemap: 'external'`、將 TS／TSX 轉成 CRLF，`main.js` 都逐位元組相同：492,324 bytes，SHA-256 `046715970deb272cbb070245362d6b51e61ad4b2d5e53ea247394e75187be95c`。map 的產物位置 `151:1426` 也能對回 `src/core/deck/read.ts:5` 的根目錄字串。這支持重建的可行性，**不是已對上某份正式安裝產物，亦不是 Obsidian 執行期 stack 的定位測試**。[esbuild external source map 說明](https://esbuild.github.io/api/#sourcemap)。
- 若第一次維修需要，再用該版本乾淨的來源與 lockfile、精確依賴及建置選項產生 map，先比保存的正式 `main.js` 雜湊，對不上就停止定位；不要把 `BUILD` 字串相同當證明。若需求是「從第一版起保證可定位」，我反而建議正式建置時就把 external map 與產物一起留在**電腦本機 release 保存處**：每版約 2.5 MB 不會增加手機或 vault 空間，通常比維護重建環境與新工具便宜。先比較這個代價，不預設不存 map 一定省。
- 還要驗證 Obsidian 載入程式時的包裝有沒有增添行／欄位偏移，以及 stack 的 1 起算座標轉 map 的 0 起算座標。測試應由真正的外掛來源行拋錯再定位；不能直接用生成檔座標取代。`.dirty` 的原始修改不在 tag 裡，不能靠 tag 還原；沒有保存當時來源／map 就標成無法可靠定位。

**P7｜備份同意；「不列清單、不還原」是新例外，現有工具沒有。**

- 分支 `claude/update-safeguards-1` 的 `src/core/backup/plan.ts`（`672db3d`）第 74 行只排除 `isLogPath`；第 101 行把 `紀錄/` 的其餘檔案套用「只補不見、同名不同內容擋住」。**已用公開的 `planRestore` 重現**：錯誤檔不見時出現在 `files`，`action=restore`；同名不同內容時 `action=blocked`；兩者都不在逐行補回的 `logs`。所以現在會採用與 AI 快照相同的通用規則，並非自動排除。
- 站在不做那邊：沿用現有分類能省下專屬例外，舊的錯誤也可能正是維修需要的證據，不能概括說「沒有用處」。但若決定診斷檔可刪、不應由還原端重建仍由裝置追加的檔，P7 的排除有道理；需在 D-150／syntax 明訂這個新例外，實作在還原分類處，不要擴大 `isLogPath` 去包含錯誤檔，否則會破壞排程隔離。這個取捨尚未當成定案。
- 還有更新防線的成本：本機已合併的 `tools/backup.ts:58` 只容許真正複習紀錄的尾端追加；錯誤檔變動會讓快照重試，持續變動可讓備份失敗。本機 `tools/update-vault.ts:102` 的 `changedSince` 也會把新增／追加的錯誤檔列成 `--check` 後資料變動；已以公開函式重現。這是偏保守的現有行為，不會讀錯排程，但不能說對備份與更新完全沒有影響。最小版可先保留並記清楚，未證明有干擾前不另改備份格式或放寬所有 JSONL 的檢查。

**P8｜同意既有時機與實機合併；驗收補真正會漏的邊界。**

- 相對整件不做，這些測試能防止「為留證據而使作答更容易失敗」，不是單純驗欄位。除了稿上已有的測試，至少補：空的新 vault 的共用父層競爭；讀不到／一直不回的診斷檔不阻塞作答與 flush；同時上報、重載、跨月與已有 `limit` 的配額；不同檔同訊息、同檔的固定重試；非 `Error` 值；初始化的非預期拒絕；只有相近 plugin ID 的其他錯誤不收；停用再啟用不累加全域監聽。
- Windows 要驗證正式版選項的 React root 錯誤與實際 stack，再驗一次真正的來源行對回；iPhone 集中在下一輪測「自身同步例外、非同步拒絕、重開後檔案仍在且回到電腦」。目前只有設計，不能把 Node 探針算成這些驗收通過。
- 維修指引加在現有品質文件即可，不必再建另一份流程清單。讀錯誤前先接受它可能因同步／配額／寫入失敗而缺漏；「沒有那行」不能推成「沒有發生」。

### 第 5 節逐題回答

1. **第 2 節有漏項與過度概括。** 讀取重試的退避大致正確，但不是每個失敗檔各報一次，而是每批第一個錯誤；作答寫入失敗靠後續作答／flush 再試，不套用讀取的 60 秒退避。另有 `ready()` 初始化例外被主機空 handler 接走，完全不進 console 或 window（P3 已重現）。React root 的未捕捉渲染錯誤有全域上報的實作依據；它與「Obsidian 在 Windows／iOS 都給指定 stack 格式」是兩件事，後者仍待實機。`void start()` 的未接拒絕一般會到全域，但其中 `state.ready()` 已被自己的 catch 接掉，不能全歸到 window。開發版收集器是動態載入後才安裝，也不涵蓋載入它以前的所有錯誤。
2. **整件不做**省下格式、寫入、去重與測試的維護，但會失去第一次 iPhone 故障的時間、版本與錯誤原文；之後再裝新版無法補回那一次。只有一家用、實際故障頻率未知，尚不能聲稱每次固定省 20 分鐘；能說的是有機會少做一次手機重現往返。因此建議保留小版：P1～P5 的自身回報與有界追加，加自己的 React root 回報；先不建 G2、診斷畫面、通用訊息正規化或任意 tag 重建工具。**只做 P1～P5、不做 P6**仍有讀寫與路徑證據，主要少未知壓縮程式錯誤的精確原始位置。只存記憶體或要求當場執行命令，無法同樣留下重開後的 iPhone 證據；現有儲存通道本身故障時，這個小版也無法保證留到。
3. **排程與讀取閘門安全，還原會分類成一般紀錄附件。** 基準的 `isLogPath`／`isDeckPath` 和 `state.notify` 都會排除該路徑；本機退版工具用 `readDecks`、`readHistory`，也不會解析錯誤行的 `need`。備份會包含，還原目前列在 `files`、只補遺失／衝突擋住，詳見 P7；不會當作複習紀錄逐行合併。AI 快照尚不是有獨立產品讀取端的功能，不要把通用還原分類誤寫成 AI 已在讀它。
4. **會；也會把不同問題合併。** 動態訊息會分裂，同句不同路徑／來源會合併。取樣門檻可先用，300 是預設而非經驗證的最佳值。需採 P4 的路徑／位置上下文、讀不到時的明確取捨與配額預留，才能談月上限；`limit` 是否算第 301 行也要先消除歧義。
5. **既有檔案下的路徑佇列獨立；首次共用父層建立與底層 I/O 並不獨立。** P5 的替身探針證明這兩者不同。診斷檔的雲端讀取卡住時，只能讓診斷停著，不能把它掛在作答 writer／flush；作答自身的佔位檔問題仍照 D-154 處理。另有 P7 的快照／更新重檢成本，不是作答先後被改了。
6. **至少要固定真實來源、lockfile 與實際相依版本（含 esbuild）、全部編譯選項、正式／DEV、`BUILD` 與 banner 等輸入，並核對保存的正式產物雜湊。** 換行在本輪的 Windows 探針不改變生成檔，但不能由此推廣到未測過的版本或平台；hash 是每次重建的閘門。map 必須對應同次重建的來源內容，再處理 Obsidian 包裝與座標差異；`.dirty` 沒有快照就不能由 tag 證明。若要現在就提供可靠保證，同次正式建置保留 map 的做法更小，見 P6。
7. **還有幾種要明列的邊界。** 外掛解析／載入失敗可能發生在 reporter 註冊以前；字串 rejection 或由外部非同步 API 建立的錯誤可能沒有自身 frame；掛住、系統直接終止與單純排程結果不對，本來就可能沒有例外，不能靠 G1 偵測。語法問題也多是 `problems` 資料而不是 throw，不應把所有問題改成錯誤紀錄。重載會重置 `n`、換月會換配額、停用需移除監聽，應列入 P8。若故障和 Obsidian 升版有關，僅 `BUILD` 與裝置名仍不知道宿主版本；需要時從現有環境資訊補查，不因此把 G2 全部拉進本次。

**交使用者確認的結論**：

1. 正式版把**這個外掛自己的**錯誤，每台裝置每月記一個小檔：`Essence Cards/紀錄/錯誤/`，每月最多 300 行、每行最多 2 KB；同一個錯誤只在第 1、10、100…次記。記時間、版本、Obsidian 版本、哪個環節、錯誤訊息，知道時加檔案路徑與程式位置；不記作答、卡片內容與設定，不上傳。
2. 寫不進去或讀不到當月的檔就不記，複習照常；不保證每個錯誤都留得下來。
3. 正式安裝時把「程式位置對照表」存在電腦本機（每版約 2.5 MB），錯誤裡的位置對得回原始碼。
4. 備份含這些檔；還原畫面不列它們，免得家長看到看不懂的衝突。
5. 時機：學生開始每天使用之前，寫成一份任務說明交本機 session；iPhone 的部分併入下一次實機測試。

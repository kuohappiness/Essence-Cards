## 1. 要解決的事

正式版遇到錯誤時沒有留下證據。iPhone 上沒有人看得到主控台；重開之後就沒了；開發版能收集（`errors` 命令），但開發版不能裝到正式使用的 vault（D-149 第 4 點）。學生真正使用後在 iPhone 碰到問題，AI 只能猜、在測試 vault 重現、再請使用者到 iPhone 重測（一輪約 20 分鐘）。

**範圍**：只留證據，給維護的 AI 讀。不加畫面、不提示、不上傳；外掛自己不讀這份檔案。「複製問題報告」命令（G2）與查單一目標排程的工具（G3）不在這次，見[規畫](../docs/plans/maintenance.md)第 2 節。

## 2. 錯誤現在去哪裡

| 來源 | 現在怎麼處理 | 使用者看得到什麼 |
|---|---|---|
| `state` 讀不到（`read`），每次重試失敗都會再報一次：1 秒起加倍，最多 60 秒一次（`retryDelay`） | `report()`：`console.error`，每次載入第一次出 Notice | 一次「有些卡組或複習紀錄暫時讀不到」 |
| 紀錄寫不進去（`write`），包括切到背景時的 `flush` | 同上 | 一次「複習紀錄暫時寫不進去」 |
| `state` 監聽者丟錯（`listener`） | `report()`，沒有 Notice | 沒有 |
| 卡片顯示不出來（`Markdown.tsx`） | `console.error`，那一塊寫「這張卡顯示不出來」 | 那一塊的字 |
| 離開筆記時補 ID 失敗（`save.ts` 的 `leave`） | `console.error` | 沒有 |
| 停用時關閉失敗、外掛事件的監聽者丟錯（`main.ts`） | `console.error` | 沒有 |
| 其他沒接住的錯：例如複習畫面的 React 錯誤（沒有 error boundary）、`void start()` 裡的拒絕 | 只變成 window 的 `error`／`unhandledrejection` | 可能是畫面空白或沒反應 |

開發版的 `collectErrors` 換掉全域的 `console.error`，連 Obsidian 與其他外掛的錯誤都收（200 筆，只在記憶體）。

## 3. 提案（💡）

### P1｜位置與檔名

💡 `Essence Cards/紀錄/錯誤/<年-月> <裝置名稱-隨機碼>.jsonl`，例如 `紀錄/錯誤/2026-11 iPhone-7f3a.jsonl`：每台裝置每個月一個檔，和複習紀錄同一種命名（syntax.md §5）。

- 每個檔只有一台裝置寫，iCloud 不會互相覆蓋；走 `Files.append`，不加新的接點（D-110）。
- `紀錄/` 底下有前例：AI 輸出快照在 `紀錄/AI 輸出/`。`isLogPath` 不讀子資料夾，`isDeckPath` 只看 `.md`，所以 `state` 收到它的變動通知也會忽略（`notify`），不會讀進排程。不加第六個系統資料夾（D-088、D-108）。
- 說明書的「資料夾管理規範」（D-048 補充 2026-10-16）加一句：外掛自己寫、給維修用，刪掉不影響複習。

**曾考慮**：外掛資料夾 `.obsidian/plugins/essence-cards/`（家長看不到，但 `Files` 的 Obsidian 版用 vault 的索引，碰不到點開頭的資料夾，要另開接點；D-150 第 4 點的備份只含 `data.json`）；新的系統資料夾 `Essence Cards/錯誤/`（要改 D-088 的清單，家長多看到一個資料夾）。

### P2｜一行記什麼

💡 一行一筆 JSON，欄位順序固定：

```
{"t":"2026-11-02T20:15:03.250+08:00","build":"0.1.0+1a2b3c4","where":"render","msg":"Cannot read properties of undefined (reading 'text')","path":"Essence Cards/國二上/自然/2-2 水溶液（卡片）.md","stack":"at Xe (plugin:essence-cards:1:20345)\nat …"}
```

| 欄位 | 內容 |
|---|---|
| `t` | 時間，和複習紀錄同一種寫法（`formatTime`） |
| `build` | `BUILD` 原樣 |
| `where` | 哪個環節：`read`、`write`、`listener`（沿用 `ErrorSource`），加上 `render`、`fill`（離開筆記補 ID）、`close`、`event`（外掛事件的監聽者）、`uncaught`（window 的錯誤）、`limit`（P4 的上限） |
| `msg` | 錯誤訊息，最多 300 字 |
| `path` | 選填，知道是哪個檔時才寫 |
| `stack` | 選填，只留含 `plugin:essence-cards` 的幾層，最多 600 字 |
| `n` | 選填，同一個錯誤到第幾次（P4） |

- 不寫的東西：作答、卡片內容、設定值、其他外掛的錯誤。`msg` 與 `path` 可能含筆記路徑或卡片的字，所以這份檔案和卡組一樣只留在家裡的 vault；維護的 AI 在本機讀，寫進 repo 時只寫摘要（D-003）。
- 外掛自己不讀這份檔案，所以 D-149 第 3 點的「永遠不改」與讀取閘門不適用：欄位可以隨版本增減，每一行有 `build` 可以對。syntax.md 加一小節寫明這點與欄位。

### P3｜收集範圍：只收自己的

💡 正式版不換掉全域的 `console.error`。改成一個函式（例如 `recordError(where, error, path?)`）：照舊 `console.error`，再寫一行；第 2 節表上每一處都改呼叫它。window 的 `error`、`unhandledrejection` 只在 stack 含 `plugin:essence-cards` 時才記。

- 換掉全域的會收到 Obsidian 與其他外掛的錯，多出雜訊，也記到不是這個外掛的資料。
- 「寫成檢查」（D-117）：ESLint 開 `no-console`，只放行這個函式所在的檔與 `src/obsidian/dev*.ts`、`src/dev/`，之後新加的錯誤處理不會漏接。
- 開發版也跑同一段，開發命令的實測就會走到它；`errors` 命令照舊。

### P4｜去重與上限

`state` 讀不到時最多每 60 秒報一次，一個檔讀不到一整天就是約 1,440 次，所以一定要去重。

💡
- 同一次載入裡，`where` 加 `msg` 相同的算同一個錯誤：第 1 次寫一行，之後只在第 10、100、1,000……次各寫一行並帶 `n`。
- 每個月的檔最多 300 行；到了寫一行 `"where":"limit"`，這個月不再寫。行數在這次載入第一次寫之前讀一次自己的檔來算；讀不到就只算這次載入寫的。最壞情況每台裝置每月約 300 KB，平常接近 0。
- 不刪舊的檔（`Files` 沒有刪除，也不需要）。

### P5｜寫入方式

💡
- 立刻追加，不累積：iPhone 切到背景常被系統關掉，放在記憶體等批次會丟。
- 和複習紀錄分開寫：不同的檔，`Files` 的排隊是一個路徑一條，不會讓作答等它。
- 錯誤紀錄自己寫不進去時，丟掉這一行就好：不 `console.error`、不呼叫 `report()`、不重試，所以不會遞迴，也不擋複習。
- iPhone 照樣寫：它和複習紀錄一樣是外掛自己的紀錄，不是卡組（D-134 的 iPhone 不寫卡組不受影響）。

### P6｜stack 對得回原始碼

`main.js` 是壓縮過的（`tools/build.mjs` 的 `minify: true`），stack 只有 `plugin:essence-cards:1:20345` 這種位置，沒有對照表讀不懂。

💡 不另存對照表：需要時從那一版的 tag 重建 source map。D-149 第 4 點已保留每一份正式產物與雜湊，重建出的 `main.js` 雜湊相同，就證明對照表是對的。

- 2026-10-29 Claude 實測（Linux、Node 22，`4a018dc`）：同一個 commit 建置兩次，`main.js` 逐位元組相同；同樣的選項加 `sourcemap: 'external'`，`main.js` 也逐位元組相同（492,324 bytes），另外多一個 2.5 MB 的 `.map`。Windows 待驗。
- 做法寫成一個工具或建置的選項（例如 `npm run build -- --sourcemap <tag>`），細節寫任務說明時定。

**曾考慮**：每次正式建置都存 `.map`（每版 2.5 MB，要多保存一種產物）；不記 stack（`msg` 像 `Cannot read properties of undefined` 時找不到是哪裡）。

### P7｜和備份、還原的關係

💡 備份照 D-150 第 4 點含 `Essence Cards/` 全部，錯誤紀錄跟著備份；還原時不列入勾選清單、不補回（舊的錯誤紀錄沒有用處）。

### P8｜維修時怎麼用、怎麼驗收

- 💡 `docs/agents/quality.md` 的「本專案的做法」加一句：使用者回報問題時，先讀 `紀錄/錯誤/` 那段時間的行，用 `build` 找到版本，要對原始碼位置時照 P6 重建。
- 驗收（寫任務說明時展開成能用程式判斷的句子）：Node 測試涵蓋欄位與截斷、去重的次數、每月上限、寫不進去時不遞迴也不影響作答、只收含 `plugin:essence-cards` 的 window 錯誤；`no-console` 擋住新的直接呼叫；Windows 版 Obsidian 用開發命令製造幾種錯誤，檔案內容符合，重建的 source map 指到正確的原始檔與行；iPhone 併入下一次實機測試：製造一筆錯誤，經 iCloud 回到電腦讀得到（D-065）。
- 時機：學生開始每天使用之前；不併進更新防線。

## 4. 這次不做

- 畫面與提示：平常不打擾，只給維修用。
- 讀取很慢或一直不回來的紀錄：那不是錯誤，D-154 第 4 點的實測有結果再談。
- 上傳到任何地方、其他外掛的錯誤、作答以外的操作紀錄（規畫第 3 節）。

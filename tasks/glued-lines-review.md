## 第二部分：L2

### 行為與風險

- **公開介面**：`mergeHistory`（`src/core/study/history.ts`），呼叫端是 `readHistory` 與 `state` 的 `batch`（`src/state/index.ts`）。`readablePieces`、`objectEnd` 不匯出。
- **不可破壞的性質**：整行讀得懂的路徑完全不變；整行是合法 JSON 時不往裡面挖（`tests/study.test.ts` 的「只在 JSON.parse 失敗時救」）；每一塊先看 `need`；`History.seen` 不漏（`tests/study.test.ts` 的 seen 性質）；重複、取消、同一個 `t` 的規則和分開成好幾行時相同；排序的 tie-break 不變（路徑、行號，同一行裡照順序）。
- **已知邊界例子**：`tests/glued-lines.test.ts`，有規格列的全部例子、state 層的原例、和分行對照的不變量與 200 組隨機組合。例子只是起點，請找新的組合。
- **真實路徑**：還沒找到正常寫入會產生這種行的途徑（兩個 `Files` 都一次追加 `line + '\n'`）；測試 vault 現有 4 個紀錄檔共 731 行沒有這種行，這只說明目前沒遇到。每項發現照舊標真實路徑會不會發生。

### 實作者自己選的做法（請先看）

1. **括號對得上、但不是 JSON 的一塊**：當成餘段，不跳過繼續。`{"t":壞}` + A + B 只救 B，和現在相同；規格的「辨認不出的餘段照現在救最後的尾段」沒有分這一種。
2. **物件之間的空白**（空格、Tab、CR）跳過，不算餘段：`A B C` 三筆都算。規格沒寫；不跳過的話只會少中間那幾筆。
3. **完整的物件後面接雜訊**：物件照採用（`A壞掉` → A）。舊版這種行什麼都不救（尾段的開頭在 0）。開頭是雜訊時照舊只救最後的尾段（`壞掉` + A + B → B），因為規格寫「從行首」。
4. **完整但缺必要欄位的物件**：不往裡面挖，也不停下來，繼續讀下一塊（`{"nested":A}` + B → B），和分開成兩行相同。
5. **`problems` 的說明改了**：統一成「寫入中斷或幾筆接在同一行；已救回讀得出來的紀錄，（有的需要新版才讀得懂，）原檔沒有改」，不寫幾筆（`A` + `A` 救了兩段但只算一筆）。`tests/need-lines.test.ts` 的兩個舊斷言跟著改。這段文字現在只有開發命令算數量，沒有畫面。
6. **`seen` 多讀一項**：`looseLts` 也照 JSON 讀 `readablePieces` 的每一段。夾在中間的完整物件用跳脫的鍵名（`lt`）時，舊的三種找法都找不到。
7. **沒改 `lastVersions`**（`src/core/backup/versions.ts:48`）：接在一起的版本行照舊跳過。影響是版本列表顯示舊一點、這台可能多寫一行版本行，不影響排程；完成條件只寫到 `mergeHistory`。請判斷這樣夠不夠。
8. **作答之後、下一次合併之前的 `problems`**：`appendLine` 不動 `problems`，所以原例作答後 `state.history().problems` 是空的，`readHistory` 已經有一個；`reviews` 兩邊相同，下一次合併後整份相同。測試只在合併後比整份。
9. **已知限制（照舊，沒有變差）**：沒關上的外層，最後一段剛好是完整的範例（`{…"val":[` + A）時，A 照舊被救回；壞的開頭 + B + C 只救 C，B 不算（規格的 (b) 要這樣）。

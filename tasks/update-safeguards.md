## 0. 格式（先做，Codex 查核後才寫程式）

### 0-1 要寫進 syntax.md 的內容

1. **§5 版本行**：`set` 種類加 `app`，`val` 是建置版本（`BUILD`，例如 `0.1.0+1a2b3c4`），沒有 `deck`／`lt`。說明：每台裝置第一次跑一個新的建置版本時寫一行，退回舊版也寫；每台裝置各記各的，不適用「兩台都發現同一個變更時取最早」。
2. **最低版本標記**：
   - 卡組筆記的屬性（§2-1）加 `需要版本`，紀錄的每一行可以有 `need`；值只接受正式版號 `主.次.修`（三段非負整數，不帶 `v`、不帶預發版字尾），比較時三段各自比數字，`+commit` 不參與。
   - 讀到比自己新、或格式不對的標記：卡組整篇不出題、Cards 也不寫它；紀錄行保留原文、停掉它影響的學習目標（`lt`，或 `undo` 指到的那一筆的 `lt`），辨認不出來就全部停，並提示更新。標記在業務欄位之前檢查。
   - 寫一句兩段發布：要寫標記的新寫法，等每台仍在用的裝置都換成讀得懂的版本才開始寫。現在沒有任何寫入端。
3. **§5 還原檔**：`紀錄/<來源檔名去掉 .jsonl> 還原 <日期> <還原的裝置碼>.jsonl`，例如 `2026-10 iPhone-7f3a 還原 2026-11-02 Windows-2c9e.jsonl`；直接放在 `紀錄/`；只有還原的那台電腦寫、一次寫完；內容是來源檔缺的行原樣照抄（含壞行）。寫明檔名為什麼要這樣排（緊貼來源檔前面，合併結果和那些行還在來源檔時相同）。D-035 的「每台裝置每個月一個檔」改寫成包含這個例外。
4. **新的一節「8. 備份檔」**（放在 §7 後面，不改既有章節編號）：zip 加一份清單 `manifest.json`。清單的草案（欄位名稱由 Codex 查核時一起定）：

   ```json
   {
     "format": "essence-cards-backup",
     "version": 1,
     "vault": { "name": "Essence", "path": "D:/…/Essence" },
     "build": "0.1.0+1a2b3c4",
     "by": "update-vault",
     "started": "2026-11-02T20:15:03.250+08:00",
     "finished": "2026-11-02T20:15:05.004+08:00",
     "scope": "這台電腦當時看得到、讀得到的檔案；不保證包含還沒同步的其他裝置紀錄",
     "files": [{ "path": "Essence Cards/紀錄/2026-10 iPhone-7f3a.jsonl", "size": 48211, "sha256": "…" }],
     "excluded": [],
     "notes": [{ "path": "Essence Cards/學業/…（卡片）.md", "message": "原本就有語法問題，照原樣備份" }]
   }
   ```

   zip 裡的路徑和 vault 裡相同；檔名 `Essence Cards 備份 <日期時間> <BUILD> <隨機 4 碼>.zip`，用暫存名寫完、檢查通過才改名。

## 1. 第一部分：Node 工具

外掛的行為不變，`src/main.ts` 不碰。純邏輯放 `src/core/backup/`（不 import Node 或 `obsidian`；之後外掛內的備份會直接用），讀寫檔案的部分放 `tools/`。

### 1-1 備份（D-150 第 5 點，過渡版）

- `npm run backup -- <vault> [--to <資料夾>] [--config <設定資料夾>]`：備份 `Essence Cards/` 全部，加上 `<設定資料夾>/plugins/essence-cards/data.json`（有的時候；沒有就在清單的 `absent` 記下）。**過渡工具不排除任何檔案**（D-150 第 4 點的排除只在外掛內做）。
- 設定資料夾（Codex 格式查核 F3，syntax §8）：預設 `.obsidian`，`--config` 可以指定別的；裡面沒有 `plugins/essence-cards/manifest.json` 就整份失敗，不把 `data.json` 記成不存在。寫進清單的 `vault.config`。
- 預設位置：Windows 是 `%LOCALAPPDATA%\Essence Cards\備份\<vault 名稱>\`，其他系統用對應的應用程式資料夾。`--to` 可以改；用實際路徑（`realpath`，解析 junction 與符號連結）檢查，落在 vault 裡就拒絕。
- 封裝 App（使用者 2026-10-29 選 A）：在 Claude 桌面 App 裡跑時，`%LOCALAPPDATA%` 會被導到 App 的私有資料夾（syntax §8「位置」）；實際路徑落在那裡就拒絕，要用 `--to` 指定 App 以外的資料夾。維護的 AI 用使用者指定的那一個（記在本機 Claude 的記憶）；`restore --apply` 的還原前備份也有 `--to`。
- 檢查（任何一步失敗就整份失敗、不留正式檔名）：
  1. 讀原始位元組（不經文字解碼）；讀不到（Windows 的 iCloud 只留雲端佔位檔、權限、消失）要分清楚原因寫進錯誤。
  2. 讀完重新列檔：檔案集合要相同；每個檔案重新算雜湊要相同；紀錄檔只多了後面的行時，檢查舊內容是新內容的完整開頭，用舊內容。卡組在中途被改了就整份重來，最多 3 次。
  3. zip 寫完重新讀回，每個檔案的雜湊和讀進來的相同。
  4. 用 `parseDeck` 讀 zip 裡的每一篇卡組與讀進來的那一份，學習目標 ID 與題目指紋相同。原本就有語法問題的照原樣備份，記在 `notes`，不算失敗。
- 不自動刪舊備份（過渡期只有幾份）。
- zip：用小型、純 JS、電腦與手機都能跑的套件（例如 fflate），釘死版本，寫明理由；之後外掛會用同一個，要能過 D-148 的建置檢查。

### 1-2 還原工具（D-150 第 7、8 點，由維護的 AI 操作）

- `npm run restore -- <vault> <備份檔> --plan`：寫一份還原計畫到備份資料夾旁（不進 repo）：
  - 和現在不同的檔案：改過的、不見的；備份後才有的列出但不動。每個改過的檔附文字差異（圖片只列大小與雜湊）。
  - 全庫 ID 檢查：假設照計畫還原後，`Essence Cards/` 裡所有卡組（不只要還原的那幾篇）有沒有重複的學習目標 ID，同一篇裡重複也算。會造成重複的檔案標成「擋住」，寫出是哪個 ID、現在在哪一篇。
  - 複習紀錄：每個來源檔，算出備份有、現在的來源檔與先前的還原檔都沒有的行（先 trim 再比，和 `mergeHistory` 相同）；備份檔最後一行如果是現在某一行的開頭，不算缺。
  - `紀錄/` 裡不是複習 JSONL 的檔案（之後的 AI 輸出快照、規則內容）：只補不見的，同名不同內容列成衝突。
  - 先照 syntax §8「讀備份的一方」驗整份備份（清單的必要欄位與型別、zip 與清單一一對應且不重複、路徑範圍）；不過就不出計畫。
  - 目的地（Codex 格式查核 F3、F4）：`data.json` 寫出來源與目的的設定路徑（目的用 `--config`，預設 `.obsidian`，同樣要有 `plugins/essence-cards/manifest.json`），確定不了就擋住；對應之後兩個來源會寫到同一個檔（照這台電腦的大小寫規則），兩個都列成衝突並擋住。
- `npm run restore -- <vault> <備份檔> --apply <計畫檔> [--files …]`：先跑一次 1-1 的備份；寫每個檔案前重新確認它還是計畫裡的那一份（雜湊），不是就跳過並列出；寫還原檔（syntax §5 的檔名，一次寫完）；最後列出每個檔案的結果（已還原、跳過、擋住、失敗）。重跑 `--plan` 就是續做。
- 前提寫在命令的說明與輸出：**這台電腦的 Obsidian 要先關掉**（外掛內的還原才處理 Editor 與補 ID 計時器）。

### 1-3 發布前比較（D-149 第 5 點）

- `npm run compare-versions -- <備份檔> <舊 commit> <新 commit>`：用 1-1 的備份當凍結的輸入（記下 zip 的雜湊），兩個版本各用 `git worktree` 開在暫存資料夾、照各自的 lockfile `npm ci`，各在自己的 Node 程序裡跑一個小轉接器，讀 zip（記憶體裡的 `Files`）輸出同一種比較資料：
  - 每篇卡組：學習目標（有 ID 用 ID，沒 ID 用位置與名稱）、題目指紋、問題清單、會影響排程的屬性。
  - 排程：用備份的時間與時區當「現在」，每個目標的下次到期時間，以及今天的份（ID、題目與方向、順序、用的保持率）。另外彙總未來 30 天每天的到期數（固定現有紀錄，不模擬之後的作答）。
- 轉接器放 `tools/compare/`，依版本範圍選；接不上（函式不存在、型別不同）就輸出「無法比較」，不能當成零差異。轉接器只拿唯讀的 `Files`，不跑會補 ID 或寫紀錄的流程。
- 報告寫到備份資料夾旁（不進 repo），開頭寫輸入的 zip 雜湊、兩邊的 `BUILD`、比較時間，以及限制：`exam` 目前是 `null`，沒有比到考前的排序。
- 第一次：舊版是正式 vault 裡現在的 `main.js` 的 `BUILD`；讀出 commit 且不帶 `.dirty` 就用那個 commit，否則報告寫「基線缺失」，由使用者決定要不要照樣裝。

### 1-4 安裝的擋法（D-149 第 4 點，寫在 `tools/install-vault.mjs` 本身）

- 測試 vault 登錄在 `.local/test-vaults.json`（加進 `.gitignore`），存實際路徑。比對時兩邊都先 `realpath`。
- `--dev`：目標必須是登錄過的測試 vault，否則拒絕。
- 不帶 `--dev`：目標是登錄過的測試 vault 時照舊；其他一律當正式 vault，要求：
  1. `git status --porcelain` 是空的（含未追蹤檔，`.gitignore` 的除外）。
  2. `HEAD` 正好是 tag `v<manifest 的 version>`，而且 `package.json` 的版本相同。
  3. 建置時 `DEV` 是 `false`；`build.mjs` 把這件事寫進產出或傳回值，安裝命令檢查，不只看 `BUILD` 有沒有 `.dirty`。
  4. 先建置到暫存資料夾、算好三個檔的雜湊，存一份到 `.local/releases/<version>/`（含雜湊清單）；複製到 vault 後重新讀回比雜湊。
- 退回：`npm run install-vault -- <vault> --release <version>` 從 `.local/releases/` 重裝那一份；第二部分做完後，退回前先檢查現有資料的 `需要版本`／`need` 有沒有比那一版新的。

### 1-5 更新命令（D-149 第 6 點、D-150 第 9 點）

`npm run update-vault -- <vault>` 分兩段，由維護的 AI 照使用者的要求跑：

1. `--check`：1-4 的條件 → `npm run check` → 考前提醒 → 1-1 備份 → 1-3 比較（舊版照 1-3 的第一次規則或上一份 `.local/releases/`）→ 印出摘要（差異數、報告位置、各裝置最後回報的版本），並記下這次的備份檔與報告。
2. `--install`：重新確認 `--check` 之後卡組與 `data.json` 沒變（和那份備份的清單比雜湊；紀錄只多了後面的行可以接受），變了就要求重跑 `--check`；然後照 1-4 安裝，最後提醒「iPhone 等同步完後，把 Obsidian 完全關掉再開」。
- **考前提醒**：讀 vault 裡生效的考試範圍（D-098 的期間，清晨 4 點換日）。考試開始前 7 天內印「離段考還有 N 天」，考試期間印「考試期間」，並說明這一版可以考後再裝；沒填日期印日期未定；讀不到考試範圍就照實說讀不到，不當成沒有考試。不擋：在範圍內時 `--install` 要多加 `--exam-ok`，AI 先問過使用者才加。
- 更新說明寫在 tag 的說明（`git tag -a v0.1.0 -m "…"`），不另開文件；比較報告的每個差異都要對得到它。

### 1-6 第一部分的測試

測試用記憶體 `Files` 或暫存資料夾，不碰任何真的 vault：

- 備份：同長度改字並保留修改時間（`Q :: A` → `Q :: B`）抓得到；中途多一個檔或少一個檔會重來或失敗；紀錄中途多一行通過、用舊內容；讀不到的檔案讓整份失敗、沒有留下正式檔名；有語法問題的卡組照樣備份並記在 `notes`；zip 讀回的雜湊相同；檔名不重複；`--to` 指到 vault 裡（含符號連結）被拒絕。
- 還原（Codex 的反例都要有）：
  - 兩台裝置同一刻的作答，其中一個來源檔不見了，補成還原檔後到期日和兩個原檔都在時相同（〈Codex 確認〉C4 反例一：good 與 miss，到期 10 月 28 日 10:01）。
  - 壞行（`{"t":"unfinished","lt":"old123"{"t":…,"lt":"abc123",…}`）補進還原檔後，救回的作答與 `seen` 的 `abc123`、`old123` 都還在（反例二）。
  - iCloud 衝突副本 `… 2.jsonl`、還原檔、來源檔三者的排序。
  - 演練：備份 → 新作答與 `undo`、把一個目標搬到另一篇、改字 → `--plan`、`--apply` → 原有的紀錄行一行都沒少、選的內容正確、全庫 ID 不重複 → 再跑一次 `--plan` 沒有要補的行。中途失敗（寫入丟錯）後重跑能續做；寫入空間不足時列為失敗、不標成功。
  - 會造成 ID 重複的檔案被擋住；計畫後被改過的檔案在 `--apply` 時跳過。
  - 「合併結果相同」照 syntax §5-3 的口徑比（Codex 格式查核 R3）：`reviews` 的內容與順序、`changes`、`cancelled`、`seen`、重播與到期相同；壞行的問題位置改指還原檔，另外斷言。
  - 備份檔的讀取（F3、F4）：同名的 zip 項目、`files` 裡重複的 `path`、兩個 `manifest.json` 都整份拒絕；清單缺必要欄位、`version` 不認得、`size` 不是整數、`sha256` 不是 64 個小寫十六進位字元都拒絕；`Essence Cards/A.md` 與 `a.md` 在 Windows 上兩個都擋住；設定資料夾不是 `.obsidian` 時，備份與還原都照指定的資料夾，沒有外掛資料夾時失敗，`data.json` 從一個設定資料夾還原到另一個時路徑對得上、碰撞時擋住。
- 比較：同一個版本比自己是零差異；兩個目標互換到期日時，30 天的總數相同但逐目標的比較抓得到；沒 ID 的目標多出或消失抓得到；轉接器丟錯時是「無法比較」。
- 安裝：開發版裝到沒登錄的 vault 被拒；有未追蹤檔、tag 不符、`package.json` 版號不符、`DEV=true` 都被拒；登錄路徑是 junction 指到別處時以實際路徑判斷；正式安裝後 `.local/releases/` 有產物與雜湊。
- 考前提醒：前 7 天內、考試期間、清晨 4 點前後、沒填日期、讀不到範圍。

## 2. 第二部分：外掛的版本行與讀取閘門

### 2-1 版本行（D-149 第 2 點）

- 核心不讀 `BUILD` 全域，由外層把目前的版本傳進 `state`。
- 載入時：這台裝置自己的紀錄檔（檔名正好是 `logPath` 的格式；還原檔與衝突副本不算）都讀到之後，找其中 `set: app` 的最後一行；和目前的 `BUILD` 不同（或沒有）就用同一個 writer 排一行 `app`，只排一次。自己的檔都讀到時，它排在這次第一筆作答之前；自己的檔還在 `unread` 時先不比、不擋作答，讀到才比、才補那一行，之前的作答版本標未知（syntax §5-1；Codex 格式查核 R2，使用者 2026-10-29 確認，見 D-149 的補充）。寫入成功以 `flush` 的結果為準；同一行寫入失敗後重試不算另一次回報。
- 裝置列表：新的純函式從**帶來源路徑的原始行**算每個來源的最後回報（不用合併後的 `History.changes`，它不帶來源、會去重）；來源是 `年-月 裝置碼.jsonl` 的歸那台裝置，衝突副本標「衝突副本」，還原檔不算進目前版本但保留來源；同一來源同一時間卻不同的 `BUILD` 標成「不確定」，不挑一個。
- 「版本」命令：除了這台的 `BUILD`，列出每台裝置最後回報的版本與時間（寫「最後回報」），以及「本機歷史待讀取」等狀態。不加新畫面。

### 2-2 讀取閘門（D-149 第 3 點）

- 版本比較是一個純函式，照 syntax §0-1（精確的整數比較）；格式不對等於讀不懂。
- **卡組**：`需要版本` 比目前新或格式不對時，以及屬性區讀不出來、原文解開跳脫後含「需要版本」時（syntax §2-1；Codex 格式查核 F1），那篇卡組標成「需要新版」：不進今天的份、不出題；`state` 的 `fillText`、`fillIds`、`resolveText`（以及之後的採用草稿）在入口一律拒絕寫它，存檔按鈕與離開時的補 ID 都經過這個入口（`save.ts`）。
- **紀錄行**：先看 `need`，再解析其他欄位。讀不懂時：保留原文，照 syntax §5-2 的三個條件（Codex 格式查核 F2）辨認影響的目標，加進「暫停」的集合，`lt` 寬鬆地收進 `seen`；任何一個條件不成立就整個歷史標成不完整、全部暫停。暫停的目標不排程、不出題，`answer` 拒絕寫它。
- 每次檔案變動重讀時都重新檢查；一篇卡組或一個目標變成暫停時，正在複習的那張卡作答時被拒絕（不寫紀錄），畫面換下一張。
- 提示：入口的「給家長」一區還沒做，先用 Obsidian 的通知在載入時提示一次（「有內容需要新版才讀得懂，請更新外掛」），並列在「版本」命令的輸出；入口做好時搬過去。

### 2-3 第二部分的測試

- 版本比較：`0.10.0 > 0.9.0`；相同版本讀得懂；這台的 `BUILD` 是 `0.6.0+不同 commit` 時能力相同（`need` 本身帶 `+` 仍是讀不懂）；`0.6`、`v0.6.0`、`0.6.0-beta`、`01.2.0`、`abc`、空字串、數字、清單都是讀不懂；超過安全整數的兩個值（例如 `9007199254740993.0.0` 與 `9007199254740992.0.0`）比得出大小。
- 版本行：兩台裝置的檔有同一個 `t` 與 `val` 的 `app` 行，列表兩台都有（Codex 第一次回應的探針）；同一個 `BUILD` 重開不再寫；退回舊版會寫；還原檔裡的 `app` 行不算目前版本。先後分兩種情況斷言（Codex 格式查核 R2）：自己的歷史就緒時 `app` 行排在第一筆作答前；未就緒期間照常作答，讀到後只補一行。
- 卡組的標記（F1）：屬性區寫壞時，`"需要版本": 9.0.0`、`  需要版本:`、`需要版本 :`、`"需要版本":`、行尾 `\` 接行拼出的鍵都算讀不懂；沒有結束的屬性區也一樣；屬性區寫壞但沒有這四個字的卡組照舊用預設值。
- 紀錄行的影響範圍（F2）：`lt` 是空字串或只有空白、`lt` 不是字串、有 `lt` 但 `undo` 指的作答找不到、`lt` 與 `undo` 都沒有，都是全部暫停；`lt` 有效、`undo` 找得到時只停那幾個。
- 閘門：Codex 的 `undo` 反例（`undo` 帶 `need: 9.0.0` 時，原本那筆作答不會復活，目標被暫停）；漏掉 `miss` 的反例（帶 `need` 的 `miss` 讓目標暫停，不是用舊的熟練度排到一週後）；帶 `need` 的行裡的 `lt` 進 `seen`，配新 ID 時避開；卡組被擋時三個寫入入口都拒絕；複習中途卡組變成被擋，作答被拒；標記壞掉的行不被當成沒有標記。
- 既有測試照舊通過。

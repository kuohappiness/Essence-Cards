**比對**（寫成 `src/dev/` 裡的純函式：輸入筆記文字與 metadataCache 的 `listItems`，輸出不一致的清單；它本身要有 Node 測試，用手寫的 `listItems` 讓下面每一種不一致都至少報一次）。先把**引言框裡的行**（去掉縮排後以 `>` 開頭）從 `listItems` 拿掉，再比：

- (a) `parseDeck` 的 `targets[].line` 集合＝metadataCache 最上層項目（`parent < 0`）的行。

- (d) 有 ID 的目標，metadataCache 在那一行的 `id` 和目標的 `id` 相同。

### 外掛的資料狀態

```ts
// src/state/index.ts（不 import obsidian；在 Node 用 createNodeFiles 測）
import type { Files } from '../core/files.ts';
import type { DeckEntry, History, NewEntry, Next, Pick, Progress, Settings, Today, TodayInput } from '../core/study/index.ts';

export interface StateOptions {
  files: Files;
  device: string;                    // 例如 'iPhone-7f3a'（§4-2）；紀錄的檔名用它
  now?: () => number;                // 預設 Date.now
  offset?: (ms: number) => number;   // 預設 -new Date(ms).getTimezoneOffset()
  settings?: Settings;               // 預設 { capMinutes: 30, retention: 0.8, filter: [] }（D-104、D-078）
  delay?: number;                    // 收到檔案變動後等多久才處理（毫秒），預設 500
  onError?: (error: unknown) => void;
}
export interface LoadTimings { decks: number; history: number; plan: number; total: number }   // 毫秒

export interface State {
  /** 第一次讀完卡組與紀錄、排好今天；之後每次呼叫回傳同一個 Promise。 */
  ready(): Promise<LoadTimings>;
  decks(): readonly DeckEntry[];
  history(): History;
  /** 目前的輸入：decks、history、settings、exam: null、呼叫當下的 now 與 offset。 */
  input(): TodayInput;
  /** 今天的份；過了清晨 4 點或 offset 變了，先重排（§3-5）。 */
  today(): Today;
  /** nextCard；不會回傳 'stale'。 */
  next(pick: Pick): Next;
  progress(): Progress;
  /** 寫一行紀錄（背景）、併進 history，回傳 t；不重排（§3-4）。 */
  answer(entry: NewEntry): string;
  /** 今天的份因為卡組或別台裝置的紀錄重排之後呼叫。 */
  onChange(listener: () => void): () => void;
  /** 等目前排隊的紀錄寫完。 */
  flush(): Promise<void>;
  /** 停止監看、等紀錄寫完。 */
  close(): Promise<void>;
}
export function createState(options: StateOptions): State;
```

`ready()` 之前呼叫 `today`、`next`、`progress`、`answer`、`input` 丟出錯誤；`decks`、`history` 回傳空的。測試只透過這些匯出測。第二部分在 `StateOptions`、`State` 加補 ID 的部分（[§8-3](#8-3-介面)）。

**為什麼多一個 `src/state/`**：D-110 的「外掛接線」需要一個地方記住全部卡組與紀錄、跟著檔案變動更新、決定什麼時候重排。放在 `main.ts` 會 import `obsidian`，在 Node 測不到；放進核心的哪個模組都不對（study 從 deck 只能 import 型別，核心模組不做跨模組的協調）。它只用 `Files` 與核心的公開匯出，不 import `obsidian`，所以在 Node 用 `createNodeFiles` 測得到；寫回筆記的文字轉換仍然只在 deck 模組。這不是 D-110「沒有採用」的那個「Obsidian 層」：那一層什麼都往裡放、而且測不到。畫面（W6 起）從 `state` 拿資料，純計算（例如 `checkTyped`）照舊直接用核心模組。

## 2. 檔案存取的 Obsidian 版

`createObsidianFiles(app)` 照 `src/core/files.ts` 每一句註解做，和 Node 版通過**同一份契約檢查**（`src/dev/files-contract.ts`，不 import `obsidian`；Node 的測試與 Obsidian 的開發命令都跑它）。契約檢查需要的「改名」「刪除」由兩邊各自提供（Node 用 `node:fs`；Obsidian 用 `vault.rename`、`vault.delete`，只動 `Essence W5/暫存/` 裡自己建的檔）。

| 代號 | 動作 | 預期 |
|---|---|---|
| C1 | `a/b.md`、`a/c/d.jsonl`、`a/x.md`、`ab/z.md` 存在，`list('a')` | `['a/b.md', 'a/c/d.jsonl', 'a/x.md']`：遞迴、只列檔案、照字串排序、不含 `ab/` |
| C2 | `list('沒有')` | `[]` |
| C3 | `read` 不存在的檔 | `null` |
| C4 | `read` 內容是 `'中文😀\r\n第二行'`（沒有檔尾換行）的檔 | 完全相同的字串 |
| C5 | `modify('n/m/新.md', edit)`，`n/` 不存在、`edit` 回傳 `'x'` | 建立上層資料夾與檔案，內容 `'x'`；`edit` 收到 `''` |
| C6 | `modify` 的 `edit` 回傳原文 | 不寫入：等事件送達的時間內，`watch` 沒有收到這個路徑 |
| C7 | 同一個檔同時呼叫兩次 `modify`，各在結尾加一個字 | 兩個字都在 |
| C8 | `edit` 丟出錯誤 | `modify` reject、檔案不變；下一次 `modify` 照常 |
| C9 | `append('p/q.jsonl', 'l1')`，`p/` 不存在 | 建立，內容 `'l1\n'` |
| C10 | 內容是 `'abc'` 的檔 `append(…, 'l2')` | `'abcl2\n'`（不替原檔補換行） |
| C11 | 不存在的檔同時呼叫 10 次 `append` | 10 行都在，照呼叫的順序 |
| C12 | `watch` 之後：新增、修改、刪除一個檔；改名 `a.md` → `b.md`；資料夾 `f/` 改名成 `g/`（裡面有 `1.md`） | 依序收到那個路徑；改名收到 `a.md` 與 `b.md`；資料夾改名收到 `f/1.md` 與 `g/1.md` |
| C13 | 取消監看之後再改檔 | 沒有通知 |
| C14 | 路徑是 `../x`、或絕對路徑 | 丟出錯誤或 reject，不碰 vault 以外 |

Obsidian 版的做法：

- `list` 用 `vault.getFiles()`；`read` 用 `vault.read`（讀到磁碟上最新的內容，包括 iCloud 剛同步來的）。`.jsonl` 和 `.md` 一樣能列、能讀、能追加。
- `modify` 用 `vault.process`（D-110）；不存在時建立上層資料夾再 `vault.create`。`edit` 回傳原文時不能寫入（不讓 iCloud 多同步一次）。
- `append`：存在時 `vault.append`，不存在時建立；同一個路徑的 `modify`、`append` 排隊，不互相蓋掉（和 Node 版相同）。
- `watch` 用 `vault.on('create' | 'modify' | 'delete' | 'rename')`，自己寫的檔一樣會通知。資料夾改名或刪除時，通知裡面每個檔案的舊、新路徑（C12）。

**完成條件**：契約檢查在 Node（`npm test`）、Windows 版 Obsidian（開發命令）全部通過；iPhone 照 [§5](#5-量測與-iphone)。

## 3. 外掛的資料狀態

### 3-1 讀取

`ready()` 依序：

1. 先開始監看（`files.watch`），再讀，這樣讀的期間改到的檔不會漏掉；讀完之前收到的通知，讀完後照 [§3-3](#3-3-檔案變動) 處理一次。
2. `readDecks(files)` → `decks`（計 `timings.decks`）。
3. 讀全部紀錄：`isLogPath` 的檔，每一個的文字記在「來源」裡，`mergeHistory(來源)` → `history`（計 `timings.history`；結果和 `readHistory(files)` 相同）。
4. `planToday(input())`（計 `timings.plan`）。`total` 是 `ready()` 開始到這裡。

`exam` 一律是 null（W4 §7）；`settings` 用選項或預設。

### 3-2 哪些檔案是什麼

- 卡組：`isDeckPath`。卡組以外的 `.md`、系統資料夾裡的筆記、`Essence Cards/` 以外的筆記都不讀。
- 紀錄：`isLogPath`。檔名是 `YYYY-MM <device>.jsonl` 的是**自己的**紀錄（例如 `2026-10 iPhone-7f3a.jsonl`）；其他都是別台裝置的，包括 iCloud 的衝突副本（例如 `2026-10 iPhone-7f3a 2.jsonl`）。
- 其他路徑的通知不理。

### 3-3 檔案變動

- 卡組的路徑：記下來，等 `delay` 之後重讀**那一篇**（讀到 `null` 就拿掉）。
- 別台裝置的紀錄：記下來，等 `delay` 之後重讀**那一個檔**、更新來源、整份重新 `mergeHistory`（Codex 審查 W4 第 10 點：外部紀錄一律重新 merge，不直接追加）。
- 自己的紀錄：**不理**。記憶中的來源與 `history` 在作答時就更新了（§3-4）；照通知重讀，每作答一次都要重新 merge 全部紀錄，違反 W4「作答後只呼叫輕的那兩個」的成本約定。
- `delay` 內又收到通知就重新計時；時間到了，同一個路徑只讀一次，全部處理完只 `planToday` 一次、呼叫 `onChange` 一次。內容沒有變（例如通知了但文字相同）時不重排、不呼叫。

### 3-4 作答

`answer(entry)`：

1. `t = writer.write(entry)`（W3 的 `createLogWriter`，`device`、`now`、`offset`、`onError` 照選項）。
2. `line = encodeEntry(t, entry)`；自己的來源（和寫檔同一個路徑，`logPath`）加上這一行。
3. `history = appendLine(history, line)`。
4. 不重排、不呼叫 `onChange`；之後的 `next`、`progress` 用新的 `history`（W4：輕的那兩個）。

`appendLine` 的規則，和 `mergeHistory` 一致：

- 作答：照 `at` 插進 `reviews`（同一個 `at` 的排在後面）；已經有 `t`、`lt`、`r`、`v`、`typed`、`src` 完全相同的一筆時不加。
- 取消（`undo`）：拿掉 `t` 是那個值的作答；找不到就什麼都不改。
- 變更（`set`）：照 `at` 加進 `changes`，完全相同的不加。
- 不改輸入的 `history`；`line` 不是合法的一行時丟出錯誤（自己寫的行不會這樣）。

驗收用的性質（T5）：一串自己的行依序 `appendLine` 的結果，和「這些行加進自己的來源後重新 `mergeHistory`」比，`reviews` 與 `changes` 的內容與順序都相同；唯一的例外是 `at` 完全相同、來自不同檔案的兩筆之間的先後（`mergeHistory` 用檔名決定，`appendLine` 不知道檔名），這時只要求照 `at` 排好、多重集合相同。

### 3-5 換日與換時區

`today()`、`next()`、`progress()` 每次先看呼叫當下的 `now` 與 `offset`：`dayOf(now, offset)` 不是今天的份的 `day`，**或 `offset` 和排今天的份時不同**，就重新 `planToday`（不呼叫 `onChange`），再回答。後者處理 Codex 審查 W4 的 F3：日編號相同、時區不同時，舊的 `Today` 用的是舊的清晨 4 點。W4 的修正（〈L2 審查後的修正〉第 4 點）讓 `Today` 記下 `offset`、`nextCard` 在時區不同時回 `stale`；但 `progress` 不回 `stale`，所以 `state` 仍要在每次呼叫前自己檢查。

`next()` 遇到 `stale` 時重排再取一次，所以不會回傳 `stale`。

### 3-6 補 ID

不在第一部分：第一部分不寫任何卡組筆記，補 ID 與 ID 的保護都在 [§8](#8-第二部分補-id-與-id-的保護)。

## 4. 外掛接線

`src/main.ts` 與 `src/obsidian/`。這些會 import `obsidian`，在 Node 測不到，所以邏輯盡量放在 `state`，這裡只接線；行為用開發版在 Windows 版 Obsidian 驗（T12）。

### 4-1 載入順序

- `onload` 只註冊命令與事件，不讀任何檔案；`workspace.onLayoutReady` 之後才建立 `state`、`void state.ready()`（Obsidian 在 layout ready 之前會對每個檔案發 `create`）。

## 5. 量測與 iPhone

### 5-1 電腦

- `npm run bench -- --vault <路徑>`：在 `<路徑>/Essence W5/量測/` 寫入 W3 產生器的三年份紀錄（2 台裝置 × 36 個月、約 16.8 萬行）與 20 篇 × 100 個目標的卡組（ID 對得上紀錄裡的 `goal0`～`goal1999`，和 W4 的 T14 相同），再用 `createNodeFiles` 跑一次 `ready()`，印出 `LoadTimings`。不加 `--vault` 時照舊。產生器用 `tools/bench-study.ts` 已有的 `threeYears` 與 `threeYearDecks`（W4 修正後和測試共用），不另寫一份；`threeYearDecks` 回傳的是解析好的卡組，要寫成檔案時，把它改成先產生文字、再解析，測試的結果不變。
- `npm run bench` 另外印出 `answer`＋`next`＋`progress` 一次的中位數（三年份資料，21 次），超過 20 ms 時結束碼不是 0。精確的效能數字只放在 bench，不放進 `npm test`（W3 L2 修正第 6 項、Codex 審查 W4 的 F5）。
- Windows 版 Obsidian：`open` 跑兩次（第一次是測試 vault 剛被 URI 打開時；使用者的 Obsidian 開著時不要關掉它，就只量開著的情況並註明），`files`、`compare`、`today`、`answer`、`watch` 各一次。`watch` 執行的期間，AI 從命令列在 `Essence Cards/紀錄/` 追加一個假裝置（例如 `2026-10 Test-0000.jsonl`）的一行，60 秒內要看到 `onChange` 與 `reviews` 多一筆；之後刪掉這個檔，再跑一次 `today`，確認和追加之前相同。

### 5-2 iPhone（集中成一次）

AI 測不了的原因：iPhone 上的 Obsidian 只能在手機上執行，iOS 的檔案存取與 localStorage 和電腦是不同的實作，iCloud 同步也要實機。數字由外掛寫成檔案、經 iCloud 傳回電腦由 Claude 讀，使用者不用抄數字。

**什麼時候做**：**併進 W6 的 iPhone 測試，一次做完**（使用者 2026-10-24 決定，[待使用者回答](#待使用者回答)第 1 題）。W5 在 Windows 驗完、L2 通過就合併；下面的步驟與 I1～I4 寫進 W6 的任務說明（backlog 技術債有一列提醒），在 W6 的 iPhone 測試裡判斷。

清單的草稿（實作時照試作外掛 README 的〈iPhone 測試清單〉寫成給使用者的步驟，約 5 分鐘）：

1. 確認測試 vault 已同步到 iPhone，社群外掛裡的 Essence Cards 開著。

3. 執行「Essence 開發：檔案存取」，再執行「Essence 開發：今天的份」。
4. 再把 Obsidian 完全關掉、重新打開，執行一次「Essence 開發：量測第一次打開」。
5. 回到對話告訴 Claude 做完了。

**驗收**（Claude 讀結果檔判斷）：

- I2：契約檢查 C1～C14 全部通過。
- I3：兩次結果的裝置碼相同、以 `iPhone-` 開頭，和 Windows 的不同。
- I4：同一天、同一份 vault（iPhone 沒有寫作答紀錄），iPhone 和 Windows 的 `today` 的 `share`、`more` 完全相同。

## 7. 測試清單

除了特別寫的，Node 的測試在暫存資料夾用 `createNodeFiles`，時區 +08:00（offset 480），`now` 由測試控制，`delay` 設 0 或很小，用公開介面測。卡組與紀錄用自編的內容或 syntax.md 的例子。每一組都要有具體的預期值，不只比數量。

**T1 F6**：§0-1 的三點各一個測試；`src/` 加了 `state/`、`obsidian/`、`dev/` 之後 `npm test` 通過。

**T2 監看**：§0-2 的紀錄（修前失敗幾次、錯誤訊息、原因）與修後 Windows 連跑 20 次全部通過。

**T3 metadataCache 對照**：§0-3 的報告不一致是 0（或已談定的決定）；對照函式的 Node 測試涵蓋 (a)～(e) 每一種不一致。

```ts
  deckStatus(path: string): { missing: number; issues: IdIssue[] };
  /** 存檔（開著的筆記）：回傳補 ID、歸位之後的文字；沒有要改、手機、不是卡組時回傳原文。 */
  fillText(path: string, text: string): string;
  /** 離開筆記時（沒開著的檔）：讀檔、照 fillText 寫回；不存在時不建立。有改字回傳 true。 */
  fillIds(path: string): Promise<boolean>;
  /** 家長選了之後：回傳寫回後的文字；證據不再成立時回傳 null，問題保留。 */
  resolveText(issue: IdIssue, choice: 'restore' | 'new', text: string): string | null;
  /** 這台電腦的編輯器裡刪掉或剪下了整個目標：這些 ID 是刻意拿掉的，重讀時不算弄丟。 */
  removedInEditor(path: string, ids: readonly string[]): void;
}
```

### 8-4 認得與歸位

- **認得**（`parseDeck`）：只看**有題目的明確目標**（不是 implicit）的名稱那一行。行尾不是 ID，但行中間有一個候選：空白、`^`、6 碼 `abcdefghjkmnpqrstuvwxyz23456789`，後面是行尾、空白，或不是 `[A-Za-z0-9-]` 的字；不在行內程式碼、公式、連結裡。只有一個候選時，它就是 ID，名稱是拿掉它之後的文字，記 `misplaced-id`。兩個以上，或和行尾的 ID 不同時，記 `ambiguous-id`。家長自己寫在行尾的合法區塊 ID 照舊。題目行、補充、資料、implicit 的題目都不套用（D-089 第 9 條）。**不改共用的 `stripId`**：目標名稱另寫一條規則，不然會吃掉題目與答案的正文、改變指紋。
- **歸位**（`assignIds`）：把 `misplaced-id` 的 ID 移到行尾，其他字（包括名稱、換行符號、檔尾）一字不動；已經在行尾的不動；第二次不改任何字。
- **縮排改正**（`assignIds`，[D-135](../docs/decisions.md#d-135-清單解析和-obsidian-對照後的處理)）：學習目標底下的項目，清單符號所在的欄比目標的內容欄多 4 欄以上（Obsidian 會把它當成目標那一行的接續文字）時，把它的縮排改成剛好在目標的內容欄，它底下的行（子項目、接續行）跟著移同樣的欄數；照原本的縮排字元（Tab 或空格）寫。只改有題目的明確目標底下第一層的項目；題目底下更深的補充不動。改完 `parseDeck` 的題目、指紋與 ID 都和改之前相同，第二次不改任何字。`skip` 的目標不動。

### 8-5 弄丟、改掉與待處理

只在**同一次載入**裡偵測；`ready()` 第一次讀的時候沒有前一版，不偵測。

- **偵測**：照 §3-3 重讀卡組 P 時，和 P 在這次載入的上一版解析比：
  - **不見的 ID**：上一版 P 有、這一版 P 沒有，也不在其他任何卡組，也不是 `removedInEditor` 報過、或 `state` 自己寫回時拿掉的。
  - **新出現的目標**：(a) 沒有 ID、不是 `ambiguous-id`；或 (b) 有一個上一版沒有、其他卡組沒有、原始紀錄裡也沒出現過的 ID。上一版就已經在、同樣沒有 ID 的目標不算。
  - 兩者**都有**時，每一個新出現的目標成為一個待處理問題（(a) 是 `lost`、(b) 是 `changed`）；不見的 ID 剛好一個、新出現的目標剛好一個時，`restore` 是那個 ID，否則是 null。只有不見、沒有新出現（例如在外部刪掉整個目標），不是問題。
  - `ambiguous-id` 的目標一律是待處理（`ambiguous`）；候選裡剛好一個是上一版這篇裡的 ID 時，`restore` 是它。
- **待處理的目標**：不出題（`state` 給 `planToday` 的卡組裡拿掉它們）、存檔時不補、不移動（`skip`）。待處理一直保留，直到家長選了、那個目標被刪掉，或這次載入結束；**同樣的內容再讀一次、家長改了它的名稱或其中一題，都仍然是待處理**（怎麼在改動之間認出同一個目標由實作決定，T 測試會檢查）。重新載入外掛之後沒有前一版，照一般規則。
- **還原原本的進度**（`restore` 不是 null 時才有）：寫回前重新確認這個問題還在、那個目標還在、`restore` 的 ID 現在不在任何卡組；成立就 `setTargetId(text, line, restore)`，不成立回傳 null、問題保留。
- **當成新的學習目標**：`setTargetId(text, line, null)` 後照一般規則補新 ID，從頭複習；舊紀錄留在檔案裡。
- **`state` 自己寫回造成的變化**（補 ID、歸位、還原、當成新的拿掉的候選）不算弄丟。
- **配新 ID 時的 `taken`**：其他卡組的 ID、原始紀錄每一行出現過的 `lt`（**包括被取消的作答**，不只看 `mergeHistory` 之後的 `reviews`）、待處理問題的 `restore`。

### 8-6 接線：存檔按鈕、離開筆記、鎖住 ID

`src/obsidian/`，只在電腦（`Platform.isDesktopApp`）。

- **存檔按鈕**：卡組筆記的標題列（`view.addAction`），加一個同名命令「Essence Cards：存檔」（對目前的筆記）。三種樣子，說明（滑鼠移上去）照寫：
  - 沒有要做的：淡的，「筆記已自動儲存；學習目標都已加入複習」。
  - 有目標還沒有 ID：醒目，「筆記已自動儲存；有 N 個學習目標尚未加入複習」。按下去用 `fillText` 經 Editor 交易寫回，跳一行 `Notice`「N 個學習目標已加入複習」。
  - 有待處理的問題：警示，「有 N 個學習目標的進度連結需要處理」。按下去先補其他目標，再開一個小視窗，每個問題一列：
    - `lost`：「〈名稱〉原本的編號不見了（可能在 Obsidian 以外改過這篇筆記）。」
    - `changed`：「〈名稱〉的編號和原本的不一樣。」
    - `ambiguous`：「〈名稱〉那一行有兩個編號。」
    - 按鈕「還原原本的進度」（`restore` 是 null 時不顯示，改寫一句「找不到可以確定的原本編號」）、「當成新的學習目標，從頭複習」。選了用 `resolveText` 經 Editor 交易寫回；回傳 null 時說「這篇筆記剛剛改過，請再按一次存檔」。
- **離開筆記時備援**：`workspace` 的 `layout-change` 與 `file-open` 時，算出現在所有 Markdown 分頁開著的檔案（還沒載入的分頁用 `leaf.getViewState()` 的 `file`）；上一次開著、這一次沒有開著的卡組，各呼叫一次 `state.fillIds`。同一篇開在兩個分頁時，兩個都關了才算離開；只是切換焦點、那篇仍開著，不補。啟動與同步讀入時不補。改名時舊路徑已經不存在，`fillIds` 回傳 false。待處理的問題不在這裡處理，只能從按鈕。
- **鎖住 ID**（`registerEditorExtension`）：
  - 目標那一行行尾的 ` ^id` 顯示成一個小而淡的標記，說明「學習目標的編號，由程式自動管理」；原始的 Markdown 不變。判斷哪幾行是目標可以用簡化的規則（例如最上層的清單項目），但不能每按一個鍵就重新解析整篇；要和 `parseDeck` 的結果對照測試。
  - 用交易層調整碰到 ID 的修改，不只靠 `atomicRanges`（它只管游標）。必須成立：在名稱後面打字、貼上、中文組字，字放在 ID 前面；在名稱最後按 Enter，ID 留在原本的目標那一行、新的一行照常；Backspace／Delete 碰到 ID 或它前面的空白時，ID 與空白不動；選一段（包括跨到 ID）再打字或貼上，ID 留在那個目標的行尾；Home／End、拖放、清單的快捷鍵（縮排、上下移動整行）不會讓 ID 離開它的目標；Undo／Redo 照常。
  - **刪掉或剪下整個目標**（目標那一行加上它底下所有的題目與資料）照常可以，ID 跟著走，並呼叫 `state.removedInEditor`。只選了目標那一行、或跨兩個目標的一部分時，照結構處理：不能留下孤立的 ID、也不能讓一行有兩個 ID；不要事後補回使用者已刪掉的整個目標。
  - 鎖定範圍是整篇（包括畫面外的部分），Live Preview 與 Source mode 都要；`[[筆記#^id]]` 的連結與跳轉、複製整行照常。
  - 擋不住的（別的編輯器、其他外掛直接寫檔）交給 §8-4、§8-5。

**I2 歸位與 `setTargetId`**：`- 能說明擴散 ^k3m9x2 的現象` 補 ID 後是 `- 能說明擴散 的現象 ^k3m9x2`，第二次不改字；CRLF 與檔尾照舊；`skip` 的行一字不動；`ambiguous-id` 的行不動。`setTargetId` 對 `ambiguous-id` 那一行設成 `k3m9x2`：只剩行尾一個 `^k3m9x2`；設成 null：兩個都拿掉；對題目行或不是目標的行回傳 null。縮排改正：`- 目標 ^k3m9x2\n        - Q :: A\n            - 例句：x` 補 ID 後是 `- 目標 ^k3m9x2\n  - Q :: A\n      - 例句：x`，題目、指紋與補充都和之前相同，第二次不改字；Tab 縮排的版本照樣用 Tab；第一部分 §0-3 的對照筆記 M1 補 ID 後，在 Windows 版 Obsidian 的 metadataCache 與閱讀模式裡都是目標的子項目。

**I3 `taken` 包括被取消的作答**：紀錄是 `lt: 'aaaaab'` 的一筆作答，加上取消它的一行；另一篇卡組有 `aaaaaa`；`random: () => 0`。補一個新目標拿到 `aaaaac`（只看合併後的 `reviews` 會拿到 `aaaaab`，Codex 重現過）。

**I4 補 ID**：`Essence Cards/補.md` 的內容：

```
- 能說明 A
    - Q1 :: A1
- 能說明 B ^b23456
    - Q2 :: A2
- borrow :: 借入
```

另一篇卡組有 ID `aaaaaa`；紀錄裡有 `lt: 'aaaaab'`（刪掉的目標）。`random: () => 0`：W2 的 `assignIds` 每次都先抽到 `aaaaaa`，被占用時照字母表往下找（`src/core/deck/assign.ts`），所以 `taken` 漏了哪一邊，結果就會不同。`fillIds('Essence Cards/補.md')` 回傳 true，檔案變成：

```
- 能說明 A ^aaaaac
    - Q1 :: A1
- 能說明 B ^b23456
    - Q2 :: A2
- borrow ^aaaaad
    - borrow :: 借入
```

（漏了紀錄裡的 ID，A 會拿到 `aaaaab`；漏了別篇的，會拿到 `aaaaaa`。）W2 的找法之後若改了，改成斷言兩個新 ID 不在 `{aaaaaa, aaaaab, b23456}`、互不相同、其他字和上面相同，並在回報說明。再來：

- 第二次 `fillIds` 回傳 false，文字一字不變；`fillText` 對同一份文字回傳原文。
- `fillIds: false` 的 `state`：回傳 false，那個檔沒有被讀；`fillText` 回傳原文。
- 不存在的路徑、`Essence Cards/錯題本/x.md`、`其他/外面（卡片）.md`：回傳 false，沒有建立或改動任何檔案。
- 補完之後（修改通知、`delay` 過後）`today()` 的 `share` 裡有 `aaaaac` 與 `aaaaad`；`deckStatus` 的 `missing` 從 2 變 0。

**I5 弄丟的偵測**（都在同一次載入；「外部改檔」用 `node:fs` 直接改）：

| 情況 | 預期 |
|---|---|
| 目標 A（`^k3m9x2`，兩題）在外部被拿掉 ID，其他不變 | 一個 `lost` 問題，`restore` `k3m9x2`；A 不在 `today()`；`fillText` 不替 A 配 ID，但照常補同一篇其他新目標 |
| 同上，再讀一次一模一樣的內容 | 問題還在 |
| 同上，再把 A 的名稱改一個字；或改其中一題 | 問題還在 |
| 同上，再把 A 整個刪掉 | 問題消失 |
| A 的 ID 在外部被換成 `^zzzzz9`（沒見過的） | 一個 `changed` 問題，`restore` `k3m9x2`；A 不出題 |
| A、B 兩個在外部都被拿掉 ID | 兩個 `lost` 問題，`restore` 都是 null |
| A 在外部整個刪掉（沒有新目標） | 沒有問題 |
| 同一次重讀：A 整個刪掉、加了新目標 C（沒有 ID） | C 是 `lost` 問題（分不出是改寫還是新寫，交給家長） |
| A 被 `removedInEditor` 報過，之後 C 出現 | 沒有問題，C 照常補 ID |
| 目標行有 `ambiguous-id`，候選之一是上一版的 `k3m9x2` | `ambiguous` 問題，`restore` `k3m9x2` |
| `ready()` 時就已經沒有 ID 的目標 | 不是問題（沒有前一版），照常補 |
| 新的 `state`（重新載入）讀到上面任何一種內容 | 沒有問題，照一般規則 |

**I6 解決**：`lost` 選「還原」→ A 的那一行行尾是 `^k3m9x2`、問題消失、A 回到 `today()`、之後的重讀不再出現問題。選「當成新的」→ A 配到一個新 ID（不是 `k3m9x2`）、問題消失。還原前 `k3m9x2` 已經出現在另一篇 → `resolveText` 回傳 null、問題保留。還原前 A 又被改過、問題已不在 → 回傳 null。`ambiguous` 選「還原」→ 只剩 `^k3m9x2`；選「當成新的」→ 候選都拿掉、配新 ID，而且這次拿掉的候選不會變成新的 `lost` 問題。

**I7 鎖住 ID**（Windows 版 Obsidian，開發命令 `lock`：在 `Essence W5/暫存/` 的卡組副本上用 Editor 介面模擬每一種操作，比對操作後的文字與 `parseDeck`；Live Preview、Source mode 各跑一次）：名稱後面打字、貼上、中文組字（`compositionstart`／`end`）；名稱最後按 Enter；在 ID 前面 Backspace、在空白前 Delete；選一段跨到 ID 再打字、貼上；Home／End 後打字；拖放一段文字到名稱尾；清單縮排與上下移動整行；Undo／Redo；刪掉整個目標、剪下整個目標貼到另一篇（ID 跟著走，`removedInEditor` 收到）；只選目標那一行刪掉；跨兩個目標的一部分刪掉再貼上（沒有孤立或重複的 ID）；全選取代；同一篇開兩個分頁；`[[筆記#^id]]` 的連結跳轉；複製整行的剪貼簿內容含 ` ^id`。每一種都要寫出操作後的文字或判斷，不只寫「通過」。

### 8-9 實作與 L2 審查後的修正（2026-10-25）

Codex 的 L2 審查（[報告](<../Claude Codex Discussion/2026-10-25-w5-ids-review.md>)）之後，規格照下面對齊；上面各節的原文保留，有出入時以這裡為準。這些都是照 D-134、D-135 的原文對齊驗收條件，不是新的決定。每一項實作修正都先寫成會失敗的測試、確認重現後才修。

規格對齊（F6）：

1. **I1 的 `- 能說明擴散 ^k3m9x2abc`**：行尾的合法區塊 ID 照舊沿用（D-134「家長自己寫在行尾的區塊 ID 照舊沿用」），`id` 是 `k3m9x2abc`，不截成前六碼；**放在行中**（`^k3m9x2abc 的現象`）才是「不認得」。在 Obsidian 以外發生時由 §8-5 當成「換成沒見過的 ID」。「有兩個 ID」指兩個**不同**的 ID；同一個 ID 在行中與行尾各一次是 `misplaced-id`。名稱是空的（`- ^aaaaaa`）照樣認得，但編輯器不鎖。
2. **I5 最後一列**限縮成 lost、changed：重新載入後讀到 ambiguous-id 仍是待處理（§8-5「ambiguous-id 的目標一律是待處理」；不然鎖住 ID 之後家長沒有方法解開），只是沒有前一版，`restore` 是 null。
3. **§8-4 縮排改正的欄位**：有正常縮排的兄弟項目時對齊它；沒有時，空格縮排對齊目標的內容欄，Tab 縮排對到下一個 Tab 位置。改完任何目標的解析結果不同就整個不改（不算改好）。ambiguous-id 與 `skip` 的目標不改。
4. **§8-5、I6 的版本確認**（D-134「寫回前重新確認內容沒變」）：待處理的目標名稱、題目或候選改過時，問題換成一個新的 `IdIssue` 物件；拿舊的物件呼叫 `resolveText` 回傳 null、問題保留。只有行號變（上面多一行）不算改過。小視窗在 `onChange` 時重畫，顯示現在的問題。
5. **§8-3 介面多一個 `restoredInEditor(path, ids)`**：編輯器裡 Redo、貼回剪下的目標讓 ID 回來時呼叫，取消 `removedInEditor` 的標記，之後再弄丟照常偵測。
6. **選取從清單符號之前開始、打進新的字**：ID 留在那一行行尾，但那一行已經不是清單項目，不再是可以出題的目標（結構由家長改了）。
7. **建置與品質文件**：`main.js` 只能 require `obsidian`、`@codemirror/state`、`@codemirror/view`（`docs/agents/quality.md` 已改）。

實作修正（F1～F5 與審查回覆裡的建議）：

8. **F1**：上面第 4 點。
9. **F2**：鎖定拿掉「貼進名稱中間的 ID」時用核心同一個辨識（`deck` 模組多匯出 `nameIds`），行內程式碼、公式、連結裡的字原樣保留。

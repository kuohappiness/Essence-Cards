| M2a | `- 目標` ／ `␣␣␣␣- Q :: A` ／ `隨手一行` ／ `␣␣␣␣- R :: B` | 頂格一行夾在題目之間；現在 R 會消失 |

**比對**（寫成 `src/dev/` 裡的純函式：輸入筆記文字與 metadataCache 的 `listItems`，輸出不一致的清單；它本身要有 Node 測試，用手寫的 `listItems` 讓下面每一種不一致都至少報一次）。先把**引言框裡的行**（去掉縮排後以 `>` 開頭）從 `listItems` 拿掉，再比：

- (a) `parseDeck` 的 `targets[].line` 集合＝metadataCache 最上層項目（`parent < 0`）的行。
- (b) `ok` 是 true、不是 implicit 的目標，每一題的 `line` 在 metadataCache 裡是清單項目，而且它的上層（`parent`）就是目標那一行。implicit 的目標，第一題的 `line` 就是目標那一行。
- (c) `ok` 是 true、不是 implicit 的目標：metadataCache 裡上層是它的項目，內容（去掉清單符號、行內程式碼與公式之後）有 `::` 或 `==`、而且不是以六個欄位名稱（出處、類型、重要性、狀態、備註、錯題補強）加冒號開頭的，一定是它的題目。（題目消失就是被這一條抓到。implicit 目標底下的項目是那一題的答案或補充，不比這一條。）
- (d) 有 ID 的目標，metadataCache 在那一行的 `id` 和目標的 `id` 相同。
- (e) **補 ID 之後**：每篇用 `assignIds(text, { taken: new Set() })` 補 ID，存成 `Essence W5/對照/補ID後/` 的同名筆記，等 metadataCache 更新後再比一次 (a)～(d)；除了 W2 刻意跳過的 implicit，每個目標都有 ID，而且 metadataCache 在那一行讀到同一個 ID。

### 外掛的資料狀態

```ts
// src/state/index.ts（不 import obsidian；在 Node 用 createNodeFiles 測）
import type { Files } from '../core/files.ts';
import type { DeckEntry, History, NewEntry, Next, Pick, Progress, Settings, Today, TodayInput } from '../core/study/index.ts';

export interface StateOptions {
  files: Files;
  device: string;                    // 例如 'iPhone-7f3a'（§4-2）；紀錄的檔名用它
  fillIds: boolean;                  // 這台裝置會補 ID：電腦 true、手機 false（§3-6）
  now?: () => number;                // 預設 Date.now
  offset?: (ms: number) => number;   // 預設 -new Date(ms).getTimezoneOffset()
  settings?: Settings;               // 預設 { capMinutes: 30, retention: 0.8, filter: [] }（D-104、D-078）
  delay?: number;                    // 收到檔案變動後等多久才處理（毫秒），預設 500
  random?: () => number;             // 傳給 assignIds，測試用
  onError?: (error: unknown) => void;
}
export interface LoadTimings { decks: number; history: number; plan: number; total: number }   // 毫秒

export interface State {
  /** 第一次讀完卡組與紀錄、排好今天；之後每次呼叫回傳同一個 Promise。 */
  ready(): Promise<LoadTimings>;
  decks(): readonly DeckEntry[];
  history(): History;
  /** 目前的輸入：decks、history、settings、exam: null、呼叫當下的 now 與 offset。 */
  input(): TodayInput;
  /** 今天的份；過了清晨 4 點或 offset 變了，先重排（§3-5）。 */
  today(): Today;
  /** nextCard；不會回傳 'stale'。 */
  next(pick: Pick): Next;
  progress(): Progress;
  /** 寫一行紀錄（背景）、併進 history，回傳 t；不重排（§3-4）。 */
  answer(entry: NewEntry): string;
  /** 補這一篇卡組缺的 ID（§3-6）；有改字時回傳 true。 */
  fillIds(path: string): Promise<boolean>;
  /** 今天的份因為卡組或別台裝置的紀錄重排之後呼叫。 */
  onChange(listener: () => void): () => void;
  /** 等目前排隊的紀錄寫完。 */
  flush(): Promise<void>;
  /** 停止監看、等紀錄寫完。 */
  close(): Promise<void>;
}
export function createState(options: StateOptions): State;
```

`ready()` 之前呼叫 `today`、`next`、`progress`、`answer`、`input` 丟出錯誤；`decks`、`history` 回傳空的。測試只透過這些匯出測。

**為什麼多一個 `src/state/`**：D-110 的「外掛接線」需要一個地方記住全部卡組與紀錄、跟著檔案變動更新、決定什麼時候重排。放在 `main.ts` 會 import `obsidian`，在 Node 測不到；放進核心的哪個模組都不對（study 從 deck 只能 import 型別，核心模組不做跨模組的協調）。它只用 `Files` 與核心的公開匯出，不 import `obsidian`，所以在 Node 用 `createNodeFiles` 測得到；寫回筆記仍然只有 deck 模組的 `assignIds`。這不是 D-110「沒有採用」的那個「Obsidian 層」：那一層什麼都往裡放、而且測不到。畫面（W6 起）從 `state` 拿資料，純計算（例如 `checkTyped`）照舊直接用核心模組。

## 2. 檔案存取的 Obsidian 版

`createObsidianFiles(app)` 照 `src/core/files.ts` 每一句註解做，和 Node 版通過**同一份契約檢查**（`src/dev/files-contract.ts`，不 import `obsidian`；Node 的測試與 Obsidian 的開發命令都跑它）。契約檢查需要的「改名」「刪除」由兩邊各自提供（Node 用 `node:fs`；Obsidian 用 `vault.rename`、`vault.delete`，只動 `Essence W5/暫存/` 裡自己建的檔）。

| 代號 | 動作 | 預期 |
|---|---|---|
| C1 | `a/b.md`、`a/c/d.jsonl`、`a/x.md`、`ab/z.md` 存在，`list('a')` | `['a/b.md', 'a/c/d.jsonl', 'a/x.md']`：遞迴、只列檔案、照字串排序、不含 `ab/` |
| C2 | `list('沒有')` | `[]` |
| C3 | `read` 不存在的檔 | `null` |
| C4 | `read` 內容是 `'中文😀\r\n第二行'`（沒有檔尾換行）的檔 | 完全相同的字串 |
| C5 | `modify('n/m/新.md', edit)`，`n/` 不存在、`edit` 回傳 `'x'` | 建立上層資料夾與檔案，內容 `'x'`；`edit` 收到 `''` |
| C6 | `modify` 的 `edit` 回傳原文 | 不寫入：等事件送達的時間內，`watch` 沒有收到這個路徑 |
| C7 | 同一個檔同時呼叫兩次 `modify`，各在結尾加一個字 | 兩個字都在 |
| C8 | `edit` 丟出錯誤 | `modify` reject、檔案不變；下一次 `modify` 照常 |
| C9 | `append('p/q.jsonl', 'l1')`，`p/` 不存在 | 建立，內容 `'l1\n'` |
| C10 | 內容是 `'abc'` 的檔 `append(…, 'l2')` | `'abcl2\n'`（不替原檔補換行） |
| C11 | 不存在的檔同時呼叫 10 次 `append` | 10 行都在，照呼叫的順序 |
| C12 | `watch` 之後：新增、修改、刪除一個檔；改名 `a.md` → `b.md`；資料夾 `f/` 改名成 `g/`（裡面有 `1.md`） | 依序收到那個路徑；改名收到 `a.md` 與 `b.md`；資料夾改名收到 `f/1.md` 與 `g/1.md` |
| C13 | 取消監看之後再改檔 | 沒有通知 |
| C14 | 路徑是 `../x`、或絕對路徑 | 丟出錯誤或 reject，不碰 vault 以外 |

Obsidian 版的做法：

- `list` 用 `vault.getFiles()`；`read` 用 `vault.read`（讀到磁碟上最新的內容，包括 iCloud 剛同步來的）。`.jsonl` 和 `.md` 一樣能列、能讀、能追加。
- `modify` 用 `vault.process`（D-110）；不存在時建立上層資料夾再 `vault.create`。`edit` 回傳原文時不能寫入（不讓 iCloud 多同步一次）。
- `append`：存在時 `vault.append`，不存在時建立；同一個路徑的 `modify`、`append` 排隊，不互相蓋掉（和 Node 版相同）。
- `watch` 用 `vault.on('create' | 'modify' | 'delete' | 'rename')`，自己寫的檔一樣會通知。資料夾改名或刪除時，通知裡面每個檔案的舊、新路徑（C12）。

**完成條件**：契約檢查在 Node（`npm test`）、Windows 版 Obsidian（開發命令）全部通過；iPhone 照 [§5](#5-量測與-iphone)。

## 3. 外掛的資料狀態

### 3-1 讀取

`ready()` 依序：

1. 先開始監看（`files.watch`），再讀，這樣讀的期間改到的檔不會漏掉；讀完之前收到的通知，讀完後照 [§3-3](#3-3-檔案變動) 處理一次。
2. `readDecks(files)` → `decks`（計 `timings.decks`）。
3. 讀全部紀錄：`isLogPath` 的檔，每一個的文字記在「來源」裡，`mergeHistory(來源)` → `history`（計 `timings.history`；結果和 `readHistory(files)` 相同）。
4. `planToday(input())`（計 `timings.plan`）。`total` 是 `ready()` 開始到這裡。

`exam` 一律是 null（W4 §7）；`settings` 用選項或預設。

### 3-2 哪些檔案是什麼

- 卡組：`isDeckPath`。卡組以外的 `.md`、系統資料夾裡的筆記、`Essence Cards/` 以外的筆記都不讀。
- 紀錄：`isLogPath`。檔名是 `YYYY-MM <device>.jsonl` 的是**自己的**紀錄（例如 `2026-10 iPhone-7f3a.jsonl`）；其他都是別台裝置的，包括 iCloud 的衝突副本（例如 `2026-10 iPhone-7f3a 2.jsonl`）。
- 其他路徑的通知不理。

### 3-3 檔案變動

- 卡組的路徑：記下來，等 `delay` 之後重讀**那一篇**（讀到 `null` 就拿掉）。
- 別台裝置的紀錄：記下來，等 `delay` 之後重讀**那一個檔**、更新來源、整份重新 `mergeHistory`（Codex 審查 W4 第 10 點：外部紀錄一律重新 merge，不直接追加）。
- 自己的紀錄：**不理**。記憶中的來源與 `history` 在作答時就更新了（§3-4）；照通知重讀，每作答一次都要重新 merge 全部紀錄，違反 W4「作答後只呼叫輕的那兩個」的成本約定。
- `delay` 內又收到通知就重新計時；時間到了，同一個路徑只讀一次，全部處理完只 `planToday` 一次、呼叫 `onChange` 一次。內容沒有變（例如通知了但文字相同）時不重排、不呼叫。

### 3-4 作答

`answer(entry)`：

1. `t = writer.write(entry)`（W3 的 `createLogWriter`，`device`、`now`、`offset`、`onError` 照選項）。
2. `line = encodeEntry(t, entry)`；自己的來源（和寫檔同一個路徑，`logPath`）加上這一行。
3. `history = appendLine(history, line)`。
4. 不重排、不呼叫 `onChange`；之後的 `next`、`progress` 用新的 `history`（W4：輕的那兩個）。

`appendLine` 的規則，和 `mergeHistory` 一致：

- 作答：照 `at` 插進 `reviews`（同一個 `at` 的排在後面）；已經有 `t`、`lt`、`r`、`v`、`typed`、`src` 完全相同的一筆時不加。
- 取消（`undo`）：拿掉 `t` 是那個值的作答；找不到就什麼都不改。
- 變更（`set`）：照 `at` 加進 `changes`，完全相同的不加。
- 不改輸入的 `history`；`line` 不是合法的一行時丟出錯誤（自己寫的行不會這樣）。

驗收用的性質（T5）：一串自己的行依序 `appendLine` 的結果，和「這些行加進自己的來源後重新 `mergeHistory`」比，`reviews` 與 `changes` 的內容與順序都相同；唯一的例外是 `at` 完全相同、來自不同檔案的兩筆之間的先後（`mergeHistory` 用檔名決定，`appendLine` 不知道檔名），這時只要求照 `at` 排好、多重集合相同。

### 3-5 換日與換時區

`today()`、`next()`、`progress()` 每次先看呼叫當下的 `now` 與 `offset`：`dayOf(now, offset)` 不是今天的份的 `day`，**或 `offset` 和排今天的份時不同**，就重新 `planToday`（不呼叫 `onChange`），再回答。後者處理 Codex 審查 W4 的 F3：日編號相同、時區不同時，舊的 `Today` 用的是舊的清晨 4 點。W4 的修正（〈L2 審查後的修正〉第 4 點）讓 `Today` 記下 `offset`、`nextCard` 在時區不同時回 `stale`；但 `progress` 不回 `stale`，所以 `state` 仍要在每次呼叫前自己檢查。

`next()` 遇到 `stale` 時重排再取一次，所以不會回傳 `stale`。

### 3-6 補 ID

D-034：「家長手寫卡片時不用寫 ID，存檔時由程式補上」。Obsidian 打字時會自動存檔，沒有「存檔」這個動作；照存檔的時機補，家長還在打字時，` ^k3m9x2` 會插在游標所在的行尾、implicit 的題目會被往內縮。所以**在家長離開那篇筆記時才補**（[待使用者回答](#待使用者回答)第 2 題），由 [§4-3](#4-3-離開筆記時補-id) 呼叫 `fillIds(path)`：

- `fillIds` 選項是 false（手機）、`path` 不是卡組、或檔案不存在時，回傳 false，不讀也不寫（**不能**因為 `modify` 對不存在的檔會用 `edit('')` 建立，就留下一篇空的卡組）。
- `taken`＝其他每一篇卡組（不論狀態、寫錯的目標也算）的 ID，加上 `history` 的 `reviews` 與 `changes` 裡出現過的每一個 `lt`（D-034：刪掉的不再用）。
- `files.modify(path, text => assignIds(text, { taken, random }).text)`；文字有變回傳 true。之後的重讀與重排走 §3-3（修改通知），不另外處理。
- 不處理和別篇重複的 ID（`replace`）：W4 已經只出路徑在前的那篇並記 problem，要自動換掉得先定「哪一篇是原本的」，延後。

## 4. 外掛接線

`src/main.ts` 與 `src/obsidian/`。這些會 import `obsidian`，在 Node 測不到，所以邏輯盡量放在 `state`，這裡只接線；行為用開發版在 Windows 版 Obsidian 驗（T12）。

### 4-1 載入順序

- `onload` 只註冊命令與事件，不讀任何檔案；`workspace.onLayoutReady` 之後才建立 `state`、`void state.ready()`（Obsidian 在 layout ready 之前會對每個檔案發 `create`）。
- `ready()` 失敗、或紀錄寫不進去（`onError`）時，`console.error`，並用 `Notice` 提示一次「Essence Cards：複習紀錄暫時寫不進去，會自動再試」（同一次載入只提示一次）。
- 畫面切到背景（`visibilitychange` 變成 hidden，iPhone 切走 Obsidian）時 `void state.flush()`；`onunload` 時 `void state.close()`。

### 4-2 裝置碼

- 第一次載入時產生 `<平台>-<4 個 0-9a-f>`：平台是 `iPhone`、`iPad`、`Android`、`Windows`、`Mac`、`Linux`，都不是時用 `Device`。之後一直用同一個。
- 存在本機：`app.saveLocalStorage` / `app.loadLocalStorage`（這個 vault 專用的 localStorage），**不存外掛的 `data.json`**：那個資料夾跟著 iCloud 同步，試作外掛就是這樣讓 iPhone 和 Windows 拿到同一個碼（D-110）。這兩個 API 從 Obsidian 1.8.7 開始有，所以 `manifest.json` 的 `minAppVersion` 改成 `1.8.7`（電腦 1.14.4、iPhone 1.14.5 都符合），建置測試一起改。

### 4-3 離開筆記時補 ID

只在電腦（`Platform.isDesktopApp`）。`workspace` 的 `layout-change` 與 `file-open` 時，算出現在所有 Markdown 分頁開著的檔案（還沒載入的分頁用 `leaf.getViewState()` 的 `file`）；上一次開著、這一次沒有開著的卡組，各呼叫一次 `state.fillIds`。同一篇開在兩個分頁時，兩個都關了才算離開。啟動時不掃描、不補（家長可能正在另一台電腦改那一篇）；改名時舊路徑已經不存在，`fillIds` 回傳 false。

### 4-4 開發版

AI 在 Windows 版 Obsidian 測試與量測要用的命令，只放在開發版（例如 esbuild 的 `define` 加上 `if (DEV)`，正式建置整段拿掉）。命令本身會 import `obsidian`，放 `src/obsidian/`；能在 Node 測的部分（契約檢查、對照的比對、只看得到某個資料夾的 `Files`）放 `src/dev/`。

- `npm run install-vault -- <vault> --dev` 裝開發版；不加 `--dev` 照舊裝正式版。測試 vault 的 `.obsidian/community-plugins.json` 加上 `essence-cards`（只動測試 vault）。
- 每個命令都可以從命令面板執行（iPhone 用），也可以用 URI `obsidian://essence-cards-dev?vault=<測試 vault 的名稱>&run=<代號>` 執行（AI 在電腦上用 `Start-Process` 開，不必操作畫面）。
- 結果寫成 `Essence W5/結果/<代號> <裝置碼> <時間>.json`，包含裝置碼、平台、Obsidian 與外掛的版本、外掛載入後經過的毫秒數、這次載入第幾次執行，以及結果本身；完成時用 `Notice` 說「<名稱>完成」。

| 代號 | 命令名稱 | 做什麼 |
|---|---|---|
| `compare` | Essence 開發：metadataCache 對照 | [§0-3](#0-3-清單解析和-metadatacache-對照) |
| `files` | Essence 開發：檔案存取 | 在 `Essence W5/暫存/` 跑 [§2](#2-檔案存取的-obsidian-版) 的契約檢查 |
| `open` | Essence 開發：量測第一次打開 | 對 `Essence W5/量測/` 建一個新的 `state`（用只看得到那個資料夾的 `Files`，裡面也有 `Essence Cards/`），`fillIds: false`，記下 `ready()` 的 `LoadTimings`、紀錄行數、卡組與目標數、`share` 的長度，量完 `close()` |
| `today` | Essence 開發：今天的份 | 外掛正在用的 `state`：`day`、`share` 與 `more` 的 `lt` 清單、`progress()` |
| `answer` | Essence 開發：寫一筆再取消 | 對 `Essence Cards/W5 範例/` 裡路徑排第一的卡組的第一個目標 `answer` 一筆 `good`，`flush` 後讀回檔案，再 `answer` 取消它 |
| `fill` | Essence 開發：離開筆記時補 ID | 把 `Essence Cards/W5 範例/補 ID 試用（卡片）.md` 重設成沒有 ID 的內容，開在新分頁、等 2 秒、確認還沒補；再開在第二個分頁、關掉一個、確認還沒補；兩個都關掉、等 2 秒、確認補好，記下前後的文字 |
| `watch` | Essence 開發：記錄檔案通知 | 記錄 60 秒內 `state.onChange` 與 `history().reviews` 長度的變化（測別台裝置的紀錄進來） |

## 5. 量測與 iPhone

### 5-1 電腦

- `npm run bench -- --vault <路徑>`：在 `<路徑>/Essence W5/量測/` 寫入 W3 產生器的三年份紀錄（2 台裝置 × 36 個月、約 16.8 萬行）與 20 篇 × 100 個目標的卡組（ID 對得上紀錄裡的 `goal0`～`goal1999`，和 W4 的 T14 相同），再用 `createNodeFiles` 跑一次 `ready()`，印出 `LoadTimings`。不加 `--vault` 時照舊。產生器用 `tools/bench-study.ts` 已有的 `threeYears` 與 `threeYearDecks`（W4 修正後和測試共用），不另寫一份；`threeYearDecks` 回傳的是解析好的卡組，要寫成檔案時，把它改成先產生文字、再解析，測試的結果不變。
- `npm run bench` 另外印出 `answer`＋`next`＋`progress` 一次的中位數（三年份資料，21 次），超過 20 ms 時結束碼不是 0。精確的效能數字只放在 bench，不放進 `npm test`（W3 L2 修正第 6 項、Codex 審查 W4 的 F5）。
- Windows 版 Obsidian：`open` 跑兩次（第一次是測試 vault 剛被 URI 打開時；使用者的 Obsidian 開著時不要關掉它，就只量開著的情況並註明），`files`、`compare`、`today`、`answer`、`fill`、`watch` 各一次。`watch` 執行的期間，AI 從命令列在 `Essence Cards/紀錄/` 追加一個假裝置（例如 `2026-10 Test-0000.jsonl`）的一行，60 秒內要看到 `onChange` 與 `reviews` 多一筆；之後刪掉這個檔，再跑一次 `today`，確認和追加之前相同。

### 5-2 iPhone（集中成一次）

AI 測不了的原因：iPhone 上的 Obsidian 只能在手機上執行，iOS 的檔案存取與 localStorage 和電腦是不同的實作，iCloud 同步也要實機。數字由外掛寫成檔案、經 iCloud 傳回電腦由 Claude 讀，使用者不用抄數字。

**什麼時候做**：**併進 W6 的 iPhone 測試，一次做完**（使用者 2026-10-24 決定，[待使用者回答](#待使用者回答)第 1 題）。W5 在 Windows 驗完、L2 通過就合併；下面的步驟與 I1～I4 寫進 W6 的任務說明（backlog 技術債有一列提醒），在 W6 的 iPhone 測試裡判斷。

清單的草稿（實作時照試作外掛 README 的〈iPhone 測試清單〉寫成給使用者的步驟，約 5 分鐘）：

1. 確認測試 vault 已同步到 iPhone，社群外掛裡的 Essence Cards 開著。
2. 把 Obsidian 從多工畫面完全關掉，重新打開測試 vault，馬上執行「Essence 開發：量測第一次打開」，等出現「完成」。
3. 執行「Essence 開發：檔案存取」，再執行「Essence 開發：今天的份」。
4. 再把 Obsidian 完全關掉、重新打開，執行一次「Essence 開發：量測第一次打開」。
5. 回到對話告訴 Claude 做完了。

**驗收**（Claude 讀結果檔判斷）：

- I1：兩次「第一次打開」的 `history + plan` 都 ≤ 1,000 ms → D-110 不加快取，在 roadmap 記下數字並結案。超過 1 秒 → **停下來回報使用者**，快取是另一件工作，不在 W5 做。`decks` 與 `total` 一併記下；`total` 超過 1 秒但 `history + plan` 沒有時，也回報。
- I2：契約檢查 C1～C14 全部通過。
- I3：兩次結果的裝置碼相同、以 `iPhone-` 開頭，和 Windows 的不同。
- I4：同一天、同一份 vault（iPhone 沒有寫作答紀錄），iPhone 和 Windows 的 `today` 的 `share`、`more` 完全相同。

1. ✅ **iPhone 的量測什麼時候做？** 使用者 2026-10-24 選：**併進 W6 的 iPhone 測試，一次做完**（§5-2）。接受的代價：iOS 上檔案存取的問題（例如 `.jsonl` 在 iOS 的 vault 讀不到）、要不要加快取，要到 W6 的 iPhone 測試才知道；真的有問題，那次測試要重做。沒選的做法是 W5 合併前單獨做一次（約 5 分鐘）。
2. **ID 什麼時候補？** D-034 寫「存檔時由程式補上」，但 Obsidian 打字時會自動存檔，沒有「存檔」這個動作。建議改成：**家長離開那篇筆記時（切到別篇、關掉分頁）才補，而且只在電腦上補**（§3-6、§4-3）。代價：家長寫完不離開那篇、直接拿 iPhone 複習時，新寫的卡在 iPhone 上還沒有 ID、不會出現，要回電腦切到別篇才會補上；另外，在 Obsidian 以外建立、從來沒在 Obsidian 打開過的卡組不會自動補（AI 製卡存草稿時自己配 ID，D-110）。不採用的代價：照字面「存檔時」補，家長打字時 ID 會插進游標所在的行、implicit 的題目會被往內縮；手機也補的話，電腦和手機可能同時替同一篇配不同的 ID，iCloud 只留一邊，另一邊的作答就對不到目標。同意後照 essence-decision 寫進決策紀錄。
   - 💬 **使用者 2026-10-24 提出：加一個「存檔」按鈕**。理由：邊打字邊補會插進正在打的那一行；切到別篇才補，打完常會忘記切；有一個存檔按鈕，反而會讓人記得做完要存檔。Claude 的看法：同意以按鈕為主，另外保留「離開筆記時補」當備援、有還沒補 ID 的目標時按鈕要醒目。
   - 💬 **使用者 2026-10-24 追問：ID 補上之後，家長之後在那一行行尾接著打字、按 Delete、在別的編輯器改，ID 一樣會壞；不能靠家長注意游標**。Claude 修正後的提案：先分清兩種錯，**弄丟複習紀錄**不能靠任何習慣避免；**卡片晚一點出現**可以靠提醒補。前者用三層全自動的保護，家長不必知道 ID 存在：
     1. **認得**（解析，iPhone 也適用）：目標那一行最後不是 ID、但行中間有一個程式產生格式的 ID（` ^` 加 6 碼，不在行內程式碼與公式裡），照樣當成這個目標的 ID，只記一個提示。例：`- 能說明擴散 ^k3m9x2 的現象` 的 ID 仍是 `k3m9x2`，名稱是「能說明擴散 的現象」。
     2. **找回**（補 ID 時）：目標沒有 ID 時，先看它的題目指紋有沒有出現在複習紀錄裡、而且那個 ID 現在不在任何卡組；剛好一個就用回那個 ID，不配新的。ID 被整個刪掉、AI 重寫時漏掉，只要題目沒改，紀錄都接得回來。D-034「刪除後不再使用」是怕新的目標繼承別人的紀錄；同一題找回原本的 ID 不違反它。
     3. **歸位**（補 ID 時）：把跑到行中間的 ID 移回行尾。
     
     唯一接不回來的是 ID 不見、同時題目也全改了，這等於一張新卡。以後做編輯畫面的樣式（D-047）時，再把 ID 在編輯器裡藏起來、游標到不了 ID 後面；那時可以改成停手幾秒就自動補，連按鈕都不必按。這三層會改到卡組模組（解析與 `assignIds`）與 syntax.md §2-3，待使用者確認後寫進決策紀錄與 §1、§3-6、§4-3、測試清單。

## 和「不做」比較（D-153、D-177）

- **不做會怎樣**：維持 D-199。在電腦改設定、還原時勾「設定」，幾分鐘後兩台的設定可能一起回預設，沒有提示；其他家長一直被 D-199 第 4 點擋住。測試 vault 的 `data.json` 已經卡住：電腦寫出來約 40 秒就變成副本（討論稿 H）。
- **做的代價**：store 換讀寫的對象、還原的「設定」那一列換來源、設定頁多一個缺檔時的提示與按鈕；一輪 L2；iPhone 測兩項。學生的畫面不變。
- **更小的做法**：
  - 只在 iPhone 改（D）：同上，只能暫行。
  - 先只換路徑，不做 `legacy` 與缺檔保護：混用期間舊版那台改的設定會被新版默默蓋掉（討論稿第二輪第 1 節第 2 項）；設定檔不見時兩台照樣回預設，A 失敗時也看不出來。這兩項是 A 唯一的安全網，一起做。
  - B2、C：見討論稿；B2 是 A 沒過時的備案。

**第 1 類（合併前做足）**：設定不再寫 `data.json`；新檔的讀、寫、讀回核對；舊版那台改的項目新版會採用；設定檔不見時不回預設、不寫觀察行；還原「設定」的來源、目的與比對；舊版外掛讀不到新檔、不受影響；V1～V4。

**第 2 類（可以延後）**：無。設定頁的提示文字與按鈕的版面先照現有的列做，使用者看過再調，資料沒有風險。

## 1. 檔案（格式查核）

- **位置**：`Essence Cards/設定.json`（暫定）。不放 `紀錄/`：那裡的檔還原時只補不見的、同名不同內容列成衝突（`plan.ts` 的 `LOG_FOLDER` 規則），設定要能還原；`紀錄/` 直接底下的 `.jsonl` 舊版會當紀錄讀（`src/core/study/history.ts:24`）。根資料夾已在系統資料夾的防呆裡（`src/core/deck/folders.ts` 的 `GUARDED`），搬走會被搬回。不是 `.md`，不算卡組，Obsidian 的檔案列預設不顯示 `.json`。
- **內容**：和 §10 現在的 `data.json` 同樣五個欄位、同樣的值與讀法，平的 JSON 物件，兩格縮排加結尾換行；不認得的欄位存檔時保留（D-149 第 3 點）。多一個欄位：
  - `legacy`：疊出這份內容的那一次讀到的 `data.json` 裡那五個欄位（照原樣，含讀不懂的值；沒有的欄位就不列）。設定頁存檔用當底的那一次讀（§2）；還原與重新建立用寫入當下的讀（§4）。那一次讀不到 `data.json`（不存在、讀不到、不是物件）：設定頁存檔沿用這份檔原本的 `legacy`，原本也沒有是 `null`；還原與重新建立是 `null`。`null` 和 `{}`（讀到空物件）不同：`null` 不疊，避免把 iPhone 的佔位檔當成可信的空基準。
- **誰寫、什麼時候建立**：只有 Essence Cards 寫：外掛的設定頁、「重新建立」（§3）、外掛與命令列工具的還原勾「設定」（§4）。這幾個時候才建立；載入時不建立、不寫，也不從 `data.json` 自動搬過來。
- **系統資料夾防呆**：只有設定檔也算根資料夾在（`presentFolders`），根資料夾整個被搬走照原本的 `GUARDED` 搬回；漏掉搬動事件、又沒記過任何系統子資料夾時，只能報根資料夾不見，找不到搬去哪裡（和只有卡組時相同）。單獨改名或刪掉設定檔走 §3。
- **讀不懂的檔**（不是 JSON 物件、含 NUL）：當成讀不到，和現在 `data.json` 讀不懂一樣：不寫、不採用；還原勾「設定」時以空的當底（plugin-restore.md §4）。
- **`data.json` 不刪**：留給舊版讀，新版只讀不寫。

## 2. 讀與寫

store（`src/core/settings/store.ts`）的隊伍、核對、`known` 的規則不變，只換交給它的 `load`／`save`（現在是 `loadData`／`saveData`，`src/main.ts:132`）。疊 `legacy` 的規則寫成純函式放在 `src/core/settings/`，接線在 `src/obsidian/`。

- **load**：
  1. 讀 `Essence Cards/設定.json`（`Files.readBytes`）。丟錯、含 NUL、不是 JSON 物件：回「讀不到」（`undefined`：store 手上的值與 `known` 都不變，§3 的讀不懂）。
  2. 是物件：讀 `data.json`（`loadData`）來疊（下一點），回疊完的內容，`legacy` 換成這一次讀到的 `data.json` 的五個欄位（讀不到就沿用設定檔原本的）。
  3. 不存在：這台確認過設定檔（§3）就回「不見」（`MISSING`：手上的值不變、`known` 變 false，§3）；沒確認過就照現在讀 `data.json`（物件時加上它自己的五個欄位當 `legacy`；不存在、讀不到照原樣交給 store）。
- **疊 `legacy`**：設定檔的 `legacy` 是物件、`data.json` 也讀到物件時，五個欄位逐一比（JSON 相同才算相同，有沒有這個欄位也算）；`semester` 與 `semesterSetOn` 算一項。不同的那幾項：`data.json` 整項都沒有就刪掉（回預設）；讀得懂（設定頁的選項，學期兩欄都對）就換成它的；讀不懂的不採用，留設定檔的（那是壞掉或手改，不是舊版設定頁存的）。其他情況不疊。意思是：舊版那台在新檔建立之後改的項目，新版採用；新版改的項目不被 `data.json` 的舊值蓋掉。
- **什麼時候算採用**：疊上的值讀到就生效（畫面、排程），下一次存任何一項時和 `legacy` 一起落進設定檔。落進去之前 `data.json` 不見或讀不懂，疊上的值退回設定檔的（§5 第一種情況）。不在載入時寫：討論稿〈Claude 回應 Codex 第二輪〉第 3 節寫的「當成一次修改寫進新檔」改成這樣，理由是載入不寫，電腦少寫一次、`update-vault --check` 與比較工具讀的時候不會改檔；混用期間很短，更新說明要兩台先重開。
- **save**：把 store 交來的內容寫進設定檔（`Files.modify`，原地寫，不存在時建立）：交來的有 `legacy` 就照寫（讀的時候換好的，和當底的是同一次 `data.json`；當底之後才變的 `data.json` 不算看過，讀回時再疊）；沒有（還原、重新建立）才讀 `data.json`，讀不到是 `null`。不呼叫 `saveData`。
- **重讀**：`Files.watch` 通知到設定檔的路徑（新增、修改、刪除、改名的舊或新路徑）就 `store.reload()`；`onExternalSettingsChange`（`data.json` 變了）照舊重讀，因為疊的結果跟著它變；iPhone 回到前景照舊重讀。
- 讀回核對：寫完重讀時，`data.json` 和當底時一樣就不再疊；寫之前它又變了，讀回時疊上，核對只看這次改的那一項（`hasChange`），被疊掉就回 `failed`。

## 3. 設定檔不見時

- **確認過**：store 採用 load 從設定檔讀到的內容（第 2 步）時，把疊完的五個欄位存進這個 vault 專用的 localStorage（`app.saveLocalStorage`，和裝置碼同一種，`src/obsidian/device.ts`）。逾時之後才回來、寫前當底的讀沒被採用，不記（L2 的 R4）。有這筆就是「這台確認過設定檔」。
- **之後不見了**（不存在，或這次執行見過、之後不見）：
  - store 一開始就用這筆當手上的值（`known` 是 false）：排程用它，不用預設值；`known` 是 false，不寫觀察行（現在的規則）。
  - 用到一半不見（load 回 `MISSING`）：手上的值不變（就是最後採用、記下的那一份），`known` 變 false，不再寫觀察行；再讀到檔才變回 true（L2 的 R1）。
  - 不見和讀不懂分開：檔還在、內容讀不懂（§1）照讀不到的規則，手上的值與 `known` 都不變，不出現下面那一列；「重新建立」只在不見時寫，不蓋掉讀不懂的檔。
  - 改設定照現在回「讀不到」，不寫。
  - 設定頁最上面多一列：「設定檔讀不到：先用這台上次確認的設定。」和一個「重新建立」按鈕。按下去走 store 的隊伍：再讀一次，還是不存在才寫，內容是輪到時這台確認的那筆加上 `legacy`（排隊時前面的重讀可能已經記下新的值，L2 第二輪的 R8）；真的寫入那一刻（`Files.modify` 交來的內容）再看一次，檔已經在了就不寫、回「已經回來」（L2 的 R2：中間讀 `data.json` 的等待裡同步可能把檔送回來）；寫完讀回核對、通知。設定檔回來了（重讀讀到）這一列就消失。
  - 已知限制（L2 第二輪的 R9，第三輪同意不修；列在 [backlog〈已知的限制〉](../docs/backlog.md#已知的限制)）：那一列跟著最近一次讀檔，不是 store 採用的那一次。設定頁開著時，一次讀超過 5 秒、期間檔被移走、晚到的又是讀不懂的內容，那一列會先收起來（手上的值與 `known` 不變、不寫）；重開設定頁會重讀，那一列就回來。
- **沒確認過**（新裝置、還沒建立過）：和現在一樣，設定檔與 `data.json` 都沒有就是預設值，`known` 是 true。
- 理由：A 失敗時（設定檔被 iCloud 改名）兩台不會默默回預設，畫面看得出來，就知道要改做 B2。iPhone 的佔位檔會回報成不存在（store.ts 的 `usable` 註解），所以不自動重建，要家長按。

## 4. 還原與備份（格式查核）

- **備份**：設定檔在 `Essence Cards/` 底下，照現在的規則進備份；`data.json` 照舊也備（`take.ts` 不改），舊版的還原讀得到它。
- **計畫**（`src/core/backup/plan.ts`）：
  - 「設定」那一列的來源與備份的值：
    - 備份裡有 `Essence Cards/設定.json`：值是它疊上同一份備份的 `data.json`（§2 的疊法）；`data.json` 不列。設定檔讀不懂（含 NUL、不是物件）就擋住（「備份裡的設定讀不懂」），不退回用 `data.json`。
    - 沒有設定檔、有 `<vault.config>/plugins/essence-cards/data.json`：值是它；讀不懂就擋住。
    - 兩個都沒有：沒有「設定」那一列；現在有設定檔就列成「備份後才有」，不動它。
  - 目的地一律是 `Essence Cards/設定.json`，不需要現在的設定資料夾。
  - 現在的值：設定檔疊上現在的 `data.json`；沒有設定檔才是現在的 `data.json`（還沒建立設定檔也能比）。現在的 `data.json` 不列成「備份後才有」。設定檔有內容但讀不懂：畫面寫讀不懂，勾選後以空的當底；讀檔失敗：整次比對失敗。
  - 兩邊的 `data.json` 都照電腦上 Obsidian 的 `loadData` 讀：開頭有 BOM 就是讀不懂（不疊；沒有設定檔時那一邊讀不懂），和外掛算的值一樣；命令列寫入的 `legacy` 也照這個讀法（L2 的 R5）。設定檔照舊拿掉 BOM，外掛自己讀位元組也是。
  - 兩邊疊完的五個欄位都相同（`sameSaved`，不看 `legacy` 與不認得的欄位）就不列；只差 `legacy`、疊完卻不同的照樣列。
  - 比的是磁碟上的檔：確認過設定檔的裝置在檔不見時用本機的值（§3），還原畫面看的仍是磁碟上的。
  - 設定檔不套用一般檔案的規則（卡組、ID、紀錄）。
- **寫入**：照現在走 `store.restore`（plugin-restore.md §4）。寫前重讀，設定檔的 sha 和比對時不同，或現在的值（同上的算法，含 `data.json`）和比對時不同，就算比對之後改過、跳過：沒有設定檔時只看 sha 會漏掉 `data.json` 的變化。以讀到的設定檔為底、拿掉 `legacy`，五個欄位換成備份的值，備份沒有的拿掉，不認得的留著；`legacy` 是寫入當下的 `data.json`，讀不到是 `null`。比對與真的寫入之間還隔著讀 `data.json` 與寫入本身的讀，所以寫入那一刻（`Files.modify` 交來的內容）再比一次設定檔的原文（開頭的 BOM 留著），和比對時不同就不寫、算比對之後改過（L2 的 R2）。寫 `legacy` 讀的 `data.json` 和比對時算現在的值讀的是兩次：這次的五個欄位和比對時的不同（舊版那台在中間改了設定），也不寫、算比對之後改過（L2 第二輪的 R7）。意思是：還原的是家長選的一整份值，之前沒看過的舊版改動由這次還原取代；沿用原本的 `legacy` 的話，`data.json` 之後回來會把剛還原的值蓋掉。
- **畫面**：還原視窗的「設定」那一列改用目的地是設定檔來認（現在是 `endsWith('/' + PLUGIN_DATA)`，`src/obsidian/restore-modal.ts:179`）。
- 命令列的工具：`tools/restore.ts` 用同一套計畫與寫入內容，`--apply` 時重算計畫，「設定」那一列另外比現在的值。重算用的是開始時讀的現況，所以寫暫存檔之前再讀一次設定檔與 `data.json`，比雜湊與現在的值，要寫的內容與 `legacy` 都用這一次讀到的；改名之前除了設定檔的雜湊，也比 `data.json` 的雜湊和那一次相同，不同就跳過（L2 的 R3）；先比 `data.json`，最後比設定檔，比完到改名之間不再等別的讀（L2 第二輪的 R6）。寫完重讀的期間設定檔又被別台改了、資料夾被換成連結，列在 [backlog〈已知的限制〉](../docs/backlog.md#已知的限制)（L2 第四輪的 R12、R13）。兩個檔各自同步，先讀的那一檔總有空檔，所以改名之後再讀兩個檔算現在的值，和備份的五個欄位不同（最後一次讀 `data.json` 之後舊版才改）或讀不到，就回「失敗」並說明設定檔已經寫了、重跑 `--plan`，和外掛的讀回核對一樣（L2 第三輪的 R11）。設定資料夾確定不了時計畫照出，但做不了還原前的備份，`--apply` 停下（syntax §8、D-150）。`tools/backup.ts`、`tools/update-vault.ts`、`tools/compare-versions.ts` 的處理見〈結果〉。
- **舊版的還原遇到新版的備份**：`0.4.0` 的外掛與命令列把備份的 `data.json` 當「設定」寫到外掛資料夾，把設定檔當一般檔照原路徑、原位元組還原（格式查核第 2 節用 `v0.4.0` 的計畫器驗過）。兩列都勾時，舊版讀回備份的 `data.json`；升回新版後讀備份裡的設定檔、疊現在的 `data.json`：例如備份裡設定檔上限 60、`data.json` 15，`legacy` 是 15 就是 60，是 30 就是 15。新版做的備份請用新版還原；備份格式版本維持 1。

## 5. 相容與退版（格式查核）

- **舊版**：只讀寫 `data.json`，讀不到設定檔（不在 `紀錄/` 直接底下，不是卡組）。新版不寫 `data.json`。舊版的還原見 §4 最後一點。
- **混用期間**（一台新版、一台還沒重開）：舊版那台在設定檔建立之後改的項目，新版經 §2 的疊法採用，下一次存檔落進設定檔；新版改的，舊版那台重開成新版之前看不到。不加 `need`，不做兩段發布的啟用（討論稿〈Claude 回應 Codex 第二輪〉第 3 節）。會丟掉舊版那台改動的情況：
  1. 疊上之後、落進設定檔之前，`data.json` 不見或讀不懂：退回設定檔的值。例：設定檔上限 45、`legacy` 30，舊版改成 15，新版先顯示 15；`data.json` 被改名之後回到 45。
  2. 設定檔建立時讀不到 `data.json`（`legacy` 是 `null`）：舊版那台之後改的都不採用，直到新版下一次存檔記下當時的 `data.json`（那時的值也當成看過、不採用）。
  3. 舊版那台存了讀不懂的值：不採用（§2）。

  兩台新版同時改設定檔照 syntax §10，一份勝出，`legacy` 跟著那一份。照更新說明兩台先重開再改設定，就碰不到這三種。
- **新安裝**：沒有 `data.json`，直接用設定檔。
- **退版**（💡 寫 D-ID 時請使用者確認）：允許退回 `0.4.x`，安裝命令不擋（D-149 第 4 點只看 `需要版本`／`need`，沒有其他資料要求新版時照樣能退）。舊版讀 `data.json`：看到的是搬家前或舊版最後寫的值，沒有就是預設，之後在新版改的設定要重選；設定檔留在 vault 裡，升回新版時照 §2 讀（退版期間舊版改的項目照 `legacy` 的規則採用）。複習資料不受影響。不擋退版：退版是出事時的退路，設定只有五項、重選很快，擋住退版的代價比較大。也不做寫回 `data.json` 的回轉：電腦寫 `data.json` 正是這個錯。寫 D-ID 時把混用與退版的這兩個例外補進 D-149 第 3 點的相容說明。
- **更新說明**：「兩台都重開一次 Obsidian 再改設定」；不寫「不會遺失」這種無條件的話（上面三種情況）。

## 6. 測試

只透過公開介面測（store、load／save 的接線函式、`planRestore`、`applyRestore`）；Files 與 `loadData`／`saveData` 用替身。預期值用下面寫死的例子。

1. 改一項：設定檔有那一項與 `legacy`；`saveData` 一次都沒被呼叫。
2. 沒有設定檔、`data.json` 是 `{"capMinutes":45,"semester":"國二上","semesterSetOn":"2026-09-15"}`：值是 45 與國二上；改保持率成 0.85 之後，設定檔是那三欄加 `retention: 0.85`，`legacy` 是那三欄。
3. 疊：設定檔 `capMinutes` 45、`retention` 0.9、`legacy` 是 `{"capMinutes":30,"retention":0.8}`；`data.json` 是 `{"capMinutes":15,"retention":0.8}` → 有效值 15 與 0.9。`data.json` 拿掉 `capMinutes` → 有效值回預設 30。學期兩欄一起換。
4. 不疊：`data.json` 不存在、讀不到、不是物件，或 `legacy` 是 `null`：有效值是設定檔的。
5. 寫入時 `data.json` 讀不到：`legacy` 沿用原本的；原本沒有是 `null`。
6. 載入（`first()`）之後沒有任何寫入，不論設定檔與 `data.json` 有沒有。
7. 確認過、設定檔不見（開啟時就不在，或用到一半不見，後者 `known` 由 true 變 false、檔回來再變 true）：值是 localStorage 那筆、`known` 是 false；改設定回 `unreadable`、設定檔沒被寫；「重新建立」寫出那筆，之後 `known` 是 true；重新建立時檔已經回來就不寫。
8. 沒確認過、兩個檔都沒有：預設值、`known` 是 true（現在的行為）。
9. 重讀：`watch` 通知設定檔的路徑（含改名的舊路徑）會重讀；其他路徑不會。
10. 還原計畫：備份只有 `data.json` → 目的地是設定檔；備份兩個都有 → 用設定檔、`data.json` 不列；現在沒有設定檔 → 和現在的 `data.json` 比；五欄相同、只差 `legacy` → 不列；現在的 `data.json` 不列成「備份後才有」。
11. 還原寫入：比對之後設定檔改過 → `changed`；寫入不碰 `data.json`。
12. 舊版：`isLogPath`、`isDeckPath` 都不認設定檔；系統資料夾防呆照常。
13. 現有的 store、還原、設定頁測試照樣全過（改到的只換路徑與來源）。
14. 疊：`data.json` 那一項讀不懂（不是選項、學期缺一半、不存在的日期）不採用；整項拿掉是回預設；學期兩欄都對才換。
15. 時序：當底讀到 `data.json` 上限 30，寫之前舊版改成 15 → 寫進去的 `legacy` 是 30，讀回疊上 15，下一次存檔落進設定檔（有設定檔、沒有設定檔各一）。
16. 還原：`legacy` 是寫入當下的 `data.json`，讀不到是 `null`；之後 `data.json` 是 15 也不蓋掉還原的值（store、外掛接線、命令列）。
17. 還原：沒有設定檔、比對之後 `data.json` 變了 → 跳過、不建立設定檔（外掛、命令列）；命令列還原之後再做計畫，「設定」不再列出。

`0.4.0` 還原新版備份的兩列不寫測試：`v0.4.0` 是不會再改的 tag，行為由格式查核用它的計畫器驗過，寫在 §4。

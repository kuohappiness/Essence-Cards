# 2026-10-10｜舊外掛分析的後續待討論題

摘要，不是逐字紀錄。決定的完整內容見[決策紀錄](../../decisions.md)。接續[資料存放、v1 範圍與舊外掛分析](2026-10-10-data-scope-and-old-plugin.md)，依[路線圖](../../roadmap.md#下一次對話從這裡開始)的順序一次一題。

## 一行多個填空

- **原提案**：舊外掛分析第二版 §7-3 由助理提出：`密度 = ==質量== ÷ ==體積==` 算一個學習目標，每次只挖一個空、輪流出題。
- **助理用真實教材重新驗證後撤回**：
  - 沒挖的空格本身就是提示，例如 `密度 = ＿ ÷ 體積`、四個空露出三個的光合作用反應式。練習比考試簡單。
  - 答得輕鬆會讓 FSRS 拉長間隔，考前反而忘掉。
  - 每個空的實際複習間隔變成好幾倍。
  - 原提案擔心「忘一個就整題失敗」：同一個知識忘一個就是還不會；不相干的空格本來就該拆開。
- **其他選項**：每個空格各自一個學習目標（Anki 的做法），因複習量倍增、答案會露在題目上而不採用。「先挖一個、答對後全挖」的漸進出題記入 backlog。
- **使用者同意**：一行＝一題，一次全挖（D-049）。
- **留待之後**：只忘了其中一個空時怎麼自評，併入「複習與檢核細節」。

## 反向、雙向與內嵌語法（2026-10-11）

- **原提案**：舊外掛分析第二版 §7-2：不沿用 `;;`、`:::`、`{{fc}}`；雙向改由卡組設定決定，程式自動多建反方向的學習目標。
- **助理用真實例子檢查後修正**：
  - 左右直接對調常常不是好題目：`big :: 大的` 反過來，答案可能是 big、large 或 huge。英文規則的拼字題本來就用「中文意思加例句挖空」。
  - 卡組設定只能整組開啟，複習量變兩倍；筆記裡看不到的學習目標，家長也無法單獨刪除或暫停。
  - 舊外掛的 `:::` 可以逐字挑選，但題目品質的問題還在。
- **使用者同意**：三種語法都不沿用，每個方向各寫一行；「中→英」、「拼字」是交給 AI 的製卡選項（D-050）。英文製卡規則的中→英題目補上提示（v0.3）。

## 使用者提出的情境：單字第一階段（2026-10-11）

- **情境**：一課 40 個單字做成一份卡組，每天快速翻一遍；第一階段只求背起來，先求有再求好。使用者問是否和現有設計衝突。
- **助理判斷：方向不衝突**：
  - 一課一份卡組（D-025）；手寫可以只寫 `borrow :: 借入`，例句必備是 AI 製卡規則，不是語法要求。
  - 「先求有再求好」對應題目池的基本題 → 進階題（D-028），以及之後再開的中→英、拼字（D-050）；這也是 D-013 的漸進結構。
  - 一課翻一遍約幾分鐘，在每天 15 分鐘以內。
- **需要在「複習與檢核細節」處理的三點**：新卡上限要讓一整課同一天開始；同一次複習中答錯的卡要不要幾分鐘後再出；要不要提供不管到期日的「整課自由練習」。記入 backlog 第 11、12 題。

## 後續補充（2026-10-11）

- **完整訓練**：使用者提議把「整課自由練習」擴大成「自訂範圍的完整訓練」。助理同意，建議直接沿用已有的範圍（D-026、D-041），範圍很大時先出最容易忘的卡。是否放進 v1，在「複習與檢核細節」一起決定（backlog 第 12 題）。
- **反方向題用例句問**：使用者認為 `大的 → big／large／huge` 改用例句問的做法值得寫進英文製卡規則。助理補充：例句加中文還是可能有好幾個答案（`The elephant is very ＿＿.`），這時再給字首。已寫進英文製卡規則 v0.3，D-050 加附註。

## 介面技術（2026-10-11）

- **助理原建議**：樣式用純 CSS 加自訂前綴；框架用 Preact（體積小）；只做一個原型，不比較四種框架。
- **使用者提問**：未來的複習形式可能結合圖片、心智圖、音檔，會不會受限？複習畫面能不能像 HTML 一樣自由？使用者很在意介面質感。
- **助理回答並修正**：
  - 外掛畫面本身就是網頁，框架不限制能做什麼。真正的限制來自畫面在 Obsidian 裡面：上下欄、側欄滑動、佈景主題、iPhone 網頁的音訊限制，換任何框架都一樣。
  - 質感主要來自設計，建議建立 Essence 自己的設計規範，只跟著 Obsidian 切換亮暗色。
  - 會受框架影響的是現成套件：動畫、手勢、拖放的好套件都以 React 為主，所以改建議 React 加 Motion，Preact 當退路。
- **使用者同意**框架與原型（D-051），並補充：藏起上下欄如果工程大或影響效能，可以接受外框；側欄滑動解決不了就寫進使用說明書。
- **樣式**：使用者要求先分析純 CSS 比 Tailwind 有沒有無法接受的缺點，再決定。
- **樣式分析**：Tailwind 最後也是產生 CSS，質感上限相同。純 CSS 的缺點（數值不一致、要取名、樣式累積、不能直接複製 Tailwind 寫的元件外觀）都有對策；Tailwind 在 Obsidian 裡則有直接衝突：卡片內容是 Obsidian 渲染的 HTML、重設樣式與撞名、CSS 圖層被 Obsidian 的樣式蓋過。使用者同意用純 CSS（D-052）。

## 開發流程（2026-10-11）

- **助理建議**：沿用三段式、Retrospective、快慢兩層測試、編碼檢查、手機相容清單；推送前測試改由 CI 跑；一鍵發版改成一鍵安裝到 vault；新增程式分層的自動檢查；不沿用 dev_log、只改文件也升版、平行路線圖編號。
- **使用者同意**，並補充：舊的 Instruction、SKILL 很多是為舊版語言模型寫的，不用照單全收，以現在的能力判斷真正需要的才寫。
- **助理看過舊 repo 的 Instruction、兩份 SKILL 後判斷**：角色設定、通用工程習慣、閱讀順序與 dev_log 程序都不需要；產品規格已有其他文件。真正需要的是專案特有的陷阱，能用工具檢查的交給工具。當下就需要的只有一條：多個 AI session 共用同一個資料夾時只 stage 自己的檔案，已加進 AGENTS.md（D-053）。

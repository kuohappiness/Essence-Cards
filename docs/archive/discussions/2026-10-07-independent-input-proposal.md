# 輸入工具獨立開發與文件交接提案

日期：2026-10-07（Asia/Taipei）
狀態：探索中的架構提案，尚未取代 C-020 的同一外掛內部分模組方案。本文件是討論摘要，非逐字紀錄。

## 使用者情境

使用者有時只需要將 YouTube 轉為筆記，沒有閃卡需求；有時只需要閃卡複習與檢核。因此詢問是否將輸入獨立開發，平常透過 AI 將各種知識來源轉成文件，保留介面，供 Essence Cards 有需要時接入。

## 助理建議｜待確認

建議把來源整理做成可獨立使用的工具，與 Essence Cards 透過文件約定連接。來源工具負責取得與整理內容、呈現可核對草稿、保存文件及來源；Essence Cards 負責學習材料、閃卡複習與學習檢核。筆記完成後即可獨立閱讀，不必建立任何閃卡；閃卡及檢核也能使用既有資料，不必安裝或執行來源工具。

功能架構仍可保留輸入、輸出、檢核三種責任；交付邊界則可分為來源整理工具，以及承載輸出與檢核的 Essence Cards。這會調整 C-020 中「全部放在同一個 Obsidian 外掛」的包裝方式，需在採用後才同步正式共識與架構圖。

來源轉換核心宜與 Essence Cards 及 Obsidian 特定 API 分開，薄的入口或轉接負責整合。獨立開發不代表必須立即另建 GitHub repo、雲端服務或兩套帳號／資料庫；初期可在同一 repo 維護可分別執行與驗收的程式。獨立工具最終採另一個外掛、桌面工具或其他形式仍待議。

## 最小交接提案

先採檔案交接：Markdown 正文、必要附件及少量來源資料。純筆記不要求填滿學習欄位；Essence Cards 也應能接收一般 Markdown，再補上需要的資訊。

- 文件識別與來源：穩定文件 ID、標題、原始 URL／來源參照，以及能取得的頁碼或時間點。
- 內容與附件：可獨立閱讀的正文、可攜的附件相對路徑；必要圖片不可只剩失效引用。
- 版本：文件版本、交接格式版本及處理狀態，讓後續能辨識重複匯入與來源更新。
- 採用與更新：AI 結果在來源工具內可核對；重跑來源轉換不得默默覆蓋手動修訂。Essence Cards 選擇採用的文件版本，更新時提示受影響材料，保留舊卡片與學習事件。

以上為候選約定，欄位名稱及必填範圍尚未定案。初期由使用者選擇文件交接即可；一鍵呼叫、任務 API 或自動偵測更新依真實需要增加，不先把兩邊綁成必須同時運作的系統。

## 取捨與下一步

收益：兩個日常情境能各自完成；來源擷取、轉錄或模型替換可分開更新；閃卡端可避免載入用不到的轉換依賴。程式碼更簡潔與效能更好仍是待驗證目標，不能由拆分直接保證。

代價：需維護兩個入口與文件相容性，處理附件、重複匯入、版本更新及人工修訂歸屬。只約定「輸出 Markdown」不足以解決這些整合問題，也不宜共用整套可變內部資料狀態。

建議先確定最小文件交接與各自資料責任，再各做一條能完成的情境：來源工具先驗 YouTube → 筆記，Essence Cards 先驗既有／手動閃卡 → 複習與檢核。實際先開發哪邊、首批格式與檢核範圍仍待選定；新提案不自動改變現有開發順序。YouTube 的文字取得、轉錄、成本與模型方式尚未選定，其他來源逐項增加。

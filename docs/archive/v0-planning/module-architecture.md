# Essence Cards｜三模組與兩階段交付

版本：0.3
更新日期：2026-10-07（Asia/Taipei）
狀態：依 C-020／C-022／C-023，本 repo 聚焦輸出、檢核與選用 AI；輸入另開 repo、之後開發為獨立 Obsidian 外掛。兩邊各自使用、按需交接；精確 MVP、資料格式與檢核操作仍待討論。

## 功能責任與交付單位

| M-ID | 功能責任 | 交付單位與階段 | 可獨立完成的情境 |
|---|---|---|---|
| M-001 | 輸入：取得、選取及整理來源，形成文件 | 另一 repo 的獨立 Obsidian 外掛，預計 Essence Capture（尚未建立），第二階段開發 | 只將 YouTube 等來源整理為可讀筆記，保存後結束 |
| M-002 | 輸出：製作、呈現與使用教材、心智圖、閃卡等材料 | Essence Cards，第一階段專注 | 用既有筆記或手動／既有卡片開始學習，不必執行來源工具 |
| M-003 | 檢核：檢查內容或學習結果，提供回饋 | Essence Cards，第一階段專注 | 使用已有材料／紀錄檢核與修訂；精確對象、操作及必要資料待議 |

整體保留三種功能責任，實際交付分成兩個工具。C-022 取代 C-020 中「全部放在同一個 Obsidian 外掛」的包裝方式；Essence Cards 第一版仍以 Obsidian 外掛開發。兩個工具都是獨立 Obsidian 外掛，分別打包與安裝；來源工具另開 repo，預計名稱 Essence Capture，尚未建立。

「輸出」指學習材料製作與使用，來源工具也可以自行產生可讀文件。單純筆記不必製卡；學習工具不必取得新來源。文件交接可選，不要求兩邊同時執行；新增來源工具不改變原有複習與檢核入口。

## 已確認的兩階段順序

| 階段 | 工作重心 | 整合要求 |
|---|---|---|
| 第一階段 | 先完成 Essence Cards 的輸出與檢核；逐步交付可用功能 | 接受既有筆記／材料／卡片；從初期細化文件、來源、附件與版本約定，使用手動樣本驗接收端 |
| 第二階段 | 另開 repo 開發 Essence Capture，擷取來源、AI 整理與萃取為可讀、可編輯筆記 | 整理成果沿用第一階段約定，按需交接；筆記可獨立讀取，接入後保留舊卡片與學習紀錄 |

階段工作重心與先後順序已確認，沒有承諾第一階段一次實作全部教材形式或全部進階檢核。先細化最小閃卡與檢核情境，再依確認的範圍交付。YouTube → 筆記是輸入的需求例子，首批來源取得、轉錄及模型仍待議；本輪不開發來源轉換器。

第一階段從既有或手動資料開始。一般手寫與其他工具筆記也可使用，YAML 非門檻。接受一份現成筆記／卡片是學習工具的基本入口，與重新取得網頁、影片或辨識附件的來源工具責任分開；筆記可沿用 Obsidian 編輯，不能因 F-003 的候選歸納在輸入而阻止學習端核對已有內容。

## 非 AI 基礎與選用 AI

Cards 的基礎製卡、筆記語法解析、自評、規則與排程不依賴 AI；第一條學習循環先接通基礎功能，再加 AI 增強。具體語法、卡型、演算法及精確 MVP 逐項確認，未承諾一次完成所有功能。

AI 融入製卡、評估與學習任務，底層模型可插拔，provider 與 API 未定。兩 repo 可共用模型介面與解析的開發程式庫，但各自打包，不設第三個必裝 AI 外掛，也不互相形成 runtime 硬依賴。AI 整理／生成完成不等於人工核對或採用。

學習事件與排程由 Cards 管理，避免每次作答改寫來源 YAML。Capture 停止、未安裝或未設定 AI 時，Cards 已選定的基礎學習流程仍可使用。

## 與學習循環的關係

「輸入 → 整理 → 學習 → 回饋」仍是完整學習循環。三模組描述功能責任，兩個工具描述交付邊界，兩階段描述開發順序，三者不要求一對一對應。

來源整理主要落在 M-001；教材製作、呈現與練習主要落在 M-002；檢核與回饋由 M-003 接入，核對後可修訂筆記或材料。同一工作區保留 C-011 的共用知識基礎，跨工具交接的資料與版本關係須明確。

[Mermaid 功能與交付圖](diagrams/functions.md)與[學習、技術、路線圖](diagrams/README.md)互相參照。

## 功能責任對照｜候選映射

F-ID 是討論索引，不要求一個功能對應一個程式模組。分工可跨界，不能從映射推導全部交付範圍：

| 主要責任 | 功能對應 | 邊界與待議事項 |
|---|---|---|
| M-001 輸入／第二階段 | F-001、F-002、F-003 | 來源取得、選段、文件建立；F-003 也涉及既有筆記編輯，學習端沿用宿主及核對修訂能力 |
| M-002 輸出／第一階段 | F-004 至 F-009 | 比較、架構、卡片、題目、互動材料與學習操作；第一階段具體形式逐項選定 |
| M-003 檢核／第一階段 | F-011 至 F-014、F-019；另涉及 F-009 評量 | 錯因、補強、安排、復盤及疑問追蹤；精確檢核對象、操作與深化範圍待議 |
| 基礎與整合約定 | F-010、F-015 至 F-018；必要的基本複習規則 | Essence Cards 的紀錄、存取、版本、保存及可選 AI；跨工具只共用必要約定，不要求共用全部執行服務或內部狀態 |

F-009 的基本操作／自評、F-013 的基本複習規則應供 M-002 使用，不以完整檢核工作區作為翻卡先決。兩邊各自保留人工核對，AI 候選不因未啟用檢核而自動採用。檢核究竟聚焦內容正確性、學習者評量，或提供兩種入口，仍待細化。

## 整合從第一階段設計

[文件交接約定](integration-contract.md)保存語意資訊、更新規則與驗收情境，現為設計草案。初期先約定可讀文件、附件、來源、文件識別與版本；一鍵傳送或 API 依需要增加。

Essence Cards 保有學習端小核心，來源工具有自己的整理與保存責任。接收端透過明確格式／轉接採用內容，不依賴輸入工具內部資料結構。跨工具修訂交接建議與依據版本，由接收端核對；不任意覆寫對方的新修改。共用約定及支援基礎不另算第四個主要模組。

交接採少量平面可選 metadata 的方向，涵蓋格式版本、穩定 ID、來源網址／頁碼／時間點與人工核對狀態；精確欄位、格式及路徑未定。來源修改只提示材料影響，不自動重寫卡片或重設進度；Capture 重新整理須保護人工修改。

必要 ID、版本、事件與索引隨當前交付建立，不先打造全部未來基礎。資料保存、附件、離線事件、併發、同步及 Git 回復依 P0／F-018 驗證；Capture 的具體部署、保存與來源取得方式仍待議。

## 具體驗收情境｜尚未執行

| 情境 | 要驗收的結果 |
|---|---|
| 第一階段只用閃卡 | 未安裝來源工具，仍能建立／編輯既有或手動卡片、複習並保存必要進度 |
| 第一階段複習與檢核 | 直接使用已有材料／紀錄完成已選檢核，核對後修訂，舊事件保留 |
| 第一階段驗交接樣本 | 手動文件與附件能被接收；同文件重複交接與新版不無聲重複或覆寫 |
| 第二階段只轉筆記 | 未安裝 Essence Cards 也能保存 Obsidian 可讀可編輯筆記與來源；AI 整理完成與人工核對分開 |
| 第二階段接入 | 真實整理成果沿用約定製作候選材料，舊卡片／進度保留，不自動加入複習 |
| 工具停止、修訂或升級 | 來源工具停止不影響已有學習材料；版本改變或衝突明示，核對後更新，不清空事件 |

以上是正式功能的設計要求；雙端最小 UI／讀寫原型已依使用者回報通過，完整 P0 與正式功能尚未完成。

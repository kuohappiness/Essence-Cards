## C-001 專案目標｜已確認

使用者曾製作基於間隔重複（spaced repetition）的 Obsidian 閃卡外掛，現希望重構新的軟體，以更有效率、更深入地萃取知識，在有限時間內學習更多內容，並對考試成績有所幫助。

三個設計概念：知識萃取、利用閃卡複習、加強記憶。記憶與考試表現的改善是預期目標，實際成效與驗證方式尚未確定。

理由：使用者明確表達以上目標與設計概念。

## C-002 軟體名稱｜已確認

正式英文名稱為 **Essence Cards**；儲存庫名稱為 `Essence-Cards`。Essence 呼應知識精華，Cards 呼應閃卡複習。

中文名稱暫緩，之後再決定。

理由：使用者已選定英文名稱，並明確要求延後中文命名。

## C-003 討論方式｜已確認

- 每輪聚焦一個核心問題，允許自由延伸，由助理整理需求、取捨與未解問題。
- 使用者需求、助理提案、待驗證假設分開標示；沒有反對不等於已同意。
- 以真實教材驗證抽象需求；研究依據與產品假設分開記錄。
- 階段收尾時檢查遺漏、矛盾及範圍偏移。

狀態標示使用已確認、提案中、待驗證、暫緩、已排除／已取代。

理由：方便逐步取得共識，並在換對話或開始開發時延續工作。

## C-004 記錄與畫板的分工｜已確認

`index.html` 是共同規劃 Essence Cards 的設計討論平台，用來討論如何做出知識學習工具。畫板上的卡片代表討論事項，不是學習閃卡；學習工具本身的功能、架構與操作介面另行討論。

- 討論過程另存為文件，保留想法與決策的演變。
- 畫板分區呈現待釐清點子、目前任務及最新、仍有效的已確認共識；新點子的收錄不等於採用。
- 討論紀錄、歷史提案、已排除選項與過期結論不呈現在畫板上。
- 畫板採固定分區的無限畫板，可縮放、拖曳、點選卡片查看當前細節，並切換文字綱要。
- Markdown 保存內容來源，HTML 與綱要依同一來源生成並保持同步。

理由：使用者希望能回顧討論經過，同時讓畫板集中顯示當下需要掌握的事項。

## C-006 先收集點子，再逐項釐清｜已確認

使用者可隨時提出零散點子，由助理先記錄在看板的待釐清區，保留原意，之後再逐項討論，不必先整理成完整規格。

參考軟體功能蒐集專區屬於設計討論平台的研究資料，初始閃卡參考包括 RemNote 與 Memory Toast。研究後是否採用其中的具體功能，另行討論；專區本身不列為未來學習工具的功能需求。

理由：使用者希望先保存討論中的想法，避免打斷發想，也希望有地方累積同類軟體的參考。

## C-008 共用知識基礎與學習回饋循環｜已確認

摘要：以概念筆記連接來源與學習材料，保存學習紀錄，依不同錯因補強並安排後續複習。

- 保留使用者手繪的「來源輸入 → 整理 → 筆記與比較表、互動教材、試題與閃卡 → 復盤、間隔重複與評分 → 回饋修訂」架構。
- 概念筆記作為共用知識基礎；來源、相關概念、教材、題目與卡片保持關聯。直接匯入真題或卡片後，也可補上概念關聯。
- 作答與評量後保存學習紀錄，支持後續判斷；本次評分、複習排程與主題復盤分工清楚。
- 補強方式依錯因區分：忘記時調整複習、觀念混淆時補充筆記或教材、不會應用時做變式練習、題目有誤時修正題目與解析。
- 回寫先提出可核對的修訂，再更新並保留版本；不把每次答錯一律當成概念筆記有誤。
- 整理拆成內容選取、概念萃取、關係整理與材料製作；依需要選擇處理內容及產出，不要求每份來源都產生所有材料。

理由：使用者提出手繪軟體架構；助理建議補上材料關聯、學習紀錄、分錯因回饋及可控整理，使用者明確表示同意並要求重繪。

確認範圍：以上為架構方向；[重繪藍圖](diagrams/README.md)中的欄位、算法及自動化細節仍待討論。後續多情境介面方向見 C-011；三個主要入口、技術選型與第一版範圍仍待確認。

討論摘要見[手繪架構整合與重繪](discussions/2026-10-06-architecture-redraw.md)。

## C-009 以整體學習循環呈現架構｜已確認

摘要：以「輸入 → 整理 → 學習 → 回饋」為整體學習循環的主軸，取消固定流程數與步驟編號。

來源、概念筆記、比較表、學習材料、練習、學習紀錄、補強修訂與復盤安排已整合在同一架構，後續討論聚焦功能、關聯及使用情境，不再以固定步驟數框定流程。

- 輸入：取得與保存來源資料。
- 整理：理解內容，建立概念筆記、關聯與比較表。
- 學習：依需要使用教材、記憶卡或考題，作答、評量並留下紀錄。
- 回饋：依學習紀錄補強、修訂與安排下一輪學習，可帶回整理或學習。

功能名稱與資料關係保留；可依需要進入、分支與回到相關內容，不要求每次依序走完。這次調整的是呈現方式，具體功能、自動化程度、平台與第一版範圍仍待釐清。

理由：使用者認為早期步驟已整合到整個大流程中，實際活動也不限於原分類，提出取消固定流程數的說法，接著明確要求將「輸入、整理、學習、回饋」加入藍圖作為學習循環。

[目前架構藍圖](diagrams/README.md)取消步驟編號；[本次討論摘要](discussions/2026-10-06-integrated-learning-cycle.md)保存調整脈絡。

## C-011 多情境介面共用概念筆記｜已確認

摘要：以概念筆記為核心建立學習工作區；閱讀、整理理解、記憶練習與回顧依情境呈現不同介面，共用同一份知識來源，確認的修訂可回寫筆記。

- 主題作為使用入口，概念作為共用知識單位；同一概念可被不同主題引用，避免各介面或主題各自維護一份內容。
- 同一工作區依任務呈現原始材料、可編輯筆記、比較表、概念關係、閃卡、題目、互動教材或學習回饋；切換時保留正在處理的概念、來源與位置。
- 使用者可先收集、稍後整理，也可從已確認的部分開始學習；不必先填完所有欄位或每次走完整套循環。
- 操作介面依當下任務顯示需要的內容與操作；學習回饋可直接連到相關概念、來源及下一個補強活動。
- 在不同學習情境產生的概念修訂可回寫共用筆記；依 C-008 保留可核對的修訂與版本。
- 筆記修改後提示可能受影響的題目與教材；涉及內容正確性的衍生修改由使用者確認。

理由：使用者明確同意前一輪「以概念筆記為核心的學習工作區」開發方向，並以多種前端 UI 共用筆記資料來源、修訂可回寫筆記重述理解，要求往此方向開發。

確認範圍：本次確立產品形式與資料共用原則。前端與資料層的分工不預先指定雲端服務；儲存技術、資料欄位、同步方式、具體版面、三個主要入口與第一版功能範圍仍待細化。現有 `index.html` 持續作為設計討論平台。

[本次討論摘要](discussions/2026-10-06-shared-knowledge-workspace.md)記錄使用者確認與助理對回寫邊界的說明。

## C-012 資料保存與同步的候選範圍｜已確認

摘要：主要考慮雲端服務與各裝置本機兩種方案；NAS 保留為使用者可選的自架方式。

- 一般使用者不需擁有 NAS，即可使用產品的主要方案。
- 後續評估以雲端服務及各裝置本機保存為主；本機方案的跨裝置同步機制仍需設計。
- 保留彈性，讓擁有 NAS 的使用者可採用自架保存或同步；具體支援方式與時程尚未決定。
- 本次確認的是候選範圍，尚未選定唯一方案，也未決定第一版是否同時支援兩種主要方案。

理由：使用者指出並非人人都有 NAS，明確要求主要考慮雲端與本機，同時保留 NAS 使用彈性。

[本次討論摘要](discussions/2026-10-06-storage-options.md)記錄候選範圍與尚待細化的同步問題。

## C-013 專案協作的模型與任務分工｜已確認

摘要：架構與重要判斷由使用者選擇的 Astra 極高處理；工作量足夠且範圍明確的執行任務可委派 6.1 Sol；短小的同步操作直接使用工具或腳本。

- 使用者已授權依此規則委派，不必每次重新指定；具體協作規則保存於 [AGENTS.md](../AGENTS.md#模型與任務分工)。
- 使用者選擇 Astra 極高時，由主代理處理需求釐清、架構設計、複雜推理與重要取捨。
- 按已確認結論進行大量文件整理、明確的程式修改及其他可獨立驗收的執行任務，可委派 `gpt-6.1-sol`，依難度指定低至中等推理強度。
- GitHub 提交、推送與重新產生 HTML 等短小操作，直接執行工具或既有腳本；不因工作簡單就另開子代理。
- 主代理提供必要上下文與驗收條件，彙整並檢查關鍵結果；模型不可用時告知限制。
- 此為專案協作政策，不會自動切換對話主模型，也不決定學習工具內部的 AI 選型。

理由：使用者希望合理分配模型工作，並明確同意助理提出的分工。委派有額外交接與回報用量，不保證總 token、費用或訂閱額度一定下降。

[本次討論摘要](discussions/2026-10-06-model-task-allocation.md)保存分工與設定方式的取捨。

## 文件維護與同步方式｜實作紀錄

文件分工：

| 文件 | 用途 | 畫板呈現 |
|---|---|---|
| `docs/consensus.md` | 最新共識與待決事項 | 只取已確認、仍有效的共識 |
| `docs/tasks.md` | 任務、狀態、下一步與暫緩項目 | 只取目前任務 |
| `docs/ideas.md` | 原始點子、待釐清問題與去向 | 只取未結案點子，與共識分區 |
| `docs/references/software.md` | 參考產品、來源與研究筆記 | 參考軟體專區 |
| `docs/discussions/` | 有日期的討論摘要與重要取捨 | 不呈現 |

每輪重要討論先留下日期、主題、使用者想法、助理提案、取捨理由與結果；有結論或狀態改變時，另外更新共識與任務。

流程：更新 Markdown → 執行 `python3 scripts/build_board.py` → 檢查內容與版本一致 → 提交。`index.html` 與綱要由相同資料生成，不分別編輯。

已建立單檔 HTML 畫板、產生程式與 GitHub Actions 同步／發布工作流程。GitHub Pages 的首次啟用與線上發布仍待確認，進度以任務文件為準。

手機檔案預覽相容性：`index.html` 直接包含目前內容全文與版本日期，互動程式成功啟動後再切換為互動看板；另產生不含腳本、隱藏區塊或互動切換的 `mobile.html` 手機閱讀版，沿用相同 Markdown 來源與內容篩選。討論歷史與已排除內容仍不嵌入 HTML。一般瀏覽器檢查不等同於 ChatGPT 手機檔案預覽的實機驗證；使用者回報仍空白，後續確認由 T-007 追蹤。

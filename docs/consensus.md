## C-001 專案目標｜已確認

使用者曾製作基於間隔重複（spaced repetition）的 Obsidian 閃卡外掛，現希望重構新的軟體，以更有效率、更深入地萃取知識，在有限時間內學習更多內容，並對考試成績有所幫助。

三個設計概念：知識萃取、利用閃卡複習、加強記憶。記憶與考試表現的改善是預期目標，實際成效與驗證方式尚未確定。

理由：使用者明確表達以上目標與設計概念。

中文名稱暫緩，之後再決定。

## C-003 討論方式｜已確認

- 每輪聚焦一個核心問題，允許自由延伸，由助理整理需求、取捨與未解問題。
- 使用者需求、助理提案、待驗證假設分開標示；沒有反對不等於已同意。
- 以真實教材驗證抽象需求；研究依據與產品假設分開記錄。
- 階段收尾時檢查遺漏、矛盾及範圍偏移。

狀態標示使用已確認、提案中、待驗證、暫緩、已排除／已取代。

理由：方便逐步取得共識，並在換對話或開始開發時延續工作。

## C-004 記錄與畫板的分工｜已確認

`index.html` 是共同規劃 Essence Cards 的設計討論平台，用來討論如何做出知識學習工具。畫板上的卡片代表討論事項，不是學習閃卡；學習工具本身的功能、架構與操作介面另行討論。

- 討論過程另存為文件，保留想法與決策的演變。
- 畫板分區呈現待釐清點子、目前任務及最新、仍有效的已確認共識；新點子的收錄不等於採用。
- 討論紀錄、歷史提案、已排除選項與過期結論不呈現在畫板上。
- 畫板採固定分區的無限畫板，可縮放、拖曳、點選卡片查看當前細節，並切換文字綱要。
- Markdown 保存內容來源，HTML 與綱要依同一來源生成並保持同步。

理由：使用者希望能回顧討論經過，同時讓畫板集中顯示當下需要掌握的事項。

## C-008 共用知識基礎與學習回饋循環｜已確認

摘要：以概念筆記連接來源與學習材料，保存學習紀錄，依不同錯因補強並安排後續複習。

- 保留使用者手繪的「來源輸入 → 整理 → 筆記與比較表、互動教材、試題與閃卡 → 復盤、間隔重複與評分 → 回饋修訂」架構。
- 概念筆記作為共用知識基礎；來源、相關概念、教材、題目與卡片保持關聯。直接匯入真題或卡片後，也可補上概念關聯。
- 作答與評量後保存學習紀錄，支持後續判斷；本次評分、複習排程與主題復盤分工清楚。
- 補強方式依錯因區分：忘記時調整複習、觀念混淆時補充筆記或教材、不會應用時做變式練習、題目有誤時修正題目與解析。
- 回寫先提出可核對的修訂，再更新並保留版本；不把每次答錯一律當成概念筆記有誤。
- 整理拆成內容選取、概念萃取、關係整理與材料製作；依需要選擇處理內容及產出，不要求每份來源都產生所有材料。

理由：使用者提出手繪軟體架構；助理建議補上材料關聯、學習紀錄、分錯因回饋及可控整理，使用者明確表示同意並要求重繪。

確認範圍：以上為架構方向；[重繪藍圖](diagrams/README.md)中的欄位、算法及自動化細節仍待討論。後續多情境介面方向見 C-011；各情境的具體入口與第一版範圍仍待確認；三模組與獨立使用方向見 C-020；平台方向見 C-014。

## C-009 以整體學習循環呈現架構｜已確認

摘要：以「輸入 → 整理 → 學習 → 回饋」為整體學習循環的主軸，取消固定流程數與步驟編號。

來源、概念筆記、比較表、學習材料、練習、學習紀錄、補強修訂與復盤安排已整合在同一架構，後續討論聚焦功能、關聯及使用情境，不再以固定步驟數框定流程。

- 輸入：取得與保存來源資料。
- 整理：理解內容，建立概念筆記、關聯與比較表。
- 學習：依需要使用教材、記憶卡或考題，作答、評量並留下紀錄。
- 回饋：依學習紀錄補強、修訂與安排下一輪學習，可帶回整理或學習。

功能名稱與資料關係保留；可依需要進入、分支與回到相關內容，不要求每次依序走完。這次調整的是呈現方式，具體功能、自動化程度、平台與第一版範圍仍待釐清。

理由：使用者認為早期步驟已整合到整個大流程中，實際活動也不限於原分類，提出取消固定流程數的說法，接著明確要求將「輸入、整理、學習、回饋」加入藍圖作為學習循環。

[目前架構藍圖](diagrams/README.md)取消步驟編號；[本次討論摘要](discussions/2026-10-06-integrated-learning-cycle.md)保存調整脈絡。

## C-011 多情境介面共用概念筆記｜已確認

摘要：以概念筆記為核心建立學習工作區；閱讀、整理理解、記憶練習與回顧依情境呈現不同介面，共用同一份知識來源，確認的修訂可回寫筆記。

- 主題作為使用入口，概念作為共用知識單位；同一概念可被不同主題引用，避免各介面或主題各自維護一份內容。
- 同一工作區依任務呈現原始材料、可編輯筆記、比較表、概念關係、閃卡、題目、互動教材或學習回饋；切換時保留正在處理的概念、來源與位置。
- 使用者可先收集、稍後整理，也可從已確認的部分開始學習；不必先填完所有欄位或每次走完整套循環。
- 操作介面依當下任務顯示需要的內容與操作；學習回饋可直接連到相關概念、來源及下一個補強活動。
- 在不同學習情境產生的概念修訂可回寫共用筆記；依 C-008 保留可核對的修訂與版本。
- 筆記修改後提示可能受影響的題目與教材；涉及內容正確性的衍生修改由使用者確認。

理由：使用者明確同意前一輪「以概念筆記為核心的學習工作區」開發方向，並以多種前端 UI 共用筆記資料來源、修訂可回寫筆記重述理解，要求往此方向開發。

確認範圍：本次確立產品形式與資料共用原則。前端與資料層的分工不預先指定雲端服務；儲存技術、資料欄位、同步方式、具體版面、各情境的具體入口與第一版功能範圍仍待細化；三模組方向見 C-020。現有 `index.html` 持續作為設計討論平台。

## C-013 專案協作的模型與任務分工｜已確認

摘要：架構與重要判斷由使用者選擇的 Astra 極高處理；工作量足夠且範圍明確的執行任務可委派 6.1 Sol；短小的同步操作直接使用工具或腳本。

- 使用者已授權依此規則委派，不必每次重新指定；具體協作規則保存於 [AGENTS.md](../AGENTS.md#模型與任務分工)。
- 使用者選擇 Astra 極高時，由主代理處理需求釐清、架構設計、複雜推理與重要取捨。
- 按已確認結論進行大量文件整理、明確的程式修改及其他可獨立驗收的執行任務，可委派 `gpt-6.1-sol`，依難度指定低至中等推理強度。
- GitHub 提交、推送與重新產生 HTML 等短小操作，直接執行工具或既有腳本；不因工作簡單就另開子代理。
- 主代理提供必要上下文與驗收條件，彙整並檢查關鍵結果；模型不可用時告知限制。

理由：使用者希望合理分配模型工作，並明確同意助理提出的分工。委派有額外交接與回報用量，不保證總 token、費用或訂閱額度一定下降。

- 新增 [F-019 學習疑問與待處理佇列](functions/issue-queue.md)：手機提出問題，電腦核對、處理與結案；區分學習者需要補強與內容可能有誤，一般忘記不必送去修題。
- 收藏不自動建立學習任務，材料候選先核對再採用；採用、啟用／暫停及待核對分開討論。
- F-009／F-010／F-013 共同設計作答、事件及排程，區分獨立答對、提示後答對與看過答案；核對誤題後保留原事件，統計與排程規則待定。
- F-013 明列新卡上限、積欠處理、時間預算及同源題錯開等討論項目，具體算法、門檻及估時仍待確認。
- F-018 分別討論跨裝置同步、可讀匯出、完整備份及個別回復，各自列出驗收情境。
- 各功能紀錄補上研究對應與採用理由、最小人工操作方式及具體驗收情境；先接通來源、材料、作答、疑問與修訂的使用情境，再深化功能。AI 接入人工流程另行設計。

理由：使用者要求依新研究評估功能目錄，並明確表示「好，照你的意思修改」，同意助理提出的六項調整、討論順序及紀錄骨架補強。

確認範圍：確認上述功能方向與討論安排；來源格式、欄位、狀態名稱、操作細節、算法、驗收門檻及第一版正式範圍仍未定案。沒有將研究的所有 A／U 候選全數採用，也沒有完成產品實作或真實裝置驗證。P0 與 Git 設計繼續保留。

[功能目錄](function-discussions.md)、[研究統整](references/design-opportunities.md)與[本次討論摘要](discussions/2026-10-07-function-catalog-refinement.md)保存詳細內容。

## C-018 自訂教材介面與可丟棄的最小驗證｜已確認

摘要：教材介面需要能自由呈現心智圖、閃卡與多媒體；在深入功能討論前，先以極簡原型檢查桌面與 iPhone 是否能執行，測試架構可完全推翻重做。

- 使用者希望將 Obsidian 作為資料層、外掛作為自訂 UI；這是需求方向，不能推導為完全不受宿主與手機環境限制。
- 優先以最低必要實作驗證跨裝置基本能力，不將原型升格為正式產品、schema 或框架承諾。
- 原型 0.0.1 已建立；2026-10-07 使用者回報手機與電腦測試全部正常，依原型驗收範圍記為 Windows／iPhone 最小實機驗證通過，T-011 結案並恢復 T-010 功能討論。
- 原型可丟棄，原 P0 的離線事件、併發、附件與 Git 回復門檻仍保留。

理由：使用者明確提出必要介面能力，要求在繼續討論前先做盡量節省 token 的最小雙端測試，並允許完全重構。

## C-019 架構圖互相參照與持續維護｜已確認

- 設計方向、功能或驗證結果變動時，更新文字來源並核對所有受影響圖，再重新產生及同步桌面／手機看板。新圖納入同一來源登錄與檢查流程。

## C-020 三個主要模組與獨立使用｜已確認

摘要：主要模組為輸入、輸出、檢核；輸入與輸出可獨立完成使用目的，共用小核心並逐步交付及整合。

- M-001 輸入：來源取得、整理與筆記保存；可以單純把 YouTube 整理成筆記，不要求繼續製卡或進入檢核。
- M-002 輸出：學習材料的製作、呈現及使用，包含教材、心智圖與閃卡等方向；可以直接複習既有或手動卡片，不需要先完成輸入，也不必啟用完整檢核工作區。
- M-003 檢核：提供檢查與回饋；具體檢核對象及操作仍待細化，不讓三模組變成強制單一路徑。
- 共用識別／資料／版本／保存等必要基礎，不另列第四個主要模組。輸入的交付邊界後續依 C-022 調整為獨立來源工具；「全部放在同一外掛」的包裝方案已取代。
- 每完成一個可用單位即整合，先釐清最小可用閃卡；依 C-022 第一階段聚焦輸出與檢核，第二階段再開發獨立輸入。接入時保留舊資料與既有模式，卡型、算法與精確範圍未定。
- 學習循環「輸入 → 整理 → 學習 → 回饋」繼續作為學習視角；三模組作為產品與開發邊界，兩者互相參照。

理由：使用者明確同意模組化規劃，並指定三個主要模組，以及只複習閃卡、只把 YouTube 轉筆記兩個獨立情境。

確認範圍：確認模組方向與獨立使用要求；F-ID 的模組歸納、跨模組服務、檢核對象、YouTube 取得／整理方式及資料格式仍是助理提案或待議事項。沒有宣稱正式模組已完成，也沒有取消完整 P0。

[三模組架構與交付](module-architecture.md)、[功能圖與候選映射](diagrams/functions.md)、[討論摘要](discussions/2026-10-07-three-modules.md)。

## C-021 開發協作與跨模組品質目標｜已確認

摘要：助理可主動提出不同建議；程式碼盡量簡潔，手機與電腦都能流暢使用，集中保存為跨模組的開發原則與品質目標。

- 使用者可隨時提出開發期待，保留原意，不要求先整理成完整規格。
- 助理發現更佳方案或重要取捨時主動說明；新建議仍與已確認結論分開。
- 程式碼盡量簡潔，作為輸入、輸出、檢核及共用核心的品質目標。
- 手機與電腦各自支援的使用情境都應流暢；具體效能門檻、測試資料規模與實作作法尚待釐清。
- [開發原則與品質目標](development-principles.md)集中保存原意、助理提案與待釐清問題；此共識摘要在看板呈現，討論歷史另存。

理由：使用者明確要求助理可主動提出不同建議，並要求記下程式碼簡潔及跨裝置流暢的期待。

確認範圍：確認協作方式、品質目標與保存需求，不表示具體精簡方法已採用或正式功能效能已通過。下一步由 T-012 與各模組交付一起細化。[討論摘要](discussions/2026-10-07-development-principles.md)保存本輪脈絡。

## C-022 輸入獨立與兩階段交付｜已確認

摘要：來源輸入獨立為工具，第一階段先完成 Essence Cards 的輸出與檢核，第二階段再開發輸入；第一階段就保留兩邊的整合邊界。

- 功能責任仍為輸入、輸出、檢核；交付單位分為獨立來源整理工具，以及承載輸出／檢核的 Essence Cards。取代 C-020 把三模組全部放在同一外掛的包裝方案。
- 第一階段專注輸出與檢核，使用既有筆記、材料與手動／既有卡片，不以來源取得或 AI 轉錄為先決。各教材形式、卡型、檢核對象及深化範圍仍逐項選定。
- 第二階段再開發來源整理工具，能單純將 YouTube 等來源整理為可讀文件，也能按需交給 Essence Cards。宿主、介面、來源取得與模型尚未選定。
- 第一階段即細化文件、來源、附件、識別與版本交接，使用手動樣本驗接收端；輸入完成後沿用約定，不要求兩邊同時執行或共用所有內部狀態。
- 交接、更新與跨工具修訂保留核對，加入來源工具後舊卡片、進度及事件仍保留。獨立使用要求、C-011 共用知識基礎與完整 P0 保持有效。

理由：使用者明確表示將輸入獨立，先專注輸出與檢核，第二階段再做輸入，並要求兩邊能彼此整合。

確認範圍：工具拆分、階段先後與整合要求已確認；[文件交接草案](integration-contract.md)的欄位、API、格式與實作仍待議。本輪更新的是正式規劃，不表示正式模組或整合程式已完成。

[三模組與兩階段交付](module-architecture.md)、[整合約定](integration-contract.md)、[討論摘要](discussions/2026-10-07-two-stage-delivery.md)。

# Essence Cards｜維修與查修的準備

狀態：💬 討論中（2026-10-29 開始）：盤點完成，第一題（G1 正式版要不要記下錯誤）等使用者

[v1 任務入口](../backlog.md#v1-需要做的任務)｜[文件存放規則](README.md)

使用者 2026-10-29 在專案討論串「讓未來維修查錯更有效率」提出：產品做好、之後要維修時，專業工程師通常怎麼處理？現在能先準備什麼，讓將來查修更有效率？使用者猜的例子是把每個程式功能模組化。

**先講結論**：模組化已經做了（[D-110](../decisions.md#d-110-v1-外掛的程式結構) 的四個核心模組，邊界由 ESLint 擋，[D-117](../decisions.md#d-117-技術債預防機械檢查全自動ai-審查只在關鍵點)）。版本、重現、回歸測試、退回，大多已經有決定，或在進行中的[更新防線](../../tasks/update-safeguards.md)裡（下表標「更新防線」的是定案、還在做）。真正缺的是第一步：**正式版遇到錯誤時沒有留下證據**，在 iPhone 上尤其看不到。

## 1. 專業的維修分成幾步，Essence 已有什麼

| 步驟 | 專業團隊常見的做法 | Essence 已有 | 還缺 |
|---|---|---|---|
| ① 知道出了問題 | 錯誤自動留下紀錄或回報；使用者有固定的回報管道 | 開 session 時 CI 沒通過就提醒（`.claude/hooks/ci-status.mjs`）；正式版讀不到或寫不進去時提示一次（`src/main.ts` 的 `NOTICES`）；讀不懂的卡組或紀錄停下來並提示家長（[D-149](../decisions.md#d-149-更新與相容版本紀錄讀取閘門與正式安裝) 第 3 點，更新防線第二部分）；開發版的 `errors` 命令收集錯誤（`src/obsidian/dev.ts` 的 `collectErrors`） | **G1**：正式版的其他錯誤（例如卡片顯示不出來、離開筆記時補 ID 失敗）只寫到 Obsidian 的主控台；iPhone 上沒有人看得到，重開就不見。開發版不能裝到正式使用的 vault（D-149 第 4 點），所以真正使用時拿不到這份證據 |
| ② 知道是哪一版、什麼環境 | 每次發布有版本號與更新說明；錯誤附上版本與裝置 | `BUILD` 是版本加 commit，有「版本」命令；每台裝置在紀錄記版本行（D-149 第 2 點，更新防線第二部分）；正式版打 tag，保留每一份產物與雜湊（D-149 第 4 點） | 錯誤沒有和版本一起留下（併進 G1） |
| ③ 在自己的電腦重現 | 拿到使用者的資料或步驟，在開發環境重現、縮到最小 | 核心不碰 Obsidian，在 Node 直接跑（D-110）；`code-quality` 的[除錯做法](../../.claude/skills/code-quality/debug.md)第 1 步「先有能重現的指令」；備份 zip 是完整的資料快照（[D-150](../decisions.md#d-150-備份與還原) 第 5 點）；[發布前比較](../../tasks/update-safeguards.md#1-3-發布前比較d-149-第-5-點)讀備份，算出每個目標的到期時間與今天的份（兩者都在更新防線第一部分，還在分支上等查核） | **G3**：「結果不對、但沒有錯誤」的回報（例如這張為什麼今天又出現），每次要臨時寫小程式查 |
| ④ 修好且不再犯 | 先寫會失敗的測試再修；自動檢查；事後檢討 | 除錯做法的回歸測試；`npm run check`、pre-commit、CI；高風險範圍做 L2；里程碑跑 retro，犯過的錯寫成檢查（D-117） | 沒有缺 |
| ⑤ 修壞了能退回 | 退回上一版；資料備份 | 保留每一份正式產物，退回時重裝（D-149 第 4 點）；備份與逐檔還原（D-150）；紀錄只追加、不改寫 | 沒有缺 |
| ⑥ 回報的管道 | 回報表單，固定要附的資訊 | 使用者在對話裡描述；「版本」命令 | **G2**：沒有固定要給的線索；學生遇到時多半說不出哪張卡、幾點 |

## 2. 缺口與建議

每一項都和「不做」比較（[D-153](../decisions.md#d-153-每個新決定與新任務先和不做比較)）。

### G1 正式版把錯誤記下來 💡 建議做

**做法**（細節待 Codex 討論）：每台裝置一份小的錯誤紀錄，存在 vault 裡，跟著 iCloud 回到電腦，維護的 AI 在電腦上就讀得到 iPhone 的錯誤。這和開發版的結果檔是同一條路：[W6 的 iPhone 測試](../../tasks/w6-iphone.md)就是外掛把量測寫成檔案、經 iCloud 傳回電腦，使用者不用抄任何數字。

- 只記錯誤：時間、`BUILD`、裝置碼、哪個環節（讀、寫、畫卡、補 ID……）、錯誤訊息；有上限（例如最近 200 筆），不會一直長大。
- 錯誤紀錄自己寫不進去時什麼都不做：不擋複習、不再報錯，不會因為記錯誤又產生錯誤。
- 不上傳到任何地方。紀錄可能寫到筆記的路徑或卡片的字，所以和卡組一樣只留在家裡的 vault；維護的 AI 在本機讀，不放進 repo（[D-003](../decisions.md#d-003-公開範圍)）。
- 放在哪個資料夾、檔名、一行的欄位、上限怎麼算，屬於寫進使用者 vault 的格式（[D-140](../decisions.md#d-140-fable-規劃opus-執行codex-查核) 第 2 點）：使用者同意方向後，寫成討論稿請 Codex 站在「不做」那一方反駁，雙方一致再請使用者確認。
- iPhone 寫的檔，在電腦上可能只是 iCloud 的雲端佔位檔，和複習紀錄同一個問題，照 [iCloud 佔位檔的討論稿](<../../Claude Codex Discussion/2026-10-29-icloud-placeholders.md>)的結論處理。

**和不做比較**：

1. **不做會怎樣**：學生真正使用後，在 iPhone 遇到錯誤時沒有任何紀錄。AI 只能猜，先在測試 vault 重現，再請使用者到 iPhone 重測（W6 的 iPhone 測試一輪約 20 分鐘，還要湊同一天）。只在真實資料才出現的錯，例如家長寫的特殊卡組、累積三年的紀錄，測試 vault 重現不了。多常發生還不知道，正式版還沒在正式使用的 vault 跑過；開發期間，W6 審查時 Windows 的五輪實測，每一輪都用開發版的 `errors` 確認沒有錯誤（[W6 審查請求](../../tasks/w6-review.md)），可見這份證據每次都用得到。
2. **做的代價**：把開發版約 10 行的 `collectErrors` 搬到正式版，加一個有上限的寫入；格式寫進 syntax.md；測試（寫不進去不影響複習、上限、不遞迴）。之後幾乎不用維護；每台裝置多一個小檔。
3. **更小的做法**：
   - 只記在記憶體，用命令才顯示：重開就沒了，iPhone 切到背景常被系統關掉，學生也不會在出錯的當下想到去執行命令。
   - 等第一次出問題再做：第一次的問題就沒有證據，而那一次通常最需要證據。

**時機**：學生開始每天使用之前（真實使用驗證之前）。不放進進行中的更新防線，避免它的範圍再變大。

### G2 問題報告：回報時固定給哪些線索

**做法**：一個命令「複製問題報告」，把版本、裝置、Obsidian 版本、平台、讀不到的檔案數、最近幾筆錯誤複製到剪貼簿，貼到和 Claude 的對話；說明書寫一節「遇到問題時怎麼回報」（[D-048](../decisions.md#d-048-使用說明書)）。

1. **不做會怎樣**：v1 只有自己一家，維護的 AI 在家裡的電腦就能直接讀 vault 和 G1 的紀錄，多半用不到；學生說不清楚時，AI 可以從紀錄找出時間點。第二階段給其他家庭用時，AI 讀不到他們的 vault，才真的需要。
2. **做的代價**：一個命令、說明書一節。
3. **更小的做法**：v1 只在說明書寫回報時說四件事：哪台裝置、大約幾點、哪一科哪張卡、畫面上看到什麼（能截圖就截）；版本用已有的「版本」命令。

💡 **建議**：v1 只寫說明書那一節，寫說明書時一起做；命令移到第二階段，和「學生回報這張有問題」（[複習體驗](experience.md#複習體驗)）一起設計。

### G3 查某個學習目標的排程：維護用的小工具

**做法**：一個 Node 工具，給一份備份和學習目標 ID，列出它的題目、每一筆紀錄、每次作答後的記憶狀態與到期日、今天排第幾。

1. **不做會怎樣**：每次有人問「這張為什麼今天又出現」「怎麼不見了」，AI 要臨時寫一次小程式，多花一些 token；發布前比較已經會讀備份、算到期日，臨時程式可以照著寫。
2. **做的代價**：一支工具和它的測試，排程的介面改了也要跟著改。
3. **更小的做法**：第一次真的需要時才寫，寫完留在 `tools/` 當工具，不當拋棄式程式刪掉。

💡 **建議**：現在不做，照第 3 點。觸發點：第一次有人回報排程或題目不對。

## 3. 專業團隊會做、這裡不建議做的

- **再細的模組化**：四個核心模組與邊界檢查已經有了；`state/index.ts` 的拆檔已在[技術債表](../backlog.md#技術債)，到觸發點再拆。現在多拆只會多出要維護的介面。
- **自動把錯誤上傳到伺服器**（當機回報服務）：會把未成年學生的使用資料送出這台裝置，還要架伺服器或註冊服務，和 D-003 不放私人學習資料、D-150「外掛不會上傳」的立場都不合。只有一家在用時，G1 的檔案就夠。
- **功能開關**（不發新版就能關掉某個功能）：適合使用者很多、天天發布的產品。這裡由 AI 做正式安裝、保留每一份產物，出問題就退回重裝（D-149 第 4 點）。
- **詳細的操作紀錄**（每按一個按鈕都記）：每次作答已經記在複習紀錄，排程的問題靠它就能重算；多記操作會讓檔案變大、iCloud 多傳，也多記孩子的使用細節。只記錯誤。
- **另開問題追蹤系統**（例如 GitHub Issues）：使用者會碰到的流程不能要求 Git；backlog 的技術債表已經是問題清單。

## 4. 已經有、對維修特別有利的設計

給之後接手的 AI 與說明書的附錄參考，不用另外做。

- **排程每次從全部紀錄重算**（[D-035](../decisions.md#d-035-複習紀錄格式)、D-110）：排程的錯修好之後，每張卡的到期日自動改正，不用搬資料、不用修紀錄。
- **紀錄只追加**：程式的錯不會改掉過去的作答。
- **寫回筆記都是「舊文字 → 新文字」的函式**（D-110）：每一種可能寫壞的情況都能用例子測。
- **決定、格式與任務都寫在 repo**（[D-141](../decisions.md#d-141-文件架構入口只放狀態同一類資訊只維護一份)）：下一個接手的 AI 不靠聊天紀錄或記憶。

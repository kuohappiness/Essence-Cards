# Essence Cards｜舊外掛分析：AI-Enriched Flashcards

更新：2026-10-10｜分析對象：[GollyKuo/Obsidian-Flash-Card](https://github.com/GollyKuo/Obsidian-Flash-Card) v0.1.30（MIT，作者為使用者本人）

狀態：💡 助理分析。文中的「建議」都是待討論的提案，不是決定。

> 這份報告是[v1 開發前要做的事](../roadmap.md#v1-開發前要做的事)中「出題語法定稿」的前置工作：使用者提供舊外掛的完整 repo，助理檢視可以參考的地方（[D-030](../decisions.md#d-030-出題語法規範)）。

## 一句話結論

舊外掛的**工程底子很扎實**：解析、同步、儲存都有測試，ID 與寫入的做法可以直接沿用。它的主要問題是**產品結構**：卡片直接寫在一般筆記裡，所以約三分之一的程式花在「讓筆記裡的卡片好看、隱藏 ID」，複習體驗只佔約 4%。卡片寫在任何筆記裡，也造成誤判與進度遺失。Essence Cards 已經做的幾個決定，例如卡組獨立存放（D-025）、只往後追加的複習紀錄（D-035），剛好都能避開這些問題。

## 2. 功能盤點

| 類別 | 做了什麼 |
|---|---|
| 語法 | 5 種卡：`問題 :: 答案`（正向）、`說明 ;; 概念`（反向）、`單字 ::: 翻譯`（雙向）、`==填空==`、`問題 ::` 加縮排的多行答案；另有內嵌包裹 `{{fc 正面 :: 背面 /fc}}`，用在段落中間 |

| 設定與維護 | 分頁式設定、高亮配色、AI 預留欄位；一鍵移除整個 vault 的 `^fc-` ID |
| 開發流程 | Instruction、RoadMap、dev_log、Retrospective、SKILL 五份規範；測試分快慢兩層、git hooks、一鍵發版、文件編碼檢查 |

## 3. 力氣花在哪裡

| 模組 | 程式行數 | 佔比 | 內容 |
|---|---|---|---|
| 編輯器呈現（editor、styles、高亮相關設定） | 約 1,800 | 約 35% | 高亮、隱藏語法與 ID、點擊顯示 |
| 儲存（store） | 1,128 | 22% | 分片儲存、索引、遷移、存檔佇列 |
| 解析（parser） | 472 | 9% | 5 種語法與內嵌包裹 |
| 同步（sync） | 397 | 8% | 檔案事件、同步狀態 |
| ID（blockid） | 356 | 7% | 補 ID、清除 ID |
| **複習（review、ui）** | **226** | **約 4%** | FSRS 包裝 61 行、複習視窗 165 行 |
| 其他（app、main、設定其餘部分） | 約 680 | 約 13% | 指令、設定頁 |

Retrospective 記錄的 4 個除錯案例中，3 個與編輯器呈現或 CSS 隔離有關（高亮失效、選擇器被錯誤加上前綴、內嵌語法與裝飾排序錯誤），1 個是文件編碼損壞。

**判讀**：把卡片寫在一般筆記裡，就必須處理「筆記要能閱讀，又要藏住語法和 ID」，這部分吃掉了最多的開發時間。學習閉環本身，包括佇列、每日上限、統計、中斷接續，反而還沒開始做。這也是 Essence Cards 把卡組獨立出來（D-025）的價值：大部分呈現問題直接消失，力氣可以放在複習體驗。

## 5. 發現的問題

### 5-1 一般筆記裡的內容被誤判成卡片

解析器套用到整個 vault 的每一行，而且沒有排除程式碼區塊。我用相同的規則測試了四種常見內容：

| 內容 | 被判成 |
|---|---|
| 程式碼區塊裡的 `auto v = std::vector<int>();` | 正向卡 |
| Dataview 的欄位 `status:: 進行中` | 正向卡 |
| 用螢光筆標重點 `這段我用 ==螢光筆== 標重點` | 填空卡 |
| 程式碼 `for (i = 0;; i++) {}` | 反向卡 |

游標離開這些行時，外掛會在行尾加上 `^fc-` ID，等於修改了使用者的筆記。使用手冊寫「程式碼區塊內不解析」，但這只適用於內嵌包裹語法；解析器本身沒有實作排除。

→ **Essence Cards**：卡片只寫在 `Essence Cards/` 裡的卡組筆記（D-025、D-041），來源筆記完全不碰，這類誤判不會發生。卡組筆記的解析仍要排除程式碼區塊。

### 5-2 刪改或搬動卡片可能讓進度歸零

同步時，筆記裡找不到某個 ID，就把那張卡的資料連同 FSRS 進度一起刪掉。因此：

- **改卡改到一半**：Obsidian 在停止輸入後不久就自動存檔，若當下那一行暫時不符合語法（例如正在改 `::`），卡片就被刪除；改好後同一個 ID 會以新卡重新建立，進度歸零。
- **把卡從 A 筆記剪下、貼到 B 筆記**：A 先同步，卡片被刪；B 再同步，以新卡建立。

→ **Essence Cards**：複習紀錄只往後追加、跟卡組分開存（D-035）。卡片暫時消失不會刪除紀錄，同一個 ID 回來時進度就接得上。

### 5-3 只存「目前狀態」，沒有複習歷史

每張卡只存最新的 FSRS 數值，過去每次作答的紀錄沒有保留。所以無法：

- 計算記憶保持率（成功標準要用）
- 換一種排程演算法重算（D-012）
- 看出哪些卡常錯

→ **Essence Cards**：D-035 的紀錄格式保留每一次作答，排程狀態隨時可以重算。

### 5-4 每次作答都改寫同一個卡片檔，跨裝置可能互相覆蓋

每按一次評分，就立即改寫那張卡的 JSON 檔。電腦和 iPhone 若在同步完成前都複習了同一張卡，iCloud 只會留下其中一邊。卡片數量多時，`Cards/` 會有上千個檔，清單檔 `data.json` 也會被兩端同時修改。

→ **Essence Cards**：每台裝置只寫自己的紀錄檔（D-035），不會互相覆蓋。

### 5-5 反向卡、雙向卡在複習時沒有差別

複習視窗對所有非填空卡都是「顯示正面 → 翻出背面」：

- `;;` 只是換一種寫法，實際行為和 `::` 相同。
- `:::` 只產生一張卡，沒有反方向。
- 一行有多個 `==填空==` 時，所有空格一次全挖，不是一個空格一張卡。

→ **Essence Cards**：方向不同就是不同的學習目標，各自排程（D-010、[架構 §2](../architecture.md#2-概念模型-第-4-步)），這個模型本來就能表達雙向。

### 5-6 新卡立刻到期、沒有上限

新卡建立時就到期，複習視窗會列出所有到期卡。一次貼上 100 張卡，當天就要複習 100 張新卡。

→ **Essence Cards**：v1 已定每日上限與優先順序（D-026、D-039）；新卡每天加入的數量也要有上限，納入「複習與檢核細節」的佇列組成討論。

### 5-7 複習畫面不渲染 Markdown

卡片內容以純文字顯示：粗體、連結會顯示原始符號，圖片和公式不會出現。

→ **Essence Cards**：自然科需要圖與公式，複習畫面要用 Obsidian 的 Markdown 渲染。

### 5-8 沒有 ID 的卡不會被收錄

卡片要等游標離開那一行、補上 ID 之後才會被收錄。一次貼上很多卡，例如 AI 的輸出，必須逐行點過才會全部生效。

→ **Essence Cards**：AI 製卡由外掛存草稿時就配好 ID（D-042）；家長手寫的卡也要有「整篇一次補 ID」的機制。

### 5-9 手機相容與金鑰存放

- 點擊顯示用的是 `mousedown`，複習視窗固定 540 px 寬，手機版的適配排在 v0.2，還沒開始。
- Gemini API 金鑰存在外掛設定檔，會跟著 vault 經 iCloud 同步。

→ **Essence Cards**：iPhone 是主要的複習裝置，複習介面要以手機為優先設計；API 金鑰只存在電腦本機（D-039）。

### 5-10 文件與流程比程式還重

約 5,000 行程式，配上約 70 KB 的五份規範文件。4 天內約發了 25 個版本，連只改文件也要升版、寫 dev_log；RoadMap 同時有 Sprint A～G、V0.2～V0.5 兩套編號。這和 Essence Cards 在 D-014 重整文件時遇到的情況類似。

### 5-11 小細節

- 到期日以 UTC 日期分組，台灣時間早上 8 點才換日。目前只影響內部分組，不影響「是否到期」的判斷；之後做每日上限與統計時，要改用本地時間換日。

## 8. 建議討論的調整 💡

### 8-1 排程直接採用 FSRS（ts-fsrs）

- **理由**：使用者用過、程式庫成熟、可離線、MIT 授權。D-035 的紀錄保留每一次作答，FSRS 的狀態可以從紀錄重播算出，也保留將來替換演算法的彈性（D-012）。
- **影響**：「寫程式前參考舊外掛決定排程演算法」這一項可以結案。

### 8-2 語法沿用使用者熟悉的寫法，但只在卡組筆記裡生效

一個可能的方向，作為語法定稿的討論起點：

```
---
年級學期: 國二上
科目: 自然
單元: 2-1 質量與密度的測量
狀態: 啟用
---

## 能說明質量與重量的不同
出處：2-1 p.45
- 質量和重量有什麼不同？ ::
    質量是物體所含物質的多少，不隨地點改變；重量是物體受到的重力。
- 同一個人到月球上，質量和重量會怎麼變？ :: 質量不變，重量變小

## 密度的計算
- 密度 = ==質量== ÷ ==體積==

borrow :: 借入
lend :: 借出
```

- `問題 :: 答案`、`問題 ::` 加縮排多行、`==填空==`：沿用舊外掛的寫法。
- 一個標題代表一個學習目標，底下每一行卡是題目池裡的一題，第一題是基本題（D-028）。
- 不在標題底下的單行卡，每一行自動成為一個學習目標，對應最簡單的寫法（D-013）。
- ID 的位置與寫法待定。
- **待解的問題**：
  - 家長可能也用標題來分組（例如「## 動詞」），要怎麼區分「學習目標標題」和「分組標題」？
  - 一行多個填空，要一個空格一張卡，還是一次全挖？

### 8-3 不沿用 `;;`、`:::`、`{{fc}}`

- `;;` 的行為和 `::` 一樣，只多一個要記的符號。
- `:::` 在舊外掛沒有真正做出雙向。在 Essence Cards 裡，雙向可以改成「一次建立兩個方向的學習目標」，例如英→中、中→英各自排程。
- `{{fc}}` 是為了在段落中間做卡，卡組筆記裡不需要。

### 8-4 自評段數

FSRS 原生是 4 段（Again／Hard／Good／Easy），Essence Cards 原本規劃 3 段（忘記／模糊／記得）。3 段可以對應到 FSRS 的 Again／Hard／Good，只是少了 Easy。這題併入「複習與檢核細節」的第 1 題討論。

### 8-5 介面技術

- **不用 Tailwind 與 PrefixWrap**：舊外掛的複習視窗最後改用 inline style，就是為了避開 Tailwind 的隔離問題；Retrospective 的 Case 001、002 也都出在前綴包裝。改成純 CSS、自訂前綴，搭配 Obsidian 的 CSS 變數就夠。
- **React 是否需要，寫程式時再決定**：複習畫面不大；手機上的載入速度要列入考量（D-015）。

### 8-6 開發流程

**沿用**：
- 先定規格再寫程式，解析器先寫測試。
- Retrospective，記錄根因與錯誤方向。
- 推送前跑完整測試與 build。
- 一鍵發版、文件編碼檢查。
- 手機相容檢查清單。

**不沿用**：
- 只改文件也要升版、寫 dev_log。

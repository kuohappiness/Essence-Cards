# 除錯

改寫自 mattpocock/skills 的 diagnosing-bugs（見 [UPSTREAM.md](UPSTREAM.md)）。

顯示指令、輸出或擷取的資料前，先把金鑰、憑證與私人資料換成 `<REDACTED>`。

## 1. 先有能重現的指令

這是整個流程的核心。還沒有一個「跑了會因為這個 bug 失敗」的指令之前，不要讀程式猜原因。

依序考慮：公開介面上的失敗測試 → 用固定輸入跑命令列並比對輸出 → 重播擷取到的真實資料 → 只啟動相關部分的拋棄式小程式 → 隨機輸入跑大量次數（偶爾才錯的）→ 兩個版本或設定跑同一個輸入、比對差異 → 二分搜尋 commit（`git bisect run`）。

讓它**快**（秒級）、**穩**（固定時間、亂數種子、隔離的暫存檔案）、**準**（斷言使用者描述的那個症狀，不只是「沒當掉」）。偶發的 bug 先提高重現率，並記下重現率。

真的做不出來時，說明試過什麼、缺哪項證據，向使用者要（可以重現的環境、去掉私人資料的紀錄或錄影）。可以做有標記的靜態分析，但不宣稱已經修好。

## 2. 重現並縮到最小

確認重現的是使用者說的那個症狀，不是旁邊的另一個錯。一次拿掉一項輸入、步驟或設定，拿掉後仍然失敗就不放回；剩下的每一項都拿不掉為止。最小的重現就是之後的回歸測試。

## 3. 根因不明時才列假設

- 根因已知：直接用失敗測試驗證，跳到第 5 步。
- 根因不明：列 3～5 個可以被推翻的假設，每個寫出預測（「如果是 X，改 Y 會讓它消失」）。先給使用者看排序，使用者可能知道哪個已經排除；使用者不在就照自己的排序做。

## 4. 量測

每個探針對應一個預測，一次只改一個變數。優先用除錯器或 REPL；要加 log，就加在能區分假設的邊界，並加上唯一的標記（例如 `[DEBUG-a4f2]`），結束時用 grep 清乾淨。效能問題先量基準再二分，不靠 log。

## 5. 修正與回歸測試

- 回歸測試放在 bug 真正發生的地方（能重現真實的呼叫鏈）。找不到這樣的位置，本身就是一項發現：記下來，交給審查或技術債清單。
- 先看測試失敗 → 修正 → 看它通過 → 再跑一次第 1 步的原始重現。

## 6. 收尾

- [ ] 原始重現不再失敗，回歸測試通過（或記下為什麼沒有回歸測試）
- [ ] 加了標記的除錯 log 都清掉；拋棄式程式刪掉
- [ ] commit 訊息或回報寫出最後證實的根因

# 審查

改寫自 mattpocock/skills 的 code-review 與 codebase-design（見 [UPSTREAM.md](UPSTREAM.md)）。

## L1：整合者對照（每次交回）

1. 讀實作者的回報與 diff。回報是待核對的資料，不是結論。
2. 逐條對照規格的限制與要做的事，讀必要的呼叫端與周邊程式。
3. 自己跑一次規格的自我測試與專案的檢查指令，不只看貼上來的輸出。
4. 用邊界例子重跑：規格列的，加上自己想到的新組合（空值、巢狀、重複、跨邊界、寫回後再讀一次）。
5. 照下面兩軸列出發現。

## L2：獨立審查（高風險改動，合併前）

用下面的範本寫審查請求，交給沒參與實作的新 session。審查者回報後，整合者逐項核對（能重現的自己重跑），再交給實作者修正。L1 與 L2 重疊的對照可以共用同一份紀錄。

### 審查請求範本

- **審查對象**：repo／worktree、分支、規格基準與待審 commit 的完整 SHA、分支的共同祖先；有沒有未提交的修改。
- **規格與優先順序**：任務規格的路徑與章節、它引用的正式規範與決定、基準之後相關規格的變動。規格衝突時列成問題，不挑容易通過的那份。
- **行為與風險**：公開介面、主要呼叫端、不可破壞的性質、已知邊界例子、明確延後的範圍。例子只是起點，請找新的組合。
- **驗證方式**：可用的指令、環境與相依版本、範例位置、實作者跑過與沒跑的項目；需要實機的部分明列。
- **回報與權限**：只審查，不改產品程式；可以在隔離環境重現。每項發現寫觸發條件、預期／實際、影響、位置與證據，並區分「已重現」「靜態推斷」「待驗證」。可以回報「規格本身有漏洞」。
- **檔頭**：審查請求與審查報告的標題下第一行寫狀態（待審、待修、再審通過、已合併的 commit）。

### 修正後收尾

- 修正者補回歸測試；在最後要合併的 commit 重跑相關重現與檢查，記下驗證的 SHA。
- 修正改到解析邊界或公開行為時，再審那段差異與相鄰案例，不必整包重審。審過一次不涵蓋之後的修改。

## 兩軸

同一個問題只報一次，標明屬於哪一軸。

- **規格**：規格要的沒做或只做一半；做了規格沒要的；看似做了但做錯；規格本身的漏洞（照局部規格做，卻破壞整體性質）。引用規格的那一行。
- **規範與設計**：違反專案寫明的規範（引用出處），以及下面的設計判斷與程式異味。自動檢查已經擋下的不重複報。

## 設計判斷

- **介面不只是函式簽名**：還包括呼叫順序、錯誤、資料不變條件與成本。例如「讀、改、寫」的約定比方法數量重要。
- **刪除測試**：想像刪掉這一層。複雜度跟著消失 → 它只是轉手；每個呼叫端都得自己處理同一條規則 → 它有價值。複雜度應集中在負責它的模組。
- **依賴要能控制**：純計算和 I/O 分開；真實環境與測試替身要核對同一份行為契約，替身通過不等於真實環境通過。
- **公開行為是主要測試面**：想越過介面測內部，通常是模組的形狀不對。不為了抽象製造第二個 adapter；但「只有一個實作就不准有介面」也不是硬規則。

## 程式異味

判斷線索，不是硬規則；專案規範認可的寫法不報。每項寫成「可能是 ×××」。

- **名稱看不出用途** → 改名；想不出誠實的名字，設計可能不清楚。
- **重複的邏輯形狀** → 考慮抽出；重複不自動等於要抽象。
- **依戀別人的資料**（一個函式大多在讀另一個物件的資料）→ 搬到資料所在的地方。
- **總是一起出現的幾個參數** → 合成一個型別。
- **用基本型別代表領域概念** → 給它自己的小型別。
- **同樣的 switch／if 鏈出現在多處** → 共用一張對照表，或改用多型。
- **一個改動要散改很多檔案** → 把會一起變的放在一起。
- **一個檔案因為幾種無關的理由被改** → 拆開。
- **為規格沒有的需求預留的抽象、參數** → 刪掉，等真的需要再加。
- **長串的 `a.b().c().d()`** → 藏到第一個物件的一個方法後面。
- **大多只是轉手的函式或類別** → 考慮直接呼叫目標；轉手不自動等於該刪。

## 回報格式

依嚴重程度排序。每項寫：哪一軸、觸發條件、預期／實際、影響、位置、證據（已重現／靜態推斷／待驗證）、建議處理（合併前修／記進技術債並寫觸發點與完成條件／加檢查規則）。最後一行寫沒測的項目與原因。

# 程式品質

改寫自 mattpocock/skills（來源與授權見 [UPSTREAM.md](UPSTREAM.md)）。這裡只寫通用做法；細節按時機讀 [review.md](review.md)、[debug.md](debug.md)、[milestone.md](milestone.md)。

## 先讀專案設定

角色由誰擔任、檢查指令、規格來源、高風險範圍、技術債清單與里程碑，寫在專案設定。依序找：

1. 任務或 AGENTS.md 指明的路徑；
2. 慣例位置 `docs/agents/quality.md`（從 repo 根目錄算）；
3. 都沒有：從現有任務、README、建置設定與 CI 推斷，記下依據繼續做。只有影響結論又判定不了的才問使用者。不自行建立設定檔。

## 原則

1. **機械的交給自動檢查**：能用程式判斷的問題（固定寫法、禁用的 API、import 方向、檔案位置），寫成檢查規則或測試，不寫成要人記得的規範。
2. **檢查不減，換成本較低的做法**：不靠少做檢查省成本。自動檢查擋掉機械問題，審查只看規格與設計。
3. **問題提早處理**：規格寫出邊界例子與能用程式判斷的驗收條件，比事後審查便宜。
4. **延後的問題要有觸發點與完成條件**，記進技術債清單，時機到了才會被看到。
5. **證據可追溯**：回報寫明測的是哪個 commit、跑了什麼、哪些沒跑與原因。工具不能用不算通過。

## 角色與成本階梯

| 層級 | 誰做 | 用在 |
|---|---|---|
| L0 自動檢查 | hook、CI | 每次改程式的 commit 與 push。先確認它真的會擋下失敗；不花 token 的只有檢查本身，讀輸出和修錯仍有成本 |
| L1 整合者對照 | 整合者 | 每次實作交回 |
| L2 獨立審查＋整合者核對 | 沒參與實作的新 session | 專案設定列為高風險的改動，合併前 |
| L3 多個子代理 | 整合者開子代理 | 只在 L2 的審查者不能用時；做不到的部分明列 |

同一個 agent 檢查自己的成果是 L1，不算獨立審查。

## 時機表

| 時機 | 做什麼 |
|---|---|
| 設計介面、寫任務規格 | 下方「寫規格」 |
| 實作或修正 | 下方「測試」；專案的檢查指令通過才 commit |
| 實作交回 | L1；高風險的加 L2。照 [review.md](review.md) |
| 測試失敗、有人回報 bug | 照 [debug.md](debug.md) |
| 審查有發現 | 機械的 → 加檢查規則或測試；要判斷的 → 當場修，或記進技術債清單（觸發點、完成條件） |
| 開始一件工作、改到某個區域 | 看技術債清單，觸發點已到的項目連同完成條件帶進這次工作 |
| 里程碑完成 | 主動提醒使用者，照 [milestone.md](milestone.md) |

## 寫規格

- 驗收條件寫成程式能判斷的句子（例如「第二次執行不改任何字」），並列出邊界例子；例子只是起點，審查者仍要自己找新的組合。
- 寫明公開介面、不可破壞的性質、明確延後的範圍、必跑的指令；必讀範圍連到本檔「測試」一節。
- 會改寫使用者資料的函式，要有往返與冪等測試，並登錄進共用的範例清單，讓之後新增的例子自動受保護。
- 新模組加進邊界規則。介面用 [review.md](review.md)「設計判斷」檢查一次。
- 規格之間有衝突，列成問題，不自行挑一份。
- 引用別的模組的行為，或寫「某件事已經驗證過」時，附上證據的位置（檔案:行、測試名或結果檔）；找不到證據就寫成待驗證。

## 測試

- **只透過公開介面測**：重構後行為沒變，測試就不該壞。不為了測試新增產品出口。
- **預期值要有獨立來源**：已知正確的字面值、規格的例子；不寫用同樣算法再算一次的斷言。
- **新行為與 bug：小步的失敗 → 通過**：先寫一個會失敗的測試，再寫剛好讓它通過的程式；一次一小段，不先寫完全部測試。
- **一個 commit 只實作一個決定或一項審查發現**：好幾項擠在同一個 commit，再審時分不出是哪一項帶進了新問題。
- **文件、機械整理與純重構**：用既有的行為測試與檢查，不為了湊失敗寫脆弱的斷言。測試全綠時的小幅整理可以當場做，但不改已約定的介面。
- **共同不變量套到所有範例，也保留具體的預期值**：解析與寫回可能共享同一個錯，只比總數不夠。
- 不把暫時的骨架形狀（檔案清單、空檔案）寫成長期契約。
- 測試用隔離的暫存資料，不碰共用工作樹或使用者的資料；留在 repo 的回歸例子用自編的最小內容。
